---
description: ゴールを設定し、既に実現済みかをチェックしたうえで、達成までのマイルストン・タスク・完了条件を設計する（必要に応じて GitHub Issue を作成）
argument-hint: <slug> <ゴール> | <slug> --check | <slug> --issues
---
入力: $ARGUMENTS

あなた（メイン）は取りまとめ役です。コードの調査は investigator、実現状況の判定は verifier、計画の設計は planner に任せ、自分ではコードを読まないでください。
出力ファイル:
- docs/plans/<slug>.md（計画書）
- docs/investigation/<slug>.logic.md / .refs.md（調査結果）
- docs/investigation/<slug>.check.md / .check.refs.md（実現状況チェック）

## モードの判定
- `--check` → 「Phase 5: 計画の再チェック」だけを実行
- `--issues` → 「Phase 5」を実行してから「Phase 6: Issue 作成」
- docs/plans/<slug>.md が既に存在し「FB:」で始まる行がある → 改訂モード。Phase 3 から再開し、FB の内容を planner に渡す
- それ以外 → Phase 1 から実行

---

## Phase 1: ゴールの設定
ゴールの文章から、以下を整理する。
- 達成したい状態（何ができるようになるか）
- ゴール全体の完了条件（測定・テストできる形。G1, G2... と ID を振る）
- やらないこと（範囲外）
- 制約（期限、互換性、性能目標など）

完了条件や範囲が曖昧で、計画が大きく変わりうる点がある場合は、AskUserQuestion で 1〜3 問だけ確認する。
確認できない場合は妥当な解釈を採用し、その解釈を計画書の「ゴール」に明記する。

## Phase 2: 実現済みチェック（ゴール単位）
verifier サブエージェントを起動し、<slug> とゴールの完了条件（G1, G2...）を渡して判定させる。

結果に応じて分岐する。
- **全ての条件が「実現済み」** → 計画は作らずに止まり、根拠（check.md の要約）を報告する。
  ゴールを広げる・性能目標を上げるなど、ゴールの見直し案があれば併せて提示する。
- **「進行中」の作業がある** → AskUserQuestion で扱いを確認する（その作業を前提に計画する／別ゴールとして並行する／中止する）。
- **「判断不能」がある** → 条件を具体化できるなら AskUserQuestion で確認して Phase 2 をやり直す（1回まで）。
- それ以外 → Phase 3 へ進む。

## Phase 3: 既存コードの調査
investigator サブエージェントを起動し、<slug>・ゴール定義・check.md の内容（どこまで実現済みか）・以下の調査観点を渡す。
実現済みの部分は深掘りせず、不足部分に調査を集中させること。
- ゴールに関係する既存の仕組み（流れ、責務、データの形）
- 変更が入りそうな箇所と、その影響範囲
- 拡張ポイント（既に用意されている差し込み口や類似の仕組み）
- テスト・検証の仕組み（テストの種類、実行方法の有無、ベンチマークや計測の有無）
- 制約やリスク（壊れやすい部分、性能やメモリの制約、互換性）

## Phase 4: マイルストンの決定
logic.md と check.md を読み、その全文とゴール定義を planner サブエージェントに渡して計画書を作成させる。
.refs.md と .check.refs.md は planner に渡さないこと。

計画書の「追加調査依頼」に項目がある場合は、investigator に追加調査させ、更新後の論理要約で planner に改訂させる（最大2回）。

あなたが .refs.md を読み、各マイルストンの「検証方法」が既存のテスト・計測の仕組みで実現可能かを確認する。
実現できないものがあれば、テストや計測の仕組みを用意するマイルストン／タスクを前倒しで追加するよう planner に改訂させる。

その後、Phase 5 を実行する（マイルストン単位の実現済みチェック）。

## Phase 5: 計画の再チェック（マイルストン単位）
docs/plans/<slug>.md の「状態」が「完了」以外の各マイルストン・タスクについて、完了条件を verifier に渡して判定させる。

判定結果を計画書に反映する。
- 各マイルストン・タスクの「実現状況」欄を、判定と確認日で更新する
- 「実現済み」になったもの → 状態を「実現済み」に更新
- 「実装あり・未検証」→ 状態を「検証のみ」に更新
- 「進行中」→ 状態を「進行中」に更新し、関連 Issue / PR を依存に追記
- 前回から判定が変わったものは、計画書の改訂履歴に記録する

実現済みのマイルストンが他のマイルストンの前提を変える場合（順序や内容の見直しが必要な場合）は、planner に改訂させる。

## 停止して人に報告
以下を報告して止まる。実装や Issue 作成には進まない（`--issues` 指定時を除く）。
- 計画書のパス
- ゴールの完了条件と、それぞれの実現状況
- マイルストン一覧を表で（名前・状態・完了条件の要約・タスク数）
- 既に実現済みだったもの、進行中の関連作業
- 未確定事項
- 次の操作の案内:
  - 計画書に「FB: ...」と書いて `/roadmap <slug>` → 計画を改訂
  - `/roadmap <slug> --check` → 現時点での実現状況を再チェック
  - `/roadmap <slug> --issues` → 再チェックのうえで GitHub Issue を作成

## Phase 6: GitHub Issue の作成（`--issues` 指定時のみ）
1. `gh auth status` と `gh repo view --json nameWithOwner` で、認証と対象リポジトリを確認する。失敗したら理由を報告して止まる。
2. docs/plans/<slug>.md を読み、作成対象を決める。
   - 対象外: 「Issue」欄に既に番号があるもの（重複防止）、状態が「実現済み」「完了」のもの
   - 状態が「進行中」のもの: 既存の Issue / PR があれば新規作成せず、その番号を「Issue」欄に書く
   - 状態が「検証のみ」のもの: タイトルに「[検証]」を付けて作成
3. 作成内容を一覧で示し、AskUserQuestion で作成してよいか確認する。
4. 作成ルール
   - ゴール全体: GitHub Milestone を1つ作成（タイトル = ゴール名。既に同名があれば再利用）
     `gh api repos/{owner}/{repo}/milestones -f title="..." -f description="..."`
   - 各マイルストン: Issue を作成し、上記 Milestone に紐づける
     - タイトル: `[<slug>] M1: <名前>`
     - 本文: 目的、依存（依存先 Issue 番号）、完了条件（チェックリスト）、検証方法、実現状況、計画書へのパス
   - タスクがある場合: タスクごとに Issue を作成し、マイルストンの Issue のサブ Issue にする
     - タイトル: `[<slug>] M1-T1: <名前>`
     - サブ Issue 化: `gh api repos/{owner}/{repo}/issues/<親番号>/sub_issues -F sub_issue_id=<子Issueのid>`
       （id は `gh api repos/{owner}/{repo}/issues/<子番号> --jq .id` で取得。失敗した場合は親 Issue 本文のチェックリストに `- [ ] #<子番号>` を記載する）
   - ラベル `roadmap` を付ける（無ければ `gh label create roadmap` で作成）
5. 作成した番号を計画書の「Issue」欄に書き戻す（例: `Issue: #123`）。
6. 作成した Issue の一覧（番号・タイトル・URL）と、実現済みのため作成しなかったものを報告する。
