以下は静的な読みから導いた予測であり、このあとの実測で当たり外れを判定する。
**外れたら、外れたことを残す**(規則 6)。

対象: `feature/fat-shrink-chain`(分岐元 `main` = `800b736`)。
調査側の宣言は `fat-overwrite.predictions.md`(直す**前**の予測。あちらは全部当たった)。

## 予測(直したあと)

対になる番号は調査側の `predictions.md` の P 番号。

| # | 操作 | 直す前(実測済み) | 直したあとの予測 | なぜそう読んだか |
|---|---|---|---|---|
| Q1 | 塊が減る全体書き換え(3000→100) | **nil**(P7) | **t。大きさは 100、中身は新しいもの** | `(t nil)` の枝が鎖を縮める処理に替わる |
| Q2 | 中身のあるファイルを書き込み用に開き直す | **中断**(P2) | **成功**。閉じたあとの大きさは書いた分だけ | 切り詰めは「空ベクタでの全体書き換え」で、Q1 が通れば通る |
| Q3 | 高い層での上書き 3 通り(小さく/同じ/大きく) | **3 通りとも中断**(P10) | **3 通りとも成功** | 同じ入口を通る |
| Q4 | 縮めたあと、余った塊の FAT 項目 | (未測) | **0(未使用)になっている** | 解放が `%fat16-set-fat-entry ... 0` で入る |
| Q5 | 縮めたあとに別のファイルを作る | (未測) | **解放した塊が割り当てられる**(陽性対照。規則 8) | 空き探索は番号の小さい側から走るので、解放済みなら拾える |
| Q6 | 縮めたあと、残ったファイルの鎖の長さ | (未測) | **必要塊数とちょうど一致**(二重使用の陽性対照) | 末尾に終端印を書いてから解放するため |
| Q7 | 縮めたあと、残ったファイルの中身 | (未測) | **新しい中身がそのまま読める** | データは解放より前に書く |
| Q8 | 0 バイトの既存ファイルを開き直す | **成功**(P4) | **成功のまま**(回帰していないこと) | 塊 0 個は「減る」に当たらず、経路が変わらない |
| Q9 | 読み書き両用で offset 50000 へ 1 バイト書く | **大きさは変わらない** | **大きさは変わらないまま** | ここは縮めてはいけない(下記) |
| Q10 | どのマウントにも無い道を書き込み用に開く | `no such mount` | **`no such mount` のまま** | 文面の直しは FAT 経路の中だけに入れる |

## 外れ方の意味

- **Q1 が nil のまま**: 枝が呼ばれていない(`cond` の順序か、AOT の変換が走っていない)
- **Q4 が 0 でない**: 解放のループが回っていない(`surplus` の切り出しが 1 つずれている)
- **Q5 が外れる**: 控え(FAT キャッシュ)の書き戻しが抜けている。
  **Q4 が真で Q5 が偽なら、キャッシュの中だけで 0 になっていて円盤に出ていない**
- **Q6 が長い**: 終端印を書いていない。**このとき Q5 と重なると二重使用になる**ので、
  Q5 と Q6 は必ず一緒に見る
- **Q9 が縮んだ**: 位置指定の書き込みまで切り詰めている。
  **これは #199 より悪い(70000 バイトのファイルが 50001 バイトになる)**

## Q9 を縮めない理由 —— 依頼と食い違う点を先に書く

依頼は「`new-size = max(end-offset, node.size)`(`fat16.lisp:639`/`fat32.lisp:840`)を
直して**大きさも縮める**」である。**ここは縮めない**ことにした。理由:

`test/lisp/fat16_test.lisp:458-479` が、読み書き両用で開いて offset 50000 へ
1 バイト書いたとき **「サイズは変化しない」ことを意図した仕様として固定している**
(`#49` で解消した非対称性の確認)。`max` を `end-offset` に替えると、
この 70000 バイトのファイルは **50001 バイトに切り詰められる**。
`set-file-position` があるので、これは実際に起こる。
**依頼が避けたい「静かな破壊」そのものが、より大きな規模で起きる。**

**大きさが縮む経路は別に用意されている**:
`fat16-write-file` / `fat32-write-file` の縮小枝(この PR で入れた)が
`new-size = (length bytes)` を書くので、

- `open-output-file`(開いた時点で 0 へ切り詰め)
- `write-vector-to-file`(全体書き換え)

のどちらでも**大きさは正しく縮む**。完了条件の
「縮めたあと `ls` の大きさが新しい値になる」はこの経路で満たす(Q1 / Q2 / Q3)。

残るのは「読み書き両用で開いて、短い中身で全体を上書きする」使い方だけで、
これは POSIX の `r+` と同じ意味なので**末尾が残るのが正しい**。
次の仕事(エディタ #218)は `open-output-file` か `write-vector-to-file` を使えばよく、
`open-io-file` で全体を上書きしてはいけない。**その旨を :639 / :840 の同じ場所に書いた。**

★ **この判断は依頼と食い違うので、人の確認が要る。** 食い違いを隠さずここに残す。

# 実測の結果(予測を書いたあとに追記。規則 6)

直したビルド(`feature/fat-shrink-chain`、`ce89fc2` + 進捗の印)で**単一段を 5 回**使った。

| # | 走らせたもの | 円盤 | 結果 |
|---|---|---|---|
| 1 | `qemu_boot_m6_fat16.lisp` | `tmp/fat16_test.img` の写し | **9 件落ちた。原因は私の直しではない**(下記) |
| 2 | 同じ(真っさらな円盤を作り直して) | 自作の `tmp/shrink16.img` | `185 passed, 0 failed` |
| 3 | 同じ(進捗の印を足して) | 同じ手順で作り直し | `185 passed, 0 failed` + 印 6 つ全通過 |
| 4 | `qemu_boot_fat32.lisp` | 自作の `tmp/shrink32.img` | `166 passed, 0 failed` + 印 6 つ全通過 |
| 5 | `qemu_boot_error_escape_gc.lisp`(文面) | 既定 | `io_signal_test.lisp` は **36 件すべて通過・[NG] 0**。段の台本自身の 2 件が落ちたのは **`GC_DEBUG=1` を渡し忘れたから**(`%%DIAG-GC-LIFO-VIOLATIONS` は `#ifdef` の中。`Makefile:1697` は自分で渡している)。**私の変更とは無関係** |

## 1 回目の 9 件について —— **計器ではなく材料の汚れだった**

落ちたのは全部ルートの一覧の期待値で、実際の一覧に `GCSTRES.LSP`(42 byte)が
混ざっていた。これは**前回の `test-qemu-load-gc-stress` がゲスト内で書いた材料**で、
写し元の `tmp/fat16_test.img` に残っていた(`Makefile:1926` の段が書く)。

**`make test-qemu-all` は冒頭で `rm -f $(FAT16_DISK_IMG)` をするので影響を受けない。**
**単一段を直接走らせるときだけ、円盤を手順どおり作り直す必要がある**(`refs.md` §7 の
「写しを使う」に加えて、**写し元が既に汚れていないかを見ること**)。
2 回目以降はその手順(Makefile の `$(FAT16_DISK_IMG)` レシピを自分の名前の
出力先へ写して実行)で真っさらな円盤を作ってから走らせた。
