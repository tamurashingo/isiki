# ディスク上のファイルの上書き保存 — 論理要約(#199)

> 対象: いま main(`800b736`)。**読み取りのみ。製品のコードは 1 行も変えていない。**
> **実機で 2 周だけ走らせた**(FAT16 で 1 周、FAT32 で 1 周)。
> **★ を付けた主張は読んで導いただけで走らせていない。★ の無い主張は実機で確かめた。**
> 測る前の宣言は別紙(同じ場所の `.predictions.md`)に置いてあり、**走らせる前に書いた**(規則 11)。
> 実測は 2 周とも「宣言した 10 項目がすべてそのとおり」だった(34 件通過・0 件失敗・打ち切り 0 件)。

---

## 0. 結論(先に書く)

**原因は仮説 2 である。**
下回りの「ファイル全体の書き換え」が、**占める塊の数が減る書き換えを受け付けず、
ただ偽を返す。** 書き込み用に開く操作は「まず中身を空にする」を**この全体書き換えで
実現している**ため、中身のあるファイルを書き込み用に開くと必ずここで落ちる。

**仮説 1 は「どこで鳴るか」としては正しいが、原因ではない。**
たしかに落ちるのは書き込み用に開く経路だけである。ただしそれは
**その経路だけが「空にする」を要求するから**であって、その経路に固有の欠陥があるからではない。

切り分けの根拠(実測):

- **中身の無い(0 バイトの)既存ファイルなら、書き込み用に開き直せる。**
  「既存であること」が原因ならここも落ちるはずだが、落ちない
- **中身のあるファイルは、これから書く量が小さくても・同じでも・大きくても、
  例外なく同じ場所で落ちる。** 書く量ではなく「空にする」段で落ちている
- 下回りの全体書き換えを直接呼ぶと、**塊が増える書き換えは通り、塊が減る書き換えだけが
  偽を返す。** 塊の数が変わらない範囲での縮小(例 100 → 50)は通る
  → 拒んでいるのは「小さくすること」ではなく「**塊の鎖を縮めること**」である

**FAT16 と FAT32 で差は無い。** 2 つの仕組みは別々に書かれているが、
**この部分は同じ形で同じ欠落**を持ち、**実機でも同じ結果**になった。
「FAT32 なら起きない」は**誤り**である。FAT32 で表に出ていなかったのは、
そちらのディスクを**読む用途でしか使っていない**からにすぎない。

## 2. 関連するドメイン概念と関係

| 概念 | いまの姿 |
|---|---|
| **ファイルの札** | 目録の中の 1 項目。名前・種別・**最初の塊の番号**・**大きさ**を持つ |
| **塊** | ディスクを一定の大きさで区切った単位。ファイルは塊を 1 つ以上占める(0 バイトなら 0 個) |
| **塊の鎖** | 「次はどの塊か」を記した表でつながる。ファイルの中身は鎖の順に並ぶ |
| **空き塊** | 鎖の表で「未使用」と記されている塊。新しく要るときはここから取る |
| **ファイルの把握** | 札を 1 つ引き当てた状態。開いた流れはこれを握って読み書きする |
| **全体書き換え** | 既にあるファイルの中身を、与えた列でまるごと置き換える操作 |
| **部分書き換え** | 位置を指定して、その範囲だけを置き換える操作 |
| **新規作成** | 札を 1 つ増やし、必要な塊を確保して中身を書く操作 |
| **切り詰め** | ファイルを 0 バイトにすること。**独立した操作としては存在せず、「空の列での全体書き換え」として表現されている** |

関係:

- 書き込み用に開く = 把握する → **切り詰める** → 流れを作る
- 読み書き両用で開く = 把握する → 流れを作る(**切り詰めない**)
- 読み込み用に開く = 把握する → 流れを作る
- 高い層の「配列をファイルへ書く」= **書き込み用に開く**の上に乗っているだけ
  → **上書き保存は、必ず切り詰めを通る**

## 3. 現状の責務の分担(概念レベル)

| 担い手 | 受け持ち |
|---|---|
| **道の割り振り** | 与えられた道から「どのディスクの、どの仕組みの、どの相対の道か」を決める |
| **橋渡し** | 把握・切り詰め・新規作成の**順番を決める**。「切り詰めは空の列での全体書き換えで行う」と決めているのはここ |
| **下回り(2 仕組みそれぞれ)** | 札の捜索、塊の鎖の読み書き、全体書き換え・部分書き換え・新規作成の実体 |
| **流れ(ストリーム)** | 溜め場を持ち、満杯になったら下回りの部分書き換えを呼ぶ |
| **高い層の便利関数** | 「配列を丸ごと書く」「ファイルを丸ごと読む」。開く操作の薄い上被せ |

**切り詰めの意味を決めているのは橋渡しの層**であり、
**下回りには「切り詰め」という操作が無い。** ここが構造上の要点である。

## 4. 現状の処理の流れ

### 4-1. 書き込み用に開く(正常系・新規)

1. 道を割り振る
2. 札を探す → **無い**
3. (切り詰めは札が無いので飛ばす)
4. 新規作成を、**空の列**で呼ぶ → 札ができる(占める塊は 0 個)
5. 札を探し直す → 流れを作る

→ **通る。** 以後の書き込みは部分書き換えが塊を足しながら進める。

### 4-2. 書き込み用に開く(例外系・既に中身があるとき)★ ではない(実測)

1. 道を割り振る
2. 札を探す → **ある**(ここは成功している。解決そのものは出来ている)
3. **切り詰め = 空の列での全体書き換えを呼ぶ**
   - 下回りは「要る塊は 0 個、いま占めているのは 1 個以上」と判断する
   - **減る場合は未実装なので、何もせず偽を返す**
4. 橋渡しは「偽が返った」を**「把握できなかった」と読み替えて**失敗にする
5. 上位は「**ファイルを解決できない**」という文面で中断する

**文面が事実と違う。** 札は 2 で見つかっている。失敗したのは切り詰めである。
原因を探す人を**別の場所へ誘導する**(現にこの Issue の初期の仮説がそうなった)。

**この経路は、これから書く量に関係なく落ちる。**
小さく・同じ・大きく、の 3 通りすべてで同じ文面になることを実機で確かめた。

### 4-3. 書き込み用に開く(既存だが中身が無いとき)

2 で札が見つかり、3 の全体書き換えが「要る塊 0 個 / いま 0 個」で**一致**するため通る。
→ **開ける。** これが「既存であること自体は原因ではない」という切り分けになる(実測)。

### 4-4. 読み書き両用で開く

切り詰めを**要求しない**ので、中身があっても開ける。
ただし後述のとおり、**大きさは縮まない**。

### 4-5. 失敗したあとの状態

切り詰めが拒まれたとき、**ファイルは一切変わらない**(中身も大きさも札も無傷)。
拒む判断は、データにも目録にも書く前に下る。実機で確認した。
**壊れるのではなく「保存できない」**。ただし呼び出した側がその中断を握り潰すと、
利用者には「保存できたように見える」ことが起こりうる(§9)。

## 5. コードから読み取れる業務ルール・不変条件

事実(読んで確かめ、実機でも裏が取れたもの):

1. **ファイル全体の書き換えは、占める塊の数が「同じ」か「増える」場合にしか成立しない。**
   減る場合は、何もせず失敗を返す
2. **判定は塊の数だけを見る。** バイト数の増減は見ていない。
   したがって**同じ塊数に収まる範囲の縮小は通る**(大きさの札も正しく小さくなる)
3. **切り詰めは「空の列での全体書き換え」として表現されている。**
   独立した操作は無い
4. **部分書き換えは大きさを縮めない。** 大きさは「今の大きさと、書いた末尾の位置の、
   大きいほう」に更新される。**小さくする方法が無い**
5. **塊を解放する処理が、2 つの仕組みのどちらにも 1 つも無い。**
   塊を確保する処理・鎖を伸ばす処理・鎖の 1 要素を書き換える処理はある
   (= 解放に必要な道具立ては既にあり、使う側が無い)
6. 確保の途中で失敗した場合、**確保済みの塊を戻さない**(取りこぼしを許容する、と決めてある)
7. **削除も改名も存在しない。** したがって「別名で書いてから入れ替える」という
   回避策は取れない
8. 新規作成は、同じ名前の札が既にあると失敗する(上書きは全体書き換えの役目、という分担)

不変条件として効いているもの:

9. 札の「最初の塊の番号」が 0 のとき、そのファイルは塊を 1 つも占めていない
10. 大きさ 0 のファイルは塊を占めない(新規作成が空の列で作るため)

## 6. 状態とその遷移

ファイル 1 つの「占める塊の数」で見る。

| 今 | 操作 | 行き先 | 成否 |
|---|---|---|---|
| 無い | 書き込み用に開く | 0 個 | 成功 |
| 0 個 | 書き込み用に開く(= 0 個へ切り詰め) | 0 個 | **成功** |
| 1 個以上 | 書き込み用に開く(= 0 個へ切り詰め) | — | **失敗(これが #199)** |
| n 個 | 全体書き換え(要る塊 n 個) | n 個 | 成功 |
| n 個 | 全体書き換え(要る塊 > n 個) | 増えた数 | 成功 |
| n 個 | 全体書き換え(要る塊 < n 個) | — | **失敗** |
| n 個 | 読み書き両用で開いて一部を書く | n 個(または増える) | 成功。**大きさは減らない** |

**「塊の数が減る」向きの遷移が、どこにも存在しない。**
これが一言でいうと欠けている不変条件である。

## 7. 外部連携・データの出入り口

| 口 | 上書き保存はできるか |
|---|---|
| ディスク(FAT16) | **できない**(中身があると失敗。実測) |
| ディスク(FAT32) | **できない**(同じ。実測。**ここが Issue の想定と違う**) |
| 母艦の共有ファイル | **できる。** 切り詰めは開くときの指定で母艦側に任せており、量の制限が無い |

**同じ 1 つの関数が、道によって意味を変えている。**
母艦の共有へ書けば上書き保存は成立し、ディスクへ書くと中断する。
試験の成果物は母艦の共有へ書かれているので、**毎回上書きできており、
この欠陥は試験の足元では一度も顕在化しない。**

さらに**読み書き両用で開く操作の意味も、道によって違う**:

- 母艦の共有 … **中身を捨てる**(開いた直後は空)
- ディスク … **中身を保つ**(開いた直後から読める)

後者は意図して揃えたものだと記録に書かれている(ディスク側が正しい振る舞い)。
**つまり母艦の共有側だけが揃っていない。** エディタがどちらを使うかで意味が変わる。★
(この非対称は読んで気づいたもので、母艦側は走らせて確かめていない)

## 8. 制約

1. **下回りの 2 つの仕組みは、別々に書かれた同じ形の双子である。**
   片方だけ直すと、もう片方に同じ欠陥が残る。**両方に同じ修正が要る**
2. 下回りは**起動時に機械語へ落とされている**。直すと作り直しの段
   (外部の道具を使う変換)が走る。手元での試し打ちが軽くない
3. 下回りには「本体に複雑な繰り返しを直接書くと実機で壊れる」という既知の罠があり、
   **実装は素の関数に切り出す**という約束がある。新しい処理もその約束に従う必要がある
4. **繰り返しは必ず関数の中に置く**(最上位に置くと 1 回ごとに入れ子で評価され、
   万回級で壊れる)という約束がある
5. 塊の鎖の表は**控えを 1 枚だけ持つ作り**で、書き換えは控えを通し、
   最後に書き戻す段がある。**縮める処理もこの作法に乗せる**必要がある
6. 鎖の表は**複数の写し全部へ同じ内容を書く**決まりである
7. **既存の試験が「減る書き換えは失敗する」ことを期待値として固定している**(2 つの仕組みの
   両方に、その 1 行がある)。直すなら**その期待値を書き換えることになる**
   → これは「期待値を黙って上げる」ではなく、**仕様を変えたことの表明**として
   扱う必要がある(規則 16)
8. 影響範囲は広い: 開く操作・高い層の「配列を書く」・エディタの保存が、
   すべて同じ 1 本の判断に乗っている

## 9. 既存の問題点・矛盾・リスク

1. **文面が原因を指していない。** 「ファイルを解決できない」と出るが、
   解決は成功しており、失敗したのは切り詰めである。
   調べる人を別の場所へ送る(**この Issue で実際に起きた**)
2. **下回りの「できなかった」が、1 種類の偽に潰れている。**
   「道が違う」「札が無い」「読めなかった」「縮小は未実装」が区別できない。
   橋渡しの層はどれも同じ扱いにするしかない
3. **上書き保存が失敗したあと、呼び出した側がそれを握り潰せば
   「書けたと思って保存できていない」になる。** 中断の理由は画面にしか出ない
   という既知の別問題と重なると、**利用者には成功と区別が付かない**
4. **読み書き両用で開いて短い内容を書くと、黙って壊れた中身が残る。**
   大きさが縮まないので、**前の内容の末尾がそのまま残り、
   新しい内容と古い内容が連結したファイルになる**。失敗の合図は一切出ない。
   実機で確認した(5 バイト書いた後も大きさは元の 3000 のままで、末尾は古い値)。
   → **「切り詰めを避けて読み書き両用で開く」という回避策は、
   別の形の静かな破壊になる。** エディタの保存をこれで実装してはいけない
5. **書き込みの試験は新規ファイルにしか当たっていない**(両方の仕組みで)。
   既存ファイルへの上書き保存を見ている試験は 1 本も無い
6. **単独で走らせると 2 周目から崩れる段が、この Issue のもの以外にもある。** ★
   同じ円盤に書く段があり、そこは**試験の材料を自分で作っている**ので、
   作り直さずに 2 周目を走らせると最初の上書きで中断すると読める。
   一周ぶん通す道筋は先頭で円盤を捨てるので当たらない。
   **走らせて確かめていない(★)。** ただし同じ形であることは読んで確認した
7. **確保の取りこぼしを許容する決まりがある**ので、縮める処理を入れるときは
   「取りこぼしを増やさない」ことを意識しないと、空き塊が静かに目減りする
8. 母艦の共有と、ディスクで**同じ関数の意味が違う**(§7)。
   どちらに書くかでアプリの正しさが変わる

## 11. 直し方の候補(設計は依頼者。ここは候補と影響範囲だけ)

### 候補 A: 塊の鎖を縮める処理を下回りへ入れる(本筋)

全体書き換えに「減る」場合の枝を足し、余った塊を鎖から切り離して空きへ戻す。

- **FAT16 と FAT32 の両方に要る。** 片方では済まない(§8-1)。
  必要な道具(鎖の 1 要素の書き換え、控えの書き戻し)は**両方に既にある**
- 影響範囲: 上書き保存・切り詰め・高い層の「配列を書く」が**同時に**通るようになる
- 期待値を固定している既存の試験の**その 1 行を書き換えることになる**(§8-7)
- 塊を 0 個にする場合、札の「最初の塊の番号」を 0 に戻す必要がある
  (新規作成が作る「空のファイル」と同じ形に揃う)
- **危うい点**: 鎖を切るのとデータを書くのと札を直すのの**順番**。
  途中で止まると、どこにも繋がっていない塊(取りこぼし)か、
  使用中の塊を空きと記した表(**二重使用 = 本当の破壊**)のどちらかになる。
  **空きへ戻すのは、札を書き換えて鎖を切り離した後**でなければならない

### 候補 B: 切り詰めを「全体書き換え」で表現するのをやめる

橋渡しの層が、切り詰めのために全体書き換えを呼ぶのをやめ、
下回りに**切り詰め専用の意味**を置く。

- 候補 A を内側に必要とする(0 個にするのは最も縮む場合である)
  → **A の代わりにはならない。A の上に乗る整理**
- 利点: 「切り詰めに失敗した」と「札が見つからない」を**区別して報告できる**(§9-1, 9-2)

### 候補 C: 失敗の文面と区別だけを直す(最小)

「ファイルを解決できない」をやめ、どの段で落ちたかを文面に出す。

- **症状は直らない。** 上書き保存はできないまま
- ただし**静かな破壊の度合いは下がる**(調べる人が正しい場所へ行く)
- 候補 A を入れるまでの間に挟む価値はある。**A と排他ではない**

### 候補 D: 読み書き両用で開いて上書きする(回避策として検討されうる)

**採ってはいけない。** 大きさが縮まないので、§9-4 の「古い中身が末尾に残る」を
そのまま踏む。**失敗ではなく静かな破壊**になるので、今より悪い。
採るなら「大きさを縮める」も同時に要り、それは候補 A と同じ仕事を含む。

### 試験について(どの候補でも要る)

いまの試験は**新規ファイルにしか当たっていない**。直すなら、
**中身のあるファイルへの上書き保存**を 2 つの仕組みの両方で見る段が要る。
さらに「同じ大きさ・大きく・小さく」の 3 通りと、
**0 バイトの既存ファイル**(今は通っている側。壊さないことの確認)を分けて置くこと。
**この調査で使った台本がそのまま素材になる**(使い捨てにしたので中身は参照マップ側に残した)。
