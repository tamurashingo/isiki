# isiki-osの性能測定手法

`feature/abi-redesign`でのJIT/AOT性能調査を通じて、以下の手法をそれぞれ
異なる場面で使い分けてきた。本書は、今後の性能調査(特にIDE/FAT I/Oの
命令数ベースでの追加最適化)で標準的に参照できるよう、各手法の特性・
使い分け・実際の使い方をまとめる。

## 手法の一覧と使い分け

| 手法 | 何を測るか | 長所 | 短所 | 主な用途 |
|---|---|---|---|---|
| ゲスト内tickカウンタ(`get-internal-real-time`) | 壁時計時間(10ms単位) | 実装が既にある、Lispコードから直接読める | タイマー割り込み自体のオーバーヘッドを含みうる、ホストのスケジューリングノイズの影響を受ける | 大まかな体感速度の比較、既存テストの回帰検知 |
| ホスト側`strace`(futex回数等) | ホストのシステムコール発行状況 | ホスト側のボトルネック(BQL競合等)の切り分けに使える | ノイズが非常に大きい(GC計装2回呼んだだけで速度が4-5倍変わった実例あり)。ホストの実行速度と相関するが厳密な指標ではない | QEMU/ホスト起因の外部要因を疑う初期切り分け段階のみ |
| **TCGプラグイン(命令数カウント)** | ゲストが実際に実行した命令数 | ホストの実行速度・スケジューリングノイズと無関係、高速(通常運転とほぼ同じ実時間) | 完全な決定論ではない(下記参照)、アドレス範囲を跨いだ内訳分離は追加の仕組みが要る | **実装変更の効果測定の主指標。以後はこれを既定の手法とする** |
| `-icount`(決定論的実行) | 命令数(TCGプラグインと同じ指標を、完全に再現性のある形で) | ビット単位で再現性がある(record/replayの基盤) | I/Oが絡む大きなワークロードは実時間で非常に遅い(実測: 通常数秒のN=1,000,000ループが3分強) | 小規模な決定論的A/B比較、TCGプラグインの結果に疑義がある場合のgold standard確認 |
| `-d in_asm,out_asm` | JIT/AOTが実際に生成した機械語 | 生成コードを直接目視確認できる | ログ量が膨大(ブートのみで53MB/145万行)、このホストのQEMUには逆アセンブラ(capstone等)が組み込まれておらず生バイト列(`OBJD-H:`/`OBJD-T:`)しか出力されない | 特定の生成コードパターンを直接確認したい場合(`-dfilter`でアドレス範囲を絞ることが前提) |

## 手法1: TCGプラグインによる命令数カウント

### 導入したプラグイン

`tools/plugins/isiki_instcount.c` — TB(translation block)ごとの命令数
(`qemu_plugin_tb_n_insns`)を、そのTBが実行されるたびに加算する方式。
1命令ごとのコールバックは極端に遅くなるため使わない。終了時に
stderrへ以下の形式で出力する:

```
[isiki_instcount] total_insns=<N>
```

オプション引数`start=0xADDR,end=0xADDR`で、その仮想アドレス範囲に含まれる
TBだけの命令数を`range_insns`として別集計できる(JIT生成コードはヒープ上の
動的アドレスのため主にAOT/C側の静的アドレスが既知な関数区間向け)。

### ビルドと使い方

`.so`はソースからのビルドを前提とし、git管理対象外(`tools/plugins/*.so`)。
`make test-qemu-instcount`が自動でビルドする(`isiki-builder`コンテナ内で
`libglib2.0-dev`をインストールし、ホストのQEMUバージョンに対応する
`qemu-plugin.h`をGitHubから取得してコンパイルする)。プラグインのABI
(`QEMU_PLUGIN_VERSION`)はヘッダとホストQEMU本体のバージョンが一致している
必要があるため、ホストのQEMUバージョンが`Makefile`の`QEMU_VERSION_FOR_PLUGIN`
(既定`10.2.1`)と異なる場合は`.envrc`等で上書きすること。

```
make test-qemu-instcount MILESTONE=test/lisp/qemu_boot_xxx.lisp [QEMU_DISK_IMG=...]
```

### 検証結果(2026-09-11、feature/icount-profiling)

**N-スケーリング(自己再帰ループのみ)**:

| N | total_insns | 起動オーバーヘッド差分 |
|---|---|---|
| 0(起動のみ) | 1,136,549,402 | - |
| 1,000,000 | 1,568,155,700 | 431,606,298 |
| 2,000,000 | 2,000,913,222 | 864,363,820 |

差分の比 864,363,820 / 431,606,298 = **2.0027**(理論値2.0とほぼ一致)。
1反復あたり約432命令(自己末尾呼び出しのトランポリン込み)。

**決定論性の検証(非icount、N=1,000,000を2回実行)**:

| 実行回 | total_insns |
|---|---|
| 1回目 | 1,568,878,009 |
| 2回目 | 1,568,731,913 |

差は146,096命令(**約0.0093%**)。通常のTCG実行(非icount)は、ブート時の
ACPI/PIT較正等の実時間依存ポーリングにより完全な決定論ではないが、
これまでのstrace/futexベースの計測(数倍単位の誤差)と比べれば
桁違いに小さいノイズである。実装変更の効果測定(通常は数%〜数十%の
差を検出したい)には十分な精度がある。

**IDE(FAT16)1MB読み込みの命令数**(ホスト側で事前にファイルを配置した
ディスクイメージを使い、書き込み側の影響を排除):

| 計測 | total_insns |
|---|---|
| 起動+mountのみ | 1,118,654,248 |
| 起動+mount+1MB読み込み | 3,671,343,591 |
| **読み込み自体の差分** | **2,552,689,343** |

1MBの読み込みに約**25.5億命令**。tickカウンタでの実測(31.28秒)と
組み合わせると、この区間のゲスト実行速度は約8,160万命令/秒
(2,552,689,343 / 31.28)であり、TCGの命令ディスパッチ自体が極端に遅い
わけではないことが分かる。**問題は1命令あたりのコストではなく、
1MBを読むのに要する命令の「絶対数」が大きいこと**を示しており、
今後の最適化(`insw`一括転送化・`READ MULTIPLE`対応等)の効果を
測る際は、この2,552,689,343を基準値として比較する。

## 手法2: `-icount`(決定論的実行モード)

```
make test-qemu-icount MILESTONE=test/lisp/qemu_boot_xxx.lisp [ICOUNT_SHIFT=N]
```

`-icount shift=auto`は本環境ではハング(または極端な遅延)を起こしたため、
固定`shift`値(既定7)を使うこと。マルチスレッドTCGと非互換のため
`-accel tcg,thread=single`もあわせて指定する(`test-qemu-icount`ターゲットが
自動で付与する)。

I/Oが絡む大きなワークロードは実時間で非常に遅い。N=1,000,000の自己再帰
ループ(通常運転なら3〜4秒)が**3分強**かかった実測がある。そのため、
日常的な計測には向かず、以下のような場合にのみ使う:

- TCGプラグインの結果(通常運転)に予期しない大きなばらつきが出て、
  実装のバグなのか、単なる実時間依存ポーリングのノイズなのかを
  切り分けたい場合。
- 極めて小さな実装差分(命令数で1%未満の変化)を、ノイズに埋もれず
  検出したい場合。

## 手法3: `-d in_asm,out_asm` + `-dfilter`

```
qemu-system-x86_64 ... -dfilter <start>+<length> -d in_asm,out_asm -D <logfile>
```

`-dfilter`の範囲指定は`start-end`ではなく**`start+length`形式**(例:
`0x100000+0x100000`)であることに注意(`start-end`形式は`Invalid range`
エラーになる)。

このホストのQEMU(Ubuntu 26.04パッケージ版）には逆アセンブラ
(capstone等)が組み込まれておらず、`in_asm`/`out_asm`は実際のニーモニックの
代わりに生バイト列(`OBJD-H:`/`OBJD-T:`)を出力する。読める形にするには、
`OBJD-H:`行の16進バイト列を抽出し、`objdump -D -b binary -m i386:x86-64
-M intel`等の外部ツールで別途逆アセンブルする必要がある(本書執筆時点で
未実施、次のフォローアップ)。

フィルタなしでの`-d in_asm,out_asm`はログ量が膨大(ブートのみで約53MB・
145万行)なため、実運用では必ず`-dfilter`でアドレス範囲を絞ること。
JIT生成コードはヒープ上の動的アドレスのため、対象アドレス範囲は実行時に
Lisp側から(例えば`%%za-compiled-p`が返す関数オブジェクトの生ポインタ等を
介して)取得する仕組みが別途必要になる(未実装、フォローアップ)。

## IDE読み込みの命令数内訳: ide.c単独 vs それ以外(2026-09-11)

「1MB=2048セクタ、約25.5億命令」という総数は、`ide_wait_drq`のポーリング
(1セクタあたり平均約156回)やデータ転送ループ(`inw`約256回/セクタ)だけを
素朴に足しても到底説明がつかない規模(1セクタあたり約124万命令)だった
ため、まず「`drivers/ide.c`内のコード(ポーリング+データ転送)」対
「それ以外(FAT層のクラスタチェイン走査+Lispランタイム)」という大枠を
切り分けた。

### アドレス範囲の特定方法

1. ビルド成果物(`esp_dir/EFI/BOOT/BOOTX64.EFI`、mingw-gccがリンクした
   PE形式)のシンボルテーブルを`x86_64-w64-mingw32-objdump -t`で読み、
   `drivers/ide.c`内の関数群(`set_err`/`ide_setup_lba`/
   `ide_delay400ns`/`ide_wait_drq`/`ide_wait_not_busy`/
   `os_ide_identify`/`os_ide_read_sectors`/`os_ide_write_sectors`)が
   連続領域(ファイル上の相対仮想アドレス、RVA)に配置されていることを
   確認した(`0x1a580`〜`0x1ab90`、1552byte、次のシンボルは
   `block_device.c`の`ide_bd_flush`で境界が明確)。
2. **【重要な落とし穴】** ファイル上のRVAは、UEFIローダが実際に
   イメージをロードする実行時ベースアドレスとは異なる。実行時ベース
   アドレスは起動のたびの再現性はある(同一ディスク構成で2回検証し
   一致を確認)一方、**アタッチするディスクイメージの構成(サイズ・
   パーティション形式の違い)によって変わる**ことを実測で発見した
   (デフォルトの`tmp/ide_disk.img`では`os_ide_read_sectors`の実行時
   アドレスが`0xD3AE8ED`だったのに対し、計測用に用意した16MB FAT16
   単純フォーマットのディスクでは`0xCF2D8ED`と異なっていた。原因は
   未特定だが、OVMFのイメージロード時のメモリ配置がディスク構成に
   影響される何らかの経路があると見られる)。このズレに気づかず
   デフォルト構成で計算したアドレス範囲を別のディスク構成の計測に
   流用した結果、最初の試行は`range_insns=0`という誤った結果になった。
   **教訓: アドレス範囲は必ず計測対象と全く同じQEMUコマンドライン
   (同じディスクイメージ)で実測してから使うこと。**
3. 実行時アドレスの取得には、`os_ide_read_sectors`(externリンケージ、
   `drivers/ide.h`で宣言済み)のポインタ値をそのまま返す診断用組み込み
   関数`%%DIAG-IDE-READ-SECTORS-ADDR`(`src/c/ide_subprimitive.c`の
   `cc_diag_ide_read_sectors_addr`)を追加し、Lisp側から
   `(%%diag-ide-read-sectors-addr)`で取得した。実行時アドレス−該当
   関数のファイルRVA=実行時ベースアドレス、という式で、`ide.c`クラスタ
   全体の実行時アドレス範囲を計算できる。

### 計測結果(1MB、FAT16、事前配置イメージで書き込み側を排除)

| 区分 | 命令数 | 全体に占める割合 |
|---|---|---|
| 総命令数(1MB読み込み自体、mountのみとの差分) | 2,581,582,199 | 100% |
| `ide.c`単独(ポーリング+データ転送、TCGプラグインのアドレス範囲指定で分離) | 9,500,016 | **0.368%** |
| それ以外(FAT層+Lispランタイム、差分) | 2,572,082,183 | **99.632%** |

1セクタ(512byte、2048セクタ/MB)あたりに換算すると、全体約132万命令の
うち`ide.c`が占めるのはわずか約4,864命令(先述の「ポーリング約156回+
inw約256回」という素朴な見積もりのオーダーとおおむね整合する)。
**残り約131.7万命令/セクタが「それ以外」に費やされている**ことになり、
支配的なボトルネックは`ide.c`(PIO層)ではなく、FAT層のクラスタチェイン
走査またはLispランタイム(AOT生成コード)側にあることが定量的に確定した。

### 判定と次の一手

「`ide.c`側が支配的であれば`insw`一括転送化・`READ MULTIPLE`対応に進む、
FAT層側が支配的であればそちらを優先する」という当初の判定基準に照らし、
**FAT層側が圧倒的に支配的(99.6%)** という結果になった。したがって
`insw`一括転送化・`READ MULTIPLE`対応は保留とし、次のフォローアップの
最優先事項を以下に変更する:

- `fat16-read-file`(または`read-file-into-vector`が最終的に呼ぶ
  `read-into!`経由の経路)が、クラスタ1個(または1セクタ)ごとに何らかの
  シンボル解決・関数呼び出しのオーバーヘッドを負っていないか。今回
  (`feature/abi-redesign`)のfn解決キャッシュ化(`za_compile_call`)は
  JITコンパイル済みのユーザー定義関数呼び出しが対象であり、`read-into!`/
  `write-from!`はILOSの総称関数(`defmethod`経由、M10クロージャリフティング
  でコンパイル)であるため、**この恩恵を受けていない可能性がある**。
  `(print (function read-into!))`等で`#<FUNCTION-COMPILED ...>`/
  `#<FUNCTION-INTERPRETED ...>`のいずれかを確認し、インタプリタ経由の
  ままになっていないかをまず確認する。
- 1セクタあたり約131.7万命令という規模感から、単純な「シンボル解決の
  やり残し」だけでは説明しきれない可能性もあるため、`-dfilter`+
  TCGプラグインのアドレス範囲指定を使い、AOT側の静的アドレスが既知な
  FAT層の関数(`%fat16-read-lba-list`/`fat16-fat-entry`等)の寄与も
  同じ手法でさらに分離することを検討する。

## FAT層側(read-into!)の命令数内訳: ILOS総称関数ディスパッチの精査(2026-09-11)

前節の切り分けで「FAT層+Lispランタイム」が全体の99.632%を占めることが
判明したため、次に**ILOS総称関数(`read-into!`)のディスパッチ処理**が
支配的かどうかを検証した。結論から言うと**ディスパッチは無視できるほど
軽微であり、真因は別の場所(`read-file-into-vector`のAOT生成コード自体の
呼び出し規約オーバーヘッド)にあった**。

### 1. ディスパッチ機構の実装確認(コードレビュー)

`src/lisp/init.lisp`/`src/lisp/init_aot.lisp`を確認したところ、`defgeneric`は
`(defun name (&rest args) (%generic-call 'name args))`という`&rest`関数に
展開され、`%generic-call`は毎回:

```lisp
(defun %generic-call (name args)
  (%invoke-method-chain (%order-methods (%applicable-methods name args)) args))
```

を実行する。`%applicable-methods`は`*generic-methods*`をname(gf名)で`assoc`
線形走査し、見つかった全メソッドに対し`subclassp`判定を行い、
`%order-methods`は挿入ソート(毎回)、`%invoke-method-chain`は
`unwind-protect`+動的変数の退避/復元を伴う。**メソッド解決結果のキャッシュは
一切無い**——コードだけを見れば、以前の`os_make_symbol`線形走査と同種の
ホットスポットに見えた。

### 2. 実測: ディスパッチは全体の0.0004%に過ぎない

`subclassp`/`class-of`/`%find-generic-methods`/`%method-applicable-p`/
`%specializers-applicable-p`/`%filter-applicable-methods`/
`%applicable-methods`/`%order-methods`/`%invoke-method-chain`/
`%generic-call`等、ディスパッチ機構一式がリンク後のバイナリで連続領域
(ファイルRVA `0x52600`〜`0x631cb`)を構成していることを確認し、TCGプラグインの
アドレス範囲指定でこの区間だけの命令数を計測したところ:

| 計測 | 命令数 |
|---|---|
| 起動+mountのみ | 20,271 |
| 起動+mount+1MB読み込み | 30,427 |
| **ディスパッチ機構自体の差分** | **10,156(全体の0.0004%)** |

`*generic-methods*`に登録される総称関数・メソッドの実数が(システム全体で
`initialize-object`/`report-condition`/`read-into!`/`write-from!`等)数個〜
十数個程度にとどまるため、「線形走査」自体はO(1000)級の`os_make_symbol`とは
規模が全く異なり、実害が無いレベルだった。**コードの見た目上の懸念(未
キャッシュの線形探索)が、実際のボトルネックとは限らない**という、本調査
全体を通じて繰り返し現れているパターンがここでも再現した。

### 3. 落とし穴: __step(consリストABI)ではなく__step_fixed(固定引数ABI)を測るべきだった

「メソッド本体(クラスタチェイン走査)」の候補として`%fat16-read-into-impl`
(`lisp_ll_fat16_read_into_impl__step`)のアドレス範囲を計測したところ
`range_insns=0`という結果になった。TBダンプで直接確認したところ、実行時に
このアドレス範囲へは一切到達していなかった。原因は、ABI-M6(AOT-to-AOT
静的呼び出しの固定引数ABI化)により、`defmethod`本体のクロージャから
`%fat16-read-into-impl`への呼び出しが実際には**consリストABI版
(`__step`)ではなく固定引数ABI版(`__step_fixed`)**を使っていたため。
`__step_fixed`(ファイルRVA `0xdbd83`)を測り直しても、やはり
`range_insns=0`だった。

### 4. 方針転換: アドレス範囲の事前予想をやめ、プラグインに実測プロファイラ機能を追加

2回連続で「予想したアドレス範囲に実行が無い」という結果になったため、
`tools/plugins/isiki_instcount.c`に`profile=1`オプションを追加した。TB単位で
(開始アドレス, 命令数, 実行回数)を記録し、終了時に「命令数×実行回数」
降順でtop 40件を出力する機能で、アドレス範囲を静的に予想する代わりに
**実際にホットな箇所を直接発見する**アプローチに切り替えた。

### 5. 実測結果: 真因は`read-file-into-vector`のAOT呼び出し規約オーバーヘッド

1MB読み込みベンチマークをプロファイルし、top 40のホットTBをシンボルに
対応付けたところ(top 40だけで全体2,566,285,269命令のうち
1,777,902,294命令≒69.3%を説明):

| シンボル | 命令数(top40内) | 割合 |
|---|---|---|
| `get_current_process` | 526,208,500 | 29.6% |
| `is_control_transfer`/`os_is_control_transfer`(合算) | 484,457,888 | 27.3% |
| `primitive_add2` | 121,852,560 | 6.9% |
| `primitive_set_elt_impl` | 108,880,356 | 6.1% |
| `number_compare` | 81,950,954 | 4.6% |
| `is_vector`/`is_float`(合算) | 70,680,930 | 4.0% |
| `strncmpignorecase` | 16,215,168 | 0.9% |
| `primitive_less_than2` | 15,156,140 | 0.9% |
| `primitive_create_vector` | 15,112,240 | 0.9% |
| `os_stream_read_char` | 13,719,810 | 0.8% |

`get_current_process`は1MB(1,000,000byte)に対し**105,241,700回**呼ばれて
いた(1byteあたり約105回)。実装自体はO(1)(`&g_processes[g_current_
process_index]`、配列添字アクセス)だが、`GC_PROTECT`マクロが1回につき
`get_current_process()`を2回呼ぶ(初期化子と代入)ため、**呼び出し回数の
絶対数**がボトルネックになっている。`is_control_transfer`/
`os_is_control_transfer`も同様に、`transpile-call-args-guarded`が生成する
「引数を1つ評価するたびにGC_PROTECTし、非局所脱出シグナルでないか
チェックする」というAOTの安全側ガード付き呼び出しパターインが、1byteの
読み込み・書き込みという極めて軽い操作に対しても律儀に発行され続けて
いることを示している。

### 判定

「ディスパッチ処理が支配的」でも「メソッド本体(クラスタチェイン走査)が
支配的」でもなく、**`read-file-into-vector`のAOT生成コード自体(1byte
ずつの`read-byte`/`set-elt`呼び出しループ)が、za.cのJITには既に適用済み
(Phase1/Phase2、documents/abi-redesign.md参照)のような「非アロケーション
演算のGC_PROTECT省略」「fixnum算術のインライン化」を一切受けていない**
ことが真因と判明した。次のアクションとして、za.cのPhase1/Phase2と同種の
最適化(leaf判定によるGC_PROTECT省略、`+`/`<`等の単純演算のインライン化)を
AOTトランスパイラ(`transpile.lisp`)側にも適用することを、新しい
マイルストンとして提案する(本書の範囲外、別途指示書で計画する)。

## AOT側GC_PROTECT削減(leaf判定)の実装と効果(2026-09-11)

前節の判定に基づき、za.cのPhase1(`za_operand_is_safe_leaf`)と同じ基準を
`transpile.lisp`に移植した。

### 実装

`transpile-call-args-guarded`(関数/プリミティブ呼び出しの各引数を1つずつ
評価する箇所、AOT生成コードの`GC_PROTECT`発行源の大半を占める)に、新設の
`aot-form-is-leaf`判定を組み込んだ。leafと判定される(=`GC_PROTECT`も
`os_is_control_transfer`チェックも省略できる)のは以下の2ケースのみ
(za.cの`za_operand_is_safe_leaf`と同一基準):

- fixnum/文字リテラル(`os_make_fixnum`/`os_make_char`が返すのは即値で
  ヒープ非経由、GCの再配置対象にならない)。
- 非box化ローカル変数への参照(束縛時に一度だけ`GC_PROTECT`された
  Cローカル変数を読むだけで、その保護は束縛を含む関数の実行が終わるまで
  有効なまま。Lisp側の`setq`は非局所脱出シグナルを弾いてからでなければ
  実際の代入を行わない生成コードのため、正しく評価が完了したローカル
  変数がシグナル値そのものを保持することはない)。

`za_emit_operand`(JIT側)がこれら2ケースで`CALL`命令を一切発行しない
(movabs/レジスタロードのみ)ことを確認済みであり、AOT側でも同じ条件で
`os_is_control_transfer`チェックまで安全に省略できると判断した(box化
ローカル・グローバル変数・quoteシンボル・文字列リテラル・裸のT・関数
呼び出し等は、za.c同様に安全側でleafとしない)。

### 効果測定

`read-file-into-vector`の内側ループ(`__lisp_lambda_417__step`、1byteの
処理につき`(< i len)`→`(read-byte stream)`→`(set-elt byte vec i)`→
`(setq i (+ i 1))`)の反復あたり`GC_PROTECT`呼び出しが**8回→1回**へ
削減された(`(read-byte stream)`の戻り値のみ、後続の`set-elt`に渡すまで
保護が必要なため残る)。

| 計測 | 修正前 | 修正後 | 変化 |
|---|---|---|---|
| 1MB読み込みの命令数(TCGプラグイン) | 約2,562,646,170 | 1,444,529,546 | **-43.6%** |
| 1MB読み込みの壁時計時間(tickカウンタ) | 31.28秒 | 14.40秒 | **-54.0%(2.17倍)** |

壁時計時間の改善率が命令数の改善率を上回っているのは、削減された命令の
多くが(`get_current_process`呼び出し等の)実関数呼び出し(CALL/RET)
であり、TCGでの1命令あたりのディスパッチコストが均一ではない
(関数呼び出し境界はより重い)ためと見られる。

ネイティブ`make test`(8135件)・QEMU`make test-qemu`(1614→1620件、
新設のGC整合性回帰テスト6件を含む)とも全てパスすることを確認済み。

### GC整合性回帰テスト

`test/lisp/aot_leaf_gc_test.lisp`(`qemu_boot_test.lisp`経由で標準テスト
スイートに常設)を追加した。`write-vector-to-file`/`read-file-into-vector`
(本改善の対象そのもの)で300KBのデータを往復させ、その前後で意図的に
大量のゴミ`vector`を確保してGCを複数回誘発し、内容(`equal`での完全一致)
が破損しないことを確認する。leaf判定は式の**静的な構文形**(fixnum/文字
リテラルか、既存のscope alistでboxed-pがnilと分かるローカル変数参照か)
だけに基づき実行時の値には一切依存しないため、za.cのfixnum溢れ時
フォールバックのような「実行時に型で分岐する」境界ケースは存在しない
(該当しない場合は常に安全側の保護付きパスにフォールバックする)。

## `os_is_control_transfer`削減の調査(実装は見送り、2026-09-11)

`is_control_transfer`の実装(`eval.c`)を確認した:

```c
static int is_control_transfer(lisp_val_t v) {
    if ((v & TAG_MASK) != TAG_INSTANCE) {
        return 0;
    }
    UINT64 *obj = (UINT64 *)(v & ~TAG_MASK);
    return obj[0] == MAGIC_BLOCK_EXIT || obj[0] == MAGIC_CATCH_EXIT || obj[0] == MAGIC_GO_EXIT;
}
```

チェック自体は極めて軽い(非TAG_INSTANCE値なら1回のタグ比較のみで即座に
falseを返し、メモリ参照すら発生しない)。にもかかわらず全体の27.3%を
占めていた理由は、GC_PROTECTと同様に**呼び出し回数そのものの多さ**と、
`os_is_control_transfer`が`eval.c`(別コンパイル単位)で定義された非
`inline`関数であるため、`lisp_compiled.c`側の呼び出し元へインライン
展開されず毎回実際のCALL/RETが発生していることにある。

**上記のGC_PROTECT削減により、leaf判定される引数についてはこのチェック
自体も既に併せて省略済み**である(残るのは、関数呼び出しの戻り値等
「呼び出しを含む式」の結果に対するチェックのみ)。

### 条件システムとの関係

`isiki-os`の条件システム(`error`/`cerror`/`with-handler`、
`src/lisp/init.lisp`/`init_aot.lisp`)は、`*handlers*`という動的変数
スタックをたどってハンドラを直接`funcall`する設計であり、
`block`/`catch`/`tagbody`の非局所脱出シグナル機構(`is_control_transfer`
が検知する対象)とは**完全に別系統**である。したがって条件システムの
挙動を壊す心配なく、`is_control_transfer`削減は`return-from`/`throw`/`go`
の到達可能性だけを考えればよい。

### 削減が難しい理由

leaf判定(GC_PROTECT削減)は「この式の評価自体がヒープ確保も呼び出しも
一切含まない」という、**式そのものの構文形だけ**から静的に判定できた。
一方`os_is_control_transfer`を安全に省略するには、「この式(典型的には
関数呼び出し)の評価結果が、`return-from`/`throw`/`go`による非局所脱出
シグナルには絶対になりえない」ことを示す必要があり、これは式単体の
構文形ではなく、**呼び出し先の関数の中身(さらにその中身が呼ぶ関数…)**
まで辿らないと判定できない(=関数単位ではなく呼び出しグラフ全体の
到達可能性解析が必要)。本セッション前半で`go`の直接goto化のために
`*enclosing-tagbodies*`を導入したが、あれは「字句的に閉じた同一C関数内」
という局所的な情報だけで済む特殊ケースであり、一般の関数呼び出しの
戻り値には適用できない。

### 判定: 実装は見送り、低リスクな代替案のみ記録

`return-from`/`throw`/`go`の到達可能性解析は、GC_PROTECT削減より
はるかに大きく・リスクの高い実装になる(呼び出しグラフ全体を辿る
必要があり、相互再帰・前方参照・動的なfuncall経由の呼び出し等を
どう扱うかという設計判断が新たに必要になる)ため、本マイルストンの
スコープには含めない。

代わりに、意味論を一切変えない、機械的で低リスクな代替案を記録して
おく: `os_is_control_transfer`(および内部の`is_control_transfer`)を
共有ヘッダで`static inline`として定義し直せば、コンパイラが
`lisp_compiled.c`の各呼び出し箇所へインライン展開できるようになり、
チェックの論理自体は変えずにCALL/RETのオーバーヘッドだけを除去できる
可能性がある。ただし実際の効果はコンパイラの最適化判断(`-O1`ビルド、
巨大な`lisp_compiled.c`1ファイルでのインライン化の可否)に依存するため
未検証であり、着手する場合は本書の手法1(TCGプラグイン)で効果を
確認すること。

GC_PROTECT削減後の残り約14.4億命令のうち、`primitive_add2`/
`primitive_less_than2`(呼び出し先の中身も含む)がどれだけを占めるかを、
実測プロファイラ(`profile=1`)のtop40出力をシンボルへ対応付けて計測した。
前回・前々回の教訓通り、アドレス範囲は静的に予想せず、計測対象と同一
ディスク構成で`%%DIAG-IDE-READ-SECTORS-ADDR`により実測した
(`0xd00d000`)。

|---|---|---|
| `primitive_add2` | 121,852,560 | 8.44% |
| `primitive_less_than2` | 15,156,140 | 1.05% |

参考(同じtop40内での他の主要項目との比較):

9.48%は判定基準の「10〜15%以上(着手)」と「5%未満(見送り)」の中間に
位置する。着手可否を左右する重要な非対称性として、`primitive_add2`と
`primitive_less_than2`とで実装のしやすさが大きく異なることが判明した:

- **`primitive_add2`**: 既に非負fixnum同士の高速パス(オーバーフロー
  チェック込み)を持つ小さな自己完結関数(`runtime.c`)。`za.c`のように
  生の機械語を生成する必要は無く、**この関数を`static inline`として
  共有ヘッダへ移し、コンパイラに`lisp_compiled.c`側の呼び出し箇所へ
  インライン展開させるだけ**で、CALL/RETのオーバーヘッドをほぼ排除
  できる可能性が高い(低リスク・低実装コスト)。
- **`primitive_less_than2`**: `return number_compare(a, b) < 0 ? ... : ...;`
  という薄いラッパーで、実処理は`number_compare`(bignum/float等を含む
  汎用の多相比較、大きめの関数)に委譲している。`primitive_less_than2`
  自体を`static inline`化しても、`number_compare`への呼び出し自体は
  残る(`number_compare`は大きく`-O1`でのインライン化候補になりにくい)
  ため、`primitive_add2`ほどの効果は見込めない。fixnum同士の比較専用の
  高速パスを`primitive_less_than2`自身に追加する(`number_compare`への
  委譲を、非fixnum時のみのフォールバックにする)実装が必要で、
  `primitive_add2`より実装コストが高い。

### 次のアクション(本書のスコープ外、別途指示書で計画)

`za.c`のPhase2(生の機械語を手書き生成)をそのままAOTへ移植するのではなく、
**まず`primitive_add2`(および同様の自己完結な高速パスを持つ2引数
プリミティブ)を`static inline`化する、より小さく低リスクな一手から
着手する**ことを推奨する。これは前節で記録した`os_is_control_transfer`の
`static inline`化案と同じ手法(意味論を変えずコンパイラのインライン化に
委ねる)であり、まとめて1つのマイルストンとして計画できる可能性がある。
`primitive_less_than2`/`number_compare`側のfixnum高速パス追加は、効果が
不確実なため、`primitive_add2`側の実測結果を見てから改めて判断する。

## AOT側`primitive_add2`のstatic inline化: 実装・実測・**revert**(2026-09-11)

前節の見積もりに基づき、`primitive_add2`を`static inline`化する低リスク
施策として着手した。**実測の結果、命令数・壁時計時間とも悪化することが
判明し、変更を完全にrevertした。** 期待に反する結果だったが、AOT最適化の
今後の方針判断に直結する重要な知見のため詳しく記録する。

### 実装した内容

za.cが`primitive_add2`のアドレスを生ポインタとしてJIT生成コードへ直接
埋め込んでいる(`za.c:1997/2014/2804`の`(void *)primitive_add2`比較・
呼び出し先アドレス埋め込み)ことを事前に確認した。これは`primitive_add2`
自体を`static inline`化(内部リンケージ化)すると、翻訳単位ごとに異なる
アドレスの複製が生成されJITの前提(単一の安定したアドレス)を崩しうる
ことを意味する。そのため、**za.c向けの既存`primitive_add2`(外部リンケージ)
はそのまま維持し、ロジック本体を`primitive_add2_inline`
(`static inline __attribute__((always_inline))`、`runtime.h`)へ複製し、
AOT生成コード(`transpile.lisp`の`*primitive-fixed-arity-c-names*`の`+`の
マッピング)だけをこちらへ向ける**という設計にした。`primitive_add2`は
`primitive_add2_inline`を呼ぶだけの薄いラッパーとして残した。

事前確認: `primitive_add2`の高速パス(非負fixnum同士)には元々
`GC_PROTECT`が無く(ヒープ確保が発生しないため不要、想定通り)、
除去すべき不要な保護は無かった。

### 実測結果: 悪化

| 計測 | leaf判定のみ(直前の状態) | `primitive_add2_inline`適用後 | 変化 |
|---|---|---|---|
| 1MB読み込みの命令数 | 1,444,529,546 | 1,513,081,220(2回の再実行でも1,511,797,386/1,511,875,874と再現) | **+4.7%(悪化)** |
| 1MB読み込みの壁時計時間 | 14.40秒 | 28.3〜28.7秒(3回計測) | **約2倍(悪化)** |
| `__lisp_lambda_417__step`(ホットループ本体)のコードサイズ | 1516byte | 1792byte | +18.2% |

2回の再実行でほぼ同じ値が出ており(誤差0.01%未満)、単なる実行時ノイズ
ではなく**再現性のある悪化**であることを確認した。`primitive_add2_inline`
という独立シンボルはビルド成果物のシンボルテーブルに存在せず(コンパイラが
実際にインライン展開したことの確認)、`always_inline`は意図通り機能して
いた。

### 原因の考察(未確定、深追いはしていない)

コンパイラが実際にインライン展開したにもかかわらず命令数が増えたことから、
**`-O1`という比較的弱い最適化レベルでは、深くネストしたGNU文式
(`transpile-call-args-guarded`が生成する`({ ... ? ... : (...) ; })`の
入れ子)へ`GC_PROTECT`の`cleanup`属性付きローカル変数を含む関数本体を
強制インライン展開すると、周囲のコード全体に対する最適化(レジスタ
割り当て等)がかえって悪化する**可能性が高いと考えている。`za.c`の
Phase2が生の機械語を直接手書きすることで確実に「call/retの排除=命令数
削減」を達成できたのに対し、AOTのC言語レベルでの「インライン化」は
**Cコンパイラの最適化パイプライン全体に委ねることになり、確実な改善を
保証しない**という、根本的な違いがあることが今回の実測で明らかになった。
原因の完全な特定(`-O2`でも同様に悪化するか等)は本書のスコープ外とし、
深追いしていない。

### 判定: revert、AOT側fixnum算術インライン化は当面見送り

変更は完全にrevertした(`primitive_add2_inline`の追加・
`primitive_add2`のラッパー化・`transpile.lisp`の`+`マッピング変更を
いずれも元に戻し、ネイティブ`make test`(8135件)・QEMU`make test-qemu`
(1620件)で回帰が無いことを確認済み)。

この結果を踏まえ、AOT側のfixnum算術インライン化(`+`/`<`等)は
**当面見送る**。再検討する場合は、以下のいずれかの前提が必要:

- カーネルビルドを`-O2`(またはそれ以上)へ引き上げた上で同じ実測を
  やり直す(ビルド全体への影響が大きいため別マイルストンが必要)。
- `transpile.lisp`のコード生成自体が、C言語の`inline`/コンパイラの
  最適化に頼らず、za.cと同じ「呼び出し元が直接、条件分岐+算術+タグ
  付けのC式をインライン展開して書く」という、コード生成レベルでの
  インライン化(コンパイラの判断を経由しない)を行う設計に変更する
  (実装コストは`static inline`化よりずっと高いが、`za.c`のPhase2と
  同じ確実性が期待できる)。

いずれも本書の当初想定より大きな投資が必要なため、次の優先度は
`os_is_control_transfer`側の`static inline`化(まだ未実装)の実測、
または全く別のホットスポットの探索に置く方が妥当と判断する。

### `os_is_control_transfer`のstatic inline化について

前節で記録した`os_is_control_transfer`の`static inline`化案について、
本セッションでは**実装していない**。今回の`primitive_add2`の否定的な
結果を踏まえると、`os_is_control_transfer`も同じ理由(`-O1`での
インライン化がかえって悪化する)で同様に失敗する可能性が相応にある。
着手する場合も、`primitive_add2`と同じ手順(実装→命令数計測基盤での
before/after比較→悪化していればrevert)を必ず踏むこと。楽観的な
「低リスクな一手」という前提そのものを疑ってかかる必要がある。

## 残り約14.4億命令のホットスポット再探索(top40全体の分類、2026-09-11)

`primitive_add2`のような「予想がついていた場所」を深追いするより、
実測プロファイラ(`profile=1`)のtop40を機械的に洗い出す方が投資対効果が
高いと判断し、`read-file-into-vector`(1MB読み込み)のtop40全項目を、
boot-onlyプロファイルとの対応する各アドレスごとの差分により
read操作への寄与を正確に切り分けた上で分類した。

### 重要な方法論上の修正: 「kernelイメージ外」領域はboot専用と確定

top40の約23%(16エントリ)が、自イメージ(約3MB)の範囲外の高位アドレス
(`0xfffcXXXX`/`0xfeecXXXX`/`0xe861XXXX`等)を指しており、当初「未調査の
領域(区分C候補)」に見えた。しかし**同一アドレスごとにboot-onlyプロファイル
と突き合わせたところ、これら全てのexec回数がboot-onlyとboot+read1mの間で
完全に一致(誤差は数千程度のノイズのみ)しており、read操作への寄与は
実質ゼロと確定した**。おそらくOVMFファームウェア/割り込み処理関連の
boot時アクティビティであり、read操作の最適化対象ではない。**top40の
生の合計を単純に読むと支配的コストを誤認する**ため、以後の命令数
プロファイリングでは必ずboot-onlyとの差分を取ることを標準手順とする。

### top40の分類(read操作への寄与のみ、boot専用分を除く)

### 区分C候補だった`strncmpignorecase`の調査結果: 新規の削減余地なし

命令数が約100万(1バイトあたり約1回に見える規模)だったため、`os_make_
symbol`系のキャッシュ漏れ(区分Cの新発見)を疑い、`os_make_symbol`
自身の実行範囲を個別計測した。結果、`os_make_symbol`自体の呼び出し回数
(read操作起因の差分)は多く見積もっても数十万回程度に留まり、「1byte
ごとに1回」という規模ではなかった。`strncmpignorecase`がホットに見えた
真因は、**該当アドレスがこの関数自身の文字比較ループの内部基本ブロック**
であり、1回の呼び出しでも比較対象のシンボル名の文字数分だけこの
ブロックが繰り返し実行されるため、実際の呼び出し回数より多い実行回数に
なっていたことだった。これは今回のB'(ハッシュ索引化)適用後の**正常な
残余コスト**であり、新たな削減余地(区分C)ではなく区分A寄りと判断する。

### 判定: `read-file-into-vector`単体のこれ以上の大幅な改善は見込みにくい

区分Aの合計(約2.08億、14.4%)は実質的な処理そのもの(ストリーム読み取り・
ベクタ書き込み・型チェック)であり削減余地が乏しい。区分Bの主要項目
(`is_control_transfer`系13.46%・`get_current_process`11.05%・
`primitive_add2`/`number_compare`/`primitive_less_than2`系15.16%)は
いずれも**既に調査済みで、削減がリスク過多(呼び出しグラフ解析が必要)
か、実測で悪化することが確認済み(`primitive_add2`のrevert)**である。
新たな区分C(未知の削減余地)は見つからなかった(`strncmpignorecase`は
調査の結果、区分Aに近い既存機構の残余コストと判明)。

したがって、`read-file-into-vector`単体のホットループについては、
低リスクで確実な追加削減の糸口が尽きたと判断する。次に投資すべき
対象は、本書で以前保留した**書き込み側(`fat16-create-file`/
`fat32-create-file`)の性能調査**(FAT32の2MB書き込みが単独でも9分以上
未完了だった問題、および直前の書き込みの後に後続の書き込みがさらに
遅くなる未解明の現象)に切り替えることを推奨する。今回確立した命令数
計測基盤(TCGプラグイン、`profile=1`のホットスポット直接探索、
boot-only差分による正確な切り分け手法)は、そちらの調査にもそのまま
再利用できる。

## read-file-into-vector-native: 素のC実装によるフロア(下限)計測(2026-09-11)

「残り約14.4億命令のホットスポット再探索」節で、`read-file-into-vector`
単体の低リスクな追加削減の糸口が尽きたと判断した後、「Lisp/AOTの呼び出し
規約・GC保護のオーバーヘッドを完全にゼロにした場合、この読み込み処理は
本来どこまで速くなりうるのか」という理論的な下限(フロア)を計測した。

### 実装

`src/c/mount.c`に`READ-FILE-INTO-VECTOR-NATIVE`(C関数名

規約を一切経由しない素のC関数として再実装し、`block_device_t::
read_sectors`を直接呼ぶ(1クラスタ分をまとめて1回のPIO転送にできる、
`read-sector`のLisp版が1セクタずつしか読めないのと異なる点)。読み込んだ

なお`dotimes`/`dolist`はISLispには存在せず(CommonLisp由来)トランスパイラも
未対応のため、higher-levelなイテレーション構文としてはISLisp標準の`for`を測った。

## letのImmobilized Spaceリーク: ループ内のletは約24,300反復でOSを停止させる(2026-09-11)

構文別ベンチマークスイート(次節)の`let`カテゴリを計測しようとしたところ、
他カテゴリが1起動2分程度で終わるのに対し、`let`のAOT版だけが33分経っても
完走しなかった。調査の結果、これは性能問題ではなく**カーネルが永久に
停止する実際のバグ**であることが判明した。

### 機構

AOTトランスパイラは`(let ((i n)) ...)`を`((lambda (i) ...) n)`へ展開した後、
インライン化せずに次のコードを生成する(`lisp_compiled.c`):

```c
os_make_lifted_closure((lisp_addr_t)(void *)__lisp_lambda_428, global_environment)
...
primitive_funcall(os_make_cons(__call_arg, os_make_cons(...)), env)
```

`os_make_lifted_closure`は内部で`os_fn_meta_alloc`を呼び、`za_fn_meta_t`
(24byte、16byte境界へ切り上げて32byte)を**Immobilized Space**から確保する。
Immobilized Spaceは`IMM_SPACE_SIZE = 4MB`の静的配列上のバンプアロケータで、
`os_fn_meta_alloc`のコメントが明記する通り「個別解放はせずOS生存期間中保持
される前提」であり、**GCでは一切回収されない**。

そして`os_imm_page_alloc`は空きが尽きると次のように振る舞う:

```c
fb->write_string(fb, "imm: space exhausted...");
for (;;) {
}
```

つまり**無限ループでカーネルが永久に停止する**。`-display none`で実行している
限りこのメッセージは見えないため、外からは「極端に遅い処理」と区別がつかない
(実測ではCPU使用率が1コアの約25%のまま、`test-results.txt`がサイズ0で
放置され続けた)。

### 実測(安全なNでの確認)

| 計測 | Immobilized Spaceの増分 | 1反復あたり |
|---|---|---|
| AOT `%%bench-aot-let` N=1000 | 163,840 byte | 163.8 byte |
| AOT `%%bench-aot-let` N=2000 | 319,488 byte | 159.7 byte |
| AOT `%%bench-aot-for` N=1000 | 28,672 byte | 28.7 byte |
| AOT `%%bench-aot-loop` N=1000(ループ内にletなし) | **0 byte** | 0 |
| C版 `%%bench-c-let` N=2000 | **0 byte** | 0 |

5変数の`let*`は入れ子のlambda 5個へ展開されるため、5クロージャ×32byte=
160byte/反復という理論値と実測が一致し、Nに対して線形に増える。ループ内に
`let`を持たないケースとC版がいずれも0byteであることから、原因が`let`の評価
そのものであることが対照実験として確定している。

### 影響範囲

起動直後のImmobilized Spaceの空きは 4,194,304 − 303,104 = 3,891,200 byte。

| 構文 | 消費 | ハングまでの反復数 |
|---|---|---|
| 5変数の`let*`をループ内で使う | 160 byte/反復 | **約 24,300 回** |
| `for`マクロ | 28.7 byte/反復 | 約 135,000 回 |

`let`はLispで最も基本的な構文であり、「ループの中で`let`を使う」ごく普通の
コードが数万反復でOSごと停止する。ファイルI/Oのような大きなループを
Lispで書く際の実質的な上限を決めてしまっており、性能比の問題より優先度が高い。

### Phase 1: za_fn_meta_tのfnptr単位一意化(実装済み)

停止性の修復だけを切り出し、性能改善(即時lambda呼び出しのインライン展開)とは
分離して実装した。

**前提条件の確認**: `za_fn_meta_t`は`cons_entry`/`fixed_entry`/`arity`の3つの
`UINT64`のみで、`lisp_val_t`フィールドを持たない(GCルート登録は不要)。
`captured_env`はmetaではなくインスタンスのword3に入るため、**metaの内容は
リフト先のC関数アドレスだけで決まる**。lifted closureでは`fixed_entry`/`arity`は
常に0のままで、生成後に書き換えるのは`os_make_jit_function_dual`(JITのコンパイル時、
実行回数比例ではない)だけである。したがって同じlambdaから作られる全クロージャが
1つのmetaを共有してよい。

**実装**: トランスパイラの`emit-closure-creation`が生成する式を、呼び出し箇所ごとの
C静的変数をmetaの実体として渡す形へ変更した。

```c
os_make_lifted_closure_with_meta(({ static za_fn_meta_t __closure_meta; &__closure_meta; }),
                                  (lisp_addr_t)(void *)__lisp_lambda_N, __closure_env_X)
```

静的記憶域はアドレスが不変でGCにもImmobilized Spaceにも依存しないため、
**Immobilized Spaceの消費は実行回数比例からゼロになる**(プログラムサイズ比例
ですらない)。`os_make_symbol_cached`+`static`局所変数という既存のイディオムと
同じ形で、毎回同じ値を書き込むだけなので初回判定の分岐も不要。

**あわせて修正した2点**:

- `%%imm-space-used-bytes`をページ粒度からバイト粒度へ変更した。従来は
  `g_imm_bump - g_imm_space`(4096byte単位でしか進まない)を返していたため、
  4096byte未満の消費が「0 byte」に見え、実行回数比例のリークを回帰テストで
  検出できなかった。各スロットカーソルが現在のページに残している未使用の末尾分を
  差し引いて実消費を返す。
- `os_imm_page_alloc`/`os_alloc_bytes`の枯渇時の空の`for(;;)`を`os_panic`へ
  置き換えた。QEMUテスト実行中はフック経由で電源断し、ハングではなくテスト失敗
  として終わらせる。フックが無い場合も`hlt`で止めることで、停止中のCPU使用率が
  ほぼ0になり「異常停止」と「極端に遅い処理」を外から判別できるようにした
  (今回33分間ハングに気づけなかった直接の原因がこれ)。

なお、当初「1反復あたり163.8 byte」と測れていた実測値と理論値160 byteの差
(3.8 byte)は、追加のリーク源ではなくページ粒度の丸めだった。3000反復×160 byte=
480,000 byteは118ページ=483,328 byteで、実測の増分合計と完全に一致する。

### forのtagbody直行化: 1711倍 → 62.8倍(実装済み)

`for`が最悪値を示した原因を確認したところ、**ループ構造自体は既に`while`と同じ
`tagbody`/`go`へ展開されており**、コストはループ本体の中にあった。ISLispの`for`は
step式を並列に評価する意味論を持つため、旧実装はそれを次の形で実現していた。

```lisp
(let ((%for-next-values (list step1 step2 ...)))   ; ← 毎反復ここを評価する
  (setq v1 (car %for-next-values))
  (setq v2 (car (cdr %for-next-values))))
```

1反復ごとに、(1)step値のconsリスト構築、(2)`let`によるクロージャ生成+consリスト
構築+`primitive_funcall`経由の動的ディスパッチ、(3)変数N個に対するO(N^2)の
car/cdr連鎖、が発生していた。`for`が`let`単体(2945命令/反復)の2.3倍も重かったのは
このためである。

**対処**: 一時変数をループの外側の`let`で一度だけ束縛し、ループ本体では素の`setq`
だけを使う形へ変更した。全step式を一時変数へ評価しきってから各束縛変数へ書き戻す
ため、並列束縛の意味論は保たれる。

```lisp
(let ((v1 init1) (v2 init2) (%for-tmp-1 nil) (%for-tmp-2 nil))
  (block nil
    (tagbody
     %for-loop
     (if end-test
         (return-from nil (progn result...))
         (progn body...
                (setq %for-tmp-1 step1) (setq %for-tmp-2 step2)
                (setq v1 %for-tmp-1)    (setq v2 %for-tmp-2)
                (go %for-loop))))))
```

| 計測 | 変更前 | 変更後 | 変化 |
|---|---|---|---|
| `for`(命令/反復) | 6870.20 | 250.18 | **-96.4%** |
| 比(AOT/C) | 1711倍 | **62.8倍** | |

これはPhase 2(即時lambda呼び出しのインライン展開)を待たずに達成できた。`for`は
もはや`let`(2945命令/反復)より軽く、単純ループ(145)と同じオーダーに収まっている。

意味論の回帰は`test/lisp/for_expansion_test.lisp`(`make test-qemu-for-expansion`)
で8件確認している。特に重要なのは並列束縛で、`(for ((a 0 b) (b 1 (+ a b))) ((> a 10) a))`
は並列なら13・逐次に壊れていると16になるため、これを最初のテストに置いた。
step式の省略・入れ子の`for`(一時変数名の衝突)・GC併走・Immobilized Space消費0も
確認済み。

なお`ide.lisp`が記録していた「`for`マクロはGCが特定のタイミングで走ると以後永久に
そのループ内での結果が壊れる」既知のバグは、原因とされていた「ループ本体に毎回
新規生成される`let`」自体が無くなった。GCを誘発しながら1000反復する回帰テストは
通っているが、元の症状が間欠的だったため、`for`をホットパスで使い直す前には
改めて確認することを勧める。

### Phase 0: 計器と前提の検証結果

Phase 1の受け入れ判定が計器に依存するため、計器そのものの正当性と、設計の前提を
個別に検証した。

**計器のバイト粒度**: `%%imm-space-used-bytes`の値が4096の倍数でないこと
(実測 275,824、4096で割った余り 1,392)を確認した。ページ粒度のままなら
必ず0になる。

**3つの実行経路すべてで消費0**:

| 経路 | 計測 | 消費 |
|---|---|---|
| 計器の粒度確認 | `for`フォームを1回/2回/128回評価 | 0 / 0 / 0 byte |
| AOT | `%%bench-aot-let`(ループ内5変数`let*`)20,000反復 | 0 byte |
| JIT | ループ内でlambdaを値として生成 20,000反復 | 0 byte |
| インタプリタ | トップレベル`while`でlambda生成 2,000反復 | 0 byte |

JIT経路は`%%za-compiled-p`が両関数についてTを返すことを確認した上で計測しており、
AOT経路だけの確認にはなっていない(`test/lisp/imm_leak_test.lisp`に恒久化済み)。

**枯渇時の挙動**: 診断専用プリミティブ`%%DIAG-IMM-BURN`でImmobilized Spaceを
意図的に使い切ったところ、**6.4秒で電源断して終了**した(修正前は空の`for(;;)`で
永久にCPUを回し続けた)。panicは消費バイト数・カーソル別の内訳・直近の確保要求
サイズを表示する。

**`za_fn_meta_t`に`lisp_val_t`フィールドは存在しない**: 構造体は
`cons_entry`/`fixed_entry`/`arity`の`UINT64`3つのみで、前2者はコードアドレス、
最後は整数である。したがって「meta内の`lisp_val_t`がGCルート未登録のため、
GC後にmetaが移動前アドレスを指し続け、そのmetaを使う限り壊れ続ける」という
`ide.lisp`記録の間欠バグに対する仮説は、**構造上ありえないものとして否定される**。
GCルート登録も不要。間欠バグの真因は引き続き未特定であり、`for`の修正で
再現しなくなった事実を根拠に解決したと判断してはならない。

**残差3.8 byte/反復は存在しない**: 修正前の実測は`let` N=1000で+163,840、
N=2000で+319,488(いずれもページ粒度)。累計3000反復の増分は483,328 = 118ページ。
消費が正確に160 byte/反復なら 3000×160 = 480,000 byte で、これは118ページ
(483,328 byte)に収まり**実測と完全に一致する**。仮に163.8 byte/反復なら
3000×163.8 = 491,400 byte となり120ページ(491,520 byte)を要するため実測と
矛盾する。163.8という値は、ページ丸めされた163,840を反復数1000で割ったことに
由来する見かけ上の数字だった。

### Phase 2: 即時lambda呼び出しのインライン展開(実装済み)

#### 着手前の見積もり(2-0-1)

インライン展開が消せるのはクロージャ生成・引数consリスト構築・
`primitive_funcall`の3つだけなので、これらが2945命令のうちどれだけを占めるかを
先に測った。まず3操作だけを繰り返す診断プリミティブ(`%%DIAG-CLOSURE-CALL`)で
**283.5命令/回**を得たが、これはAOTのラッパーを含まない下限である。

実コード上の値を得るため、束縛数1の`let*`(`%%bench-aot-let1`)を追加し、
boot時のゆらぎが相殺される**傾き法**(同じ関数をN=100万と300万で測り差を取る)で
比較した。

| 束縛数 | N=100万 | N=300万 | 傾き(命令/反復) |
|---|---|---|---|
| 1 | 1,927,669,992 | 3,538,537,692 | 805.4 |
| 5 | 4,108,451,313 | 10,080,604,477 | 2,986.1 |

`cost(k) = base + k × per_binding`を解くと**base = 260、1束縛あたり = 545.2命令**。
5束縛で2,726命令となり、**全体の91.3%が束縛あたりのコスト**だった。
インライン展開の対象が支配的であることが確認できたため実装に進んだ。

#### 実装

`transpile-expr`の即時lambda分岐に、インライン経路を追加した。判定には
**既存の`captured-params`をそのまま再利用する**(独立した解析器を新たに書くと
既存のラムダリフティング判定との食い違いが将来のバグ源になるため)。
`boxed-params`が`(intersection (setq-targets ...) (captured-params body params))`と
定義されていることから、`captured-params`が既存の捕捉判定そのものだと確認できる。

束縛変数がネストしたlambdaに捕捉されない場合のみインライン化し、捕捉がある場合は
従来のクロージャ経路へフォールバックする。`&rest`つき・arity不一致も
フォールバックさせる。

並列束縛の意味論は、**initを外側スコープ・bodyを内側スコープで展開**することで
満たす。束縛変数には一意のC名(`__inl_N`)を割り当てるため、
`(let ((a 1)) (let ((a 2) (b a)) b))`のbのinit `a`は外側の`a`へ解決される。
`let*`は入れ子のlambdaへ展開済みなので、各段が個別にこの経路を通って逐次束縛になる。

`GC_PROTECT`の省略条件は関数引数より厳しくしている。関数呼び出しの引数は評価後
すぐ消費されるためleafなら省略できるが、`let`の束縛変数はbodyの実行中ずっと生き、
body内で`setq`されてヒープ上の値を持ちうる。そのためleafであっても、その変数が
body内で`setq`される場合は保護を省略しない。

#### 実装中に検出したバグ

最初の実装ではinitも内側スコープで展開していたため、
`(let ((a 1)) (let ((a 2) (b a)) b))`が**2を返した**(逐次束縛になっていた)。
正解は1。ネイティブのフィクスチャテストで検出し、initを外側スコープで展開するよう
修正した。

#### 結果

| カテゴリ | Phase 2前 | Phase 2後 | 変化 |
|---|---|---|---|
| `let`(命令/反復) | 2945 | **643.03** | **-78.2%** |
| `let`の比(AOT/C) | 630倍 | **126.2倍** | |
| `cons`(命令/反復) | 485.53 | **243.15** | **-49.9%** |
| `cons`の比 | 4.2倍 | **2.1倍** | |

`cons`が半減したのは、ベンチマークのループ本体が内側に`let`を持っており、それが
インライン化されたため(副次的な効果)。他のカテゴリ(`for`/`branch`/`arith`/
`funcall`/`tailrec`/`nontailrec`/`vector`/`loop`)はいずれも±5%以内で退行なし。

到達点は2-0-1の見積もり(base 260 + 5×(init算術 + GC_PROTECT) ≒ 500〜650)の
上端とよく一致した。カーネルバイナリは2,612,350 → 2,161,996 byte(**-17%**)へ縮み、
リフトされたlambda関数群が実際に消えたことが裏付けられた。

フォールバックの集計はトランスパイル時に標準エラーへ出力される。現状は
**210件すべて`:captured`**で、想定通り「クロージャに捕捉される束縛」だけが
従来経路に残っている。ベンチマークの`let`が実際にインライン化されていることは、
生成コードに`__inl_`が現れ`os_make_lifted_closure`/`primitive_funcall`が
現れないことで確認済み。

#### 検証

意味論は`test/c/lisp_compiled_test.c`の`test_transpile_fixture_let_inline`で12件確認
(`make test`、ネイティブなので数秒で回る)。並列束縛・逐次束縛・`setq`・
シャドーイング・`return-from`貫通・`tagbody`/`go`貫通・init中の非局所脱出・
入れ子の`let`/`let*`/`for`・10段の深い入れ子・捕捉ありのフォールバック経路2種、
および**インライン化された`let`とフォールバックした`let`が同一関数内に混在する
状態でGCを跨ぐ**ケースを含む。
