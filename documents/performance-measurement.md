# isiki-osの性能測定手法

`feature/abi-redesign`でのJIT/AOT性能調査を通じて、以下の手法をそれぞれ
異なる場面で使い分けてきた。本書は、今後の性能調査(特にIDE/FAT I/Oの
命令数ベースでの追加最適化)で標準的に参照できるよう、各手法の特性・
使い分け・実際の使い方をまとめる。

## 手法の一覧と使い分け

| 手法 | 何を測るか | 長所 | 短所 | 主な用途 |
|---|---|---|---|---|
| ゲスト内tickカウンタ(`get-internal-real-time`) | 壁時計時間(10ms単位) | 実装が既にある、Lispコードから直接読める | タイマー割り込み自体のオーバーヘッドを含みうる、ホストのスケジューリングノイズの影響を受ける | 大まかな体感速度の比較、既存テストの回帰検知 |
| ホスト側`strace`(futex回数等) | ホストのシステムコール発行状況 | ホスト側のボトルネック(BQL競合等)の切り分けに使える | ノイズが非常に大きい(GC計装2回呼んだだけで速度が4-5倍変わった実例あり)。ホストの実行速度と相関するが厳密な指標ではない | QEMU/ホスト起因の外部要因を疑う初期切り分け段階のみ |
| **TCGプラグイン(命令数カウント)** | ゲストが実際に実行した命令数 | ホストの実行速度・スケジューリングノイズと無関係、高速(通常運転とほぼ同じ実時間) | 完全な決定論ではない(下記参照)、アドレス範囲を跨いだ内訳分離は追加の仕組みが要る | **実装変更の効果測定の主指標。以後はこれを既定の手法とする** |
| `-icount`(決定論的実行) | 命令数(TCGプラグインと同じ指標を、完全に再現性のある形で) | ビット単位で再現性がある(record/replayの基盤) | I/Oが絡む大きなワークロードは実時間で非常に遅い(実測: 通常数秒のN=1,000,000ループが3分強) | 小規模な決定論的A/B比較、TCGプラグインの結果に疑義がある場合のgold standard確認 |
| `-d in_asm,out_asm` | JIT/AOTが実際に生成した機械語 | 生成コードを直接目視確認できる | ログ量が膨大(ブートのみで53MB/145万行)、このホストのQEMUには逆アセンブラ(capstone等)が組み込まれておらず生バイト列(`OBJD-H:`/`OBJD-T:`)しか出力されない | 特定の生成コードパターンを直接確認したい場合(`-dfilter`でアドレス範囲を絞ることが前提) |

## 手法1: TCGプラグインによる命令数カウント

### 導入したプラグイン

`tools/plugins/isiki_instcount.c` — TB(translation block)ごとの命令数
(`qemu_plugin_tb_n_insns`)を、そのTBが実行されるたびに加算する方式。
1命令ごとのコールバックは極端に遅くなるため使わない。終了時に
stderrへ以下の形式で出力する:

```
[isiki_instcount] total_insns=<N>
```

オプション引数`start=0xADDR,end=0xADDR`で、その仮想アドレス範囲に含まれる
TBだけの命令数を`range_insns`として別集計できる(JIT生成コードはヒープ上の
動的アドレスのため主にAOT/C側の静的アドレスが既知な関数区間向け)。

### ビルドと使い方

`.so`はソースからのビルドを前提とし、git管理対象外(`tools/plugins/*.so`)。
`make test-qemu-instcount`が自動でビルドする(`isiki-builder`コンテナ内で
`libglib2.0-dev`をインストールし、ホストのQEMUバージョンに対応する
`qemu-plugin.h`をGitHubから取得してコンパイルする)。プラグインのABI
(`QEMU_PLUGIN_VERSION`)はヘッダとホストQEMU本体のバージョンが一致している
必要があるため、ホストのQEMUバージョンが`Makefile`の`QEMU_VERSION_FOR_PLUGIN`
(既定`10.2.1`)と異なる場合は`.envrc`等で上書きすること。

```
make test-qemu-instcount MILESTONE=test/lisp/qemu_boot_xxx.lisp [QEMU_DISK_IMG=...]
```

### 検証結果(2026-09-11、feature/icount-profiling)

**N-スケーリング(自己再帰ループのみ)**:

| N | total_insns | 起動オーバーヘッド差分 |
|---|---|---|
| 0(起動のみ) | 1,136,549,402 | - |
| 1,000,000 | 1,568,155,700 | 431,606,298 |
| 2,000,000 | 2,000,913,222 | 864,363,820 |

差分の比 864,363,820 / 431,606,298 = **2.0027**(理論値2.0とほぼ一致)。
1反復あたり約432命令(自己末尾呼び出しのトランポリン込み)。

**決定論性の検証(非icount、N=1,000,000を2回実行)**:

| 実行回 | total_insns |
|---|---|
| 1回目 | 1,568,878,009 |
| 2回目 | 1,568,731,913 |

差は146,096命令(**約0.0093%**)。通常のTCG実行(非icount)は、ブート時の
ACPI/PIT較正等の実時間依存ポーリングにより完全な決定論ではないが、
これまでのstrace/futexベースの計測(数倍単位の誤差)と比べれば
桁違いに小さいノイズである。実装変更の効果測定(通常は数%〜数十%の
差を検出したい)には十分な精度がある。

**IDE(FAT16)1MB読み込みの命令数**(ホスト側で事前にファイルを配置した
ディスクイメージを使い、書き込み側の影響を排除):

| 計測 | total_insns |
|---|---|
| 起動+mountのみ | 1,118,654,248 |
| 起動+mount+1MB読み込み | 3,671,343,591 |
| **読み込み自体の差分** | **2,552,689,343** |

1MBの読み込みに約**25.5億命令**。tickカウンタでの実測(31.28秒)と
組み合わせると、この区間のゲスト実行速度は約8,160万命令/秒
(2,552,689,343 / 31.28)であり、TCGの命令ディスパッチ自体が極端に遅い
わけではないことが分かる。**問題は1命令あたりのコストではなく、
1MBを読むのに要する命令の「絶対数」が大きいこと**を示しており、
今後の最適化(`insw`一括転送化・`READ MULTIPLE`対応等)の効果を
測る際は、この2,552,689,343を基準値として比較する。

## 手法2: `-icount`(決定論的実行モード)

```
make test-qemu-icount MILESTONE=test/lisp/qemu_boot_xxx.lisp [ICOUNT_SHIFT=N]
```

`-icount shift=auto`は本環境ではハング(または極端な遅延)を起こしたため、
固定`shift`値(既定7)を使うこと。マルチスレッドTCGと非互換のため
`-accel tcg,thread=single`もあわせて指定する(`test-qemu-icount`ターゲットが
自動で付与する)。

I/Oが絡む大きなワークロードは実時間で非常に遅い。N=1,000,000の自己再帰
ループ(通常運転なら3〜4秒)が**3分強**かかった実測がある。そのため、
日常的な計測には向かず、以下のような場合にのみ使う:

- TCGプラグインの結果(通常運転)に予期しない大きなばらつきが出て、
  実装のバグなのか、単なる実時間依存ポーリングのノイズなのかを
  切り分けたい場合。
- 極めて小さな実装差分(命令数で1%未満の変化)を、ノイズに埋もれず
  検出したい場合。

## 手法3: `-d in_asm,out_asm` + `-dfilter`

```
qemu-system-x86_64 ... -dfilter <start>+<length> -d in_asm,out_asm -D <logfile>
```

`-dfilter`の範囲指定は`start-end`ではなく**`start+length`形式**(例:
`0x100000+0x100000`)であることに注意(`start-end`形式は`Invalid range`
エラーになる)。

このホストのQEMU(Ubuntu 26.04パッケージ版）には逆アセンブラ
(capstone等)が組み込まれておらず、`in_asm`/`out_asm`は実際のニーモニックの
代わりに生バイト列(`OBJD-H:`/`OBJD-T:`)を出力する。読める形にするには、
`OBJD-H:`行の16進バイト列を抽出し、`objdump -D -b binary -m i386:x86-64
-M intel`等の外部ツールで別途逆アセンブルする必要がある(本書執筆時点で
未実施、次のフォローアップ)。

フィルタなしでの`-d in_asm,out_asm`はログ量が膨大(ブートのみで約53MB・
145万行)なため、実運用では必ず`-dfilter`でアドレス範囲を絞ること。
JIT生成コードはヒープ上の動的アドレスのため、対象アドレス範囲は実行時に
Lisp側から(例えば`%%za-compiled-p`が返す関数オブジェクトの生ポインタ等を
介して)取得する仕組みが別途必要になる(未実装、フォローアップ)。

## IDE読み込みの命令数内訳: ide.c単独 vs それ以外(2026-09-11)

「1MB=2048セクタ、約25.5億命令」という総数は、`ide_wait_drq`のポーリング
(1セクタあたり平均約156回)やデータ転送ループ(`inw`約256回/セクタ)だけを
素朴に足しても到底説明がつかない規模(1セクタあたり約124万命令)だった
ため、まず「`drivers/ide.c`内のコード(ポーリング+データ転送)」対
「それ以外(FAT層のクラスタチェイン走査+Lispランタイム)」という大枠を
切り分けた。

### アドレス範囲の特定方法

1. ビルド成果物(`esp_dir/EFI/BOOT/BOOTX64.EFI`、mingw-gccがリンクした
   PE形式)のシンボルテーブルを`x86_64-w64-mingw32-objdump -t`で読み、
   `drivers/ide.c`内の関数群(`set_err`/`ide_setup_lba`/
   `ide_delay400ns`/`ide_wait_drq`/`ide_wait_not_busy`/
   `os_ide_identify`/`os_ide_read_sectors`/`os_ide_write_sectors`)が
   連続領域(ファイル上の相対仮想アドレス、RVA)に配置されていることを
   確認した(`0x1a580`〜`0x1ab90`、1552byte、次のシンボルは
   `block_device.c`の`ide_bd_flush`で境界が明確)。
2. **【重要な落とし穴】** ファイル上のRVAは、UEFIローダが実際に
   イメージをロードする実行時ベースアドレスとは異なる。実行時ベース
   アドレスは起動のたびの再現性はある(同一ディスク構成で2回検証し
   一致を確認)一方、**アタッチするディスクイメージの構成(サイズ・
   パーティション形式の違い)によって変わる**ことを実測で発見した
   (デフォルトの`tmp/ide_disk.img`では`os_ide_read_sectors`の実行時
   アドレスが`0xD3AE8ED`だったのに対し、計測用に用意した16MB FAT16
   単純フォーマットのディスクでは`0xCF2D8ED`と異なっていた。原因は
   未特定だが、OVMFのイメージロード時のメモリ配置がディスク構成に
   影響される何らかの経路があると見られる)。このズレに気づかず
   デフォルト構成で計算したアドレス範囲を別のディスク構成の計測に
   流用した結果、最初の試行は`range_insns=0`という誤った結果になった。
   **教訓: アドレス範囲は必ず計測対象と全く同じQEMUコマンドライン
   (同じディスクイメージ)で実測してから使うこと。**
3. 実行時アドレスの取得には、`os_ide_read_sectors`(externリンケージ、
   `drivers/ide.h`で宣言済み)のポインタ値をそのまま返す診断用組み込み
   関数`%%DIAG-IDE-READ-SECTORS-ADDR`(`src/c/ide_subprimitive.c`の
   `cc_diag_ide_read_sectors_addr`)を追加し、Lisp側から
   `(%%diag-ide-read-sectors-addr)`で取得した。実行時アドレス−該当
   関数のファイルRVA=実行時ベースアドレス、という式で、`ide.c`クラスタ
   全体の実行時アドレス範囲を計算できる。

### 計測結果(1MB、FAT16、事前配置イメージで書き込み側を排除)

| 区分 | 命令数 | 全体に占める割合 |
|---|---|---|
| 総命令数(1MB読み込み自体、mountのみとの差分) | 2,581,582,199 | 100% |
| `ide.c`単独(ポーリング+データ転送、TCGプラグインのアドレス範囲指定で分離) | 9,500,016 | **0.368%** |
| それ以外(FAT層+Lispランタイム、差分) | 2,572,082,183 | **99.632%** |

1セクタ(512byte、2048セクタ/MB)あたりに換算すると、全体約132万命令の
うち`ide.c`が占めるのはわずか約4,864命令(先述の「ポーリング約156回+
inw約256回」という素朴な見積もりのオーダーとおおむね整合する)。
**残り約131.7万命令/セクタが「それ以外」に費やされている**ことになり、
支配的なボトルネックは`ide.c`(PIO層)ではなく、FAT層のクラスタチェイン
走査またはLispランタイム(AOT生成コード)側にあることが定量的に確定した。

### 判定と次の一手

「`ide.c`側が支配的であれば`insw`一括転送化・`READ MULTIPLE`対応に進む、
FAT層側が支配的であればそちらを優先する」という当初の判定基準に照らし、
**FAT層側が圧倒的に支配的(99.6%)** という結果になった。したがって
`insw`一括転送化・`READ MULTIPLE`対応は保留とし、次のフォローアップの
最優先事項を以下に変更する:

- `fat16-read-file`(または`read-file-into-vector`が最終的に呼ぶ
  `read-into!`経由の経路)が、クラスタ1個(または1セクタ)ごとに何らかの
  シンボル解決・関数呼び出しのオーバーヘッドを負っていないか。今回
  (`feature/abi-redesign`)のfn解決キャッシュ化(`za_compile_call`)は
  JITコンパイル済みのユーザー定義関数呼び出しが対象であり、`read-into!`/
  `write-from!`はILOSの総称関数(`defmethod`経由、M10クロージャリフティング
  でコンパイル)であるため、**この恩恵を受けていない可能性がある**。
  `(print (function read-into!))`等で`#<FUNCTION-COMPILED ...>`/
  `#<FUNCTION-INTERPRETED ...>`のいずれかを確認し、インタプリタ経由の
  ままになっていないかをまず確認する。
- 1セクタあたり約131.7万命令という規模感から、単純な「シンボル解決の
  やり残し」だけでは説明しきれない可能性もあるため、`-dfilter`+
  TCGプラグインのアドレス範囲指定を使い、AOT側の静的アドレスが既知な
  FAT層の関数(`%fat16-read-lba-list`/`fat16-fat-entry`等)の寄与も
  同じ手法でさらに分離することを検討する。

## FAT層側(read-into!)の命令数内訳: ILOS総称関数ディスパッチの精査(2026-09-11)

前節の切り分けで「FAT層+Lispランタイム」が全体の99.632%を占めることが
判明したため、次に**ILOS総称関数(`read-into!`)のディスパッチ処理**が
支配的かどうかを検証した。結論から言うと**ディスパッチは無視できるほど
軽微であり、真因は別の場所(`read-file-into-vector`のAOT生成コード自体の
呼び出し規約オーバーヘッド)にあった**。

### 1. ディスパッチ機構の実装確認(コードレビュー)

`src/lisp/init.lisp`/`src/lisp/init_aot.lisp`を確認したところ、`defgeneric`は
`(defun name (&rest args) (%generic-call 'name args))`という`&rest`関数に
展開され、`%generic-call`は毎回:

```lisp
(defun %generic-call (name args)
  (%invoke-method-chain (%order-methods (%applicable-methods name args)) args))
```

を実行する。`%applicable-methods`は`*generic-methods*`をname(gf名)で`assoc`
線形走査し、見つかった全メソッドに対し`subclassp`判定を行い、
`%order-methods`は挿入ソート(毎回)、`%invoke-method-chain`は
`unwind-protect`+動的変数の退避/復元を伴う。**メソッド解決結果のキャッシュは
一切無い**——コードだけを見れば、以前の`os_make_symbol`線形走査と同種の
ホットスポットに見えた。

### 2. 実測: ディスパッチは全体の0.0004%に過ぎない

`subclassp`/`class-of`/`%find-generic-methods`/`%method-applicable-p`/
`%specializers-applicable-p`/`%filter-applicable-methods`/
`%applicable-methods`/`%order-methods`/`%invoke-method-chain`/
`%generic-call`等、ディスパッチ機構一式がリンク後のバイナリで連続領域
(ファイルRVA `0x52600`〜`0x631cb`)を構成していることを確認し、TCGプラグインの
アドレス範囲指定でこの区間だけの命令数を計測したところ:

| 計測 | 命令数 |
|---|---|
| 起動+mountのみ | 20,271 |
| 起動+mount+1MB読み込み | 30,427 |
| **ディスパッチ機構自体の差分** | **10,156(全体の0.0004%)** |

`*generic-methods*`に登録される総称関数・メソッドの実数が(システム全体で
`initialize-object`/`report-condition`/`read-into!`/`write-from!`等)数個〜
十数個程度にとどまるため、「線形走査」自体はO(1000)級の`os_make_symbol`とは
規模が全く異なり、実害が無いレベルだった。**コードの見た目上の懸念(未
キャッシュの線形探索)が、実際のボトルネックとは限らない**という、本調査
全体を通じて繰り返し現れているパターンがここでも再現した。

### 3. 落とし穴: __step(consリストABI)ではなく__step_fixed(固定引数ABI)を測るべきだった

「メソッド本体(クラスタチェイン走査)」の候補として`%fat16-read-into-impl`
(`lisp_ll_fat16_read_into_impl__step`)のアドレス範囲を計測したところ
`range_insns=0`という結果になった。TBダンプで直接確認したところ、実行時に
このアドレス範囲へは一切到達していなかった。原因は、ABI-M6(AOT-to-AOT
静的呼び出しの固定引数ABI化)により、`defmethod`本体のクロージャから
`%fat16-read-into-impl`への呼び出しが実際には**consリストABI版
(`__step`)ではなく固定引数ABI版(`__step_fixed`)**を使っていたため。
`__step_fixed`(ファイルRVA `0xdbd83`)を測り直しても、やはり
`range_insns=0`だった。

### 4. 方針転換: アドレス範囲の事前予想をやめ、プラグインに実測プロファイラ機能を追加

2回連続で「予想したアドレス範囲に実行が無い」という結果になったため、
`tools/plugins/isiki_instcount.c`に`profile=1`オプションを追加した。TB単位で
(開始アドレス, 命令数, 実行回数)を記録し、終了時に「命令数×実行回数」
降順でtop 40件を出力する機能で、アドレス範囲を静的に予想する代わりに
**実際にホットな箇所を直接発見する**アプローチに切り替えた。

### 5. 実測結果: 真因は`read-file-into-vector`のAOT呼び出し規約オーバーヘッド

1MB読み込みベンチマークをプロファイルし、top 40のホットTBをシンボルに
対応付けたところ(top 40だけで全体2,566,285,269命令のうち
1,777,902,294命令≒69.3%を説明):

| シンボル | 命令数(top40内) | 割合 |
|---|---|---|
| `get_current_process` | 526,208,500 | 29.6% |
| `is_control_transfer`/`os_is_control_transfer`(合算) | 484,457,888 | 27.3% |
| `primitive_add2` | 121,852,560 | 6.9% |
| `primitive_set_elt_impl` | 108,880,356 | 6.1% |
| `number_compare` | 81,950,954 | 4.6% |
| `is_vector`/`is_float`(合算) | 70,680,930 | 4.0% |
| `strncmpignorecase` | 16,215,168 | 0.9% |
| `primitive_less_than2` | 15,156,140 | 0.9% |
| `primitive_create_vector` | 15,112,240 | 0.9% |
| `os_stream_read_char` | 13,719,810 | 0.8% |

`get_current_process`は1MB(1,000,000byte)に対し**105,241,700回**呼ばれて
いた(1byteあたり約105回)。実装自体はO(1)(`&g_processes[g_current_
process_index]`、配列添字アクセス)だが、`GC_PROTECT`マクロが1回につき
`get_current_process()`を2回呼ぶ(初期化子と代入)ため、**呼び出し回数の
絶対数**がボトルネックになっている。`is_control_transfer`/
`os_is_control_transfer`も同様に、`transpile-call-args-guarded`が生成する
「引数を1つ評価するたびにGC_PROTECTし、非局所脱出シグナルでないか
チェックする」というAOTの安全側ガード付き呼び出しパターインが、1byteの
読み込み・書き込みという極めて軽い操作に対しても律儀に発行され続けて
いることを示している。

### 判定

「ディスパッチ処理が支配的」でも「メソッド本体(クラスタチェイン走査)が
支配的」でもなく、**`read-file-into-vector`のAOT生成コード自体(1byte
ずつの`read-byte`/`set-elt`呼び出しループ)が、za.cのJITには既に適用済み
(Phase1/Phase2、documents/abi-redesign.md参照)のような「非アロケーション
演算のGC_PROTECT省略」「fixnum算術のインライン化」を一切受けていない**
ことが真因と判明した。次のアクションとして、za.cのPhase1/Phase2と同種の
最適化(leaf判定によるGC_PROTECT省略、`+`/`<`等の単純演算のインライン化)を
AOTトランスパイラ(`transpile.lisp`)側にも適用することを、新しい
マイルストンとして提案する(本書の範囲外、別途指示書で計画する)。

## AOT側GC_PROTECT削減(leaf判定)の実装と効果(2026-09-11)

前節の判定に基づき、za.cのPhase1(`za_operand_is_safe_leaf`)と同じ基準を
`transpile.lisp`に移植した。

### 実装

`transpile-call-args-guarded`(関数/プリミティブ呼び出しの各引数を1つずつ
評価する箇所、AOT生成コードの`GC_PROTECT`発行源の大半を占める)に、新設の
`aot-form-is-leaf`判定を組み込んだ。leafと判定される(=`GC_PROTECT`も
`os_is_control_transfer`チェックも省略できる)のは以下の2ケースのみ
(za.cの`za_operand_is_safe_leaf`と同一基準):

- fixnum/文字リテラル(`os_make_fixnum`/`os_make_char`が返すのは即値で
  ヒープ非経由、GCの再配置対象にならない)。
- 非box化ローカル変数への参照(束縛時に一度だけ`GC_PROTECT`された
  Cローカル変数を読むだけで、その保護は束縛を含む関数の実行が終わるまで
  有効なまま。Lisp側の`setq`は非局所脱出シグナルを弾いてからでなければ
  実際の代入を行わない生成コードのため、正しく評価が完了したローカル
  変数がシグナル値そのものを保持することはない)。

`za_emit_operand`(JIT側)がこれら2ケースで`CALL`命令を一切発行しない
(movabs/レジスタロードのみ)ことを確認済みであり、AOT側でも同じ条件で
`os_is_control_transfer`チェックまで安全に省略できると判断した(box化
ローカル・グローバル変数・quoteシンボル・文字列リテラル・裸のT・関数
呼び出し等は、za.c同様に安全側でleafとしない)。

### 効果測定

`read-file-into-vector`の内側ループ(`__lisp_lambda_417__step`、1byteの
処理につき`(< i len)`→`(read-byte stream)`→`(set-elt byte vec i)`→
`(setq i (+ i 1))`)の反復あたり`GC_PROTECT`呼び出しが**8回→1回**へ
削減された(`(read-byte stream)`の戻り値のみ、後続の`set-elt`に渡すまで
保護が必要なため残る)。

| 計測 | 修正前 | 修正後 | 変化 |
|---|---|---|---|
| 1MB読み込みの命令数(TCGプラグイン) | 約2,562,646,170 | 1,444,529,546 | **-43.6%** |
| 1MB読み込みの壁時計時間(tickカウンタ) | 31.28秒 | 14.40秒 | **-54.0%(2.17倍)** |

壁時計時間の改善率が命令数の改善率を上回っているのは、削減された命令の
多くが(`get_current_process`呼び出し等の)実関数呼び出し(CALL/RET)
であり、TCGでの1命令あたりのディスパッチコストが均一ではない
(関数呼び出し境界はより重い)ためと見られる。

ネイティブ`make test`(8135件)・QEMU`make test-qemu`(1614→1620件、
新設のGC整合性回帰テスト6件を含む)とも全てパスすることを確認済み。

### GC整合性回帰テスト

`test/lisp/aot_leaf_gc_test.lisp`(`qemu_boot_test.lisp`経由で標準テスト
スイートに常設)を追加した。`write-vector-to-file`/`read-file-into-vector`
(本改善の対象そのもの)で300KBのデータを往復させ、その前後で意図的に
大量のゴミ`vector`を確保してGCを複数回誘発し、内容(`equal`での完全一致)
が破損しないことを確認する。leaf判定は式の**静的な構文形**(fixnum/文字
リテラルか、既存のscope alistでboxed-pがnilと分かるローカル変数参照か)
だけに基づき実行時の値には一切依存しないため、za.cのfixnum溢れ時
フォールバックのような「実行時に型で分岐する」境界ケースは存在しない
(該当しない場合は常に安全側の保護付きパスにフォールバックする)。

## `os_is_control_transfer`削減の調査(実装は見送り、2026-09-11)

`is_control_transfer`の実装(`eval.c`)を確認した:

```c
static int is_control_transfer(lisp_val_t v) {
    if ((v & TAG_MASK) != TAG_INSTANCE) {
        return 0;
    }
    UINT64 *obj = (UINT64 *)(v & ~TAG_MASK);
    return obj[0] == MAGIC_BLOCK_EXIT || obj[0] == MAGIC_CATCH_EXIT || obj[0] == MAGIC_GO_EXIT;
}
```

チェック自体は極めて軽い(非TAG_INSTANCE値なら1回のタグ比較のみで即座に
falseを返し、メモリ参照すら発生しない)。にもかかわらず全体の27.3%を
占めていた理由は、GC_PROTECTと同様に**呼び出し回数そのものの多さ**と、
`os_is_control_transfer`が`eval.c`(別コンパイル単位)で定義された非
`inline`関数であるため、`lisp_compiled.c`側の呼び出し元へインライン
展開されず毎回実際のCALL/RETが発生していることにある。

**上記のGC_PROTECT削減により、leaf判定される引数についてはこのチェック
自体も既に併せて省略済み**である(残るのは、関数呼び出しの戻り値等
「呼び出しを含む式」の結果に対するチェックのみ)。

### 条件システムとの関係

`isiki-os`の条件システム(`error`/`cerror`/`with-handler`、
`src/lisp/init.lisp`/`init_aot.lisp`)は、`*handlers*`という動的変数
スタックをたどってハンドラを直接`funcall`する設計であり、
`block`/`catch`/`tagbody`の非局所脱出シグナル機構(`is_control_transfer`
が検知する対象)とは**完全に別系統**である。したがって条件システムの
挙動を壊す心配なく、`is_control_transfer`削減は`return-from`/`throw`/`go`
の到達可能性だけを考えればよい。

### 削減が難しい理由

leaf判定(GC_PROTECT削減)は「この式の評価自体がヒープ確保も呼び出しも
一切含まない」という、**式そのものの構文形だけ**から静的に判定できた。
一方`os_is_control_transfer`を安全に省略するには、「この式(典型的には
関数呼び出し)の評価結果が、`return-from`/`throw`/`go`による非局所脱出
シグナルには絶対になりえない」ことを示す必要があり、これは式単体の
構文形ではなく、**呼び出し先の関数の中身(さらにその中身が呼ぶ関数…)**
まで辿らないと判定できない(=関数単位ではなく呼び出しグラフ全体の
到達可能性解析が必要)。本セッション前半で`go`の直接goto化のために
`*enclosing-tagbodies*`を導入したが、あれは「字句的に閉じた同一C関数内」
という局所的な情報だけで済む特殊ケースであり、一般の関数呼び出しの
戻り値には適用できない。

### 判定: 実装は見送り、低リスクな代替案のみ記録

`return-from`/`throw`/`go`の到達可能性解析は、GC_PROTECT削減より
はるかに大きく・リスクの高い実装になる(呼び出しグラフ全体を辿る
必要があり、相互再帰・前方参照・動的なfuncall経由の呼び出し等を
どう扱うかという設計判断が新たに必要になる)ため、本マイルストンの
スコープには含めない。

代わりに、意味論を一切変えない、機械的で低リスクな代替案を記録して
おく: `os_is_control_transfer`(および内部の`is_control_transfer`)を
共有ヘッダで`static inline`として定義し直せば、コンパイラが
`lisp_compiled.c`の各呼び出し箇所へインライン展開できるようになり、
チェックの論理自体は変えずにCALL/RETのオーバーヘッドだけを除去できる
可能性がある。ただし実際の効果はコンパイラの最適化判断(`-O1`ビルド、
巨大な`lisp_compiled.c`1ファイルでのインライン化の可否)に依存するため
未検証であり、着手する場合は本書の手法1(TCGプラグイン)で効果を
確認すること。

GC_PROTECT削減後の残り約14.4億命令のうち、`primitive_add2`/
`primitive_less_than2`(呼び出し先の中身も含む)がどれだけを占めるかを、
実測プロファイラ(`profile=1`)のtop40出力をシンボルへ対応付けて計測した。
前回・前々回の教訓通り、アドレス範囲は静的に予想せず、計測対象と同一
ディスク構成で`%%DIAG-IDE-READ-SECTORS-ADDR`により実測した
(`0xd00d000`)。

|---|---|---|
| `primitive_add2` | 121,852,560 | 8.44% |
| `primitive_less_than2` | 15,156,140 | 1.05% |

参考(同じtop40内での他の主要項目との比較):

9.48%は判定基準の「10〜15%以上(着手)」と「5%未満(見送り)」の中間に
位置する。着手可否を左右する重要な非対称性として、`primitive_add2`と
`primitive_less_than2`とで実装のしやすさが大きく異なることが判明した:

- **`primitive_add2`**: 既に非負fixnum同士の高速パス(オーバーフロー
  チェック込み)を持つ小さな自己完結関数(`runtime.c`)。`za.c`のように
  生の機械語を生成する必要は無く、**この関数を`static inline`として
  共有ヘッダへ移し、コンパイラに`lisp_compiled.c`側の呼び出し箇所へ
  インライン展開させるだけ**で、CALL/RETのオーバーヘッドをほぼ排除
  できる可能性が高い(低リスク・低実装コスト)。
- **`primitive_less_than2`**: `return number_compare(a, b) < 0 ? ... : ...;`
  という薄いラッパーで、実処理は`number_compare`(bignum/float等を含む
  汎用の多相比較、大きめの関数)に委譲している。`primitive_less_than2`
  自体を`static inline`化しても、`number_compare`への呼び出し自体は
  残る(`number_compare`は大きく`-O1`でのインライン化候補になりにくい)
  ため、`primitive_add2`ほどの効果は見込めない。fixnum同士の比較専用の
  高速パスを`primitive_less_than2`自身に追加する(`number_compare`への
  委譲を、非fixnum時のみのフォールバックにする)実装が必要で、
  `primitive_add2`より実装コストが高い。

### 次のアクション(本書のスコープ外、別途指示書で計画)

`za.c`のPhase2(生の機械語を手書き生成)をそのままAOTへ移植するのではなく、
**まず`primitive_add2`(および同様の自己完結な高速パスを持つ2引数
プリミティブ)を`static inline`化する、より小さく低リスクな一手から
着手する**ことを推奨する。これは前節で記録した`os_is_control_transfer`の
`static inline`化案と同じ手法(意味論を変えずコンパイラのインライン化に
委ねる)であり、まとめて1つのマイルストンとして計画できる可能性がある。
`primitive_less_than2`/`number_compare`側のfixnum高速パス追加は、効果が
不確実なため、`primitive_add2`側の実測結果を見てから改めて判断する。

## AOT側`primitive_add2`のstatic inline化: 実装・実測・**revert**(2026-09-11)

前節の見積もりに基づき、`primitive_add2`を`static inline`化する低リスク
施策として着手した。**実測の結果、命令数・壁時計時間とも悪化することが
判明し、変更を完全にrevertした。** 期待に反する結果だったが、AOT最適化の
今後の方針判断に直結する重要な知見のため詳しく記録する。

### 実装した内容

za.cが`primitive_add2`のアドレスを生ポインタとしてJIT生成コードへ直接
埋め込んでいる(`za.c:1997/2014/2804`の`(void *)primitive_add2`比較・
呼び出し先アドレス埋め込み)ことを事前に確認した。これは`primitive_add2`
自体を`static inline`化(内部リンケージ化)すると、翻訳単位ごとに異なる
アドレスの複製が生成されJITの前提(単一の安定したアドレス)を崩しうる
ことを意味する。そのため、**za.c向けの既存`primitive_add2`(外部リンケージ)
はそのまま維持し、ロジック本体を`primitive_add2_inline`
(`static inline __attribute__((always_inline))`、`runtime.h`)へ複製し、
AOT生成コード(`transpile.lisp`の`*primitive-fixed-arity-c-names*`の`+`の
マッピング)だけをこちらへ向ける**という設計にした。`primitive_add2`は
`primitive_add2_inline`を呼ぶだけの薄いラッパーとして残した。

事前確認: `primitive_add2`の高速パス(非負fixnum同士)には元々
`GC_PROTECT`が無く(ヒープ確保が発生しないため不要、想定通り)、
除去すべき不要な保護は無かった。

### 実測結果: 悪化

| 計測 | leaf判定のみ(直前の状態) | `primitive_add2_inline`適用後 | 変化 |
|---|---|---|---|
| 1MB読み込みの命令数 | 1,444,529,546 | 1,513,081,220(2回の再実行でも1,511,797,386/1,511,875,874と再現) | **+4.7%(悪化)** |
| 1MB読み込みの壁時計時間 | 14.40秒 | 28.3〜28.7秒(3回計測) | **約2倍(悪化)** |
| `__lisp_lambda_417__step`(ホットループ本体)のコードサイズ | 1516byte | 1792byte | +18.2% |

2回の再実行でほぼ同じ値が出ており(誤差0.01%未満)、単なる実行時ノイズ
ではなく**再現性のある悪化**であることを確認した。`primitive_add2_inline`
という独立シンボルはビルド成果物のシンボルテーブルに存在せず(コンパイラが
実際にインライン展開したことの確認)、`always_inline`は意図通り機能して
いた。

### 原因の考察(未確定、深追いはしていない)

コンパイラが実際にインライン展開したにもかかわらず命令数が増えたことから、
**`-O1`という比較的弱い最適化レベルでは、深くネストしたGNU文式
(`transpile-call-args-guarded`が生成する`({ ... ? ... : (...) ; })`の
入れ子)へ`GC_PROTECT`の`cleanup`属性付きローカル変数を含む関数本体を
強制インライン展開すると、周囲のコード全体に対する最適化(レジスタ
割り当て等)がかえって悪化する**可能性が高いと考えている。`za.c`の
Phase2が生の機械語を直接手書きすることで確実に「call/retの排除=命令数
削減」を達成できたのに対し、AOTのC言語レベルでの「インライン化」は
**Cコンパイラの最適化パイプライン全体に委ねることになり、確実な改善を
保証しない**という、根本的な違いがあることが今回の実測で明らかになった。
原因の完全な特定(`-O2`でも同様に悪化するか等)は本書のスコープ外とし、
深追いしていない。

### 判定: revert、AOT側fixnum算術インライン化は当面見送り

変更は完全にrevertした(`primitive_add2_inline`の追加・
`primitive_add2`のラッパー化・`transpile.lisp`の`+`マッピング変更を
いずれも元に戻し、ネイティブ`make test`(8135件)・QEMU`make test-qemu`
(1620件)で回帰が無いことを確認済み)。

この結果を踏まえ、AOT側のfixnum算術インライン化(`+`/`<`等)は
**当面見送る**。再検討する場合は、以下のいずれかの前提が必要:

- カーネルビルドを`-O2`(またはそれ以上)へ引き上げた上で同じ実測を
  やり直す(ビルド全体への影響が大きいため別マイルストンが必要)。
- `transpile.lisp`のコード生成自体が、C言語の`inline`/コンパイラの
  最適化に頼らず、za.cと同じ「呼び出し元が直接、条件分岐+算術+タグ
  付けのC式をインライン展開して書く」という、コード生成レベルでの
  インライン化(コンパイラの判断を経由しない)を行う設計に変更する
  (実装コストは`static inline`化よりずっと高いが、`za.c`のPhase2と
  同じ確実性が期待できる)。

いずれも本書の当初想定より大きな投資が必要なため、次の優先度は
`os_is_control_transfer`側の`static inline`化(まだ未実装)の実測、
または全く別のホットスポットの探索に置く方が妥当と判断する。

### `os_is_control_transfer`のstatic inline化について

前節で記録した`os_is_control_transfer`の`static inline`化案について、
本セッションでは**実装していない**。今回の`primitive_add2`の否定的な
結果を踏まえると、`os_is_control_transfer`も同じ理由(`-O1`での
インライン化がかえって悪化する)で同様に失敗する可能性が相応にある。
着手する場合も、`primitive_add2`と同じ手順(実装→命令数計測基盤での
before/after比較→悪化していればrevert)を必ず踏むこと。楽観的な
「低リスクな一手」という前提そのものを疑ってかかる必要がある。

## 残り約14.4億命令のホットスポット再探索(top40全体の分類、2026-09-11)

`primitive_add2`のような「予想がついていた場所」を深追いするより、
実測プロファイラ(`profile=1`)のtop40を機械的に洗い出す方が投資対効果が
高いと判断し、`read-file-into-vector`(1MB読み込み)のtop40全項目を、
boot-onlyプロファイルとの対応する各アドレスごとの差分により
read操作への寄与を正確に切り分けた上で分類した。

### 重要な方法論上の修正: 「kernelイメージ外」領域はboot専用と確定

top40の約23%(16エントリ)が、自イメージ(約3MB)の範囲外の高位アドレス
(`0xfffcXXXX`/`0xfeecXXXX`/`0xe861XXXX`等)を指しており、当初「未調査の
領域(区分C候補)」に見えた。しかし**同一アドレスごとにboot-onlyプロファイル
と突き合わせたところ、これら全てのexec回数がboot-onlyとboot+read1mの間で
完全に一致(誤差は数千程度のノイズのみ)しており、read操作への寄与は
実質ゼロと確定した**。おそらくOVMFファームウェア/割り込み処理関連の
boot時アクティビティであり、read操作の最適化対象ではない。**top40の
生の合計を単純に読むと支配的コストを誤認する**ため、以後の命令数
プロファイリングでは必ずboot-onlyとの差分を取ることを標準手順とする。

### top40の分類(read操作への寄与のみ、boot専用分を除く)

### 区分C候補だった`strncmpignorecase`の調査結果: 新規の削減余地なし

命令数が約100万(1バイトあたり約1回に見える規模)だったため、`os_make_
symbol`系のキャッシュ漏れ(区分Cの新発見)を疑い、`os_make_symbol`
自身の実行範囲を個別計測した。結果、`os_make_symbol`自体の呼び出し回数
(read操作起因の差分)は多く見積もっても数十万回程度に留まり、「1byte
ごとに1回」という規模ではなかった。`strncmpignorecase`がホットに見えた
真因は、**該当アドレスがこの関数自身の文字比較ループの内部基本ブロック**
であり、1回の呼び出しでも比較対象のシンボル名の文字数分だけこの
ブロックが繰り返し実行されるため、実際の呼び出し回数より多い実行回数に
なっていたことだった。これは今回のB'(ハッシュ索引化)適用後の**正常な
残余コスト**であり、新たな削減余地(区分C)ではなく区分A寄りと判断する。

### 判定: `read-file-into-vector`単体のこれ以上の大幅な改善は見込みにくい

区分Aの合計(約2.08億、14.4%)は実質的な処理そのもの(ストリーム読み取り・
ベクタ書き込み・型チェック)であり削減余地が乏しい。区分Bの主要項目
(`is_control_transfer`系13.46%・`get_current_process`11.05%・
`primitive_add2`/`number_compare`/`primitive_less_than2`系15.16%)は
いずれも**既に調査済みで、削減がリスク過多(呼び出しグラフ解析が必要)
か、実測で悪化することが確認済み(`primitive_add2`のrevert)**である。
新たな区分C(未知の削減余地)は見つからなかった(`strncmpignorecase`は
調査の結果、区分Aに近い既存機構の残余コストと判明)。

したがって、`read-file-into-vector`単体のホットループについては、
低リスクで確実な追加削減の糸口が尽きたと判断する。次に投資すべき
対象は、本書で以前保留した**書き込み側(`fat16-create-file`/
`fat32-create-file`)の性能調査**(FAT32の2MB書き込みが単独でも9分以上
未完了だった問題、および直前の書き込みの後に後続の書き込みがさらに
遅くなる未解明の現象)に切り替えることを推奨する。今回確立した命令数
計測基盤(TCGプラグイン、`profile=1`のホットスポット直接探索、
boot-only差分による正確な切り分け手法)は、そちらの調査にもそのまま
再利用できる。

## read-file-into-vector-native: 素のC実装によるフロア(下限)計測(2026-09-11)

「残り約14.4億命令のホットスポット再探索」節で、`read-file-into-vector`
単体の低リスクな追加削減の糸口が尽きたと判断した後、「Lisp/AOTの呼び出し
規約・GC保護のオーバーヘッドを完全にゼロにした場合、この読み込み処理は
本来どこまで速くなりうるのか」という理論的な下限(フロア)を計測した。

### 実装

`src/c/mount.c`に`READ-FILE-INTO-VECTOR-NATIVE`(C関数名

規約を一切経由しない素のC関数として再実装し、`block_device_t::
read_sectors`を直接呼ぶ(1クラスタ分をまとめて1回のPIO転送にできる、
`read-sector`のLisp版が1セクタずつしか読めないのと異なる点)。読み込んだ

なお`dotimes`/`dolist`はISLispには存在せず(CommonLisp由来)トランスパイラも
未対応のため、higher-levelなイテレーション構文としてはISLisp標準の`for`を測った。

## letのImmobilized Spaceリーク: ループ内のletは約24,300反復でOSを停止させる(2026-09-11)

構文別ベンチマークスイート(次節)の`let`カテゴリを計測しようとしたところ、
他カテゴリが1起動2分程度で終わるのに対し、`let`のAOT版だけが33分経っても
完走しなかった。調査の結果、これは性能問題ではなく**カーネルが永久に
停止する実際のバグ**であることが判明した。

### 機構

AOTトランスパイラは`(let ((i n)) ...)`を`((lambda (i) ...) n)`へ展開した後、
インライン化せずに次のコードを生成する(`lisp_compiled.c`):

```c
os_make_lifted_closure((lisp_addr_t)(void *)__lisp_lambda_428, global_environment)
...
primitive_funcall(os_make_cons(__call_arg, os_make_cons(...)), env)
```

`os_make_lifted_closure`は内部で`os_fn_meta_alloc`を呼び、`za_fn_meta_t`
(24byte、16byte境界へ切り上げて32byte)を**Immobilized Space**から確保する。
Immobilized Spaceは`IMM_SPACE_SIZE = 4MB`の静的配列上のバンプアロケータで、
`os_fn_meta_alloc`のコメントが明記する通り「個別解放はせずOS生存期間中保持
される前提」であり、**GCでは一切回収されない**。

そして`os_imm_page_alloc`は空きが尽きると次のように振る舞う:

```c
fb->write_string(fb, "imm: space exhausted...");
for (;;) {
}
```

つまり**無限ループでカーネルが永久に停止する**。`-display none`で実行している
限りこのメッセージは見えないため、外からは「極端に遅い処理」と区別がつかない
(実測ではCPU使用率が1コアの約25%のまま、`test-results.txt`がサイズ0で
放置され続けた)。

### 実測(安全なNでの確認)

| 計測 | Immobilized Spaceの増分 | 1反復あたり |
|---|---|---|
| AOT `%%bench-aot-let` N=1000 | 163,840 byte | 163.8 byte |
| AOT `%%bench-aot-let` N=2000 | 319,488 byte | 159.7 byte |
| AOT `%%bench-aot-for` N=1000 | 28,672 byte | 28.7 byte |
| AOT `%%bench-aot-loop` N=1000(ループ内にletなし) | **0 byte** | 0 |
| C版 `%%bench-c-let` N=2000 | **0 byte** | 0 |

5変数の`let*`は入れ子のlambda 5個へ展開されるため、5クロージャ×32byte=
160byte/反復という理論値と実測が一致し、Nに対して線形に増える。ループ内に
`let`を持たないケースとC版がいずれも0byteであることから、原因が`let`の評価
そのものであることが対照実験として確定している。

### 影響範囲

起動直後のImmobilized Spaceの空きは 4,194,304 − 303,104 = 3,891,200 byte。

| 構文 | 消費 | ハングまでの反復数 |
|---|---|---|
| 5変数の`let*`をループ内で使う | 160 byte/反復 | **約 24,300 回** |
| `for`マクロ | 28.7 byte/反復 | 約 135,000 回 |

`let`はLispで最も基本的な構文であり、「ループの中で`let`を使う」ごく普通の
コードが数万反復でOSごと停止する。ファイルI/Oのような大きなループを
Lispで書く際の実質的な上限を決めてしまっており、性能比の問題より優先度が高い。

### Phase 1: za_fn_meta_tのfnptr単位一意化(実装済み)

停止性の修復だけを切り出し、性能改善(即時lambda呼び出しのインライン展開)とは
分離して実装した。

**前提条件の確認**: `za_fn_meta_t`は`cons_entry`/`fixed_entry`/`arity`の3つの
`UINT64`のみで、`lisp_val_t`フィールドを持たない(GCルート登録は不要)。
`captured_env`はmetaではなくインスタンスのword3に入るため、**metaの内容は
リフト先のC関数アドレスだけで決まる**。lifted closureでは`fixed_entry`/`arity`は
常に0のままで、生成後に書き換えるのは`os_make_jit_function_dual`(JITのコンパイル時、
実行回数比例ではない)だけである。したがって同じlambdaから作られる全クロージャが
1つのmetaを共有してよい。

**実装**: トランスパイラの`emit-closure-creation`が生成する式を、呼び出し箇所ごとの
C静的変数をmetaの実体として渡す形へ変更した。

```c
os_make_lifted_closure_with_meta(({ static za_fn_meta_t __closure_meta; &__closure_meta; }),
                                  (lisp_addr_t)(void *)__lisp_lambda_N, __closure_env_X)
```

静的記憶域はアドレスが不変でGCにもImmobilized Spaceにも依存しないため、
**Immobilized Spaceの消費は実行回数比例からゼロになる**(プログラムサイズ比例
ですらない)。`os_make_symbol_cached`+`static`局所変数という既存のイディオムと
同じ形で、毎回同じ値を書き込むだけなので初回判定の分岐も不要。

**あわせて修正した2点**:

- `%%imm-space-used-bytes`をページ粒度からバイト粒度へ変更した。従来は
  `g_imm_bump - g_imm_space`(4096byte単位でしか進まない)を返していたため、
  4096byte未満の消費が「0 byte」に見え、実行回数比例のリークを回帰テストで
  検出できなかった。各スロットカーソルが現在のページに残している未使用の末尾分を
  差し引いて実消費を返す。
- `os_imm_page_alloc`/`os_alloc_bytes`の枯渇時の空の`for(;;)`を`os_panic`へ
  置き換えた。QEMUテスト実行中はフック経由で電源断し、ハングではなくテスト失敗
  として終わらせる。フックが無い場合も`hlt`で止めることで、停止中のCPU使用率が
  ほぼ0になり「異常停止」と「極端に遅い処理」を外から判別できるようにした
  (今回33分間ハングに気づけなかった直接の原因がこれ)。

なお、当初「1反復あたり163.8 byte」と測れていた実測値と理論値160 byteの差
(3.8 byte)は、追加のリーク源ではなくページ粒度の丸めだった。3000反復×160 byte=
480,000 byteは118ページ=483,328 byteで、実測の増分合計と完全に一致する。

### forのtagbody直行化: 1711倍 → 62.8倍(実装済み)

`for`が最悪値を示した原因を確認したところ、**ループ構造自体は既に`while`と同じ
`tagbody`/`go`へ展開されており**、コストはループ本体の中にあった。ISLispの`for`は
step式を並列に評価する意味論を持つため、旧実装はそれを次の形で実現していた。

```lisp
(let ((%for-next-values (list step1 step2 ...)))   ; ← 毎反復ここを評価する
  (setq v1 (car %for-next-values))
  (setq v2 (car (cdr %for-next-values))))
```

1反復ごとに、(1)step値のconsリスト構築、(2)`let`によるクロージャ生成+consリスト
構築+`primitive_funcall`経由の動的ディスパッチ、(3)変数N個に対するO(N^2)の
car/cdr連鎖、が発生していた。`for`が`let`単体(2945命令/反復)の2.3倍も重かったのは
このためである。

**対処**: 一時変数をループの外側の`let`で一度だけ束縛し、ループ本体では素の`setq`
だけを使う形へ変更した。全step式を一時変数へ評価しきってから各束縛変数へ書き戻す
ため、並列束縛の意味論は保たれる。

```lisp
(let ((v1 init1) (v2 init2) (%for-tmp-1 nil) (%for-tmp-2 nil))
  (block nil
    (tagbody
     %for-loop
     (if end-test
         (return-from nil (progn result...))
         (progn body...
                (setq %for-tmp-1 step1) (setq %for-tmp-2 step2)
                (setq v1 %for-tmp-1)    (setq v2 %for-tmp-2)
                (go %for-loop))))))
```

| 計測 | 変更前 | 変更後 | 変化 |
|---|---|---|---|
| `for`(命令/反復) | 6870.20 | 250.18 | **-96.4%** |
| 比(AOT/C) | 1711倍 | **62.8倍** | |

これはPhase 2(即時lambda呼び出しのインライン展開)を待たずに達成できた。`for`は
もはや`let`(2945命令/反復)より軽く、単純ループ(145)と同じオーダーに収まっている。

意味論の回帰は`test/lisp/for_expansion_test.lisp`(`make test-qemu-for-expansion`)
で8件確認している。特に重要なのは並列束縛で、`(for ((a 0 b) (b 1 (+ a b))) ((> a 10) a))`
は並列なら13・逐次に壊れていると16になるため、これを最初のテストに置いた。
step式の省略・入れ子の`for`(一時変数名の衝突)・GC併走・Immobilized Space消費0も
確認済み。

なお`ide.lisp`が記録していた「`for`マクロはGCが特定のタイミングで走ると以後永久に
そのループ内での結果が壊れる」既知のバグは、原因とされていた「ループ本体に毎回
新規生成される`let`」自体が無くなった。GCを誘発しながら1000反復する回帰テストは
通っているが、元の症状が間欠的だったため、`for`をホットパスで使い直す前には
改めて確認することを勧める。

### Phase 0: 計器と前提の検証結果

**計器のバイト粒度**: `%%imm-space-used-bytes`の値が4096の倍数でないこと

**`za_fn_meta_t`に`lisp_val_t`フィールドは存在しない**: 構造体は
`cons_entry`/`fixed_entry`/`arity`の`UINT64`3つのみで、前2者はコードアドレス、
最後は整数である。したがって「meta内の`lisp_val_t`がGCルート未登録のため、
GC後にmetaが移動前アドレスを指し続け、そのmetaを使う限り壊れ続ける」という
`ide.lisp`記録の間欠バグに対する仮説は、**構造上ありえないものとして否定される**。
GCルート登録も不要。間欠バグの真因は引き続き未特定であり、`for`の修正で
再現しなくなった事実を根拠に解決したと判断してはならない。

**残差3.8 byte/反復は存在しない**: 修正前の実測は`let` N=1000で+163,840、
N=2000で+319,488(いずれもページ粒度)。累計3000反復の増分は483,328 = 118ページ。
消費が正確に160 byte/反復なら 3000×160 = 480,000 byte で、これは118ページ
(483,328 byte)に収まり**実測と完全に一致する**。仮に163.8 byte/反復なら
3000×163.8 = 491,400 byte となり120ページ(491,520 byte)を要するため実測と
矛盾する。163.8という値は、ページ丸めされた163,840を反復数1000で割ったことに
由来する見かけ上の数字だった。

### Phase 2: 即時lambda呼び出しのインライン展開(実装済み)

#### 着手前の見積もり(2-0-1)

インライン展開が消せるのはクロージャ生成・引数consリスト構築・
`primitive_funcall`の3つだけなので、これらが2945命令のうちどれだけを占めるかを
先に測った。まず3操作だけを繰り返す診断プリミティブ(`%%DIAG-CLOSURE-CALL`)で
**283.5命令/回**を得たが、これはAOTのラッパーを含まない下限である。

実コード上の値を得るため、束縛数1の`let*`(`%%bench-aot-let1`)を追加し、
boot時のゆらぎが相殺される**傾き法**(同じ関数をN=100万と300万で測り差を取る)で
比較した。

| 束縛数 | N=100万 | N=300万 | 傾き(命令/反復) |
|---|---|---|---|
| 1 | 1,927,669,992 | 3,538,537,692 | 805.4 |
| 5 | 4,108,451,313 | 10,080,604,477 | 2,986.1 |

`cost(k) = base + k × per_binding`を解くと**base = 260、1束縛あたり = 545.2命令**。
5束縛で2,726命令となり、**全体の91.3%が束縛あたりのコスト**だった。
インライン展開の対象が支配的であることが確認できたため実装に進んだ。

#### 実装

`transpile-expr`の即時lambda分岐に、インライン経路を追加した。判定には
**既存の`captured-params`をそのまま再利用する**(独立した解析器を新たに書くと
既存のラムダリフティング判定との食い違いが将来のバグ源になるため)。
`boxed-params`が`(intersection (setq-targets ...) (captured-params body params))`と
定義されていることから、`captured-params`が既存の捕捉判定そのものだと確認できる。

束縛変数がネストしたlambdaに捕捉されない場合のみインライン化し、捕捉がある場合は
従来のクロージャ経路へフォールバックする。`&rest`つき・arity不一致も
フォールバックさせる。

並列束縛の意味論は、**initを外側スコープ・bodyを内側スコープで展開**することで
満たす。束縛変数には一意のC名(`__inl_N`)を割り当てるため、
`(let ((a 1)) (let ((a 2) (b a)) b))`のbのinit `a`は外側の`a`へ解決される。
`let*`は入れ子のlambdaへ展開済みなので、各段が個別にこの経路を通って逐次束縛になる。

`GC_PROTECT`の省略条件は関数引数より厳しくしている。関数呼び出しの引数は評価後
すぐ消費されるためleafなら省略できるが、`let`の束縛変数はbodyの実行中ずっと生き、
body内で`setq`されてヒープ上の値を持ちうる。そのためleafであっても、その変数が
body内で`setq`される場合は保護を省略しない。

#### 実装中に検出したバグ

最初の実装ではinitも内側スコープで展開していたため、
`(let ((a 1)) (let ((a 2) (b a)) b))`が**2を返した**(逐次束縛になっていた)。
正解は1。ネイティブのフィクスチャテストで検出し、initを外側スコープで展開するよう
修正した。

#### 結果

| カテゴリ | Phase 2前 | Phase 2後 | 変化 |
|---|---|---|---|
| `let`(命令/反復) | 2945 | **643.03** | **-78.2%** |
| `let`の比(AOT/C) | 630倍 | **126.2倍** | |
| `cons`(命令/反復) | 485.53 | **243.15** | **-49.9%** |
| `cons`の比 | 4.2倍 | **2.1倍** | |

Immobilized Spaceリーク対策の名残でN=100,000で測っており、信号(約48M命令)が
boot時のゆらぎと同程度だった。リーク解消後にNを揃えて測り直すと485.53→480.34で
ほぼ変化がない。`let`の改善は傾き法で裏付けた2986を起点にしているため本物である。
他のカテゴリ(`for`/`branch`/`arith`/`funcall`/`tailrec`/`nontailrec`/

到達点は2-0-1の見積もり(base 260 + 5×(init算術 + GC_PROTECT) ≒ 500〜650)の

フォールバックの集計はトランスパイル時に標準エラーへ出力される。現状は

## Phase 3 第0部: leaf判定の不健全性を発見・是正(2026-09-11)

### 発見

Phase 2で導入した`GC_PROTECT`省略条件の健全性を確認したところ、**省略が不健全で
あり、しかも同じ不具合がPhase 2以前の関数引数の経路にも存在していた**ことが
分かった。

leaf判定はinit式に対するホワイトリスト(fixnum/文字リテラル、非box化ローカル変数
参照)で、`(cons a b)`のような割り付け式は最初から対象外だった。問題は
**非box化ローカル変数参照**の扱いにあった。旧実装の論拠はこうである。

> 束縛時に一度GC_PROTECTしたCローカル変数を単に読むだけであり、その保護は
> 束縛を含む関数の実行が終わるまで有効なままなので、読み出しのたびの再保護は不要

保護されているのは**元の**Cローカル変数である。その値を写した一時変数
(`__call_arg_N` / `__inl_N`)は別のCローカルであり、**GCはこちらを更新しない**。
ローカル変数はヒープ値(cons/vector/string等)を保持しうるため、写した後にGCが
走ると一時変数はstaleなアドレスを指したままになる。

ネイティブのフィクスチャテストで両方とも再現した(いずれも実際に値が壊れた)。

```lisp
(let ((x pair)) (progn <GC誘発> (car x)))   ; Phase 2で導入した経路
(cons pair <GC誘発>)                        ; 関数引数側(Phase 2以前からの経路)
```

後者は`64f2741`(GC_PROTECT削減、命令数-43.6%)以来の潜在バグである。当時の
GCストレステスト(`aot_leaf_gc_test.lisp`)が通っていたのは、GCのタイミングが
この窓に当たらなかっただけだった。

### 是正

判定を2つの述語へ分けた。

| 述語 | 条件 | 省略できるもの |
|---|---|---|
| `aot-form-is-immediate` | fixnum/文字リテラル/nil | `GC_PROTECT`と`os_is_control_transfer`の両方 |
| `aot-form-is-signal-free` | 上記 + 非box化ローカル変数参照 | `os_is_control_transfer`のみ |

さらに、**健全な条件での省略を別途復活させた**。一時変数を代入してから実際に使う
までの間にGCが起こりえないなら、ヒープ値を保持していてもstaleにならない。その
条件は次の2つである。

- 呼び出しが引数consリストを組まない**直接呼び出し**であること
  (`name__fixed(env, t1, t2)` / `primitive_add2(t1, t2)`の形。consリストを組む
  経路は`os_make_cons`が割り付けを行うためGCが起こりうる)
- 自分を含む以降の全引数が**割り付けを伴わない評価**であること(即値または
  非box化ローカル変数の読み出しのみ)

呼び出し先の内部で割り付けが起きても、その時点で一時変数は既に引数として
読み出され済みで以後参照されないため問題にならない。20万回の割り付けでGCを
何度も跨ぐテストで確認している。

`let`の束縛変数はbody全体を通じて生きるためこの復活は適用できず、即値かつ
body内で`setq`されない場合のみ省略という保守的な条件のままとした。

### 性能への影響

| カテゴリ | Phase 2後(不健全) | 即値限定(安全だが遅い) | 健全な省略を復活 |
|---|---|---|---|
| `let` | 643.03 | 865.86 | 531.01 |
| `for` | 265.42 | 469.57 | 245.11 |
| `arith` | 178.11 | 341.05 | 169.32 |
| `loop` | 150.23 | 204.11 | 147.80 |
| `funcall` | 270.24 | 409.02 | 270.21 |
| `branch` | 643.35 | 877.50 | 665.95 |
| `cons` | 243.15 | 575.23 | 304.72 |

即値限定にした時点で全カテゴリが27〜137%悪化した。`64f2741`の-43.6%という数字は、
健全でない最適化の上に乗っていた分を含んでいたことになる。健全な条件での復活後は

### 副産物: 小さいNでの測定は信用できない

上表の`let`が「不健全版643.03より健全版531.01の方が速い」という辻褄の合わない
値になっているのは、**測定そのものが信用できないため**である。`let`/`for`/`cons`は

Phase 2の「`cons`が半減した」という記述が誤りだったことも判明した(上記で訂正済み)。

## Phase 3 第1部: letの限界コスト測定(2026-09-11)

baseを仮定した引き算ではなく、束縛数を振った傾きから直接測った。測定はすべて
boot時のゆらぎが相殺される傾き法(同じ関数をN=100万と300万で測り差を2,000,000で
割る)による。

### 傾きと切片

| 束縛数 | 傾き(命令/反復) |
|---|---|
| 1 | 280.6 |
| 5 | 590.9 |
| 10 | 961.1 |

1→5で77.6/束縛、5→10で74.0/束縛と**直線に乗っており**、束縛数に対して非線形な
コストは存在しない。

- **1束縛あたりの限界コスト = 約76命令**
- **切片(ループ自体のbase) = 約203命令**

これまで`(643 − 260) / 5 = 77命令/束縛`と引き算で見積もっていた値は正しかったが、
baseの見積もり260は実測203に対して約28%過大だった。

### 内訳(init評価分とGC_PROTECT分の分離)

initの種類だけを変えた3種を比較する。いずれも束縛数5、bodyは最後の束縛だけを
参照する(全変数を参照すると内側lambdaに捕捉されフォールバック経路になり、
19,200命令/反復という別物を測ることになる。最初の測定でこれを踏んだ)。

| init | 発行されるもの | 傾き | 1束縛あたり |
|---|---|---|---|
| 即値リテラル | なし | 231.9 | **5.8** |
| 非box化ローカル参照 | `GC_PROTECT` | 406.5 | **40.7** |
| 算術式`(+ x 1)` | `GC_PROTECT` + `os_is_control_transfer` | 590.9 | **86.8** |

- **束縛そのもの = 5.8命令/束縛**。単なるCローカルへの代入なのでほぼ無料。
- **`GC_PROTECT` = 約34.9命令/束縛**(40.7 − 5.8)。これが束縛コストの支配項。
- 残り46.1は`(+ x 1)`の評価と`os_is_control_transfer`チェックの合計。

`let*`(逐次束縛)と`let`(並列束縛)で、同じ種類のinitに対する1束縛あたりの
コストは一致した。逐次束縛の展開に余分なコストは乗っていない。

## Phase 3 第2部: os_is_control_transferの内訳分類(2026-09-11)

### branchのループ本体17箇所の分類

削減方針を決めるため、`branch`(665.95命令/反復)のループ本体に発行されている
17箇所が何に対するものかを分類した。

| 分類 | 件数 |
|---|---|
| `if`/`cond`のtest結果 | 7 |
| `progn`の中間値 | 4 |
| `setq`の値 | 3 |
| **引数評価(プリミティブ呼び出し)** | **1** |
| `tagbody`の値 | 1 |
| `block`の値 | 1 |

**17件中16件が構文自体に対するチェックであり、プリミティブ呼び出しの引数評価に
対するものは1件しかない。** したがって「プリミティブへ『control transferしうるか』の
属性を持たせ、トランスパイラがそれを見てチェック発行を決める」という方式だけでは、
17件中1件しか消えない。

### 方針の再検討

構文自体のチェック(16件)は、**その構文の値になる部分式が非局所脱出シグナルに
なりえないと分かれば**消せる。つまり必要なのは、現在2ケースのホワイトリストで
ある`aot-form-is-signal-free`を、構造的に再帰する判定へ拡張することである。

```
signal-free(form) =
    即値 | 非box化ローカル参照
  | 属性で「transferしない」と宣言されたプリミティブ呼び出しで、全引数がsignal-free
  | (if t a b) で t/a/b がすべてsignal-free
  | (progn ...) で全フォームがsignal-free
  | (setq v e) で e がsignal-free
```

この形なら属性は再帰の**基底ケース**として効き、`branch`のような純粋なfixnum演算と
比較だけのコードでは16件の大半が消える。属性の付与漏れが安全側(チェックを
発行する)に倒れる設計は指示書の通りに保つ。

### ただし優先順位は`GC_PROTECT`の方が高い

第1部の実測では**`GC_PROTECT`が1箇所あたり約34.9命令**である。一方
`os_is_control_transfer`は、算術init 1箇所あたりの46.1命令から`(+ x 1)`の評価分を
引いた残りなので**1箇所あたり10命令未満**と見積もられる。`branch`のループ本体には
`GC_PROTECT`が8箇所あり、単純計算で約280命令(665.95の約42%)を占める。
17箇所のチェック(約100〜170命令)より大きい。

`os_is_control_transfer`の削減は横断的に効くため価値はあるが、**同じ労力を
`GC_PROTECT`の削減に向けた方が効果が大きい**というのが実測から出た結論である。
`GC_PROTECT`の削減には、第0部で確立した「一時変数を代入してから最後に使うまでに
GCが起こりえないか」という判定を、関数引数だけでなく他の一時変数へも広げる
方向が考えられる。

## Phase 4: 自明なランタイム関数のインライン化で全カテゴリ26〜41%削減(2026-09-11)

### 計測方法の変更: 傾き法をドライバの既定にした

`tools/bench/run_construct_bench.sh`を、boot-onlyとの差分から**傾き法**へ変更した。
同じベンチマークをNと3Nの2点で測り差を2Nで割る。bootのコストは両方に等しく
含まれるため引き算で完全に相殺され、boot時のゆらぎが結果に混入しない。
「カテゴリごとに適正Nを決める」問題自体が消える(固定コストは切片に入り傾きに
乗らない)。Phase 3までの単一N方式は、同一実装で17%違う値を出したり
「consが半減した」という誤った結論を出したりしていた。

### 34.9命令/GC_PROTECTの正体は関数呼び出し3回だった

GCルート1つの登録に34.9命令は異常であり(シャドースタックへのpushなら2〜3命令)、
内訳を調べたところマクロ展開形にあった。

```c
#define GC_PROTECT(var) \
    gc_rootnode _gcnode_##var __attribute__((cleanup(gc_unprotect_node))) = \
        { (lisp_val_t *)&(var), get_current_process()->gc_roots }; \
    get_current_process()->gc_roots = &_gcnode_##var
```

`get_current_process()`をマクロ本体で2回、さらにスコープ脱出時の
`gc_unprotect_node`で1回、**計3回**呼ぶ。この関数の実体は`process.c`にあり
`process.h`は宣言だけなので、`-O1`・LTO無しでは3回とも本物のクロスTU呼び出しに
なる。中身は`&g_processes[g_current_process_index]`という配列参照だけである。
1回あたり10命令強×3回≒33で、実測34.9とほぼ一致する。

ヘッダの`static inline`へ移した結果、呼び出しもシンボルも完全に消え、
`GC_PROTECT`の単価は実質0になった(束縛数5で測った差が+174.6→−16.6と
測定ノイズの範囲に収まった)。**保護の意味論は一切変えていない。**

`branch`の改善が予測280命令に対し12命令しかなかったため逆アセンブルで内訳を

`os_is_control_transfer`の単価も実測した(診断用`%%DIAG-CT-CHECK`、傾き法)。

### 副産物: 非末尾再帰ベンチマークのスタックオーバーフロー

1レベルあたり`__fixed`(136byte)と`__step_fixed`(112byte)の2フレームを積み、

**スタックガードが無いためオーバーフローは検出されず、ゲストが無反応のまま
停止する。** CPU使用率が1%未満になるだけで、外からは極端に遅い処理と区別しにくい
(この状態のQEMUを2時間放置してしまい、後続の測定とCPUを奪い合わせていた)。
ベンチマークの再帰深度を100へ下げて解消した(仕事の単位数はNのままなので比較の
前提は保たれる)。

停止している」と判断できたが、**スタックオーバーフローは`os_panic`を経由しない**
ため、そこは依然として検出できていない。

## Phase 5 第0部: スタックガードの実装と、Phase 4の誤診断の訂正(2026-09-11)

### 実装

スタックにはガードページが無く、溢れてもページフォルトにならない。ページング機構を
この段階で触るのは影響範囲が大きいため、次の2点で検出する方式にした。

- 各プロセススタックの最下端に**カナリア**(`STACK_CANARY`)を置く
- **タイマ割り込みハンドラ**(`c_timer_switch`)で、割り込み時の`rsp`の範囲と
  全プロセスのカナリアを検査する

`c_timer_switch`は割り込み時の`rsp`を引数で受け取るため、通常パスのコストはゼロで
ある。検出時は`os_panic_stack_overflow`が`rsp`・スタック下端・消費バイト数を表示して
停止する(QEMUテスト中は電源断してテスト失敗になる)。

実装時に2つの誤りを踏んだ。`g_current_process_index`は**表示フォーカス用**であり
スケジューラの実行中プロセス(`*CURRENT-PROCESS*`)とは別物なので、indexではなく
`rsp`がどのスタック範囲に入るかで判定する必要がある。また**起動直後の初回tickは
カーネルのidleループのスタック上**で走りどのプロセススタックにも属さないため、
その場合は検査対象外としなければならない。どちらも修正前は全深度で誤検出していた。

### 検証

| 深度 | 消費見込み | 結果 |
|---|---|---|
| 100 / 400 / 600 / 800 / 1000 | 16〜160KB | 正常に完走 |
| 5000 | 約800KB | **panicして電源断**(無反応にならない) |

### Phase 4の「スタックオーバーフロー」は誤診断だった

Phase 4で`%%bench-aot-nontailrec`(深度1000×1000回)がハングした件を、フレーム
サイズの計算から「深度1000で約330KB、256KBのスタックを溢れる」と診断したが、
**これは誤りだった。**

実測したフレームは1レベルあたり160byte(`__step_fixed`が4 push+0x78、
`__fixed`が2 push+0x88だが、**再帰の自己呼び出しは`__step_fixed`へ直接行き
`__fixed`を経由しない**)で、深度1000でも160KBに収まる。実際、単発の深度1000
再帰(`%%bench-aot-deep-recursion 1000`)は正常に完走する。

さらに、スタックガードを入れた状態で元の症状(深度1000×1000回)を再現させても
**ガードは発動せず、ハングしたままだった**。深度5000ではガードが正しく発動する
ことを確認済みなので、ガードの不備ではない。

**したがって、この
ハングの原因は未解明のまま残っている。** 分かっているのは次の通り。

- 深度1000×1000回で再現する。単発の深度1000は完走する。
- 深度100×10000回(現在のベンチマーク設定、総呼び出し回数は同じ1e6)は4.8秒で完走する。
- Phase 4のインライン化前(基準表の測定時)は完走していた(324.89を記録している)。
- スタックガードは発動しない。CPU使用率は約25%で、完全な暴走ループでもない。

ベンチマークの再帰深度は100のままとする(仕事の単位数はNで変わらないため測定の
前提は保たれる)。再挑戦する際は`%%bench-aot-deep-recursion`(深度を直接指定できる
診断用関数)と`BENCH_REC_DEPTH`を使って切り分けられる。

## Phase 5 第1部/第2部: 単価の確定と、cc_car回帰の原因(2026-09-11)

### os_is_control_transferの単価は19.5ではなく約9.08だった

Phase 3で測った19.5命令/回は、**Phase 4で`os_is_control_transfer`自身を
`static inline`化する前**の値だった(`%%DIAG-CT-CHECK`を追加したのは
`get_current_process`のインライン化と同時で、`os_is_control_transfer`自体の
インライン化はその後)。現HEADで傾き法により測り直すと**9.08命令/回**である
(この値には診断ループ自身のオーバーヘッド4〜5命令が含まれるため、チェック本体は
数命令)。

したがって`branch`(463.86)のうち17回のチェックが占めるのは約85命令(18%)であり、
「71%を占めるので構造的再帰への拡張が最優先に戻る」というシナリオには該当しない。
`os_is_control_transfer`の**発行箇所削減**の優先度は下がったままでよい。

### cc_car/cc_cdrのinline化は見送る

`static inline`(TUごとに実体が増える)と、C99の`inline`+1TUでの`extern`宣言
(実体を1つだけ残す)の両方を試したが、**どちらでも同じ回帰が出た**。シンボルが
一意であることをobjdumpで確認した上で回帰したので、「アドレスの多重化」という
仮説は**外れ**である。

引き金を1回の起動で絞り込んだ結果、**`labels`の本体内に`let`がある場合だけ**
JIT化されなくなることが分かった(`labels`単独・`let`単独・`let`+自己再帰はいずれも
正常)。

JITのコンパイル断念は`*ok = 0`や`return 0`を書くだけで黙って進むため、
指示書2-3に従って断念箇所の行番号を記録する仕組み(`%%DIAG-ZA-BAIL-LINE`)を
入れた。これにより断念箇所が`za_rewrite_body_list`の
「`forms`が`TAG_CONS`でない」判定であることが特定できた。**コンパイル時に
組み直しているbodyリストが壊れている**ことを示す。

同関数は次の形をしている。

```c
GC_PROTECT(forms);
lisp_val_t first = za_rewrite_fn_refs(cc_car(forms), env, scope, ok);
GC_PROTECT(first);
lisp_val_t rest = za_rewrite_body_list(cc_cdr(forms), env, scope, ok);
return os_make_cons(first, rest);   /* restは未保護 */
```

`first`は保護されているが**`rest`は未保護**であり、直後の`os_make_cons`は確保を
行うためGCが走りうる。原則4(保護されているのはその変数であって、そこから写した値
ではない)と同じクラスの漏れに見える。

ただし`GC_PROTECT(rest)`を足すと別の形で壊れる(`EVAL-ERROR`になり、それまで
JIT化できていた`let`+自己再帰まで落ちる)。za.cのコンパイル時アロケーション経路
全体の監査が必要であり、**その調査を経るまでinline化は行わない**。cc_car/cc_cdrは
非インラインのまま据え置いた。

### 得られたもの

- `%%DIAG-ZA-BAIL-LINE`: JITが断念した行番号を読める。今回の切り分けに直接効いた。
- `za_rewrite_body_list`の`rest`未保護という**具体的な調査対象**。

## Phase 5 追補: za_rewrite_*系のenv未保護を修正(2026-09-11)

### 仮説「formsが未保護」は前提が成り立たなかった

`za_rewrite_body_list`の`forms`は**既に`GC_PROTECT`されていた**。また
`os_make_cons`は引数を内部で保護してから確保する(`GC_PROTECT(car);
GC_PROTECT(cdr);`の後に`os_alloc_bytes`)ため、`rest`を未保護のまま渡すのも
**安全**である。以前「`rest`が未保護」としたのは誤りだった。

### 実際に未保護だったのは`env`

2-2の判定基準(「`lisp_val_t`のCローカルは、確保を伴いうる呼び出しを跨いで
生存するなら例外なく保護されていなければならない」)で見ると、`env`が
`za_rewrite_body_list` / `za_rewrite_binding_list` / `za_rewrite_fn_refs`の
**3関数すべてで未保護**だった。いずれも確保を伴う再帰呼び出しを跨いで生存し、
環境オブジェクトはGCで移動する。`documents/pitfalls.md`原則4と同じクラスの漏れで、
**本コミットで修正した**。

なお保護スロット(2-3)は固定長配列ではなくCスタック上のノードを連結リストに
つなぐ方式(`types.h`の`gc_rootnode`)なので、再帰の深さで溢れる心配は無い。
深度1000の非末尾再帰が完走することも確認済み。

### ただしcc_car/cc_cdrのinline化は引き続き見送る

`env`の保護を入れた状態でinline化を再適用すると、回帰は**別の箇所へ移動した**
(`za_compile_body_forms`経由、za.c:4703で伝播、`EVAL-ERROR`)。同型の保護漏れが
za.cのコンパイル時経路にまだ残っていることを示す。

`%%DIAG-ZA-BAIL-LINE`は失敗を表す`return 0;`だけを捉えており、正常終了と
区別できない`return nil;`経由の失敗は追えない。したがって真の失敗箇所へは
到達できず、**za.cのコンパイル時アロケーション経路全体の監査**が必要である。
指示書の判定表でいう「解消するが別の箇所で断念 = 同型のバグが他にもある」に
該当する。

## GCデバッグ機構(第0部)の実装と、za.cの保護漏れの実測(2026-09-11)

### 実装したもの

`GC_DEBUG=1`でビルドすると有効になる調査用の網。通常ビルドでは何も行わない
(マクロが空になる)ため性能に影響しない。

| 機構 | 内容 | 状態 |
|---|---|---|
| stale参照の検出 | GC後の旧From空間`[g_to_start, g_to_end)`を指すアドレスの
デリファレンスを`cc_car`/`cc_cdr`で検出し**計数**する | 有効 |
| 強制GC | `%%DIAG-GC-STRESS n`で確保n回ごとにGCを走らせる(実行時に切り替え) | 有効 |
| 検出数の取得 | `%%DIAG-GC-STALE-HITS` | 有効 |
| トラップ塗り潰し | 旧From空間をタグ`TAG_FORWARD`のパターンで塗る | **既定で無効** |

### 塗り潰しは使えなかった(重要な制約)

指示書は塗り潰しを最重要としていたが、**このコードベースでは使えない。**
`os_alloc_raw`で確保したGC非管理の生データ(`os_stream_t`、ファイル読み込み
バッファ等)がGCヒープ内に置かれており、GCはこれらをコピーしない。つまり旧From空間に
残ったまま「上書きされるまで生き延びる」ことに依存している。塗り潰すとこれらが
即座に破壊され、`init.lisp`のload中に停止する。

塗り潰しを使うには、先にこれらの生データをGCヒープ外(Immobilized Space等)へ
移す必要がある。それまでは範囲検査だけで運用する。`ISIKIOS_GC_PAINT`として
別フラグに分離してあり、上記の移設が済んだ時点で有効化できる。

### 強制GCはブート中には使えない

ブートは膨大な確保を行うため、確保N回ごとの強制GCをコンパイル時に固定すると
起動が終わらない(N=200で実測、200秒でタイムアウト)。実行時に
`%%DIAG-GC-STRESS`で切り替える形にし、ブートは通常速度で終わらせてから
調査対象の直前で有効化する運用にした。

### panicではなく計数にした理由

当初はstale参照を検出した時点でpanicさせたが、起動初期のpanic処理自体が
成立せず切り分けにならなかった。**計数して後から読む**形に変えたことで、
「どこでどれだけ踏んでいるか」の全体像が取れるようになった。

### 実測結果と、その**撤回**

当初の測定は次の通りだった。

| 時点 | stale参照の検出数 |
|---|---|
| ブート + `init.lisp`のload完了後 | 0 |
| 強制GC下で`labels`+`let`を含む関数をJITコンパイル | 2,035 |

これを「za.cのコンパイル経路に2,035件の保護漏れがある」と解釈したが、
**この結論は誤りであり撤回する。**

「ブート中が0件だから誤検出ではない」という論拠が成立していなかった。
**ブートは強制GCなしで走っており、2,035件は強制GC下の測定である。** 条件の
異なる2つを比べていたため、「強制GCを入れると誤検出する検出器」と「本物のバグを
捉えている検出器」を区別できていなかった。

### 特異度の確認(対照実験)

正しい対照は「強制GC下で、za.cを通らないワークロードを流して0件であること」である。
`cons`ベンチマーク(確保を行うので強制GCが発火する。`loop`/`arith`は確保しないため
対照にならない)で測ったところ:

| 条件 | stale検出数 | 箇所 |
|---|---|---|
| **対照**(za.c非経由 + 強制GC) | **2,044** | 10 |
| 本命(za.c経由 + 強制GC) | **0** | 0(JIT成功) |

**za.cとは無関係のワークロードで大量に出て、za.c経路では0件だった。** 当初の
2,035件は、za.cの保護漏れではなく検出器の誤検出だったことになる。

原因は**GC自身がコピー先(To空間)のオブジェクトを`cc_car`/`cc_cdr`で走査する**
ことだった。検査は「`[g_to_start, g_to_end)`を指すか」で判定しており、GCの走査は
まさにその範囲を読む。GC実行中は検査を抑止するよう修正し、対照・本命ともに0件に
なった。

### 感度の確認(revertテスト)— **通過していない**

`env`保護(`4378425`)を一時的に外し、既知のバグを検出できるかを確認した。

| 強制GC間隔 | JITコンパイル | stale検出数 |
|---|---|---|
| 20回ごと | **失敗(NIL)** | **0** |

**バグは再現している(JITが失敗している)のに、検出器は0を返す。**
`os_get_variable`にも検査を足したが変わらなかった。検査点が
`cc_car`/`cc_cdr`/`os_get_variable`に限られており、staleな環境が実際に
参照される経路を覆えていない。

### 現状の結論

- **特異度: 確認済み**(対照0件)。
- **感度: 未確認**(既知のバグを捉えられない)。

指示書の基準「2-1と2-2の両方が揃って初めて検出器を信用できる」に照らし、
**この検出器はまだ監査に使えない。** 0という測定値は「保護漏れが無い」ことの
根拠にならない。

za.cの監査(第2部)に進む前に、検査点をヒープ参照全般(インスタンスのword
アクセス、環境の走査、VECTORのデータ部等)へ広げ、revertテストで検出できることを
確認する必要がある。

### 次の手順

1. `%%DIAG-GC-STALE-HITS`を使い、`za.c`の関数単位で検出数を切り分ける
   (`cc_car`/`cc_cdr`に渡す`where`文字列を呼び出し元ごとに変える、
   あるいは関数の入口/出口で差分を取る)。
2. 検出数が多い関数から、判定基準(「`lisp_val_t`のCローカルは、確保を伴いうる
   呼び出しを跨いで生存するなら例外なく保護されていなければならない」)で
   仮引数とローカルを洗う。
3. 0になったらインライン化を再適用する。

## env stale仮説の決着: 仮説は崩れた(2026-09-11)

### 直接アサーションによる確認

検査点(`cc_car`等)では捉えられない可能性があるため、`za_rewrite_body_list` /
`za_rewrite_binding_list` / `za_rewrite_fn_refs`の**入口**へ、`env`がどの空間に
属するかを直接分類して数えるアサーションを置いた(live=生きているFrom空間 /
stale=旧From空間 / other=Immobilized・静的)。

| 条件 | JITコンパイル | `env`入口分類 |
|---|---|---|
| A: `env`保護あり | T | live=18, **stale=0**, other=0 |
| B: `env`保護なし(revert) | T | live=18, **stale=0**, other=0 |

**両者は完全に同一である。** 保護を外しても`env`は一度もstale領域を指さない。
保護ありでlive=18が出ているためアサーション自体は機能している。

### 結論: `env`のstale仮説は崩れた

指示書の判定表の「一度もfrom-spaceを指さない → stale仮説は崩れる。回帰の原因は別」
に該当する。

さらに、**保護を外してもJITは成功する**(この条件では)。つまり`env`保護は
`cc_car`/`cc_cdr`インライン化時の回帰の必要条件ですらなかった。

したがって`4378425`の`env`保護が回帰を解消したのは、staleの修正としてではなく
**保護ノードが1つ増えてGCのタイミングがずれたから**である。`rest`を足したときと
同じ機構で、あのときは悪化し今回は改善しただけだった。`env`の3件は
**「保護すべきだが、あの回帰の原因ではなかった」**という位置づけになる
(判定基準上は保護が正しいので、修正自体は維持する)。

### 副産物: GC圧力を上げるとJITが失敗する

強制GCを20回ごとにすると、`env`保護の有無にかかわらずJITコンパイルが失敗する。
このとき`za_rewrite_*`の3関数は**一度も呼ばれていない**(分類カウンタが全て0)ため、
失敗はそれらに到達する前に起きている。GC圧力そのものがJITコンパイルを壊す経路が
別に存在することを示しており、これも未解明の項目として記録する。

### 検査点の列挙は行わない

前回の報告で次の手として挙げた「検査点をヒープ参照全般へ広げる」は**実施しない。**
検査点の列挙はomission listであり、列挙漏れがあれば検出器は0を返し、その0が
安全の証拠として読まれてしまう。デフォルトが安全側でないomission listは使えない
(`os_is_control_transfer`の属性表について「デフォルトはtransferしうる」とした
議論と同じ形)。塗り潰しは列挙を要求せず、staleを読んだ時点で値が壊れるため
どこで読もうと落ちる。**検査点がゼロでも機能する**ので、そちらを優先する。

既存の検査点機構(`%%DIAG-GC-STALE-SITES`ほか)は維持するが、**その0を
「漏れがない」の根拠として使わないこと。**

## 陽性対照の作成と、範囲検査方式の構造的限界(2026-09-12)

### 陽性対照・陰性対照

`env` revertは陽性対照ではないことが確定したため(`env`は一度もstale領域を
指さない)、**必ずstaleになる合成バグ**を診断専用に用意した
(`%%DIAG-STALE-POSITIVE` / `%%DIAG-STALE-NEGATIVE`、`bench_subprimitive.c`)。
陽性は`lisp_val_t`のローカルを保護せずに確保を跨がせて後で読む、陰性は同じ構造で
`GC_PROTECT`を正しく行う。

| 対照 | 返り値(正解11) | stale検出 |
|---|---|---|
| 陰性(保護あり) | 11 | 0 |
| 陽性(保護なし) | **NIL(壊れている)** | **0** |

**陽性対照は実際に壊れているのに検出器は0を返した。** 適切な陽性対照により、
範囲検査方式に感度がないことが確定した。

### 原因: GC世代の偶奇

GC回数を変えて測ると原因が特定できた。

| GC回数 | 返り値(正解11) | stale検出 |
|---|---|---|
| 約1回 | 11 | **1**(検出成功) |
| 約2回 | **397(壊れている)** | **0**(見逃し) |

コピーGCはFrom空間とTo空間を毎回入れ替える。**GCが2回走ると空間が元に戻るため、
staleなアドレスが再び「生きている側」の範囲に入る。** 範囲検査
(`[g_to_start, g_to_end)`に入るか)は**GC世代が奇数回のときしか検出できない**
という構造的な限界を持つ。

これは検査点の不足ではなく方式そのものの限界であり、検査点をいくら増やしても
解消しない。**塗り潰しが必要である**という指示書の優先順位が正しかったことになる
(塗り潰しなら値そのものが壊れるため、GC世代の偶奇に関係なく検出できる)。

### 検出器を有効にすると回帰が消える

`cc_car`/`cc_cdr`のインライン化による回帰を、GC_DEBUGビルドで観測しようとしたが
**再現しなかった**。GC_DEBUGビルドは`cc_car`の中に検査呼び出しを入れるため、
インライン化の効果が打ち消され、非インライン版と同じ挙動になる。

| ビルド | 回帰 |
|---|---|
| 通常ビルド + インライン化 | **EVAL-ERROR(再現)** |
| GC_DEBUGビルド + インライン化 | 再現しない |

**観測しようとすると対象が消える**形であり、この回帰を検出器で追うことは
原理的にできない。

### インライン化状態の記録(2-3)

`d7e7889`のA/B測定は**インライン化なし**の状態だった。回帰はインライン化時にのみ
現れるため、あの測定だけでは回帰について何も言えていなかった。表を埋めると:

| | `env`保護あり | `env`保護なし |
|---|---|---|
| インライン化なし | T | T |
| インライン化あり | **EVAL-ERROR** | NIL |

**`env`保護はインライン化時の回帰を解消しない**ことが確定した。`env`がstale領域を
一度も指さないという事実は独立に成立するため、stale仮説が崩れたという結論は
変わらない。

## 第2部着手前の「変更前」測定と、前提の訂正(2026-09-12)

### GC圧力によるJIT失敗の閾値(変更前の状態として固定)

強制GCの間隔Nを振り、`labels`本体内に`let`を持つ関数のJITコンパイル可否を測った。

| 強制GC間隔N | JITコンパイル | 断念行 |
|---|---|---|
| 圧力なし | T | - |
| 1000 | T | 0 |
| 200 | T | 0 |
| **50** | **NIL** | 0 |

**閾値は50と200の間にあり、GC回数が増えるほど失敗する累積的な破壊である**
(1回のGCで壊れるわけではない)。第2部(生データ分離)完了後に同じ測定を行えば、
変化が直接の指標になる。

### %%DIAG-ZA-BAIL-LINEのreturn nil問題を解消した

上表の断念行が全て0なのは、計器が失敗を表す`return 0;`しか捉えておらず、
`za_try_compile_defun`が`nil`で失敗を返す経路(コンパイル断念の大半)を
取りこぼしていたためである。同関数内の`return nil;`は7箇所すべてが失敗パスで
あることを確認し、個別に計器化した。

以前`return nil;`へ一括で計器を入れて`za_rewrite_body_list`のリスト終端(正常終了)
まで拾った失敗を繰り返さないよう、**対象を「失敗を表す返却」だけに限る**という
判断基準をコード中のコメントに残した。

### 第2部の前提は大きく崩れた

`os_alloc_raw`の全呼び出し元(16箇所)を列挙し、GCによる扱いを確認した。

| 呼び出し元 | 用途 | GCの扱い |
|---|---|---|
| `stream_lisp.c` ×9 | `os_stream_t`本体 | **`gc_relocate_stream`がTo空間へコピー** |
| `stream_lisp.c:268,281` | STRING系ストリームの`str_buf` | **`gc_relocate_stream`がコピー** |
| `mount.c:154` | ファイル読み込みバッファ | STRING_INPUTの`str_buf`になるため**コピーされる** |
| `stream_lisp.c:38` | `make_string_from_bytes` | TAG_STRINGのLispオブジェクト、**通常のGC対象** |
| `print.c:51,61` | bignum印字の作業バッファ | **コピーされない**(ただしbignum印字中のみ) |

**`os_stream_t`とそのバッファはGC管理下にあった。** 「GC非管理の生データがGCヒープに
置かれ、上書きされるまで生き延びることに依存している」という前提は、
`print.c`の2箇所を除いて成立していない。`cc_load`のストリームもCスタック上の
ローカル(`os_stream_t stream;`)でGCヒープ外である。

したがって**第2部は当初想定したアーキテクチャ変更ではない。** 塗り潰しが
`init.lisp`のload中に停止させる原因は、生データのGCヒープ内配置ではなく別にある。
**この原因の特定が第2部の新しい起点になる。**

`print.c`の2箇所は`print_bignum`内の作業バッファで、`sink_write_char`が確保を
伴う場合にGCを跨ぐ可能性がある。実害の有無は未確認だが、判定基準上は保護が必要な
形である(これ自体は小さな修正で済む)。

## 塗り潰しの解禁: 原因はprint.cの2箇所だけだった(2026-09-12)

`print_bignum`が`work`と`digits`を別々に`os_alloc_raw`していた。生バッファはGCの
コピー対象ではないため、**2回目の確保がGCを誘発した時点で1回目の`work`が無効になる。**
1回の確保にまとめ、確保後は一切確保を伴わない形にした(`sink_write_char`は
関数ポインタ経由の出力のみで確保を伴わない)。

この2箇所が**塗り潰しを止めていた唯一の原因**だった。修正後、
`ISIKIOS_GC_PAINT`有効で`init.lisp`のloadが完走する。**第0部の受け入れ条件を達成。**

当初「`os_stream_t`やファイル読み込みバッファがGCヒープに置かれた非管理データ」と
していた前提は誤りで、それらはすべて`gc_relocate_stream`がコピーしていた
(`documents/pitfalls.md`原則7に訂正を記録)。想定していたアーキテクチャ変更は
不要だった。

### 感度・特異度の確認(受け入れ条件を達成)

塗り潰し有効で陽性対照・陰性対照を、**偶奇の両側**で測った。

| GC回数 | 陽性対照(保護なし) | 陰性対照(保護あり) |
|---|---|---|
| 約1回 | **999(検出)** | 11(正常) |
| 約2回 | **999(検出)** | 11(正常) |

(999は陽性対照がトラップパターンを読んだことを示す固定値。そのままLisp値として
返すとタグがTAG_FORWARDのため印字側で暴走するので、対照側で判定して置き換えている)

**範囲検査が見逃していた偶数世代でも検出できており、偶奇に依存しない。**
検査点の列挙も不要である(staleを読んだ時点で値が壊れるため、どこで読もうと分かる)。

### 範囲検査で得た過去の0件はすべて疑わしい

コピーGCの空間入れ替えにより、範囲検査はGC世代が奇数回のときしか検出できない。
したがって以下は**未確定に戻る**。

- `za.c`経路の0件(`4e967ac`)。「漏れがない可能性がある」の根拠は消えた。
- `env`入口アサーションの`live=18`(`d7e7889`)。「18個が健全」ではなく
  「18個がlive側の範囲を指していた」であり、偶数世代のstaleを排除できない。

ただし`env`が回帰の原因でないという結論は2×2の表から独立に成立する(保護の有無に
かかわらずインライン化時は回帰し、壊れ方も違う)。不確かなのは中間の主張である。

### 塗り潰しは「読んだ瞬間にGP例外」になる

トラップパターン`0xDEADDEADDEADDEA6`は上位16bitが`0xDEAD`で**canonicalではない**。
そのためこれをアドレスとしてデリファレンスすると、ページフォルトではなく
**GP例外(vector=13, error_code=0)**になる。つまり:

- GP例外の瞬間にレジスタへトラップが載っていれば、その例外は**staleポインタの
  参照そのもの**である。例外ハンドラにレジスタ一式とスタックの生ダンプを足し、
  トラップを検出したら明示するようにした。
- `rip`だけではソース上の位置が分からない(UEFIの読み込みアドレスは実行ごとに
  変わる)ため、ハンドラ自身のアドレスを`handler=`として併記し、差分から
  PE上のアドレスへ戻せるようにした。`tools/bench/locate_rip.sh --serial`が
  これを自動化する。

ただし**そこでOSが止まると、その1件で以後の監査が全部隠れる**。監査は1回の実行で
全体像を取りたいので、`cc_car`/`cc_cdr`と`gc_copy_value`にトラップ判定を入れ、
読まずに記録して`nil`を返す形にした(`ISIKIOS_GC_DEBUG`ビルドのみ)。

`gc_copy_value`側が必要なのは、トラップのタグが`TAG_FORWARD`(0x6)だからである。
GCは転送ポインタとみなして追いかけ、そこで落ちる。実際、最初の実測では
`gc_copy_value+0x33`(`words[0]`の読み出し)でGP例外になっていた。

### 塗り潰しの構造的な限界(範囲検査と同型)

塗り潰すのは旧From空間だが、**その領域は次のGCのコピー先になる**。したがって
GCを2回以上跨いだstaleアドレスは、塗り潰しではなく新しい生きたオブジェクトを
指してしまい、トラップとしては観測されない。

| 書き込みと読み出しの間のGC回数 | 陽性対照の戻り値 |
|---|---|
| 1回 | **999**(トラップを読んだ) |
| 6回 | 190(別の生きた値を読んだ。トラップとしては検出できない) |

範囲検査の偶奇汚染とは別の形だが、**「トラップ0件」もまた無罪の証明ではない**という
点では同じである。対照はGCちょうど1回に固定した(`%%DIAG-STALE-POSITIVE`の引数0で
`os_gc_collect`を1回だけ走らせる)。これで感度が毎回確定する。

### カバレッジ: 強制GCなしでは0%

小規模確認(`room_test` 13件 + `environment_pages_test` 20件)の結果:

- 強制GCなし: 33件すべて**GC 0回**。塗り潰しはGCが走らなければ何も検出しないので、
  この条件で全件が通っても監査としては**何も言えていない**。
- 強制GC間隔1000: GCを跨いだアサーションが10/33件(30.3%)。

したがって監査本体は強制GCと組み合わせて流す必要がある。これは指示書 第0部3が
「0回の試験が多ければ強制GCと組み合わせる。その判断は集計後に行う」としていた
判断であり、**集計の結果として強制GCが必須と確定した**。

### 小規模確認で既に1件検出している

強制GC間隔1000で`environment_pages_test`を流したところ:

- アサーション5件目 `(%%za-compiled-p (function iep-call-other))` が**NIL**を返して失敗
  (期待はT)。同じアサーションでGC 1回、トラップ読み出し2回。
- 検出箇所は`eval_args+0x93`(`cc_car(args)`)と`eval_args+0x123`(`cc_cdr(args)`)の2箇所。
  いずれも`args`が塗り潰し済み領域のcons cellを指しており、読み出した内容が
  トラップパターンだった。

これは**「GC圧力を上げるとJITコンパイルが失敗する」という既知の未解明項目
(`c3da14e`のN=50)と同じ症状**である。塗り潰しの網にかかったことになる。
真因の特定は監査本体の集計と合わせて行う。

### 強制GCを強くすると連鎖的に壊れる

対照を一切使わず、ふつうのLispの仕事(非末尾再帰とリスト構築)だけを流した場合:

| 強制GC間隔 | 結果 |
|---|---|
| 1000 / 100 | 正常(ただしGC 0〜1回でカバレッジは低い) |
| 16 | GCが「生きた構造の中の塗り潰し済み領域へのポインタ」を1件検出。以後、
`format`の引数まで壊れ、ラベル文字列が`NIL`、数値がすべて同一の巨大値になった |

**対照を使わなくても検出が出る**ので、これは対照の合成バグとは無関係の本物の
保護漏れである。同時に、**最初の検出より後ろの結果は独立に再確認が必要**である
ことの実例にもなっている(指示書 第0部2)。


## `eval_args` の stale の真因は `os_eval_top_level` と `reader.c` だった(指示書 第0部)

`bbef5c3` で `environment_pages_test` に出た検出は `eval_args+0x93`(`cc_car(args)`)と
`eval_args+0x123`(`cc_cdr(args)`)だったが、**`eval_args` にバグはなかった。**
`args`・`env`・`head` はいずれも `GC_PROTECT` されており、唯一保護されていない `tail` は
`os_make_cons` の引数にしかならない(内部保護される)。判定基準上、正しい。

### 検出箇所は「最初に stale を読んだ関数」であって「バグのある関数」ではない

staleポインタ自体は**ふつうのアドレスに見える**。塗り潰し済み領域を指していても、
ポインタの値そのものはトラップパターンではない。トラップが現れるのは、そのポインタを
**デリファレンスした結果**であり、つまり1段あとの読み出しである。

そのため「ポインタ側の判定」では犯人にたどり着けない。実際に効いたのは次の2つ:

1. **読んだ結果がトラップかを見る**(`cc_car`/`cc_cdr` の戻り値側)。
   最初に stale を読んだ場所が直接出る。
2. **`GC_PROTECT` しようとした値が既に stale かを見る**。
   `os_make_cons` はインライン展開されるため、`__builtin_return_address(0)` は
   **その `os_make_cons` を呼んだ側**を指す。バグのある呼び出し箇所が直接出る。

2 を入れた1回の測定で、犯人が3箇所(実体は2つ)出た。

### 真因

| 箇所 | 何を確保を跨いで持っていたか |
|---|---|
| `os_eval_top_level` の `env` | `wrapped` を組み立てる3回の `os_make_cons` |
| `reader.c` `read_list` の `car` | `read_list_rest`(リストの残り全体を読む再帰) |
| `reader.c` `read_list_rest` の `elem` | 同上 |
| `reader.c` `os_parse_number` の `str` / `env` | `read_expr`(数値リテラルの確保)+ `os_resolve_class` + `initargs` を組む4回の `os_make_cons` |

最後の1件だけは計器ではなく、同じパターンを`reader.c`全体に当てて見つけた
(数値パース失敗時のcondition構築という、テストが通らない経路のため実行されていない)。
`initargs` の式は内側から評価されるので `number_class` は内部保護されるが、
`str` はその4回ぶん手前から生存しており対象外である。

いずれも最後に `os_make_cons(x, y)` を呼ぶので「保護済み」に見えていた。
**`os_make_cons` の内部保護が守るのは呼んだ瞬間の値だけで、それより前の確保で
古くなった値は救えない。**

`os_eval_top_level` に `GC_PROTECT(env)` を1行足しただけで、`eval_args` を含む
下流の検出がすべて消えた。

### 受け入れ条件

対照を使わない通常の Lisp 処理(非末尾再帰 + リスト構築 + `length`)を強制GC下で流す:

| 強制GC間隔 | GC回数 | 保護時stale | トラップ読み | 塗り潰しフィールド | LIFO違反 |
|---|---|---|---|---|---|
| 16 | 7 | 0 | 0 | 0 | 0 |
| 4 | 36 | 0 | 0 | 0 | 0 |

陽性対照は999(検出)、陰性対照は11。**機構を壊さずに検出が消えた。**

### 保護時の検査は実行時スイッチにした(既定は無効)

`GC_PROTECT` はインタプリタで最も多く通る場所である。そこに検査の呼び出しを
無条件で置いたところ、**`labels` + `let` の JIT コンパイルが10分経っても終わらなく
なった**(通常は数秒)。バグ探しには効いたが、常時有効にはできない。

`%%DIAG-GC-PROTECT-CHECK` で実行時に切り替える形にし、既定を無効にした。
残るのはフラグ読み出し1回ぶんで、これは無視できる。

計器を入れるときは、**それが対象の実行時間を変えていないか**も見る必要がある
(原則6の「計器が対象を消していないか」の、時間側の現れ方である)。

### 否定された仮説: shadow stack の LIFO 違反

`GC_PROTECT` は `get_current_process()->gc_roots` へ繋ぐが、`get_current_process()` が
返すのは `g_current_process_index`(=**表示フォーカス**)であって、スケジューラが
実際に走らせているプロセスではない。スケジューラは `*RUN-QUEUE*` を tick ごとに
回してスタックを切り替える。したがって複数プロセスのノードが1本のリストへ混ざり、
一方のスコープ脱出が他方のノードをリストから落とす、という筋書きが立つ。

`gc_unprotect_node` に「外そうとしているノードが先頭か」の検査を入れて実測したところ、
**違反は0件**だった。この仮説は成立しない(テスト実行中に Lisp を走らせるプロセスが
1つしかないためと思われる)。検査自体は計器として残してある。

## トラップパターンのタグを選び直した(指示書 第1部)

### 「タグとして不正な値」は作れない

`0x0`〜`0x7` の8値はすべて使用中である
(FIXNUM/CONS/SYMBOL/CHAR/STRING/INSTANCE/FORWARD/RAW_POINTER)。
そのかわり **GC が決して追いかけないタグ**が3つある。`gc_copy_value` は
FIXNUM・CHAR・RAW_POINTER をその場で返してデリファレンスしない。

トラップパターンを `0xDEADDEADDEADDEA6`(TAG_FORWARD)から
`0xDEADDEADDEADDEA7`(TAG_RAW_POINTER)に変えた。これで GC が転送ポインタとして
追いかけることがなくなり、`gc_copy_value` の判定は**安全網ではなく計数のためだけ**の
1行になった(生きた構造のフィールドが塗り潰し済み領域を指していた、という形の
漏れはこれでしか数えられない)。

### `cc_car`/`cc_cdr` のポインタ側判定は外した

トラップを読むと GP 例外になるのは、上位16bitが `0xDEAD` で non-canonical だから
である。これは例外ハンドラ側で識別できる(ダンプにレジスタ一式を出し、トラップを
検出したら明示する)ので、読み出し側の判定は不要になった。外した。

### 戻り値側の判定は外せない

**塗り潰した領域は読んでもフォルトしない。** ただトラップの値が返るだけである。
したがって「読んだ結果がトラップか」は例外ハンドラでは代替できず、
`cc_car`/`cc_cdr` に残さざるを得ない。そしてこれは真因の特定に実際に効いた判定である。

これを不要にできるのは**第2部のアンマップ方式だけ**である。仮想アドレスを使い捨てれば、
stale を読んだ時点でページフォルトになるので、判定点を1つも置かずに済む。

### 確認したこと

| 項目 | 結果 |
|---|---|
| 陽性対照(GCちょうど1回) | 999(検出) |
| 陰性対照 | 11(誤検出なし) |
| 通常処理でGP例外により停止しないこと | 強制GC間隔16・4のいずれも例外なし |
| **本物のGP例外では従来どおり停止すること** | `%%DIAG-FORCE-GP`で停止。ダンプに「GC PAINT TRAP」は**出ない** |
| `cc_car`/`cc_cdr` の生成コード | ポインタ側の`os_gc_debug_trap_read`呼び出しが消え、戻り値側の`os_gc_debug_trap_result`のみ |

`%%DIAG-FORCE-GP`は`0xBADC0FFEE0DDF00D`(トラップではないnon-canonicalアドレス)を
読む診断コマンドで、トラップ判定が本物の例外を握り潰していないことを確認するために
追加した。逆引きも正しく効いており、`cc_diag_force_gp+0x0`と呼び出し元
`apply_function+0x5a`が出た。

### ビルドフラグの取り違えをビルドシステムで防いだ

`$(TARGET)`はソースのファイル依存で追跡するため、`GC_PAINT=1`を付け外ししても
再ビルドされない。これまでは「先に`rm -f`する」という手順に頼っていたが、忘れると
**塗り潰し無効のバイナリを有効のつもりで測る**ことになり、しかも無言で成立する。

使用したフラグをスタンプファイル(`tmp/.gc-debug-flags`)に残し、変わったときだけ
再ビルドが走るようにした。監査ドライバも`make`を内側から呼ぶので、フラグを
明示的に引き継ぐようにした(引き継がないと、測定の途中でソースが更新された瞬間に
別物のバイナリへ入れ替わる)。実際にこの取り違えが一度起きかけている。

### GP 例外からの再開は見送った

「識別して記録し継続する」には、フォルトした命令をスキップする必要がある。x86 は
可変長命令なので、正しくスキップするには命令長デコーダが要る。対象を `mov r64,[r64+disp]`
に絞れば小さく書けるが、**それ自体が omission list であり、読み違えれば黙って別の
実行結果になる**(停止するより悪い)。判定点を1つ残すほうを選んだ。


## 「累積的破壊」は誤りだった: GC 1回で壊れる(指示書 第5部)

`c3da14e` は強制GC間隔Nを振って「N=1000/200は成功、N=50は失敗。GC回数が増えるほど
失敗する累積的な破壊」と記録していた。**この読みは誤りである。**

同じ測定を、今度は**各点でのGC回数も記録して**`bbef5c3`(修正前)で取り直した:

| 強制GC間隔N | JITコンパイル | **GC回数** | 断念行 |
|---|---|---|---|
| 圧力なし | T | 0 | - |
| 1000 | T | **0** | 0 |
| 200 | NIL | **1** | 4711 |
| 50 | NIL | 2 | 4711 |
| 20 | NIL | 5 | 5056 |

**N=1000で成功していたのは、そこでGCが1回も走っていなかったからである。**
GCが1回起きた時点で失敗している。累積でも確率的でもなく、**1回のGCで決定的に壊れる**。

指示書 第5部 3-2 が「stale説なら対象を動かす最初のGCで壊れるはずで、100回程度の
GCを要するのは単純な stale の振る舞いではない」と指摘していた点は、
**そもそも100回のGCを要していなかった**というのが答えだった。素直な stale の
振る舞いと矛盾しない。

これは指示書 第4部1の「集計の指標はNではなく各試験のGC回数にすること」が、
カバレッジだけでなく**過去の結論の妥当性**にも効くことを示している。
Nを条件として記録し、GC回数を記録しなかったために、1年分の解釈が食い違っていた。

### 修正前後の比較(第0部の修正はJIT失敗を解消していない)

第0部で`os_eval_top_level`・`reader.c`の保護漏れを直したが、**JIT失敗は残っている**。
修正後も N=200(GC 1回)で NIL、断念行 4711 で同じである。

さらに N=50 は**失敗ではなくハングに変わった**。保護を足したことでGCのタイミングが
ずれ、別の潜在バグが表面化した形である(`rest`のときと同じ現象)。
計器(`GC_PROTECT`検査・LIFO検査)を無効にしても再現するので、計器のせいではない。

### 断念行4711は起点ではない

`za.c:4711` は `za_compile_body_forms` が0を返したときの伝播点にすぎず、
`ZA_BAIL_LINE()` は最初の1回だけを記録する設計なので、
**本当の起点には計器が入っていない**ということを意味する。
`za_try_compile_defun` の失敗パスだけに絞った計器化(`c3da14e`)では足りない。
起点を出すには `za_compile_body_forms` 以下の失敗経路へ計器を広げる必要がある。


## 計器が対象を数十倍遅くしていた: `cleanup`ハンドラと`__builtin_return_address`

第0部で入れた計器のうち2つが、**JITコンパイルを数秒から数分へ悪化させていた**。
どちらも「検出は正しいが、対象の実行時間を変えてしまう」形である。

| 計器 | 何が起きたか | 対処 |
|---|---|---|
| `gc_unprotect_node` のLIFO検査 | このハンドラは`cleanup`属性で、**GC_PROTECTを使う全関数のスコープ脱出**に現れる。ここへ関数呼び出しを置くとインライン展開が効かなくなる | カウンタ変数を直接インクリメントし、ハンドラを自明なまま保つ |
| `GC_PROTECT` の `__builtin_return_address(0)` | GC_PROTECTを含む**全関数**がフレームポインタを保持させられる。実行時スイッチで無効にしてもbuiltin自体は展開されるので効かない | `__FILE__`/`__LINE__` にする。逆引きが要らず読みやすくもなる |

切り分けには**ビルドと測定スクリプトを同時に変えない**ことが要った。
一度この2つを同時に変えてしまい、原因の切り分けが1周ぶん無駄になっている。

修正後、同じ測定が4分42秒(タイムアウト)から**3.9秒**になった。

## JIT断念の起点には計器が入っていない(指示書 第5部 3-5)

断念行を1つしか持たない設計では、記録されるのは伝播点である。最初のN件を順に残す
形(`%%DIAG-ZA-BAIL-COUNT` / `%%DIAG-ZA-BAIL-AT`)にして測り直したが、
N=200(GC 1回)で得られた連鎖は**2件だけ**だった。

```
#r n200 compiled=NIL gc=1 count=2 first=4739
#chain 4739 5085
```

4739は`za_compile_body_forms`が0を返したときの伝播、5085はその外側である。
**つまり本当の起点は依然として計器の外にある。**

一括で計器を広げるのは誤りだった。`za_compile_fold`/`za_compile_binary`/
`za_compile_unary` の `return 0;` は「この特化経路は当てはまらない」という
**正常な否定**であって断念ではない。84箇所へ機械的に入れたところ、正常経路を
断念として拾う形になった(`documents/pitfalls.md` 原則6の実例そのもので、
同じ誤りを2度繰り返したことになる)。

起点を出すには、`return 0;` を1つずつ「失敗」か「否定」かで分類する必要がある。
現状の44箇所は分類済みのものだけである。


## 「GC圧力でJITが失敗する」の真因: za.c のコンパイル経路全体がGC非安全

指示書の順序に従い、まず**gc=1の実行での stale 検出数**を見た。安く、方向が決まる。

既存のログには無かった(JITを走らせた測定と stale を数えた測定が別々だった)ので
1回測った。結果:

| 強制GC間隔 | JIT | GC回数 | 保護時stale | 範囲検査 | トラップ読み |
|---|---|---|---|---|---|
| なし | T | 0 | 0 | 0 | 0 |
| 200 | T | **0** | 0 | 0 | 0 |
| 100 | **NIL** | **1** | **4** | **2** | **3** |

**検出は出ている。** 失敗する実行でだけ出る。方向は決まった —
テーブルの枯渇でも飽和でもなく、**保護漏れ**である。
GC 1回=奇数世代なので、範囲検査も偶奇汚染を受けない条件で一致している。

### 起点を1フレームずつ潰すと、そのたびに1つ上のフレームへ移る

| 修正 | 検出箇所 |
|---|---|
| (未修正) | `eval.c:81` = `make_interpreted_function`の`GC_PROTECT(params)` |
| `eval_defun`の`params`/`body`、`za_try_compile_defun`の`params`/`env`/`form`を保護 | 保護時stale 4→**0**。読み出し側は `za_compile_body_forms+0xaa/+0xb5` に残る |
| `za_compile_body_forms`の`rest`/`params`/`env`を保護 | 保護時stale が **`za.c:3725`/`3727`(いま足した`GC_PROTECT`自身)** に出る = `forms`と`env`が**入ってきた時点で既にstale** |

つまり `za_compile_expr` 以下の呼び出し元が、ASTと`env`を確保を跨いで保護せずに
持っている。**1つ直すと検出が1フレーム上へ移るだけ**で、JIT失敗自体は消えない。

### 結論: これは局所修正ではなくza.c全体の作業である

`za.c` のコンパイル経路は、AST走査とenvの保持についてGC安全に書かれていない。
これまで問題にならなかったのは、**コンパイル中にGCが実質的に発火しなかった**
からである。判定基準を当てると、各`za_compile_*`が

- 仮引数の `params` / `env`(下位のコンパイルを跨いで再使用する)
- リスト走査の作業変数(`for`の初期化子で宣言されているものは`while`へ展開が要る)

を保護する必要がある。数十関数に及ぶ。

### 副次的な結論: `return 0;` のセンチネル分離は優先度が下がった

断念行の計器は「どこで諦めたか」しか出さない。いま効いているのは
**GC_PROTECT時のstale検査**で、こちらは`__FILE__`/`__LINE__`でソース位置を直接出す。
`return 0;` を1つずつ「失敗」か「否定」かに分類する作業は、真因の特定には
もう要らない(修正が進んで検出が消えた後、残った失敗を追うときに価値が戻る)。


## `za.c` のGC安全化(指示書 第2部・第3部)

### 第0部: 測定軸を GC 回数に入れ替えた

`N`(強制GC間隔)は操作量にすぎず、同じ `N` でも計器の増減で実行速度が変わると
GC 回数が変わる。**主キーは GC 回数にする。**

`c3da14e` の「N=200でT、N=50でNIL」という表は**破棄した**。計器の追加・除去と
保護修正を経た現在とは条件が違い、比較に使えない。累積説も死んでいるため、
第5部(累積的破壊の再測定)は項目ごと不要になった。

### 第1部: コンパイル1回あたりの確保量

| AST | 確保量 |
|---|---|
| `labels`+`let` 1個 | 2,288 byte |
| 同 4束縛×2呼び出し | 3,152 byte |
| `labels` 3個 | 5,392 byte |

AST サイズに比例し、数KBに収まる。「コンパイル中は GC を走らせない」という別解は
技術的には成立する。ただし判定基準上 `za.c` は不正なままで、将来 GC を走らせたく
なったときに同じ場所へ戻る。**35関数という規模が現実的だったため、正攻法を採った。**

### 第2部: 何を洗ったか

`za_*` 関数 90個のうち、確保に到達しうるものを推移閉包で求めて **35個**。そのうち

| 対象 | 件数 |
|---|---|
| 仮引数(`params`/`env`/`form` 等) | 25関数・48箇所 |
| リスト走査の作業変数 | 6箇所 |
| 中間ローカル | 49箇所 |

`GC_PROTECT` は 35箇所 → **145箇所**になった。

**保護不要と判定したもの**: 確保に到達しない55関数(オフセット計算、`jit_*` の
コード生成、`za_local_lookup` 等の探索)。これらは `lisp_val_t` を確保点を跨いで
持たない。

### 作業中に分かった2つの落とし穴

**1. 保護は「最初の確保点より前」に置かなければ意味がない。**
`za_rewrite_fn_refs` は `form`/`env` を保護していたが、**位置が `za_macroexpand`
(確保する)の後ろ**だった。実測で、ここを通った後に `os_get_function` が stale な
`env` を読んで GP 例外になっていた。保護の有無だけを見る検査では見落とす。

**2. `for` の初期化子から宣言を外へ出すと、無関係な箇所と組み合わせてハングする。**
走査変数を保護するために `for (lisp_val_t rest = ...)` を
`lisp_val_t rest = ...; GC_PROTECT(rest); for (; ...)` へ展開したところ、
**単独では通るのに2箇所を同時に適用するとブートが終わらなくなった**(7.2秒 → 90秒超で
打ち切り、CPU例外もパニックも出ない)。原因は未解明だが、スコープを変えない形

```c
for (lisp_val_t rest = X; COND; rest = cc_cdr(rest)) {
    GC_PROTECT(rest);   /* 本体先頭。stepのcc_cdrは確保を伴わない */
```

に変えたところ解消した。**保護を足すときはスコープを変えないこと。**

### 第3部: 測定結果(主キー = GC回数)

| GC回数 | JITコンパイル | 保護時stale | 範囲検査 | トラップ読み |
|---|---|---|---|---|
| 0 | T | 0 | 0 | 0 |
| 1 | **T**(修正前は NIL) | 0 | 0 | 0 |
| 5 | **T** | 0 | 0 | 0 |
| 18 | **T** | 0 | 0 | 0 |

**「GC が 1 回でも起きると JIT コンパイルが失敗する」は解消した。** 18回跨いでも
成功し、3つの計器すべてが 0 である。

この 0 が意味するのは **「GC 1世代ぶんの stale が無かった」まで**である。塗り潰しは
旧From空間を塗るが、そこは次のGCのコピー先になるため、2世代以上前の stale は
検出できない(世代限界)。無罪の証明には第4部のアンマップ方式が要る。

### 残った本物のバグ: コンパイルは通るが生成コードが動かない

`gc=1` を跨いでコンパイルされた関数は `%%ZA-COMPILED-P` が T を返すのに、
**呼び出すと `EVAL-ERROR` になる**(再現性あり)。`gc=0`・`gc=5`・`gc=18` のものは
正しく動く。

修正前は「コンパイルに失敗 → インタプリタへフォールバック」だったので動いていた。
いまは「コンパイルに成功 → 生成コードが壊れている」に変わっている。
**これは改善ではなく、別のバグを露出させただけである。**

コンパイル中の stale 読み出しは 0 なので、AST を読み違えたのではない。
生成コードが焼き込んだ何か(Function Cell アドレス、`za_fn_meta_t`)が GC の
再配置に追随していない疑いが強い。`d23022e` の per-call-site Function Cell
アドレスキャッシュは、まさにこの条件で落ちる設計である。

なお、この症状は第4部 4-4 の 2×2 表の「インライン化あり・env保護あり → EVAL-ERROR」
と同じ現れ方をしている。同じ原因である可能性がある。

### `za_analyze_var_usage` は未修正のまま残した

このAST解析関数は `za_macroexpand`(確保する)を呼び、`lambda_vars`/`lambda_body` 等の
中間ローカルがその後の再帰呼び出しを跨ぐため、判定基準上は保護が要る。

しかし**中間ローカル7箇所を保護するとブートが7.2秒から90秒超になる**(打ち切り)。
1サブフォームごとに呼ばれる深い再帰で、フレームあたりのコストに極端に敏感である。
他の49箇所を入れても7.2秒のままなので、この関数固有の性質である。

**既知の保護漏れとして残す。** 第3部の測定で検出されなかったのは、この経路で
GC が起きなかっただけかもしれない。

### 性能への影響: 退行なし(指示書 第3部 3)

`GC_PROTECT` を 35→145箇所に増やしたため、実行時コストの退行を確認した。
**デバッグ機構は無効にして**傾き法で全10カテゴリを測った。

| カテゴリ | Phase 4完了後 | 今回(za.c GC安全化後) | 差 |
|---|---|---|---|
| `branch` | 463.86 | 468.09 | +0.9% |
| `vector` | 462.06 | 456.72 | -1.2% |
| `let` | 355.62 | 358.06 | +0.7% |
| `cons` | 280.93 | 283.44 | +0.9% |
| `nontailrec` | 238.02 | 239.36 | +0.6% |
| `tailrec` | 231.68 | 219.82 | -5.1% |
| `funcall` | 196.88 | 196.05 | -0.4% |
| `for` | 157.98 | 156.54 | -0.9% |
| `arith` | 142.20 | 143.97 | +1.2% |
| `loop` | 104.85 | 104.99 | +0.1% |

`tailrec` の −5.1% 以外はすべて ±1.2% 以内で、測定ノイズの範囲である。**退行はない。**

これは予想どおりである。`za.c` は **JIT コンパイラ本体**であり、動くのは `defun` の
時点だけで、ベンチマークのループ内では1命令も実行されない。ベンチマークが測って
いるのは AOT 経路(`lisp_compiled.c`)で、そこは今回の変更に含まれない。

言い換えると、**この保護追加のコストはコンパイル時にしか出ない。**
ブート時間も 7.2秒 のまま変わっていない(145箇所を入れた後の実測)。

## JIT生成コードのEVAL-ERROR: 真因はスコープ構造体の中のシンボルだった(指示書 第0部・第1部)

### 生成コードを直接読んで確定させた

これまで観測してきたのはすべてC側の状態(`GC_PROTECT`に渡した値、`cc_car`が読んだ値、
範囲検査)で、**コードバッファに書き出された即値を読んだことは一度もなかった**。
第0部でそこを直接見た。

`%%DIAG-ZA-CODE-ADDR`/`-LEN`/`-SCAN`/`-IMM-OFF`/`-IMM-VAL`/`-IMM-REGION`/`-CODE-BYTE`
を追加し、`os_addr_region`(0=From空間 1=To空間 2=Immobilized 4=その他)で
即値ごとに所属領域を判定できるようにした。

### (b) は否定された — 生成コードはヒープアドレスを焼き込んでいない

同じバッファをGCの前後で2回読んだ。

| | 長さ | 即値 | From空間を指す即値 | 呼び出し |
|---|---|---|---|---|
| コンパイル直後 | 1580 byte | 52 | **0** | 5 |
| GC 23回後 | 1580 byte | 52 | **0** | 5 |

バッファはバイト単位で同一、From空間を指す即値は0。**コンパイル後のGCでは壊れない。**
`za.c`はリテラルを`g_za_quote_slots`等の静的スロット経由(`os_gc_register_root`済み)で
参照しており、この点は正しく設計されている。

### (a) だった — ただし「値が古い」ではなく「形が違う」

同じ関数をGC 0回とGC 1回跨ぎでコンパイルして diff した。

| | 長さ | movabs即値 |
|---|---|---|
| GC 0回 | 1580 byte | 52 |
| GC 1回跨ぎ | **1635 byte** | **53** |

**構造そのものが違う。** 逆アセンブルの差分を取ると、オフセット0x3a8で

```
GC 0回:   movabs r11, <slot>        ; ローカル解決(直接スロットロード)
          mov    r13, [r11]
GC 1回:   movabs r14, <cache slot>  ; グローバル名解決(za_emit_fn_resolve_cached)
          mov    rax, [r14]
          test   r10, r10
          jne    ...                ; os_make_symbol → os_get_function_cell
```

`labels`の内側関数への呼び出しが、**ローカル解決からグローバル名解決に化けていた。**
`labels`の関数はgensymで束縛されているので実行時に名前で引けず、EVAL-ERRORになる。

### 真因: Cスタック上の構造体に置いたシンボルがstaleになる

`za_local_scope_t`/`za_fn_scope_t` はシンボルを構造体フィールドに持ち、ポインタ等価で
名前を引く。`GC_PROTECT`は変数を守る機構なのでフィールドには届かず、
`os_gc_register_root`はアドレス安定性を要求するのでCスタック上の構造体には使えない。

コンパイル中にGCが1回でも走るとこれらがstaleになり、**エラーではなく「その名前は
無い」というもっともらしい結果**になる。`%%ZA-COMPILED-P`はTを返すので、
コンパイルは成功したように見える。

修正には**既存の仕組みをそのまま使った**。`za.c`には既に
`za_gc_protect_batch_push`/`za_gc_protect_batch_cleanup`(配列要素を1個ずつ
shadow stackへ繋ぐヘルパー)があり、`za_compile_flet_labels`の`name_syms`等に
使われていた。**同じ問題に対する解法が既にあったのに、構造体フィールドには
適用されていなかった**というのが実態である。

最初は新しいマクロ(`GC_ROOT_BATCH`/`GC_ROOT_FIELD`)を足したが、同じ役割の機構が
2つ並ぶ形になり、通常ビルドで1620件中173件が壊れた。既存ヘルパーへ寄せて解消した。
**同型の機構を探さずに追加するとこうなる。**修正後、GC 1回跨ぎでコンパイルしたコードは**GC 0回のものと同じ1580 byte・
52即値**になり、呼び出しも正常になった。

### 第1部: 5通りの測定(軸はGC回数)

| # | コンパイル中 | コンパイル後 | compiled | 呼び出し |
|---|---|---|---|---|
| 1 | 0 | 0 | T | 5 |
| 2 | 0 | 21 | T | 5 |
| 3 | 0 | 37 | T | 5 |
| 5 | **1** | 0 | T | **5** |
| 6 | 0 | +2(累計) | — | 4関数すべて 5 |

**(b) は否定、(a) は解消。** コンパイル後に何回GCしても壊れない。

### 3つの計器がすべて0だった理由

このバグでstaleを読んでいたのは**JITが生成した機械語**であり、`cc_car`でも
`gc_copy_value`でも計器化されたCコードでもない。第3部で「3つの計器すべてが0」と
書いたが、**このバグについては何も言っていなかった。** 世代限界より、
「計器がCコードにしか入っていない」ことのほうが効いていた。

生成物を扱うコードを疑うときは、**生成物そのものを読む**必要がある。

## 検出機構を常時回す形にした(指示書 第2部 2-3)

原則8のバグクラス(生成コードに焼き込まれたアドレス)には守る機構が無い。
**検出を常時回す形にしておかないと omission list になる。**

`za_try_compile_defun` がコンパイルのたびに生成コードを走査し、
「GCで動く領域(From/To空間)を指す即値」を数えるようにした
(`%%ZA-HEAP-IMM-COUNT`、累計)。`test/lisp/za_code_imm_test.lisp` を
`make test-qemu` の試験列へ加え、ブート後およびlabels+let・quote付き関数を
新たにコンパイルした後も0であることを確認する(**1626件**に増えた)。

誤検出を避けるため、タグがヒープオブジェクトを表すもの(CONS/SYMBOL/STRING/INSTANCE)
に限って判定する。fixnum即値がたまたまヒープ範囲に落ちるのを拾わないためである。

### インライン展開の発火確認も常時テストにした

AOTの`let`インライナは`expand-let`の出力形にパターンマッチしている。マクロ側の
出力が変わるとインライナが**黙って発火しなくなり**、`let`が355から2,945へ戻る。
エラーにならずテストも通る(原則6の形)。

`make test-inline-expansion`(`tools/bench/check_inline_expansion.sh`)を追加し、
生成コードに`__inl_`が現れ、フォールバック経路の`os_make_lifted_closure`/
`primitive_funcall`が現れないことを確認する。現状は`__inl_=34`・他0で発火している。

## ガードページの導入と、閾値がすべて誤っていたこと(指示書 第0部)

### 実装

各プロセススタックの直下に**64KBのガード領域**を置き、未マップにした。
1ページでは大きなローカル配列を持つ関数がSPを一気に下げて跨いで着地しうるため、
広めに取る(`g_stacks[i] = [ガード64KB][実スタック256KB]`)。

UEFIの恒等マップは2MBページ(`%%DIAG-PAGE-LEVEL`が2を返す)なので、4KBページ512個へ
**分割**してからPresentを落とす。さらに**ページテーブル自体が書き込み保護されている**
(PDエントリへの書き込みが`error_code=0x3`の#PFになった)ため、CR0.WPをその間だけ
落とす必要がある。

境界の最初の書き込みで止まり、診断が読める。

```
!! CPU EXCEPTION vector=0x0E rsp=0x0D6D0000 cr2=0x0D6CFFF8
   ** STACK OVERFLOW: ガードページを踏んだ **
   stack=0x0D6D0000 guard=0x0D6C0000 guard_size=0x10000
```

`cr2`はスタック下端のちょうど8byte下、つまり最初の踏み越しで捕まっている。

### これまでの閾値はすべて誤っていた

| 深度 | 以前の理解 | 実測(ガードページ導入後) |
|---|---|---|
| 800 | 完走 | 完走 |
| **1000** | **完走** | **溢れる** |
| **2000** | **完走** | **溢れる** |
| 4000 | 溢れる | 溢れる |

真の閾値は **800と1000の間**(256KB ÷ 約900段 ≒ 290 byte/フレーム)。
深度1000・2000は完走していたのではなく、**検出されずに下のメモリを壊しながら
走っていた**だけである。値が正しく見えたのは、壊した先がたまたま使われて
いなかったからにすぎない。

### `nontailrec` 深度1000×1000回のハングが解決した

長らく真因未特定だった項目である。深度1000は閾値の上なので、**スタック溢れ**だった。
ガードページ導入後は診断付きの#PFになる。

かつて「フレームは160byteなので深度1000=160KB<256KBであり溢れない」として
スタック溢れ説を撤回したが、**その撤回自体が誤りだった。**

## 基準の取り直し(指示書 第1部)

### 7.2秒と3.2秒はビルドの違いだった

| ビルド | ブート | tick |
|---|---|---|
| 通常 | **3.235秒** | 41 |
| `GC_DEBUG` | **7.255秒** | 109 |

どちらも同一条件で正確に再現する。測定条件のドリフトではなく、
**私が異なるビルド間で比較していた**だけである。

### ビルド直後の初回実行は捨てなければならない

命令数の同一条件6回測定:

| 回 | 命令数 |
|---|---|
| 1〜6 | 1,120.2M / 1,119.4M / 1,117.2M / 1,120.4M / 1,119.5M / 1,120.3M |

なる(イメージ再生成やFATキャッシュの差と思われる)。

**この人工物を「保護追加のコスト+10.6%」と誤読していた。** ウォームアップを捨てて
測り直すと:

| | 中央値 |
|---|---|
| 保護なし | 1,119.9M |
