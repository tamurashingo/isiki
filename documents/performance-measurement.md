# isiki-osの性能測定手法

`feature/abi-redesign`でのJIT/AOT性能調査を通じて、以下の手法をそれぞれ
異なる場面で使い分けてきた。本書は、今後の性能調査(特にIDE/FAT I/Oの
命令数ベースでの追加最適化)で標準的に参照できるよう、各手法の特性・
使い分け・実際の使い方をまとめる。

## 手法の一覧と使い分け

| 手法 | 何を測るか | 長所 | 短所 | 主な用途 |
|---|---|---|---|---|
| ゲスト内tickカウンタ(`get-internal-real-time`) | 壁時計時間(10ms単位) | 実装が既にある、Lispコードから直接読める | タイマー割り込み自体のオーバーヘッドを含みうる、ホストのスケジューリングノイズの影響を受ける | 大まかな体感速度の比較、既存テストの回帰検知 |
| ホスト側`strace`(futex回数等) | ホストのシステムコール発行状況 | ホスト側のボトルネック(BQL競合等)の切り分けに使える | ノイズが非常に大きい(GC計装2回呼んだだけで速度が4-5倍変わった実例あり)。ホストの実行速度と相関するが厳密な指標ではない | QEMU/ホスト起因の外部要因を疑う初期切り分け段階のみ |
| **TCGプラグイン(命令数カウント)** | ゲストが実際に実行した命令数 | ホストの実行速度・スケジューリングノイズと無関係、高速(通常運転とほぼ同じ実時間) | 完全な決定論ではない(下記参照)、アドレス範囲を跨いだ内訳分離は追加の仕組みが要る | **実装変更の効果測定の主指標。以後はこれを既定の手法とする** |
| `-icount`(決定論的実行) | 命令数(TCGプラグインと同じ指標を、完全に再現性のある形で) | ビット単位で再現性がある(record/replayの基盤) | I/Oが絡む大きなワークロードは実時間で非常に遅い(実測: 通常数秒のN=1,000,000ループが3分強) | 小規模な決定論的A/B比較、TCGプラグインの結果に疑義がある場合のgold standard確認 |
| `-d in_asm,out_asm` | JIT/AOTが実際に生成した機械語 | 生成コードを直接目視確認できる | ログ量が膨大(ブートのみで53MB/145万行)、このホストのQEMUには逆アセンブラ(capstone等)が組み込まれておらず生バイト列(`OBJD-H:`/`OBJD-T:`)しか出力されない | 特定の生成コードパターンを直接確認したい場合(`-dfilter`でアドレス範囲を絞ることが前提) |

## 手法1: TCGプラグインによる命令数カウント

### 導入したプラグイン

`tools/plugins/isiki_instcount.c` — TB(translation block)ごとの命令数
(`qemu_plugin_tb_n_insns`)を、そのTBが実行されるたびに加算する方式。
1命令ごとのコールバックは極端に遅くなるため使わない。終了時に
stderrへ以下の形式で出力する:

```
[isiki_instcount] total_insns=<N>
```

オプション引数`start=0xADDR,end=0xADDR`で、その仮想アドレス範囲に含まれる
TBだけの命令数を`range_insns`として別集計できる(JIT生成コードはヒープ上の
動的アドレスのため主にAOT/C側の静的アドレスが既知な関数区間向け)。

### ビルドと使い方

`.so`はソースからのビルドを前提とし、git管理対象外(`tools/plugins/*.so`)。
`make test-qemu-instcount`が自動でビルドする(`isiki-builder`コンテナ内で
`libglib2.0-dev`をインストールし、ホストのQEMUバージョンに対応する
`qemu-plugin.h`をGitHubから取得してコンパイルする)。プラグインのABI
(`QEMU_PLUGIN_VERSION`)はヘッダとホストQEMU本体のバージョンが一致している
必要があるため、ホストのQEMUバージョンが`Makefile`の`QEMU_VERSION_FOR_PLUGIN`
(既定`10.2.1`)と異なる場合は`.envrc`等で上書きすること。

```
make test-qemu-instcount MILESTONE=test/lisp/qemu_boot_xxx.lisp [QEMU_DISK_IMG=...]
```

### 検証結果(2026-09-11、feature/icount-profiling)

**N-スケーリング(自己再帰ループのみ)**:

| N | total_insns | 起動オーバーヘッド差分 |
|---|---|---|
| 0(起動のみ) | 1,136,549,402 | - |
| 1,000,000 | 1,568,155,700 | 431,606,298 |
| 2,000,000 | 2,000,913,222 | 864,363,820 |

差分の比 864,363,820 / 431,606,298 = **2.0027**(理論値2.0とほぼ一致)。
1反復あたり約432命令(自己末尾呼び出しのトランポリン込み)。

**決定論性の検証(非icount、N=1,000,000を2回実行)**:

| 実行回 | total_insns |
|---|---|
| 1回目 | 1,568,878,009 |
| 2回目 | 1,568,731,913 |

差は146,096命令(**約0.0093%**)。通常のTCG実行(非icount)は、ブート時の
ACPI/PIT較正等の実時間依存ポーリングにより完全な決定論ではないが、
これまでのstrace/futexベースの計測(数倍単位の誤差)と比べれば
桁違いに小さいノイズである。実装変更の効果測定(通常は数%〜数十%の
差を検出したい)には十分な精度がある。

**IDE(FAT16)1MB読み込みの命令数**(ホスト側で事前にファイルを配置した
ディスクイメージを使い、書き込み側の影響を排除):

| 計測 | total_insns |
|---|---|
| 起動+mountのみ | 1,118,654,248 |
| 起動+mount+1MB読み込み | 3,671,343,591 |
| **読み込み自体の差分** | **2,552,689,343** |

1MBの読み込みに約**25.5億命令**。tickカウンタでの実測(31.28秒)と
組み合わせると、この区間のゲスト実行速度は約8,160万命令/秒
(2,552,689,343 / 31.28)であり、TCGの命令ディスパッチ自体が極端に遅い
わけではないことが分かる。**問題は1命令あたりのコストではなく、
1MBを読むのに要する命令の「絶対数」が大きいこと**を示しており、
今後の最適化(`insw`一括転送化・`READ MULTIPLE`対応等)の効果を
測る際は、この2,552,689,343を基準値として比較する。

## 手法2: `-icount`(決定論的実行モード)

```
make test-qemu-icount MILESTONE=test/lisp/qemu_boot_xxx.lisp [ICOUNT_SHIFT=N]
```

`-icount shift=auto`は本環境ではハング(または極端な遅延)を起こしたため、
固定`shift`値(既定7)を使うこと。マルチスレッドTCGと非互換のため
`-accel tcg,thread=single`もあわせて指定する(`test-qemu-icount`ターゲットが
自動で付与する)。

I/Oが絡む大きなワークロードは実時間で非常に遅い。N=1,000,000の自己再帰
ループ(通常運転なら3〜4秒)が**3分強**かかった実測がある。そのため、
日常的な計測には向かず、以下のような場合にのみ使う:

- TCGプラグインの結果(通常運転)に予期しない大きなばらつきが出て、
  実装のバグなのか、単なる実時間依存ポーリングのノイズなのかを
  切り分けたい場合。
- 極めて小さな実装差分(命令数で1%未満の変化)を、ノイズに埋もれず
  検出したい場合。

## 手法3: `-d in_asm,out_asm` + `-dfilter`

```
qemu-system-x86_64 ... -dfilter <start>+<length> -d in_asm,out_asm -D <logfile>
```

`-dfilter`の範囲指定は`start-end`ではなく**`start+length`形式**(例:
`0x100000+0x100000`)であることに注意(`start-end`形式は`Invalid range`
エラーになる)。

このホストのQEMU(Ubuntu 26.04パッケージ版）には逆アセンブラ
(capstone等)が組み込まれておらず、`in_asm`/`out_asm`は実際のニーモニックの
代わりに生バイト列(`OBJD-H:`/`OBJD-T:`)を出力する。読める形にするには、
`OBJD-H:`行の16進バイト列を抽出し、`objdump -D -b binary -m i386:x86-64
-M intel`等の外部ツールで別途逆アセンブルする必要がある(本書執筆時点で
未実施、次のフォローアップ)。

フィルタなしでの`-d in_asm,out_asm`はログ量が膨大(ブートのみで約53MB・
145万行)なため、実運用では必ず`-dfilter`でアドレス範囲を絞ること。
JIT生成コードはヒープ上の動的アドレスのため、対象アドレス範囲は実行時に
Lisp側から(例えば`%%za-compiled-p`が返す関数オブジェクトの生ポインタ等を
介して)取得する仕組みが別途必要になる(未実装、フォローアップ)。

## IDE読み込みの命令数内訳: ide.c単独 vs それ以外(2026-09-11)

「1MB=2048セクタ、約25.5億命令」という総数は、`ide_wait_drq`のポーリング
(1セクタあたり平均約156回)やデータ転送ループ(`inw`約256回/セクタ)だけを
素朴に足しても到底説明がつかない規模(1セクタあたり約124万命令)だった
ため、まず「`drivers/ide.c`内のコード(ポーリング+データ転送)」対
「それ以外(FAT層のクラスタチェイン走査+Lispランタイム)」という大枠を
切り分けた。

### アドレス範囲の特定方法

1. ビルド成果物(`esp_dir/EFI/BOOT/BOOTX64.EFI`、mingw-gccがリンクした
   PE形式)のシンボルテーブルを`x86_64-w64-mingw32-objdump -t`で読み、
   `drivers/ide.c`内の関数群(`set_err`/`ide_setup_lba`/
   `ide_delay400ns`/`ide_wait_drq`/`ide_wait_not_busy`/
   `os_ide_identify`/`os_ide_read_sectors`/`os_ide_write_sectors`)が
   連続領域(ファイル上の相対仮想アドレス、RVA)に配置されていることを
   確認した(`0x1a580`〜`0x1ab90`、1552byte、次のシンボルは
   `block_device.c`の`ide_bd_flush`で境界が明確)。
2. **【重要な落とし穴】** ファイル上のRVAは、UEFIローダが実際に
   イメージをロードする実行時ベースアドレスとは異なる。実行時ベース
   アドレスは起動のたびの再現性はある(同一ディスク構成で2回検証し
   一致を確認)一方、**アタッチするディスクイメージの構成(サイズ・
   パーティション形式の違い)によって変わる**ことを実測で発見した
   (デフォルトの`tmp/ide_disk.img`では`os_ide_read_sectors`の実行時
   アドレスが`0xD3AE8ED`だったのに対し、計測用に用意した16MB FAT16
   単純フォーマットのディスクでは`0xCF2D8ED`と異なっていた。原因は
   未特定だが、OVMFのイメージロード時のメモリ配置がディスク構成に
   影響される何らかの経路があると見られる)。このズレに気づかず
   デフォルト構成で計算したアドレス範囲を別のディスク構成の計測に
   流用した結果、最初の試行は`range_insns=0`という誤った結果になった。
   **教訓: アドレス範囲は必ず計測対象と全く同じQEMUコマンドライン
   (同じディスクイメージ)で実測してから使うこと。**
3. 実行時アドレスの取得には、`os_ide_read_sectors`(externリンケージ、
   `drivers/ide.h`で宣言済み)のポインタ値をそのまま返す診断用組み込み
   関数`%%DIAG-IDE-READ-SECTORS-ADDR`(`src/c/ide_subprimitive.c`の
   `cc_diag_ide_read_sectors_addr`)を追加し、Lisp側から
   `(%%diag-ide-read-sectors-addr)`で取得した。実行時アドレス−該当
   関数のファイルRVA=実行時ベースアドレス、という式で、`ide.c`クラスタ
   全体の実行時アドレス範囲を計算できる。

### 計測結果(1MB、FAT16、事前配置イメージで書き込み側を排除)

| 区分 | 命令数 | 全体に占める割合 |
|---|---|---|
| 総命令数(1MB読み込み自体、mountのみとの差分) | 2,581,582,199 | 100% |
| `ide.c`単独(ポーリング+データ転送、TCGプラグインのアドレス範囲指定で分離) | 9,500,016 | **0.368%** |
| それ以外(FAT層+Lispランタイム、差分) | 2,572,082,183 | **99.632%** |

1セクタ(512byte、2048セクタ/MB)あたりに換算すると、全体約132万命令の
うち`ide.c`が占めるのはわずか約4,864命令(先述の「ポーリング約156回+
inw約256回」という素朴な見積もりのオーダーとおおむね整合する)。
**残り約131.7万命令/セクタが「それ以外」に費やされている**ことになり、
支配的なボトルネックは`ide.c`(PIO層)ではなく、FAT層のクラスタチェイン
走査またはLispランタイム(AOT生成コード)側にあることが定量的に確定した。

### 判定と次の一手

「`ide.c`側が支配的であれば`insw`一括転送化・`READ MULTIPLE`対応に進む、
FAT層側が支配的であればそちらを優先する」という当初の判定基準に照らし、
**FAT層側が圧倒的に支配的(99.6%)** という結果になった。したがって
`insw`一括転送化・`READ MULTIPLE`対応は保留とし、次のフォローアップの
最優先事項を以下に変更する:

- `fat16-read-file`(または`read-file-into-vector`が最終的に呼ぶ
  `read-into!`経由の経路)が、クラスタ1個(または1セクタ)ごとに何らかの
  シンボル解決・関数呼び出しのオーバーヘッドを負っていないか。今回
  (`feature/abi-redesign`)のfn解決キャッシュ化(`za_compile_call`)は
  JITコンパイル済みのユーザー定義関数呼び出しが対象であり、`read-into!`/
  `write-from!`はILOSの総称関数(`defmethod`経由、M10クロージャリフティング
  でコンパイル)であるため、**この恩恵を受けていない可能性がある**。
  `(print (function read-into!))`等で`#<FUNCTION-COMPILED ...>`/
  `#<FUNCTION-INTERPRETED ...>`のいずれかを確認し、インタプリタ経由の
  ままになっていないかをまず確認する。
- 1セクタあたり約131.7万命令という規模感から、単純な「シンボル解決の
  やり残し」だけでは説明しきれない可能性もあるため、`-dfilter`+
  TCGプラグインのアドレス範囲指定を使い、AOT側の静的アドレスが既知な
  FAT層の関数(`%fat16-read-lba-list`/`fat16-fat-entry`等)の寄与も
  同じ手法でさらに分離することを検討する。

## FAT層側(read-into!)の命令数内訳: ILOS総称関数ディスパッチの精査(2026-09-11)

前節の切り分けで「FAT層+Lispランタイム」が全体の99.632%を占めることが
判明したため、次に**ILOS総称関数(`read-into!`)のディスパッチ処理**が
支配的かどうかを検証した。結論から言うと**ディスパッチは無視できるほど
軽微であり、真因は別の場所(`read-file-into-vector`のAOT生成コード自体の
呼び出し規約オーバーヘッド)にあった**。

### 1. ディスパッチ機構の実装確認(コードレビュー)

`src/lisp/init.lisp`/`src/lisp/init_aot.lisp`を確認したところ、`defgeneric`は
`(defun name (&rest args) (%generic-call 'name args))`という`&rest`関数に
展開され、`%generic-call`は毎回:

```lisp
(defun %generic-call (name args)
  (%invoke-method-chain (%order-methods (%applicable-methods name args)) args))
```

を実行する。`%applicable-methods`は`*generic-methods*`をname(gf名)で`assoc`
線形走査し、見つかった全メソッドに対し`subclassp`判定を行い、
`%order-methods`は挿入ソート(毎回)、`%invoke-method-chain`は
`unwind-protect`+動的変数の退避/復元を伴う。**メソッド解決結果のキャッシュは
一切無い**——コードだけを見れば、以前の`os_make_symbol`線形走査と同種の
ホットスポットに見えた。

### 2. 実測: ディスパッチは全体の0.0004%に過ぎない

`subclassp`/`class-of`/`%find-generic-methods`/`%method-applicable-p`/
`%specializers-applicable-p`/`%filter-applicable-methods`/
`%applicable-methods`/`%order-methods`/`%invoke-method-chain`/
`%generic-call`等、ディスパッチ機構一式がリンク後のバイナリで連続領域
(ファイルRVA `0x52600`〜`0x631cb`)を構成していることを確認し、TCGプラグインの
アドレス範囲指定でこの区間だけの命令数を計測したところ:

| 計測 | 命令数 |
|---|---|
| 起動+mountのみ | 20,271 |
| 起動+mount+1MB読み込み | 30,427 |
| **ディスパッチ機構自体の差分** | **10,156(全体の0.0004%)** |

`*generic-methods*`に登録される総称関数・メソッドの実数が(システム全体で
`initialize-object`/`report-condition`/`read-into!`/`write-from!`等)数個〜
十数個程度にとどまるため、「線形走査」自体はO(1000)級の`os_make_symbol`とは
規模が全く異なり、実害が無いレベルだった。**コードの見た目上の懸念(未
キャッシュの線形探索)が、実際のボトルネックとは限らない**という、本調査
全体を通じて繰り返し現れているパターンがここでも再現した。

### 3. 落とし穴: __step(consリストABI)ではなく__step_fixed(固定引数ABI)を測るべきだった

「メソッド本体(クラスタチェイン走査)」の候補として`%fat16-read-into-impl`
(`lisp_ll_fat16_read_into_impl__step`)のアドレス範囲を計測したところ
`range_insns=0`という結果になった。TBダンプで直接確認したところ、実行時に
このアドレス範囲へは一切到達していなかった。原因は、ABI-M6(AOT-to-AOT
静的呼び出しの固定引数ABI化)により、`defmethod`本体のクロージャから
`%fat16-read-into-impl`への呼び出しが実際には**consリストABI版
(`__step`)ではなく固定引数ABI版(`__step_fixed`)**を使っていたため。
`__step_fixed`(ファイルRVA `0xdbd83`)を測り直しても、やはり
`range_insns=0`だった。

### 4. 方針転換: アドレス範囲の事前予想をやめ、プラグインに実測プロファイラ機能を追加

2回連続で「予想したアドレス範囲に実行が無い」という結果になったため、
`tools/plugins/isiki_instcount.c`に`profile=1`オプションを追加した。TB単位で
(開始アドレス, 命令数, 実行回数)を記録し、終了時に「命令数×実行回数」
降順でtop 40件を出力する機能で、アドレス範囲を静的に予想する代わりに
**実際にホットな箇所を直接発見する**アプローチに切り替えた。

### 5. 実測結果: 真因は`read-file-into-vector`のAOT呼び出し規約オーバーヘッド

1MB読み込みベンチマークをプロファイルし、top 40のホットTBをシンボルに
対応付けたところ(top 40だけで全体2,566,285,269命令のうち
1,777,902,294命令≒69.3%を説明):

| シンボル | 命令数(top40内) | 割合 |
|---|---|---|
| `get_current_process` | 526,208,500 | 29.6% |
| `is_control_transfer`/`os_is_control_transfer`(合算) | 484,457,888 | 27.3% |
| `primitive_add2` | 121,852,560 | 6.9% |
| `primitive_set_elt_impl` | 108,880,356 | 6.1% |
| `number_compare` | 81,950,954 | 4.6% |
| `is_vector`/`is_float`(合算) | 70,680,930 | 4.0% |
| `strncmpignorecase` | 16,215,168 | 0.9% |
| `primitive_less_than2` | 15,156,140 | 0.9% |
| `primitive_create_vector` | 15,112,240 | 0.9% |
| `os_stream_read_char` | 13,719,810 | 0.8% |

`get_current_process`は1MB(1,000,000byte)に対し**105,241,700回**呼ばれて
いた(1byteあたり約105回)。実装自体はO(1)(`&g_processes[g_current_
process_index]`、配列添字アクセス)だが、`GC_PROTECT`マクロが1回につき
`get_current_process()`を2回呼ぶ(初期化子と代入)ため、**呼び出し回数の
絶対数**がボトルネックになっている。`is_control_transfer`/
`os_is_control_transfer`も同様に、`transpile-call-args-guarded`が生成する
「引数を1つ評価するたびにGC_PROTECTし、非局所脱出シグナルでないか
チェックする」というAOTの安全側ガード付き呼び出しパターインが、1byteの
読み込み・書き込みという極めて軽い操作に対しても律儀に発行され続けて
いることを示している。

### 判定

「ディスパッチ処理が支配的」でも「メソッド本体(クラスタチェイン走査)が
支配的」でもなく、**`read-file-into-vector`のAOT生成コード自体(1byte
ずつの`read-byte`/`set-elt`呼び出しループ)が、za.cのJITには既に適用済み
(Phase1/Phase2、documents/abi-redesign.md参照)のような「非アロケーション
演算のGC_PROTECT省略」「fixnum算術のインライン化」を一切受けていない**
ことが真因と判明した。次のアクションとして、za.cのPhase1/Phase2と同種の
最適化(leaf判定によるGC_PROTECT省略、`+`/`<`等の単純演算のインライン化)を
AOTトランスパイラ(`transpile.lisp`)側にも適用することを、新しい
マイルストンとして提案する(本書の範囲外、別途指示書で計画する)。
