# 既知の課題: ネスト 79 段で JIT コンパイルが返ってこなくなる(コンパイル時スタック枯渇)

> 観測日: 2026-09-15 / ブランチ: `feature/frame-separation`
> **優先度: 低から引き上げ。** 当初「深いネストは重い」と見ていたが、実際は
> **79 段ちょうどで落ちる崖**であり、原因はネストの重さではなく
> **コンパイル時の C スタック枯渇**とほぼ確定した(下記)。
> 閾値は `if` に固有ではなく `za_compile_expr` の再帰段数で決まるので、
> **別の形のコードでも同じ段数で踏む。**

## 症状

`(if (cc) 1 (if (cc) 1 ...))` の形で `if` を深くネストした `defun` を評価すると、
**79 段から JIT コンパイルが返ってこなくなる**(QEMU は生きたままで、テスト出力が
そこで途切れる)。

- **78 段までは 80ms 以内に完了する**
- **79 段は返ってこない**(1プロセスで昇順に流し、78 段まで出力して 79 段で停止)
- 80 / 100 / 150 段も同様(それぞれ 700 / 1200 / 約300 秒で打ち切り)

**曲線ではなく崖である。** 78 段(8 tick)と 79 段(未完了)の間で不連続に落ちる。
78 段まで所要時間は 4〜8 tick で横ばいのままで、負荷曲線には一切乗っていない。

## 段数と所要時間・生成コード長

`defun`(= JIT コンパイル)の所要時間と、`%%DIAG-ZA-CODE-LEN`(直近の生成コード長)を
1段刻みで測った。tick は 10ms 単位(`internal-time-units-per-second` = 100)。

| 段数 | defun (tick) | 生成コード長 (byte) | JIT |
|---|---|---|---|
| 1 | 0 | 989 | 完了 |
| 20 | 0 | 14,118 | 完了 |
| 40 | 4 | 27,938 | 完了 |
| 60 | 4 | 41,758 | 完了 |
| 70 | 8 | 48,668 | 完了 |
| 71 | 4 | 49,359 | 完了 |
| 72 | 8 | 50,050 | 完了 |
| 73 | 4 | 50,741 | 完了 |
| 74 | 8 | 51,432 | 完了 |
| 75 | 4 | 52,123 | 完了 |
| 76 | 8 | 52,814 | 完了 |
| 77 | 4 | 53,505 | 完了 |
| **78** | **8** | **54,196** | 完了 |
| **79** | **未完了** | — | **返ってこない** |

**生成コード長は完全に線形で、崖の直前まで 691 byte/段ちょうど**(1段→78段の全区間で
誤差ゼロ)。79 段の推定値は 54,887 byte で、`JIT_CODE_SIZE`(524,288)には遠く届かない。
**生成結果側には不連続が無い**ので、これはコンパイル過程だけの問題であり、
正しさの問題には化けない。

計測は `feature/frame-separation`、既定メモリ、1プロセスで昇順に流して各段で
`finish-output` している(ハングした段の手前まで必ず残る形)。

## 再現手順

```python
def nested_if(n):
    s = "0"
    for _ in range(n):
        s = "(if (cc) 1 %s)" % s
    return s
```

```lisp
(defun cc () 1)
(defun deep () <nested_if(80)>)
(format *isiki-test-stream* "compiled=~S~%" (%%za-compiled-p (function deep)))
```

を `test/lisp/` に置き、`make test-qemu-milestone MILESTONE=<boot-entry>` で読み込ませる。

## 原因: コンパイル時の C スタック枯渇(ほぼ確定)

`za_compile_expr` は `if` の各段で自分自身を再帰呼び出しするが、**1フレームが 3,184 byte**
ある(`sub $0xc38,%rsp` = 3,128 byte + callee-saved の push 6 本 48 byte + 戻り番地 8 byte。
`x86_64-w64-mingw32-objdump -d tmp/za.o` で確認)。
一方プロセススタックは **256KB**(`STACK_SIZE`、`process.c:27`)。

```
262,144 / 3,184 = 82.3 段
```

再帰だけで使い切る段数が 82。実際にはこの上に `os_eval` →
`za_try_compile_defun`(840 byte)…という呼び出し鎖があり、下にも
`za_compile_call`(744 byte)等のリーフが乗るので、**実効上限が 79 段に落ちるのは
数字として合う**。

| 段数 | 再帰だけの消費 | 256KB の残り |
|---|---|---|
| 75 | 238,800 byte | 23,344 byte |
| 78 | 248,352 byte | 13,792 byte |
| **79** | **251,536 byte** | **10,608 byte** |
| 80 | 254,720 byte | 7,424 byte |

### これが意味すること

- **`if` に固有の問題ではない。** 閾値は `za_compile_expr` の**再帰段数**で決まるので、
  ネストできる構文であれば何でも同じ 79 段付近で踏む。
  「実コードは 70 段ネストを書かないから無関係」とは言えない
- **1フレーム 3,128 byte は大きい。** `za_compile_expr` がローカルに大きな配列を
  持っていることを示唆する。ここを削れば上限は比例して伸びる
- **溢れた後の振る舞いが「返ってこない」になっている。** ガードページは
  `unmap_range` で張られている(`process.c:142`)ので #PF にはなるはずだが、
  テスト出力には何のメッセージも出ないまま止まる。
  タイマ割り込みによるカナリア検査(`process.c:209` 付近)も、
  この場合に何を出すのか未確認

### 調べて外れたもの(確認済み)

- **disp8 → disp32 の収束ループではない。** za.c が発行する分岐は
  `jit_emit_{je,jmp,jne,js,jb}_rel32_placeholder` の5種のみで、**rel8 を出す箇所が
  1つも無い**(`0xEB` / `0x7x` の発行なし)。命令長が固定なのでパッチで後続の
  オフセットがずれることが無く、再計算を繰り返す実装にはなっていない
- **コード生成バッファの上限・やり直しではない。** 79 段の推定生成長 54,887 byte は
  `JIT_CODE_SIZE`(524,288、`za.c:105`)の 10% で、まだ遠い。
  生成コード長が 691 byte/段で完全に線形なことも、やり直しが起きていない傍証
- **固定長テーブルの溢れではない。** `ZA_MAX_JIT_RELOCS`(128、`za.c:285-290`)、
  `ZA_MAX_TRAMPOLINE_JMPS`(128、`za.c:452`)、`ZA_MAX_LITERAL_SLOT_ALLOCS`
  (96、`za.c:265`)はいずれも書き込み前に境界検査し、超過時は `g_jit_overflow = 1` で
  グレースフルにフォールバックする。線形探索やリトライには落ちない。
  `ZA_MAX_FN_CELL_CACHE_SLOTS`(2048)は 79 段なら 79 スロットで足りている
- **ページ境界ではない。** 生成コード長は 20 段(14KB)の時点で既に何ページも
  またいでおり、そこで不連続は起きていない

### 残っている確認(未実施)

- 79 段を走らせたまま QEMU の gdb stub にアタッチし、rsp がガード領域に
  居ることを直接見る。これでスタック枯渇が**確定**する
- 溢れた時に何も出ないまま止まるのはなぜか(ガードページ #PF の扱い、
  カナリア検査の出力先)

### 直し方の候補

1. **`za_compile_expr` に再帰段数の上限を設ける**(`ZA_MAX_CALL_DEPTH` と同じ形)。
   超えたら `g_jit_overflow` 相当でインタプリタへグレースフルに落ちる。
   **崖を「静かに止まる」から「遅いが正しく動く」に変えるのが最優先**
2. `za_compile_expr` のフレーム 3,128 byte を削る。上限が比例して伸びる
3. スタック溢れの検出時に、せめて何が起きたかを出す
