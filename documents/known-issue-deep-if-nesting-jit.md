# 修正済み: ネスト 79 段で JIT コンパイルが C スタックを踏み越える

> 観測日: 2026-09-15 / **修正済み(2026-09-15、`feature/jit-compile-depth-limit`)**
>
> 当初「深いネストは重い」と見ていたが、実際は **79 段ちょうどで落ちる崖**で、
> 原因は **コンパイル時の C スタック枯渇**だった(因果テストと直接観測の両方で確定)。
> 閾値は `if` に固有ではなく `za_compile_expr` の再帰段数で決まるので、
> **別の形のコードでも同じ段数で踏む。**
>
> `za_compile_expr` に再帰段数の上限 `ZA_MAX_COMPILE_NEST`(60)を入れ、
> 超えたら JIT を断念してインタプリタへ落ちるようにした。

## 症状

`(if (cc) 1 (if (cc) 1 ...))` の形で `if` を深くネストした `defun` を評価すると、
**79 段から JIT コンパイルが返ってこなくなる**(QEMU は生きたままで、テスト出力が
そこで途切れる)。

- **78 段までは 80ms 以内に完了する**
- **79 段は返ってこない**(1プロセスで昇順に流し、78 段まで出力して 79 段で停止)
- 80 / 100 / 150 段も同様(それぞれ 700 / 1200 / 約300 秒で打ち切り)

**曲線ではなく崖である。** 78 段(8 tick)と 79 段(未完了)の間で不連続に落ちる。
78 段まで所要時間は 4〜8 tick で横ばいのままで、負荷曲線には一切乗っていない。

## 段数と所要時間・生成コード長

`defun`(= JIT コンパイル)の所要時間と、`%%DIAG-ZA-CODE-LEN`(直近の生成コード長)を
1段刻みで測った。tick は 10ms 単位(`internal-time-units-per-second` = 100)。

| 段数 | defun (tick) | 生成コード長 (byte) | JIT |
|---|---|---|---|
| 1 | 0 | 989 | 完了 |
| 20 | 0 | 14,118 | 完了 |
| 40 | 4 | 27,938 | 完了 |
| 60 | 4 | 41,758 | 完了 |
| 70 | 8 | 48,668 | 完了 |
| 71 | 4 | 49,359 | 完了 |
| 72 | 8 | 50,050 | 完了 |
| 73 | 4 | 50,741 | 完了 |
| 74 | 8 | 51,432 | 完了 |
| 75 | 4 | 52,123 | 完了 |
| 76 | 8 | 52,814 | 完了 |
| 77 | 4 | 53,505 | 完了 |
| **78** | **8** | **54,196** | 完了 |
| **79** | **未完了** | — | **返ってこない** |

**生成コード長は完全に線形で、崖の直前まで 691 byte/段ちょうど**(1段→78段の全区間で
誤差ゼロ)。79 段の推定値は 54,887 byte で、`JIT_CODE_SIZE`(524,288)には遠く届かない。
**生成結果側には不連続が無い**ので、これはコンパイル過程だけの問題であり、
正しさの問題には化けない。

計測は `feature/frame-separation`、既定メモリ、1プロセスで昇順に流して各段で
`finish-output` している(ハングした段の手前まで必ず残る形)。

## 再現手順

```python
def nested_if(n):
    s = "0"
    for _ in range(n):
        s = "(if (cc) 1 %s)" % s
    return s
```

```lisp
(defun cc () 1)
(defun deep () <nested_if(80)>)
(format *isiki-test-stream* "compiled=~S~%" (%%za-compiled-p (function deep)))
```

を `test/lisp/` に置き、`make test-qemu-milestone MILESTONE=<boot-entry>` で読み込ませる。

## 原因: コンパイル時の C スタック枯渇(確定)

`za_compile_expr` は `if` の各段で自分自身を再帰呼び出しするが、**1フレームが 3,184 byte**
ある(`sub $0xc38,%rsp` = 3,128 byte + callee-saved の push 6 本 48 byte + 戻り番地 8 byte。
`x86_64-w64-mingw32-objdump -d tmp/za.o` で確認)。
一方プロセススタックは **256KB**(`STACK_SIZE`、`process.c:27`)。

```
262,144 / 3,184 = 82.3 段
```

再帰だけで使い切る段数が 82。実際にはこの上に `os_eval` →
`za_try_compile_defun`(840 byte)…という呼び出し鎖があり、下にも
`za_compile_call`(744 byte)等のリーフが乗るので、**実効上限が 79 段に落ちるのは
数字として合う**。

| 段数 | 再帰だけの消費 | 256KB の残り |
|---|---|---|
| 75 | 238,800 byte | 23,344 byte |
| 78 | 248,352 byte | 13,792 byte |
| **79** | **251,536 byte** | **10,608 byte** |
| 80 | 254,720 byte | 7,424 byte |

### 確定させた根拠 1: 因果テスト

`STACK_SIZE` を 256KB → **512KB** にしただけで、**崖が 79 段から 165 段へ動いた**。

| 段数 | 256KB | 512KB |
|---|---|---|
| 79 / 80 / 100 / 120 | **停止** | 完了(JIT 成功) |
| 165 | 停止 | **停止** |

512KB / 3,184 = **164.9 段**で、観測値 165 と一致する。
スタック容量に比例して崖が動くので、**原因はスタック以外にありえない**。

(なお 512KB では 140〜160 段が `compiled=NIL` で速やかに戻る。これは別の既存上限
——おそらく `ZA_MAX_ANALYZE_STEPS`——が先に効いている区間で、本件とは別。)

### 確定させた根拠 2: 例外ハンドラの直接観測

79 段を `-serial stdio` 付きで走らせると、カーネル自身が正確に報告していた:

```
!! CPU EXCEPTION vector=0x0E rip=0x0C7A4090 rsp=0x0CA31CC0
   handler_sp=0x0C9F8258 ist=0x0C9F4350 cr2=0x0CA31CB8
   ** STACK OVERFLOW (下端側): 再帰が深すぎる **
   stack=0x0CA32000 guard=0x0CA22000 guard_size=0x10000
```

- `cr2` = 0x0CA31CB8 は**ガード領域**(0x0CA22000〜0x0CA32000)の中。`rsp` も同様
- `handler_sp` が `ist` の範囲内 → **IST は正しく効いていて、ハンドラは専用スタックで
  動き、報告まで到達できている**(`interrupt.c:15` の設計どおり)

**[記録] 当初「溢れても何も出ないまま止まる」と報告したが、これは誤りだった。**
原因は調査側が QEMU の出力を `> /dev/null` で捨てていたこと。
`documents/pitfalls.md` 原則5 が言う「無反応で区別できない」状態には**なっていない**。
ガードページも IST もスタック溢れの報告機構も、意図どおり働いている。
**深いネストを調べるときは `QEMU_EXTRA_FLAGS='-serial stdio'` を付けて出力を残すこと。**

ただし、報告の直後に出る次の1行は**この場合は誤りを誘う**:

```
   (rspがどのプロセススタックの範囲にもない: 溢れではなくrspの破壊の可能性...)
```

ガードを踏んだと直上で断定できているときは、rsp がスタック範囲外なのは当然である。

### 残る制約(修正後も変わらない)

例外が出た後、その式の評価は再開されない。上限を入れたことで JIT 経由で
ここへ来ることは無くなったが、**他の経路で C スタックが枯渇したときの振る舞いは
変わっていない**(深い再帰を書いた Lisp コード、深いリストの再帰的処理など)。
報告は出るが、プロセスは止まったままになる。

### 修正

`za_compile_expr` を薄いラッパと `za_compile_expr_inner` に分け、ラッパで再帰段数を
数えて `ZA_MAX_COMPILE_NEST`(60)を超えたら `g_jit_overflow = 1` で断念する
(`ZA_MAX_JIT_RELOCS` 等の固定上限と同じ形)。

**60 という値は Cスタックの容量から来る数字で、言語仕様上の制限ではない。**
実測 79 段から安全率を取った。`za_compile_expr` のローカル変数を増やせば
フレームが太り、実際に踏める段数は 79 より下がる。**フレームサイズを変えたら
測り直すこと。** 導出は `za.c` の `ZA_MAX_COMPILE_NEST` のコメントにも書いてある。

修正後の実測:

| 段数 | JIT | 所要 | 値 |
|---|---|---|---|
| 59 | 成功 | 4 tick | 1 |
| 60 | 断念 | 4 tick | 1 |
| 79 | 断念 | 4 tick | 1 |
| 150 | 断念 | 4 tick | 1 |
| 300 | 断念 | 8 tick | 1 |

**どの深さでも返ってきて、値は正しい。** 回帰テストは
`test/lisp/jit_nest_depth_test.lisp`(59/60/100 段の境界と、断念の次の defun が
普通に JIT されること = 段数カウンタが戻っていること)。

### 調べて外れたもの(確認済み)

- **disp8 → disp32 の収束ループではない。** za.c が発行する分岐は
  `jit_emit_{je,jmp,jne,js,jb}_rel32_placeholder` の5種のみで、**rel8 を出す箇所が
  1つも無い**(`0xEB` / `0x7x` の発行なし)。命令長が固定なのでパッチで後続の
  オフセットがずれることが無く、再計算を繰り返す実装にはなっていない
- **コード生成バッファの上限・やり直しではない。** 79 段の推定生成長 54,887 byte は
  `JIT_CODE_SIZE`(524,288、`za.c:105`)の 10% で、まだ遠い。
  生成コード長が 691 byte/段で完全に線形なことも、やり直しが起きていない傍証
- **固定長テーブルの溢れではない。** `ZA_MAX_JIT_RELOCS`(128、`za.c:285-290`)、
  `ZA_MAX_TRAMPOLINE_JMPS`(128、`za.c:452`)、`ZA_MAX_LITERAL_SLOT_ALLOCS`
  (96、`za.c:265`)はいずれも書き込み前に境界検査し、超過時は `g_jit_overflow = 1` で
  グレースフルにフォールバックする。線形探索やリトライには落ちない。
  `ZA_MAX_FN_CELL_CACHE_SLOTS`(2048)は 79 段なら 79 スロットで足りている
- **ページ境界ではない。** 生成コード長は 20 段(14KB)の時点で既に何ページも
  またいでおり、そこで不連続は起きていない

### 残っているタスク(別件として切る)

**C スタック枯渇からの復帰**。今は報告はされるがプロセスは止まる。
JIT の再帰は、たまたまそれを踏んだ 1 例にすぎず、他の経路
(深い再帰の Lisp コード、深いリストの処理など)では同じことが起きる。
ハンドラ側から安全に巻き戻す、あるいは該当プロセスだけを落として
REPL へ戻す設計が要る。設計の話なので別タスク。
