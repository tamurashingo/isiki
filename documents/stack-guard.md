# スタック枯渇をハングではなくエラーにする(issue #110、2026-10-07)

> **対象は JIT 経路だけである。** インタプリタと AOT は**守られていない**(§4)。
> 「スタック枯渇はエラーになる」と一般化して読まないこと。

## 0. この作業の位置づけ — **案 d の代わりではない**

| | 効果 | 症状 |
|---|---|---|
| **本作業(signal)** | 深さは増えない | **無反応 → `<storage-exhausted>`** |
| **案 d(フレームの実寸化)** | 35 → 68 段 | **無反応のまま** |

**案 d をやっても 68 段は偶然当たる深さである**(100 要素のリストの素朴な再帰、
少し深い木の走査、再帰で書いたパーサ)。
**症状が「無反応」のままでは、段数が倍になっても可用性は戻らない。**

> **signal は、フレームの大きさと独立に可用性を回復する。**
> **案 d は「深さのため」ではなく「フレームの 44.5% が 93.2% の関数に不要だから」やる**
> (`documents/jit-frame-survey.md` §8-6)。**この 2 つを混ぜないこと。**

### 案 d より先にやる理由

**signal も案 d も、触るのはプロローグである。** そしてプロローグは
PR #120 で**「漏らすと静かにスタックが壊れる」**と特定された場所である
(`documents/jit-static-code-check.md`)。

- **signal を先に**すると、フレームが変わっていない状態で費用が測れる
- **案 d を先に**すると、並べ替えと検査の追加が同じ場所で混ざる

**危ない場所を 2 回触るなら、1 回目はできるだけ単純にする。**

---

## 1. 検査の位置 — **`sub rsp` より前。プロローグの先頭**

`sub rsp` の後ろに置くと、**既に溢れてから気づく**ことになる。

`za.c` のプロローグは 2 つの入口(cons リスト ABI / 固定引数レジスタ渡し)に
それぞれ出力される:

```
push rbx ; push r13 ; (pin nil) ; sub rsp, ZA_FRAME_TOTAL
```

**検査はこの `push rbx` より前**に置く。そうすると断念経路で
`rsp` が入口のままなので、**何も巻き戻さずに `call` して `ret` できる。**
レジスタと 1 回のメモリ読みだけで判定するので、**検査自身はスタックを使わない。**

(測定結果・実装の詳細は §5 以降)

---

## 2. スタックの下限をどこから取るか

既にあるものを使う。**新しい組み込み関数は追加しない**
(1 つ足すと `SMALL_HEAP_SIZE` の再調整が要る既知の罠がある)。

| | 既存のもの |
|---|---|
| プロセスのスタック下端 | `os_process_stack_base(i)`(`process.c`)。Lisp からは `%%DIAG-STACK-BASE` |
| ガード(未マップ 64KB)の先頭 | `os_process_guard_base(i)`。Lisp からは `%%DIAG-GUARD-BASE` |
| スタックの大きさ | `STACK_SIZE = 256 * 1024`(`process.c`) |
| 既存の検査 | `os_process_stack_check()` が**タイマ tick ごと**に rsp とカナリアを見る |

**プロセスごとにスタックが違う**(`g_stack_area` 内の 320KB スロット。
64KB ガード + 256KB スタック)。だから**単一の絶対下限では判定できない。**

採った形: **グローバル 1 個を文脈切り替えのときに書き換える。**

- `c_timer_switch`(`interrupt.c`)が `next_rsp` を決めた直後に、
  その rsp が属するスタックの下端から閾値を計算して格納する
- 生成コードは `movabs r11, &g_za_stack_limit` / `cmp rsp, [r11]` で読む

**最初の tick より前(カーネルの idle ループ上)は 0 のままで、検査は発火しない。**
そこで深い再帰は起きない(`process_trampoline_c` 以降が Lisp の実行点)が、
**「下限が 0 のときは検査が無効」という性質は記録しておく。**

## 3. 閾値 — **余裕は「signal 経路が使う最大量」**

```
閾値 = ZA_FRAME_TOTAL + SIGNAL_RESERVE
```

`ZA_FRAME_TOTAL` ぶんの空きだけを見て通すと、**ぎりぎりで通ったときに
signal の処理中に溢れる。** signal は

- 条件インスタンスを作る(`make-instance` → **確保 → GC が走りうる**)
- ハンドラを探す(`signal-condition`)
- ハンドラを**その場の深さで**呼ぶ(ISLisp の `with-handler` は signal 点の動的文脈で動く)

を全部スタックの上でやる。**`os_signal_condition` は C から Lisp を呼び戻す**ので、
使用量は「C 関数 1 つ分」では済まない。

> **`SIGNAL_RESERVE` は推測せず実測する。** 足りないと
> **「エラーを出そうとしてハングする」**という、いまより分かりにくい症状になる。

測り方と結果は §5。

### 3-1 ハンドラが深く潜る場合

ユーザのハンドラがまた深い再帰を呼ぶことがある。**その場合は再び同じ検査に当たって
signal すれば足りる。** ただし**余裕の中で signal が完了すること**が前提なので、
上と同じ話になる。

### 3-2 signal の深さ打ち切り(PR #113)との関係

`os_signal_condition` には打ち切りがある(`runtime.c`):

```c
#define SIGNAL_MAX_DEPTH 16
if (g_signal_depth >= SIGNAL_MAX_DEPTH) { g_signal_overflow_count++; return g_sym_eval_error; }
```

**当たると、signal しようとして打ち切られ、何も起きない。**
枯渇状態から signal するとき、ここに当たらないことを確かめる
(`%%DIAG-SIGNAL-OVERFLOWS` が 0 のままであること)。結果は §6。

## 4. 守られる経路と、守られない経路

**スタックを溢れさせるのは JIT だけではない。**

| 経路 | フレーム | 本作業 |
|---|---|---|
| **JIT** | 7504 byte/段(`ZA_FRAME_TOTAL` 7480 + `push` 16 + 戻り番地 8) | **守る** |
| **インタプリタ**(`os_eval` の再帰) | §5 で実測 | **守らない。測って記録するだけ** |
| **AOT** | §5 で実測 | **守らない。測って記録するだけ** |

**JIT を先にやる理由は、35 段がいちばん浅いからである。**

> **片方だけ守ると「スタック枯渇はエラーになる」と誤解される。**
> インタプリタで同じことが起きたとき、今回と同じ時間を使って原因を探すことになる。

## 5. 測定

### 5-1 **期待値を測定前に宣言する**(規則 11)

#### 生成コードに増える命令

```
movabs r11, &g_za_stack_limit      ; 49 BB imm64   10 byte
cmp    rsp, [r11]                  ; 49 3B 23       3 byte
jae    +N                          ; 73 xx          2 byte
```

**通常経路で実行されるのは 3 命令。** 断念経路(`jae` が落ちない側)は
`movabs` + `sub rsp,32` + `call r11` + `add rsp,32` + `ret` = 22 byte。
**入口 2 つに出すので、1 関数あたりのコード増加は (15 + 22) × 2 = 74 byte。**

依拠する前提(**未確認のものに印を付ける**):

| | 前提 | 状態 |
|---|---|---|
| 1 | **`r11` は JIT 関数の入口で死んでいる**(MS x64 の引数は rcx/rdx/r8/r9) | **未確認** |
| 2 | プロローグは入口 2 つに出るが、1 回の呼び出しで実行されるのは一方だけ | 確認済み(PR #120 §8-5。`sub` が 2、`add` が 3) |
| 3 | 末尾呼び出しも callee の入口へ `jmp` するので検査を通る | **未確認** |
| 4 | AOT は `za.c` のプロローグを通らないので**対照群になる** | 確認済み(規則 12) |
| 5 | TCG は `cmp rsp,[r11]` のメモリ読みを 1 命令として数える | **未確認** |

#### ベンチの数字

**PR #120 の単価の記録**: タグ検査 1 組 = 10 命令/回。**それより小さいはず。**

| 行 | 予測 | 根拠 |
|---|---|---|
| `jit/funcall` | **+3**(364.10 → 367.1) | 1 単位 = 1 回の関数呼び出し |
| `jit/tailrec` | **+3**(396.09 → 399.1) | 末尾呼び出しも入口へ jmp する(前提 3) |
| `jit/loop` `jit/arith` `jit/let` `jit/for` | **±0** | 1 単位の中で JIT 関数を呼ばない |
| `aot/*` 全 10 行 | **±0**(**対照群**) | 前提 4 |
| `c/*` 全 10 行 | **±0** | C の素の実装 |

> **ここで正直に言っておく: +3 は帯 20.00 では判定できない。**
> `jit` 行の跨セッション分解能は **±6.19**(PR #118 で実測)、
> 帯は 20.00 である。**+3 は両方より小さい。**
> だから本作業の費用は
> **(a) 生成コードの逆アセンブルで命令数を数える**(決定的、ノイズ 0)と
> **(b) AOT 側が動かないこと**(対照群)の 2 つで示す。
> **ベンチの数字で +3 を「測った」とは言わない**(規則 3)。

### 5-2 スタックの使用量を測る技法 — **塗って最高水位を読む**

**ハングさせずに「1 段あたり何 byte 使うか」を測る。**
PR #117 の傾き法を、命令数ではなくスタックに適用する。

1. スタック下端から 200KB ぶんを、64 byte 間隔で `0xA5` に塗る(`%%POKE`)。
   **いま走っている rsp より下だけを塗る**(上を塗ると自分のフレームを壊す)
2. 深さ N の再帰を 1 回走らせる
3. 下から上へ走り、**最初に塗りが残っていない点**を探す = 最高水位
4. `使用量(N) = スタック上端 − 最高水位`
5. `1 段あたり = (使用量(3N) − 使用量(N)) / 2N`

**新しい組み込み関数は要らない**(`%%DIAG-STACK-BASE` / `%%PEEK` / `%%POKE` で足りる)。

**技法の校正**(規則 8): **JIT 経路は真の値が分かっている**
(`ZA_FRAME_TOTAL` 7480 + `push rbx`/`push r13` 16 + 戻り番地 8 = **7504**)。
**この技法が 7504 を返さなければ、技法が間違っている。**

(測定結果は実測後に記入)

## 6. `safety` の分類 — **これは 4 つ目の族である**

PR #113 以降、検査を 3 つに分類してきた。**スタック残量の検査は 4 つ目で、
`safety` で外してよい検査ではない。**

| | 検査 | `safety 0` で外すと | 性質 |
|---|---|---|---|
| 1 | **タグ検査** | ゴミを読む。**プログラマがそう頼んだ** | 型の検査 |
| 2 | **桁溢れ検査** | `-0` ができる。**外せない** | 型の検査(表現の限界) |
| 3 | **ゼロ除算検査** | #DE で機械が止まる。**外せない** | 値の検査 |
| **4** | **スタック残量の検査** | **静かにハングに戻る。外せない** | **資源の検査** |

> **資源の検査であって、型の検査ではない。**
> 型の検査は「宣言を信じる」ことで省ける。**資源の検査は、宣言しても
> 資源が増えるわけではないので省けない。**

`documents/declaim-design.md`(issue #112)の `safety` の設計に、この 4 分類を
反映すること。**外せる検査を増やすときに、ここが混ざると危険である。**
