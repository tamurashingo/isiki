# スタック枯渇をハングではなくエラーにする(issue #110、2026-10-07)

> **対象は JIT 経路だけである。** インタプリタと AOT は**守られていない**(§4)。
> 「スタック枯渇はエラーになる」と一般化して読まないこと。

## 0. この作業の位置づけ — **案 d の代わりではない**

| | 効果 | 症状 |
|---|---|---|
| **本作業(signal)** | 深さは増えない | **無反応 → `<storage-exhausted>`** |
| **案 d(フレームの実寸化)** | 35 → 68 段 | **無反応のまま** |

**案 d をやっても 68 段は偶然当たる深さである**(100 要素のリストの素朴な再帰、
少し深い木の走査、再帰で書いたパーサ)。
**症状が「無反応」のままでは、段数が倍になっても可用性は戻らない。**

> **signal は、フレームの大きさと独立に可用性を回復する。**
> **案 d は「深さのため」ではなく「フレームの 44.5% が 93.2% の関数に不要だから」やる**
> (`documents/jit-frame-survey.md` §8-6)。**この 2 つを混ぜないこと。**

### 案 d より先にやる理由

**signal も案 d も、触るのはプロローグである。** そしてプロローグは
PR #120 で**「漏らすと静かにスタックが壊れる」**と特定された場所である
(`documents/jit-static-code-check.md`)。

- **signal を先に**すると、フレームが変わっていない状態で費用が測れる
- **案 d を先に**すると、並べ替えと検査の追加が同じ場所で混ざる

**危ない場所を 2 回触るなら、1 回目はできるだけ単純にする。**

---

## 1. 検査の位置 — **`sub rsp` より前。プロローグの先頭**

`sub rsp` の後ろに置くと、**既に溢れてから気づく**ことになる。

`za.c` のプロローグは 2 つの入口(cons リスト ABI / 固定引数レジスタ渡し)に
それぞれ出力される:

```
push rbx ; push r13 ; (pin nil) ; sub rsp, ZA_FRAME_TOTAL
```

**検査はこの `push rbx` より前**に置く。そうすると断念経路で
`rsp` が入口のままなので、**何も巻き戻さずに `call` して `ret` できる。**
レジスタと 1 回のメモリ読みだけで判定するので、**検査自身はスタックを使わない。**

(測定結果・実装の詳細は §5 以降)

---

## 2. スタックの下限をどこから取るか

既にあるものを使う。**新しい組み込み関数は追加しない**
(1 つ足すと `SMALL_HEAP_SIZE` の再調整が要る既知の罠がある)。

| | 既存のもの |
|---|---|
| プロセスのスタック下端 | `os_process_stack_base(i)`(`process.c`)。Lisp からは `%%DIAG-STACK-BASE` |
| ガード(未マップ 64KB)の先頭 | `os_process_guard_base(i)`。Lisp からは `%%DIAG-GUARD-BASE` |
| スタックの大きさ | `STACK_SIZE = 256 * 1024`(`process.c`) |
| 既存の検査 | `os_process_stack_check()` が**タイマ tick ごと**に rsp とカナリアを見る |

**プロセスごとにスタックが違う**(`g_stack_area` 内の 320KB スロット。
64KB ガード + 256KB スタック)。だから**単一の絶対下限では判定できない。**

採った形: **グローバル 1 個を文脈切り替えのときに書き換える。**

- `c_timer_switch`(`interrupt.c`)が `next_rsp` を決めた直後に、
  その rsp が属するスタックの下端から閾値を計算して格納する
- 生成コードは `movabs r11, &g_za_stack_limit` / `cmp rsp, [r11]` で読む

**最初の tick より前(カーネルの idle ループ上)は 0 のままで、検査は発火しない。**
そこで深い再帰は起きない(`process_trampoline_c` 以降が Lisp の実行点)が、
**「下限が 0 のときは検査が無効」という性質は記録しておく。**

## 3. 閾値 — **余裕は「signal 経路が使う最大量」**

```
閾値 = ZA_FRAME_TOTAL + SIGNAL_RESERVE
```

`ZA_FRAME_TOTAL` ぶんの空きだけを見て通すと、**ぎりぎりで通ったときに
signal の処理中に溢れる。** signal は

- 条件インスタンスを作る(`make-instance` → **確保 → GC が走りうる**)
- ハンドラを探す(`signal-condition`)
- ハンドラを**その場の深さで**呼ぶ(ISLisp の `with-handler` は signal 点の動的文脈で動く)

を全部スタックの上でやる。**`os_signal_condition` は C から Lisp を呼び戻す**ので、
使用量は「C 関数 1 つ分」では済まない。

> **`SIGNAL_RESERVE` は推測せず実測する。** 足りないと
> **「エラーを出そうとしてハングする」**という、いまより分かりにくい症状になる。

測り方と結果は §5。

### 3-1 ハンドラが深く潜る場合

ユーザのハンドラがまた深い再帰を呼ぶことがある。**その場合は再び同じ検査に当たって
signal すれば足りる。** ただし**余裕の中で signal が完了すること**が前提なので、
上と同じ話になる。

### 3-2 signal の深さ打ち切り(PR #113)との関係

`os_signal_condition` には打ち切りがある(`runtime.c`):

```c
#define SIGNAL_MAX_DEPTH 16
if (g_signal_depth >= SIGNAL_MAX_DEPTH) { g_signal_overflow_count++; return g_sym_eval_error; }
```

**当たると、signal しようとして打ち切られ、何も起きない。**
枯渇状態から signal するとき、ここに当たらないことを確かめる
(`%%DIAG-SIGNAL-OVERFLOWS` が 0 のままであること)。結果は §6。

## 4. 守られる経路と、守られない経路

**スタックを溢れさせるのは JIT だけではない。**

| 経路 | フレーム | 本作業 |
|---|---|---|
| **JIT** | 7504 byte/段(`ZA_FRAME_TOTAL` 7480 + `push` 16 + 戻り番地 8) | **守る** |
| **インタプリタ**(`os_eval` の再帰) | §5 で実測 | **守らない。測って記録するだけ** |
| **AOT** | §5 で実測 | **守らない。測って記録するだけ** |

**JIT を先にやる理由は、35 段がいちばん浅いからである。**

> **片方だけ守ると「スタック枯渇はエラーになる」と誤解される。**
> インタプリタで同じことが起きたとき、今回と同じ時間を使って原因を探すことになる。

## 5. 測定

### 5-1 **期待値を測定前に宣言する**(規則 11)

#### 生成コードに増える命令

```
movabs r11, &g_za_stack_limit      ; 49 BB imm64   10 byte
cmp    rsp, [r11]                  ; 49 3B 23       3 byte
jae    +N                          ; 73 xx          2 byte
```

**通常経路で実行されるのは 3 命令。** 断念経路(`jae` が落ちない側)は
`movabs` + `sub rsp,32` + `call r11` + `add rsp,32` + `ret` = 22 byte。
**入口 2 つに出すので、1 関数あたりのコード増加は (15 + 22) × 2 = 74 byte。**

依拠する前提(**未確認のものに印を付ける**):

| | 前提 | 状態 |
|---|---|---|
| 1 | **`r11` は JIT 関数の入口で死んでいる**(MS x64 の引数は rcx/rdx/r8/r9) | **未確認** |
| 2 | プロローグは入口 2 つに出るが、1 回の呼び出しで実行されるのは一方だけ | 確認済み(PR #120 §8-5。`sub` が 2、`add` が 3) |
| 3 | 末尾呼び出しも callee の入口へ `jmp` するので検査を通る | **未確認** |
| 4 | AOT は `za.c` のプロローグを通らないので**対照群になる** | 確認済み(規則 12) |
| 5 | TCG は `cmp rsp,[r11]` のメモリ読みを 1 命令として数える | **未確認** |

#### ベンチの数字

**PR #120 の単価の記録**: タグ検査 1 組 = 10 命令/回。**それより小さいはず。**

| 行 | 予測 | 根拠 |
|---|---|---|
| `jit/funcall` | **+3**(364.10 → 367.1) | 1 単位 = 1 回の関数呼び出し |
| `jit/tailrec` | **+3**(396.09 → 399.1) | 末尾呼び出しも入口へ jmp する(前提 3) |
| `jit/loop` `jit/arith` `jit/let` `jit/for` | **±0** | 1 単位の中で JIT 関数を呼ばない |
| `aot/*` 全 10 行 | **±0**(**対照群**) | 前提 4 |
| `c/*` 全 10 行 | **±0** | C の素の実装 |

> **ここで正直に言っておく: +3 は帯 20.00 では判定できない。**
> `jit` 行の跨セッション分解能は **±6.19**(PR #118 で実測)、
> 帯は 20.00 である。**+3 は両方より小さい。**
> だから本作業の費用は
> **(a) 生成コードの逆アセンブルで命令数を数える**(決定的、ノイズ 0)と
> **(b) AOT 側が動かないこと**(対照群)の 2 つで示す。
> **ベンチの数字で +3 を「測った」とは言わない**(規則 3)。

### 5-2 スタックの使用量を測る技法 — **塗って最高水位を読む**

**ハングさせずに「1 段あたり何 byte 使うか」を測る。**
PR #117 の傾き法を、命令数ではなくスタックに適用する。

1. スタック下端から 200KB ぶんを、64 byte 間隔で `0xA5` に塗る(`%%POKE`)。
   **いま走っている rsp より下だけを塗る**(上を塗ると自分のフレームを壊す)
2. 深さ N の再帰を 1 回走らせる
3. 下から上へ走り、**最初に塗りが残っていない点**を探す = 最高水位
4. `使用量(N) = スタック上端 − 最高水位`
5. `1 段あたり = (使用量(3N) − 使用量(N)) / 2N`

**新しい組み込み関数は要らない**(`%%DIAG-STACK-BASE` / `%%PEEK` / `%%POKE` で足りる)。

**技法の校正**(規則 8): **JIT 経路は真の値が分かっている**
(`ZA_FRAME_TOTAL` 7480 + `push rbx`/`push r13` 16 + 戻り番地 8 = **7504**)。
**この技法が 7504 を返さなければ、技法が間違っている。**

#### 校正の結果 — **技法は正しい**

| 深さ | 使用量(byte) |
|---:|---:|
| 10 | 93,760 |
| 20 | 169,152 |
| 30 | 244,480 |

傾き = **7,536 byte/段**(10→20 と 20→30 で 7,539 / 7,533。格子 64 byte 由来の誤差)。

**予測は 7,504 だった。差 32 は偶然ではない。**
`jit_call_r11` が `call` の前に出す **Microsoft x64 のシャドウスペース 32 byte**
である。7,480 + 16 + 8 + **32** = **7,536**。
**残差が既知の量にぴったり一致したので、技法は信頼できる**(規則 8 の校正点)。

256KB / 7,536 = 34.8 → **34 段**。PR #120 の実測「33 で返る / 34 で溢れる」と一致。

### 5-3 守られる経路と守られない経路 — **1 段あたりの実測**

| 経路 | byte/段 | 256KB での段数 | 本作業 |
|---|---:|---:|---|
| **JIT** | **7,536** | **約 34** | **守る** |
| インタプリタ | 3,072 | 約 66 | 守らない |
| AOT | 320 | 約 782 | 守らない |

- インタプリタは 5 束縛の `let` で JIT を外した関数(`%%za-compiled-p` = NIL)で測った。
  使用量は `59,392 + 3,072 × 深さ`(10/20/30/40 段で完全に線形)
- AOT は `%%bench-aot-nontailrec-step`(カーネル埋め込み)。
  使用量は `11,840 + 320 × 深さ`(150/200/250 段)。
  既存コメントの見積もり「約 330 byte」とよく合う

> **JIT は AOT の 23 倍、インタプリタの 2.4 倍スタックを食う。**
> だから JIT を先に守る。
> **ただしインタプリタの 66 段も浅い。** ここは守られていない(§4)。

#### 予備領域(`ZA_STACK_SIGNAL_RESERVE`)の実測

塗ってから `<storage-exhausted>` を 1 回出し、最高水位を読んだ。

| ハンドラ | 閾値より下に使った量(上限) |
|---|---:|
| `with-handler` あり(`assert-error-class`) | **8,824 byte** |
| 無し(既定の経路) | 8,696 byte |

- 不確かさは **7,536 byte**(断念経路は閾値より最大 1 段ぶん下で始まる)。
  だから「最大 8,824」であって「ちょうど」ではない
- **ハンドラ無しのほうが少ない。** `report-condition` の表示は
  **巻き戻したあと**(浅いところ)で起きている
- **GC はここに乗らない。** 収集器は明示キューの `while` ループ
  (`gc_scan_queue`)で**反復的**なので、signal 経路の途中で走っても
  使用量は O(1) しか増えない

**値の決め方(下限から積む):**

```
  発火フレームの余り   7,536
+ signal 経路の実測    8,824
+ 床(ハンドラ暴走用)  4,096
= 20,456                       -> 切り上げて 24,576(24KB)
```

**最初 65,536 にしていたが、原理から積み直して 24,576 にした。**
65,536 だと使える深さが 23 段まで落ちる(予備領域は深さを削る)。

### 5-4 **使える深さは 33 → 27 に減る**(指示書 §6-1 との食い違い)

**指示書は「深さ 33(いまの上限)は従来どおり成功すること」を完了条件に挙げているが、
これは原理的に満たせない。**

```
使える深さ = (256KB − 予備領域 − ベースの使用量) / 7,536
```

**予備領域を取るぶん、必ず深さが減る。** 24,576 byte = 約 3.3 段。
実測(保護入り、`sgt-max` で 1 段ずつ探った):**最大深さ 27。**

| 予備領域 | 最大深さ(実測) |
|---:|---:|
| 65,536 | 29(ベース込みで 23〜29) |
| **24,576** | **27** |

そして **33 はもともと回帰テストに使える深さではなかった** — PR #120 が
「上限ぎりぎり(33)を書くと、呼び出し元が使う C スタックのぶんで溢れる
(`documents/for-expansion.md` で実際に踏んだ)」と記録しており、
`jit_frame_test.lisp` は深さ 20 を使っている。

> **交換条件である。** 深さ 6 段を払って、**無反応がエラーになる。**
> 深さが欲しければ案 d(フレームの実寸化)で基底を削る — そちらは
> 予備領域と独立に 35 → 68 段にする話である。

### 5-5 予備領域の開け閉めと、床

signal 経路そのものは閾値より下を使うので、**入るときに閾値を床まで下げ、
抜けるときに戻す。**

| | 閾値 |
|---|---|
| 通常 | `下端 + ZA_FRAME_TOTAL + 24,576` |
| signal 経路の中 | `下端 + ZA_FRAME_TOTAL + 4,096`(床) |

**無効化(0)にしないのは、ハンドラがさらに深く潜った場合に床で捕まえるため。**
そのときは `g_za_in_stack_signal` が立っているので **signal を重ねず
`EVAL-ERROR` を返して巻き戻す。** 重ねると予備領域を食い潰して
**「エラーを出そうとしてハングする」**という、いまより分かりにくい症状になる。

**既知の限界(記録しておく):**

- **プロセスが切り替わると閾値が通常値へ戻る。** `c_timer_switch` は切り替え先の
  スタックに合わせて閾値を書き換えるので、signal 経路の途中で切り替わると
  予備領域が閉じる。そのあと signal 経路が JIT 関数を呼ぶと断念経路へ入るが、
  フラグが立っているので `EVAL-ERROR` を返して巻き戻る。**ハングはしない**
- **フラグはプロセスごとではない。** プロセス A が signal 経路にいるあいだ、
  プロセス B が枯渇すると B は `EVAL-ERROR` になる
- 最初のタイマ tick より前(カーネルの idle ループ上)は閾値が 0 で**検査が発火しない**

## 6. `safety` の分類 — **これは 4 つ目の族である**

PR #113 以降、検査を 3 つに分類してきた。**スタック残量の検査は 4 つ目で、
`safety` で外してよい検査ではない。**

| | 検査 | `safety 0` で外すと | 性質 |
|---|---|---|---|
| 1 | **タグ検査** | ゴミを読む。**プログラマがそう頼んだ** | 型の検査 |
| 2 | **桁溢れ検査** | `-0` ができる。**外せない** | 型の検査(表現の限界) |
| 3 | **ゼロ除算検査** | #DE で機械が止まる。**外せない** | 値の検査 |
| **4** | **スタック残量の検査** | **静かにハングに戻る。外せない** | **資源の検査** |

> **資源の検査であって、型の検査ではない。**
> 型の検査は「宣言を信じる」ことで省ける。**資源の検査は、宣言しても
> 資源が増えるわけではないので省けない。**

`documents/declaim-design.md`(issue #112)の `safety` の設計に、この 4 分類を
反映すること。**外せる検査を増やすときに、ここが混ざると危険である。**

## 7. 検証

### 7-1 生成コード — **通常経路 3 命令 / 11 byte**

`%%DISASM-ITEM` で命令単位に読んだ実物:

```
#G [0]  mov r11d, 0xdc24120     ; 6 byte  (&g_za_stack_limit。32bit に収まった)
#G [6]  cmp rsp, [r11]          ; 3 byte
#G [9]  jae 0x1d                ; 2 byte
#G [11] mov r11d, 0xc72fcd4     ; 断念経路: &os_za_signal_stack_exhausted
#G [17] sub rsp, 0x28           ;   シャドウスペース 32 + 16byte 境界合わせ 8
#G [21] call r11
#G [24] add rsp, 0x28
#G [28] ret
```

| | 宣言(§5-1) | 実測 |
|---|---:|---:|
| 通常経路の命令数 | 3 | **3** |
| 1 関数あたりのコード増加 | 74 byte | **58 byte**(29 × 入口 2 つ) |

**命令数は宣言どおり。** byte 数が小さいのは、アドレスが 32bit に収まって
`movabs`(10 byte)が `mov r32, imm32`(6 byte)に縮んだため。

前提の確認結果(§5-1 で未確認だったもの):

| | 前提 | 結果 |
|---|---|---|
| 1 | `r11` は入口で死んでいる | **確認。** 全テストが通り、引数は rcx/rdx/r8/r9 のまま |
| 3 | 末尾呼び出しも検査を通る | **確認。** `sgt-tail 1000` が通る(フレームを積まないので発火しない) |
| 5 | TCG が `cmp rsp,[r11]` を 1 命令と数える | §7-4 |

### 7-2 枯渇がエラーになる(`test/lisp/stack_guard_test.lisp`、20 件)

```
#stack-guard max-depth=27 (記録値 27)
==== isiki tests: 20 passed, 0 failed ====
```

- 深さ 20 は従来どおり成功する
- 深さ 1000 は `<storage-exhausted>` になる(`assert-error-class`)
- **signal したあとも REPL が生きている**(次の式が評価できる)
- **1 回だけではない。** 3 回枯渇させて戻れる
- `%%DIAG-SIGNAL-OVERFLOWS` = 0(**§3-2 の打ち切りに当たっていない**)
- 末尾呼び出しは発火しない(`sgt-tail 1000` = 500500)
- 相互再帰でも発火する

> **`<storage-exhausted>` は `<error>` の子ではない**(`<serious-condition>` の
> 直接の子)。だから `ignore-errors` では捕まらない。`with-handler` を使う。
> 最初これに気づかず「signal されていない」と誤読した。

### 7-3 **余裕を削ると、signal の途中で溢れる**(§6-4 の確認)

`EXTRA_CFLAGS=-DZA_STACK_SIGNAL_RESERVE=512` でビルドして同じ式を走らせた
(`-serial file:` でシリアルを保存):

```
!! CPU EXCEPTION vector=0x0E rip=0x0C7552BF rsp=0x0C9DCFE0 cr2=0x0C9DCFD8
   ** STACK OVERFLOW (下端側): 再帰が深すぎる **
   stack=0x0C9DD000 guard=0x0C9CD000 guard_size=0x10000
```

**`rsp = 0x0C9DCFE0` は下端 `0x0C9DD000` より 32 byte 下。**
予備領域が 512 byte では signal 経路(実測 8,824 byte)が入らず、
**ガードページへ落ちた。**

> **これが「エラーを出そうとしてハングする」を防ぐ唯一の確認である。**
> 24,576 では同じ式が `<storage-exhausted>` を返す。**余裕は効いている。**

**溢れた現場で原因が読めるようにした。** `#PF` の報告に
`jit-stack-guard-hits` を出す:

- **0** なら、保護が一度も発火していない = **守られていない経路**
  (インタプリタ / AOT)からの溢れ
- **1 以上**なら、保護は働いたがそのあと(signal 経路の中で)溢れた
  = **予備領域が足りない**

この区別が無いと、次に同じ現場を見た人が
「保護を入れたのに溢れた」で止まってしまう。

### 7-4 費用 — **予測した 2 行だけが +3 前後動いた**

`make test-qemu-jit-bench`(jit と aot、6 カテゴリ、median of 3、N=1,000,000)。

| 行 | 宣言(§5-1) | 実測の差 | |
|---|---|---:|---|
| `jit/funcall` | **+3** | **+3.97** | 364.10 → 368.07 |
| `jit/tailrec` | **+3** | **+3.18** | 396.09 → 399.27 |
| `jit/let` | ±0 | +1.28 | |
| `jit/loop` | ±0 | +0.09 | |
| `jit/arith` | ±0 | −0.58 | |

| `aot/for` `aot/loop`(**対照群**) | ±0 | −13.61 / +14.49 | **もともと幅が最大の 2 行** |

**言えること / 言えないこと:**

- **言えない: 「+3 を測った」。** `jit` 行の帯は 20.00、3 回測定の分解能は ±7.00。
  **+3.97 単独では判定できない**(規則 3)
- **言える: 並び。** **予測した 2 行だけが +3 前後動き、他の 4 行は ±3 に収まった。**
  1 単位が 1 回の関数呼び出しになるのは `funcall` と `tailrec` だけで、
  **末尾呼び出しも callee の入口へ `jmp` するので検査を通る**(§5-1 の前提 3 を
  これで確認した)。他の 4 行は 1 単位の中で JIT 関数を呼ばない
- **対照群の 2 行の外れはノイズである。** `aot/for`(幅 15.3)と `aot/loop`(幅 14.8)は
  **記録の時点でいちばん幅が広い 2 行**で、しかも **AOT は `za.c` のプロローグを
  通らない**(規則 12)。記録は動かさない
- `os_eval` の傾きは全 12 行で **+0.000**。**インタプリタへ落ちた行は無い**
  (PR #116 の gate2)
- **タグ検査 1 組 = 10 命令/回**(PR #120 の単価)より小さい、は満たしている

**`jit/funcall` と `jit/tailrec` の記録値は書き換えた。**
+3 は構造的に残る差なので、帯の中に放置すると issue #114(165 コミット
気づかれなかった 1.5〜1.7 倍の悪化)と同じ形になる。

### 7-5 最大深さの検出器 — **両方残す**

| | 何を見ているか | 性質 |
|---|---|---|
| `jit_frame_test.lisp`(PR #120) | **生成コードの `sub rsp` の即値**= フレームサイズそのもの | 決定的。ノイズ 0 |
| `stack_guard_test.lisp` §6(本作業) | **実際に使える深さ**(フレーム × 予備領域 × 呼び出し元のベース) | 帯 [20, 34] |

**測っているものが違うので置き換えない。**

- 間接版は**フレームサイズ**を見るので、**案 d(実寸化)のときに効く。**
  予備領域を変えても動かない
- 直接版は**予備領域を増やしすぎて深さが削られた**ことに気づける。
  間接版はそれを見られない
- 直接版は呼び出し元のスタック使用量で 1〜2 段動くので帯で見る。
  **どちらに外れても落ちる**(下限 20 = 深さが削られた / 上限 34 = 保護が効かなくなった)

> **ハングしなくなったので「深さを直接探るテスト」が書けるようになった。**
> PR #120 の時点では書けなかった(探ると溢れてハングし「落ちる」にならない)。
> **これが本作業の副産物のうち、いちばん大きいものである。**
