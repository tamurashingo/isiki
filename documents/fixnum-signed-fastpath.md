# 改善A: 負の fixnum が bignum 機構を通る問題の修正

> 実施日: 2026-09-16 / ブランチ: `feature/fixnum-signed-fastpath`(分岐元 `feature/compiler-optimization` `e05a4a7`)
> 発端: `documents/type-system-survey.md` §1-4 / §7-4 / §10-4
> 関連: `documents/jit-immediate-operands.md`(PR #64)、`documents/bench-pinned-nil.md`(PR #66)

---

## 0. 結論

**`(+ -1 1)` のヒープ確保が 32 byte/回 → 0 byte/回 になり、速度は 5.76 µs → 0.38 µs(15 倍)になった。**

目標だった「`(+ -1 1)` が `(+ s 1)` と同程度になること」は達成した
(0.38 µs vs 0.42 µs。同一ブート内で `nop` ループとの差分を取った値)。

| ベンチ | 修正前 | 修正後 | 倍率 |
|---|---:|---:|---:|
| `(setq s (+ s 1))`(**変更なしの経路**) | 0.44 µs | 0.42 µs | 1.0 |
| **`(setq s (+ -1 1))`** | **5.76 µs** | **0.38 µs** | **15.2×** |
| `(setq s (- s 1))` 正のまま(**変更なしの経路**) | 0.51 µs | 0.53 µs | 1.0 |
| **`(setq s (- s 1))` 負へ落ちる** | **4.14 µs** | **0.85 µs** | **4.9×** |
| **`(setq s (- 1 -1))`** | **3.98 µs** | **0.48 µs** | **8.3×** |
| `(setq s (+ *max-fix* 1))`(桁あふれ。**一般パスの対照**) | 9.86 µs | 7.81 µs | 1.3 |

**変更していない経路は 2 ビルド間で 2〜6 tick しか動いていない。**
PR #66 で問題になった実行間ドリフトが今回はほとんど出ておらず、
変わった 3 本だけが 4〜15 倍動いていることが、この比較の信頼性を担保している。

ヒープ確保のほうはドリフトの影響を受けない決定的な数字である:

| ループ(200,000 回) | 修正前 used 差 | 修正後 used 差 |
|---|---:|---:|
| `(+ s 1)` | 48 byte | 48 byte |
| **`(+ -1 1)`** | **6,400,048 byte**(32 byte/回) | **48 byte** |
| `(- s 1)` 正のまま | 48 byte | 48 byte |
| **`(- s 1)` 負へ落ちる** | **6,400,048 byte** | **48 byte** |
| **`(- 1 -1)`** | **6,400,048 byte** | **48 byte** |
| `(+ *max-fix* 1)`(一般パス) | 16,000,048 byte | 16,000,048 byte |

48 byte は `heap-probe` 自身(`funcall` 等)の固定オーバーヘッドで、
**確保しないループ 4 本すべてで同じ値**である。**`(+ -1 1)` のヒープ確保は完全に消えた。**

## 1. 修正前の条件(3-1)

### 1-1 何が「非負」を要求していたか

| 関数 | 高速 path の条件 | 外れたときの行き先 |
|---|---|---|
| `primitive_add`(n 項) | 全オペランドが FIXNUM **かつ非負**、途中の和が 60bit 以内 | 符号マグニチュード一般パス(`decompose`/`limb_alloc`/`mag_add`/`mag_sub`/`os_make_integer`) |
| `primitive_add2`(2 項、JIT 用) | 両方 FIXNUM **かつ非負**、和が 60bit 以内 | `os_make_cons` ×2 → `primitive_add` |
| `primitive_subtract`(n 項) | 全オペランドが FIXNUM **かつ非負**、**途中経過が負にならない** | 一般パス |
| `primitive_subtract2`(2 項、JIT 用) | 両方 FIXNUM **かつ非負**、**`mag_b <= mag_a`** | `os_make_cons` ×2 → `primitive_subtract` |

`(+ -1 1)` は 3 つ目・4 つ目の条件をすべて満たさないので、

```
primitive_add2 → os_make_cons ×2 (32 byte) → primitive_add
              → LIMB_FRAME / decompose ×4 / limb_alloc / mag_compare / mag_sub
              → os_make_integer → (60bit に収まるので) os_make_fixnum_signed
```

を通っていた。**結果は最初から fixnum なのに、bignum の全機構を経由していた。**

### 1-2 ヒープ確保 32 byte の正体

計測で分かったこと: 一般パス自身は**ヒープを確保していない**。
`limb_alloc` は静的な作業アリーナ(`g_limb_arena`)を使い、`os_make_integer` は
60bit に収まれば `os_make_fixnum_signed` で即値を返すからである。

**32 byte はすべて `primitive_add2` / `primitive_subtract2` の
`os_make_cons(a, os_make_cons(b, nil))` である**(cons 2 個 × 16 byte)。

これは修正前の warmup 計測とも一致する: `(+ -1 1)` を 100 回で 3,248 byte
= 100 × 32 + 48(固定オーバーヘッド)。

### 1-3 なぜこうなっていたか

fixnum は **符号マグニチュード表現**である(2 の補数ではない)。

```
 63    62                        3   2 1 0
+---+------------------------------+-------+
| S |        magnitude (60bit)     | 0 0 0 |
+---+------------------------------+-------+
```

非負どうしなら raw 値をそのまま `add` / `sub` できるが、符号が絡むとそのままでは
足せない。そこを一般パスへ丸投げしていたのが修正前の姿である。

## 2. 修正の内容(4-1)

### 2-1 `fixnum_add_signed`(`src/c/runtime.c:4939`)

符号込みの fixnum 加算を 1 箇所に集約した。

```c
static int fixnum_add_signed(lisp_val_t a, lisp_val_t b, lisp_val_t *out) {
    if ((a & TAG_MASK) != TAG_FIXNUM || (b & TAG_MASK) != TAG_FIXNUM) {
        return 0;
    }
    UINT64 mag_a = os_fixnum_magnitude(a);
    UINT64 mag_b = os_fixnum_magnitude(b);
    int neg_a = os_fixnum_is_negative(a);
    int neg_b = os_fixnum_is_negative(b);

    if (neg_a == neg_b) {
        /* 同符号: マグニチュードを足す。60bitを超えたらbignumへ */
        UINT64 sum = mag_a + mag_b;
        if (sum > FIXNUM_MAGNITUDE_MASK) {
            return 0;
        }
        *out = os_make_fixnum_signed(neg_a, sum);
        return 1;
    }
    /* 異符号: マグニチュードの大きいほうから小さいほうを引き、符号は大きいほうに従う */
    if (mag_a >= mag_b) {
        *out = os_make_fixnum_signed(neg_a, mag_a - mag_b);
    } else {
        *out = os_make_fixnum_signed(neg_b, mag_b - mag_a);
    }
    return 1;
}
```

`-` 側は `fixnum_negate`(符号ビットだけ反転した新しい即値を作る)を通して
**`a - b` を `a + (-b)` に帰着**させた。符号マグニチュード表現では反転が常に正確で、
2 の補数の `INT_MIN` のような「反転できない値」が存在しないため、この帰着は無条件に安全である。

### 2-2 適用箇所

| 関数 | 変更 |
|---|---|
| `primitive_add2` | `fixnum_add_signed(a, b)` 1 本に置き換え |
| `primitive_subtract2` | `fixnum_add_signed(a, fixnum_negate(b))` に置き換え |
| `primitive_add`(n 項) | アキュムレータを `UINT64 sum` から**タグ付き `lisp_val_t sum_val`** へ変え、各項を `fixnum_add_signed` で畳む |
| `primitive_subtract`(n 項) | 同様。各項を `fixnum_negate` してから畳む |

n 項版のアキュムレータは**常に FIXNUM の即値**なので、ループ中にヒープ確保も GC も起きない
(`args` を辿る `cc_cdr` も確保しない)。修正前と同じ性質を保っている。

### 2-3 変更していないもの(7 章の制約)

- **fixnum の表現**。符号マグニチュードのまま
- **JIT のインライン展開**(`za_emit_arith_call_or_inline`)。出す機械語は 1 byte も変えていない
- `*` / `/` / 比較。§5 に記録して別作業として提案する

`za.c` は**コメントのみ**変更した。修正前は

> それぞれの C 実装が持つ fixnum 高速 path(共に非負 fixnum かつ結果が 60bit に収まる)と
> **完全に同一の条件・結果**になるインラインアセンブリを生成し

と書かれていたが、改善A で C 側が広がったのでこの記述は成り立たなくなる。
**JIT のインライン path は C 側高速 path の「真部分集合」になった**ことを明記した
(結果の値はどちらの経路でも同一)。嘘になったコメントを残さないための変更である。

## 3. 境界の扱い(4-3)

### 3-1 昇格

マグニチュードが 60bit を超えたら `fixnum_add_signed` は 0 を返し、
**従来どおり一般パス経由で bignum になる**。

```lisp
(bignump (+ *max-fix* 1))          ; => t  正側
(bignump (+ (- *max-fix*) -1))     ; => t  負側
(bignump (- (- *max-fix*) 1))      ; => t  減算からの負側
(bignump (- *max-fix* -1))         ; => t  減算からの正側
```

同符号の加算で `mag_a + mag_b` が `UINT64` で溢れることはない
(高々 `2*(2^60-1) < 2^61`)。異符号のときは結果のマグニチュードが元の最大値以下なので
60bit を超えようがない。

### 3-2 降格

`os_make_integer` が 60bit に収まれば `os_make_fixnum_signed` を返す既存の仕組みが
そのまま働く。

```lisp
(fixnump (- (+ *max-fix* 1) 1))    ; => t  bignum → fixnum
(= (- (+ *max-fix* 1) 1) *max-fix*)
```

### 3-3 `-0` を作らない

`os_make_fixnum_signed` はマグニチュード 0 のとき符号ビットを落とす(`runtime.c:3000`)。
結果が 0 になるのは (1) 同符号で `mag_a = mag_b = 0`、(2) 異符号で `mag_a == mag_b` の
2 通りで、どちらもここを通る。

**fixnum は即値なので `-0` ができると `(eq 0 x)` が偽になり、`eq` で 0 を判定している
既存コードが静かに壊れる。** テストで明示的に確認している:

```lisp
(eq 0 (+ -1 1))        ; => t
(eq 0 (- 1 1))         ; => t
(eq 0 (- 0))           ; => t
(eq 0 (+ *max-fix* (- *max-fix*)))   ; => t
```

### 3-4 多項での順序依存は変わらない

高速 path は左から順に畳むので、**途中で 60bit を超えたら最終結果が fixnum に
収まっていても一般パスへ落ちる**。この性質は改善A の前後で同じである。

```lisp
(+ *max-fix* *max-fix* (- *max-fix*) (- *max-fix*))  ; => 0(一般パス経由、fixnum)
```

### 3-5 bignum / float が絡むケース

`fixnum_add_signed` はタグを見て 0 を返すだけなので、**従来と完全に同じ経路**を通る。

## 5. 同じ問題が残っている箇所(3-2。**本作業では直していない**)

### 5-1 `*` — まったく同じ構造(改善B として提案)

`primitive_multiply2`(`runtime.c:5325`)と `primitive_multiply`(`runtime.c:5259`)の
高速 path が、`+`/`-` と同じく `!os_fixnum_is_negative(a) && !os_fixnum_is_negative(b)`
を要求している。**`(* -2 3)` は bignum 機構を通る。**

**直し方は `+`/`-` より単純である。** 符号は `neg_a ^ neg_b`、マグニチュードは
`mag_a * mag_b` で、既存のオーバーフロー判定
(`mag_a == 0 || mag_b <= FIXNUM_MAGNITUDE_MASK / mag_a`)をそのまま使える。
場合分けが要らない分、`+`/`-` のような「同符号/異符号」の分岐すら不要である。

**注意: これは「`*` の JIT インライン化」とは別物である。**
インライン化(`imul` + オーバーフロー検査)は符号マグニチュード表現では 2 段の検査が
必要で、`documents/type-system-survey.md` §9-4 のとおり別の難しさがある。
ここで言っているのは **C 側の高速 path の条件を広げるだけ**の話。

### 5-2 `/` — 同じ構造だが、直し方は自明ではない

`primitive_divide`(`runtime.c:5351`)も `!os_fixnum_is_negative` を要求している。

ただし除算は**切り捨ての方向**を決めないと符号付きに広げられない
(`(/ -7 2)` を -3 とするか -4 とするか)。一般パスが現在どちらの規則を実装しているかを
確認してから合わせる必要があり、`*` のように機械的ではない。

### 5-3 比較(`<` / `>` / `=`)は**この問題を持っていない**

`number_compare`(`runtime.c:4632`)は fixnum×fixnum のとき

```c
int neg_a = os_fixnum_is_negative(a);
int neg_b = os_fixnum_is_negative(b);
if (neg_a != neg_b) { return neg_a ? -1 : 1; }
/* 同符号ならマグニチュードを比較 */
```

と**最初から符号を扱っている**。負数でも bignum 機構には落ちない。

比較に足りないのは JIT のインライン化のほうで、これは
`documents/type-system-survey.md` §7-3 に記録済み(別作業)。

## 6. `-` が `+` より速い件(3-3)— **再現しなかった**

`documents/type-system-survey.md` §7-4 に「`-`(0.25 µs)が `+`(0.63 µs)より速い理由が
説明できていない」と残した件について、今回**同一形のベンチを組んで測り直した**。

### 6-1 対照を揃えた測定

§7-4 の 2 本は、実は**比較可能な形になっていなかった**。

- `(+ s 1)` は `s` を **0** から始めていた
- `(- s 1)` は `s` を **1,000,000,000** から始めていた

初期値を揃えた 2 本(`(+ s 1)` / `(- s 1)`、どちらも s0=1e9、他はすべて同一)と、
リテラルどうしの 2 本(`(+ 5 3)` / `(- 5 3)`)を足して測った結果:

| | 修正前 | 修正後 |
|---|---:|---:|
| `(+ s 1)` s0=1e9 | **0.41 µs** | **0.35 µs** |
| `(- s 1)` s0=1e9 | 0.51 µs | 0.53 µs |
| `(+ 5 3)` | **0.15 µs** | **0.19 µs** |
| `(- 5 3)` | 0.65 µs | 0.62 µs |

**形を揃えると `+` のほうが速い。** これは生成される命令数と一致する。

```
+ のインライン(高速 path を通る分): mov / or / movabs / test / jne / mov / add / js / mov / jmp   = 10 命令
- のインライン(高速 path を通る分): mov / or / movabs / test / jne / cmp / jb / mov / sub / mov / jmp = 11 命令
```

`-` は結果が非負かどうかを `cmp` + `jb` で先に判定する分、命令が 1 つ多い。
**TCG のコストは命令数に比例するので、`+` のほうが速いのが素直な結果である。**

### 6-2 §7-4 の値は何だったのか

同じコード(どちらも今回の変更の影響を受けない経路)を別ブートで測ると:

| | §7-4 の測定 | 今回(修正前) | 今回(修正後) |
|---|---:|---:|---:|
| `(+ s 1)` | 0.63 µs | 0.44 µs | 0.42 µs |
| `(- s 1)` 正のまま | 0.25 µs | 0.51 µs | 0.53 µs |

**`(- s 1)` が 0.25 → 0.51 と 2 倍動いている。** コードは 1 byte も変わっていない。
これは PR #66 で報告した実行間ドリフトそのもので、
§7-4 の 2 本はたまたま逆方向に振れたものを並べていたことになる。

### 6-3 結論

**§7-4 の「`-` が `+` より速い」は再現しない。** 形を揃えると
命令数どおり `+` のほうが速く、修正前・修正後の両ビルドで同じ順序になる。

**`+` 側に無駄があったわけではなかったので、本作業で一緒に直せるものは無かった。**

なお、この件は「同一ブート内で比較する」だけでは足りないことを示している。
§7-4 の測定も同一ブート内だったが、**比較する 2 本のループの形が揃っていなかった**。
今後は「同一ブート内」に加えて「被測定以外を完全に揃える」ことを条件にする。

## 7. 今後の選択肢(本作業では決めない)

### 7-1 JIT のインライン path を符号込みに広げるか

現在、JIT は**両方が非負のときだけ**インラインで計算し、それ以外は
`primitive_add2` / `primitive_subtract2` を call する。改善A でその call 先が速くなったので、
`(+ -1 1)` は 5.76 → 0.38 µs になった。

さらに JIT 側も符号込みにすれば call すら消せるが、

- 符号マグニチュードでは「同符号なら加算、異符号なら比較して減算」の**分岐が要る**
- Phase 3 で「分岐を増やすと TCG では遅くなる」ことを踏んでいる
- 現状で `(+ -1 1)` は 0.38 µs、インライン path に乗る `(+ s 1)` は 0.42 µs で、
  **すでに差が無い**(`-` 側は 0.85 µs vs 0.53 µs で差が残っている)

**測ってから決めるべきで、少なくとも `+` については広げる理由が見当たらない。**
