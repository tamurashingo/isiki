# JIT のタグ関連定数を C 側の定義から導出する形に整理する

実施日: 2026-09-17 / ブランチ: `feature/jit-tag-constants` / base: `main`
（PR #72・#73・#74 マージ後の main から派生）

タグ拡張（ポインタの下位4bitをタグに使う）の前段として、JIT が機械語へ埋め込んでいる
タグ由来の定数を、すべて C 側の定義から導出する形にした。

**挙動を一切変えないリファクタリングである。** タグの値・タグ幅・fixnum のエンコードは
変更していない。JIT の出力バイト列が変更前と完全に一致することを実測で確認した（第5章）。

---

## 1. なぜ必要だったか

JIT は `jit_emit8/32/64` で生のバイト列を組み立てる。生バイト列の中では `0x07` や `0xF8` は
ModRM・REX・レジスタ番号としても普通に現れるので、**grep ではタグの定数と命令の
エンコーディングを見分けられない**。実際 `~TAG_MASK` を表す `0xF8` が9箇所へ独立に
直書きされており、`TAG_MASK` を変えても追随しない状態だった。

これは PR #72 の報告書 7.1 が「将来の改修で不一致を生む構造的リスク」として記録していた
ものと同じ形である。

## 2. Step 2: `jit_emit8/32/64` の全呼び出しの分類

### 2.1 呼び出しの構造

`jit_emit8/32/64` の呼び出しは **70箇所**あり、そのすべてが
`za.c` の薄いヘルパ層（`jit_emit8` の定義から `jit_*_rel32_placeholder` まで、
行 128〜411 付近）と、シンボル名をコードページへ埋め込む1箇所（行 2121-2124）に
閉じている。つまり**分類すべき「値」はヘルパの引数**であり、呼び出し元まで
さかのぼって分類した。

| 分類 | 意味 |
|---|---|
| E | 命令のエンコーディング（オペコード・ModRM・SIB・REX） |
| T1 | タグマスク |
| T2 | タグの値 |
| T3 | タグを外すための変位 |
| T4 | fixnum のエンコード |
| L | オブジェクト／フレームのレイアウト |
| A | アドレス |
| O | その他 |

#### T3: タグを外すための変位

**該当なし（0箇所）。**

`jit_mov_reg_from_mem_disp8` / `jit_mov_mem_disp8_from_reg` に渡している disp8 の値は
実測で **0 / 8 / 16 / 24 の4種類だけ**で、いずれも「ワード番号 × 8」の素直な
フィールドオフセットである。タグ付きポインタのままフィールドを読む箇所は無く、
必ず `za_emit_untag_instance`（= `and reg, ~TAG_MASK`）で実アドレスにしてから読む。

例（`za_compile_catch`、`za.c:4833-4854`）:

```c
za_emit_untag_instance(ZA_REG_RCX, ZA_REG_R13);        // ここで untag
jit_mov_reg_from_mem_disp8(ZA_REG_RAX, ZA_REG_RCX, 0);  // word0
...
jit_mov_reg_from_mem_disp8(ZA_REG_RAX, ZA_REG_RCX, 8);  // word1
jit_mov_reg_from_mem_disp8(ZA_REG_RAX, ZA_REG_RCX, 16); // word2
```

つまり **disp に `8 - tag` のような補正が混ざっている箇所は1つも無い**。
指示書が「見落としやすい」と警告していた分類だが、この JIT には存在しなかった。

#### T4: fixnum のエンコード

`movabs` の imm64 に埋め込む絶対アドレス。`(void *)` 付きの C 関数ポインタ、

ダンプではこれらをマスクしてからハッシュする。

## 3. Step 3: C 側の概念との対応

### 3.1 対応表

| JIT が必要とする概念 | C 側の定義 | 追加した JIT マクロ |
|---|---|---|
| タグを取り出すマスク | `TAG_MASK`（`runtime.h:8`） | `JIT_IMM8_TAG_MASK` |
| タグを落とすマスク（imm8） | `~TAG_MASK` | `JIT_IMM8_UNTAG_MASK` |
| タグの値 | `TAG_INSTANCE` 等 | （そのまま使用。imm64 なので幅の問題が無い） |
| fixnum のエンコード | `os_make_fixnum()` / `FIXNUM_SIGN_BIT` | （そのまま使用） |
| オブジェクトのワードオフセット | — | （数値のまま。タグ非依存） |

### 3.2 値が同じで概念が異なるもの

**これらを同じマクロにまとめてはならない。** 現在はすべて 3（またはそこから導く値）だが、
「ポインタのタグ幅だけを4bitへ広げ、即値の表現は据え置く」案がありうる
（PR #72 報告書 5.5）。まとめると、片方だけ動かしたい改修で必ず事故になる。

| 概念 | 定義 | 現在の値 |
|---|---|---|
| ポインタのタグ幅 | `TAG_MASK` = `0x7`（幅3bit） | 3bit |
| FIXNUM の値シフト量 | `FIXNUM_VALUE_SHIFT`（**本PRで新設**） | 3 |
| CHAR の値シフト量 | `CHAR_VALUE_SHIFT`（**本PRで新設**） | 3 |

### 3.3 C 側に残っていた直書き

**PR #72 の「C側のタグ操作に直書きは0件」は、*タグマスク*についての確認だった。**
本 PR で改めて `>> 3` / `<< 3` を洗ったところ、**fixnum・CHAR の値シフトが
49箇所直書きされていた**（PR #72 以降に入ったものではなく、元からあったもの）。

| ファイル | 件数 | 内容 |
|---|---|---|
| `runtime.c` | 22 | fixnum のエンコード/デコード、CHAR のコード取り出し |
| `subprimitive.c` | 19 | I/Oポート番号・アドレス・値の fixnum デコード、CHAR-CODE/CODE-CHAR |
| `ide_subprimitive.c` | 3 | デバイス番号・LBA の fixnum デコード |
| `format.c` | 2 | CHAR の出力 |
| `print.c` | 1 | CHAR の印字 |
| `stream_lisp.c` | 1 | CHAR の書き出し |
| `lisp.c` | 1 | fixnum キーの比較（下記 3.4） |
| `runtime.h` | 1 | `os_make_fixnum` 本体 |
| **合計** | **49** | すべて `FIXNUM_VALUE_SHIFT` / `CHAR_VALUE_SHIFT` 経由へ置き換えた |

`za.c` に残る `>> 3` は 7箇所あるが、すべて **REX プリフィクスのレジスタ番号上位bit
取り出し**（`(reg >> 3) & 1`）で、タグとは無関係なので対象外とした。

### 3.4 調査中に見つけた既存の不具合（本PRでは直していない）

`cc_assoc_eq`（`lisp.c:82`）:

```c
else if (k & TAG_FIXNUM && (k >> 3) == (key >> 3)) {
```

`TAG_FIXNUM` は `0x0ULL` なので `k & TAG_FIXNUM` は**常に 0**、この `else if` は
**到達しない死んだ分岐**である。意図は `(k & TAG_MASK) == TAG_FIXNUM` だったと思われる。

**実害は無い。** fixnum はタグが 0 なので、同じ値の fixnum は `k == key` という
上の分岐でそのまま一致する（`(k>>3)==(key>>3)` かつ符号ビットも一致するなら
`k == key` も成り立つ）。つまりこの分岐は活かしても冗長である。

**本 PR では直さない。** 直すと死んでいた分岐が動き出すので、
「挙動を一切変えないリファクタリング」という本 PR の前提から外れる。
シフトのマクロ化だけ行い、条件式はそのまま残した。

## 4. Step 4: 追加した `_Static_assert`

`src/c/za_jit_tags.h`（新設）:

| 検査 | 意図 |
|---|---|
| `TAG_MASK <= 0x7F` | imm8（符号付き8bit）に収まること。収まらなくなったら `and r/m64, imm8` では表現できない |
| `(INT64)(INT8)JIT_IMM8_UNTAG_MASK == (INT64)~(UINT64)TAG_MASK` | **符号拡張した結果が `~TAG_MASK` と一致すること**。`and r/m64, imm8` の imm8 は64bitへ符号拡張されるので、ここが崩れると「タグを落としたつもりで別のビットを落とす」 |
| `(INT64)(INT8)JIT_IMM8_TAG_MASK == (INT64)(UINT64)TAG_MASK` | 同上（マスクを取り出す側） |

`src/c/types.h` に `INT8`（`signed char`）を追加した。`INT16`/`INT32`/`INT64` はあったが
`INT8` だけ無く、上の符号拡張の検査に必要だったため。

## 5. Step 1・5: JIT 出力の同一性

### 5.1 ダンプの仕組み

`JIT_DUMP=1` のときだけ、JIT がコンパイルした関数ごとに
「出力サイズ・マスクしたバイト数・バイト列のハッシュ（FNV-1a 64bit）」を
シリアルへ出す（`za.c`、`[JITDUMP]` 行）。

素朴にバイト列をハッシュすると、`movabs` に埋め込む**絶対アドレス**が起動ごとに
変わる（UEFI のロードアドレス・Lisp ヒープ・`nil` 等）ため一致しない。
そこでアドレスの即値だけをマスクしてからハッシュする。

アドレスかどうかは `jit_emit64` の時点で値だけを見て判定する:

```
タグを外した値が [0x10000, 2^48) に入っていればアドレスとみなす
```

- 上限 2^48 は x86-64 の canonical な下位半分の上限。
  `TAG_MASK | FIXNUM_SIGN_BIT`（`0x8000000000000007`）のような
  「大きいが定数」をアドレスと誤認しないため
- 下限 0x10000 は、MAGIC 値・タグ値・`argc`・`os_make_fixnum(n)` のような
  小さな定数をマスクしないため（**マスクしてしまうと、まさに検出したい
  タグ定数の変化が見えなくなる**）

この判定が安定していることは、同じ条件で2回流してダンプが一致することで確かめた。

### 5.2 結果

| 比較 | 結果 |
|---|---|
| 変更前を2回実行（決定性の確認） | **1038関数、完全一致** |
| 変更前 vs T1置き換え後 | **1038関数、完全一致** |
| 変更前 vs 全変更後（C側シフト整理も含む） | **1038関数、完全一致** |

### 5.3 `za.o` の `.text` 比較

`objdump -d` の生の比較では **182行（91命令）が異なる**。内訳を確認したところ、
**すべて `movl $0x14xx, ...` の形**で、`ZA_BAIL_LINE()`（`za.c:4942`）が記録する
`__LINE__` の定数が +1 ずれたものだった。`#include "za_jit_tags.h"` を足したことによる
行番号の移動で、**生成される命令列そのものではない**。

`__LINE__` 定数だけを正規化して再比較すると:

```
★ __LINE__定数を正規化すると完全一致(他の命令は1つも変わっていない)
```

`__LINE__` は `%%DIAG-ZA-BAIL-LINE` の診断表示にしか使われず、JIT が**出力する**
バイト列には入らない。実際、実行時の JIT ダンプ（5.2）は完全一致している。

### 5.4 変異テスト（置き換え漏れがないことの確認）

出力が同一というだけでは「全箇所をマクロに置き換えた」証明にならない
（直書きが残っていても値が同じなら出力は変わらない）。そこで、マクロの値だけを
一時的に変えてビルドし、**変化した命令の数が分類表の件数と一致するか**を確かめた。
変異中は `_Static_assert` を外している（変異させると当然落ちるため）。

| マクロ | 変異後の値 | 期待件数 | 実際 | 判定 |
|---|---|---|---|---|
| `JIT_IMM8_UNTAG_MASK` | `0xE0` | 9 | **9** | 一致 |
| `JIT_IMM8_TAG_MASK` | `0x1F` | 1 | **1** | 一致 |

復元後の `za.o` が変異前と一致することも確認済み。

T2・T4 は**元からマクロ／関数経由**で直書きが無いため、変異テストの対象外とした
（`TAG_INSTANCE` や `os_make_fixnum()` を書き換えれば C 側の全利用箇所が動くので、
「JIT だけが古い値を使う」という本 PR が対象にする形の事故は起きない）。

## 7. タグ拡張で変更が必要になる箇所

タグ幅を 3bit → 4bit（`TAG_MASK` = `0xF`）にした場合。

### 7.1 自動的に追随するもの

| 箇所 | 現在の値 | 4bit化後 | 命令の幅に収まるか |
|---|---|---|---|
| `JIT_IMM8_UNTAG_MASK` | `0xF8`（= −8） | `0xF0`（= **−16**） | **収まる**（imm8 は −128〜127） |
| `JIT_IMM8_TAG_MASK` | `0x07` | `0x0F` | **収まる** |
| C 側の `TAG_MASK` 利用箇所（`runtime.c` 141件、`za.c` 136件ほか） | — | — | マクロ経由なので追随 |

`_Static_assert` が両方とも成立し続けることは、値を入れて確かめられる:
`(INT64)(INT8)0xF0 == -16 == (INT64)~0xFULL`。

### 7.2 手で直す必要があるもの

| 箇所 | 理由 |
|---|---|
| `FIXNUM_VALUE_SHIFT` / `CHAR_VALUE_SHIFT` | **タグ幅とは別の定数にしてある**（3.2）。即値の表現も4bitへ寄せるなら両方を4にする。fixnum のマグニチュードが 60bit → 59bit に縮むので `FIXNUM_MAGNITUDE_MASK` も連動する |
| `TAG_*` の値の割り当て | 0x0〜0x7 の8値がすべて埋まっている（PR #72 報告書 2.2）。4bit化して初めて空きができる |
| `MAGIC_*` と `TAG_FORWARD` の下位ビット衝突 | 現在 `MAGIC_STREAM`(0x6)・`MAGIC_BUILTIN_CLASS`(0xE) が `TAG_FORWARD`(0x6) と下位3bitで衝突しており、範囲検査の下限だけで弾いている（PR #72 報告書 7.2）。4bit化すると衝突する顔ぶれが変わるので、`MAGIC_MUST_BE_BELOW` の不変条件を見直す必要がある |
| `GC_DEBUG_TRAP_PATTERN_VALUE`（`0xDEADDEADDEADDEA7`） | 下位4bitが `0x7`。4bit化すると意味が変わる |

### 7.3 幅に関するリスク

**imm8 に収まらなくなるものは無い。** タグ幅を 4bit にしても
`~TAG_MASK` の下位8bit は `0xF0` = −16 で、`and r/m64, imm8` の範囲内である。
disp8 側も、T3 が0箇所（2.2）なのでタグ幅の影響を受けない。

タグ幅を **5bit 以上**にする場合は `~TAG_MASK` = `0xE0` = −32 … と続き、
7bit（`~TAG_MASK` = `0x80` = −128）までは imm8 に収まる。
`TAG_MASK <= 0x7F` の `_Static_assert` がその限界を守る。
