# 記録と計測の規則

PR #84〜#93(`declare` の型特化と四則の高速路)で踏んだ失敗から、
**規則の形**で取り出したもの。個々の事情は各文書にあり、ここには
「次に同じことをしないために何を書くか」だけを置く。

## この文書自身の規約

**番号と ID は固定する。追加は末尾のみ。振り直さない。**

規則は PR のコメントや他の文書から「規則 6」のように番号で参照される。
**振り直すと、過去の参照が別の規則を指すようになる。**
これはこの文書が防ごうとしている事故そのものである。

> **【実例。この文書で起こした】** 規則 8・9 を足したとき、
> 話の流れが良くなるからという理由で**通し番号を振り直した**。
> その結果、直前のレビューで書かれた「規則 6 に従って否定の結果を残す」が、
> 振り直し後は「時間より確保量と命令数を測る」を指すようになった。
> レビューで指摘されて戻した。**並べ替えたくなったら、見出しの順だけ変えて
> 番号は動かさない。**

括弧内の `R-claim` のような**不変 ID** を併記してある。
番号より ID で参照するほうが安全である。

| ID | 規則 |
|---|---|
| R-claim | 1. 「確認済み」と書くなら何をどう確認したかを同じ行に書く |
| R-identical | 2. 完全一致は「疑え」の合図であって証明ではない |
| R-floor | 3. 床を測ってから差を語る |
| R-repro | 4. 再現するまでは効果と呼ばない |
| R-control | 5. 対照群は嘘をついていてはならない |
| R-negative | 6. 否定の結果は消さずに残す |
| R-lie | 7. 「手で試したら正しかった」は何の保証にもならない |
| R-positive | 8. 陽性対照を置く |
| R-instrument | 9. 時間より、確保量と命令数を測る |
| R-resolution | 10. 「差が無い」と書く前に、計器の分解能を示す |
| R-predeclare | 11. 例外の宣言は、観測より前に置いたときだけ有効 |

## 規則 1 (R-claim): 「確認済み」と書くなら、**何をどう確認したかを同じ行に書く**

書けないなら「実装から読んだ」「未確認」と書く。

### なぜ

**誤りそのものより、伝播の仕方が問題になる。**

`documents/divide-direct-call.md` に
「`/` が速くなれば `quotient` 経由でも効く」と書かれ、
それが `documents/declare-typed-arith.md` §3-3 へ
**「(PR #88 で確認済み)」という札付きで**写され、
さらに次の作業指示書がそれを前提に「`quotient` を別に測れ」と指示した。

**三つの文書を経由しても、誰も「何をどう測って確認したのか」を問わなかった。**
実際には `init.lisp` を一段読めば分かることだった
(`%quotient2` は整数どうしなら `mod` と `div` を使い、`/` を呼ばない)。

### 何が起きていたか(この件の全容)

PR #88 の測定自体は正しかった。**ラベルと一般化が間違っていた。**

| | PR #88 の記録 | 実際 |
|---|---|---|
| `quotient` 整数 bytes/call 272 → 240 | 「内側の `/` の cons が消えたぶん」 | **割り切れないときの `(/ (float x) (float y))` の cons**。float 経路の `/` である |
| そこからの一般化 | 「`/` が速くなれば `quotient` にも効く」 | **整数の高速路には効かない。** `quotient` はそこを通らない |

PR #93 で `/` の整数経路から内側の cons を消したとき、
**`quotient` の確保量は 1 byte も動かなかった。**

| | 変更前 | 変更後 |
|---|---:|---:|
| `/` 整数 | 80 byte/call | **48**(= 何もしない関数と同じ) |
| `quotient` 整数(割り切れる) | 192 | **192** |
| `quotient` 整数(割り切れず) | 288 | **288** |
| `quotient` single | 128 | **128** |

**「効くはず」を数字が否定した。** 読みの裏づけは、この 0 のほうである。

### 書き方の例

```
悪い: / が速くなれば quotient 経由でも効く(PR #88 で確認済み)
良い: PR #88 で quotient の bytes/call が 272 → 240 に減った。ただし減ったのは
      割り切れないときの (/ (float x) (float y)) のぶんで、整数の高速路は
      quotient から到達しない(init.lisp の %quotient2 を読んだ。未測定)
```

## 規則 2 (R-identical): **完全一致は「疑え」の合図であって「間違っている」の証明ではない**

疑って調べて白だったときも、**調べたことと白だったことを報告に残す。**

黙ってしまうと、次の人は「完全一致は毎回ビンゴ」だと思い込む。

| いつ | 完全一致したもの | 結果 |
|---|---|---|
| PR #87 / #88 | ベンチの数字が宣言あり/なしで完全一致 | **本物**。`git stash` が空振りして同じバイナリを 2 回測っていた |
| PR #89 | code-len が完全一致 | **本物**。ベンチの片方がリテラルで型不明になり、特化が一度も発動していなかった |
| PR #93 | `.text` のサイズが分岐元と完全一致 | **偶然**。md5 は違い、`.pdata` は +36 byte。16 byte のアラインメント枠にたまたま収まっただけ |

確かめ方は「別の計器を当てる」。PR #93 では `.text` の md5 と `.pdata` の
サイズを見た。**サイズだけを見ていたら白黒が付かなかった。**

## 規則 3 (R-floor): **床を測ってから差を語る**

ベンチの総時間のうち、**測りたいものが占める割合**を先に出す。
出していない数字の百分率には意味が無い。

### なぜ

`declare` の型特化を 4 演算ぶん測って、`+8` `+28` `±0` `−36` といった数字を
4 つの PR に書いた。**あとから「何もしない関数」を同じループで測ったら、
それが総時間の 88〜98% を占めていた。**

```
n=2,000,000、同一ブート
  (defun f-id (x y) x)   ← funcall とループと JIT フレームだけ   1280
  + fixnum 宣言なし                                              1304  (床+24)
  + single 宣言なし                                              1712  (床+432)
  + single 宣言あり                                              1316  (床+36)
```

**床を引く前の「single は 11% 速い」と、引いたあとの「演算のコストが
432 → 36 に落ちた」は、同じ測定の別の言い方である。** 後者が事実に近い。

そして fixnum 側の `+8` や `+28` は、床を引くと**再現しない大きさ**だった
(規則 4)。

### 床の測り方

`(defun f-id (x y) x)` を同じループで回す。**特化の対象に何もしない関数を
差し込む版**も作れるなら、なお良い(呼び出しそのもののコストが分離できる)。

```
同一ブート、n=2,000,000
  f-id(call 無し)                      1164
  no-op の特化関数を call               1400   ← call 自体が +236
  GENERIC(本当に割る)                  1380   ← 除算そのものは測れない
```

**「呼び出しを 1 回足す」が +236、「その中で実際に割る」が ±0。**
ここまで分解して初めて、次に削るべきものが決まる。

## 規則 4 (R-repro): **再現するまでは効果と呼ばない**

同一ブート内の最小値を 3 回取っても足りない。**ベンチの形を変えて、
別のブートで、もう一度出ること**を確認する。

### 実例

PR #91 は「`-` の fixnum は宣言すると 23% 遅くなる(120 → 148)」と報告した。
同一ブート・3 回の最小値で、3 回とも一貫していた。

**PR #93 で同じベンチの形・同じ引数・同じビルド系列で取り直したら、
120 対 120 で差が消えた。** 床の行を足したこと以外は同じである。

```
PR #91   fixnum nodecl 120 / decl 148   (+28)
PR #93   FLOOR 116, fixnum nodecl 120 / decl 120   (±0)
```

関数の配置が変わると TCG の測定は 10% 程度動く。
**「同一ブート内で一貫している」は再現性の保証にならない。**

### 目安

- 差が**床の 10% 未満**なら、まず再現を疑う
- 分解能が足りないなら **n を 10 倍にする**(tick は 10ms。
  n=200,000 では 4 tick が最小単位で、そこに数 tick の差を乗せても読めない)
- 再現しなかったら、**前の報告を訂正する。** 黙って上書きしない

## 規則 5 (R-control): 対照群は**嘘をついていてはならない**

「変わらないはずのもの」を置くのが対照群だが、
**置き方を間違えると対照群がいちばん派手に動く。**

PR #91 で bignum の対照を `(declare (type <fixnum> x))` の関数で取った。
bignum を `<fixnum>` と宣言するのは嘘で、特化版はタグを見ずにゴミを読み、
**「宣言すると 1.7 倍速い」**という最も目立つ改善に見えた。

**対照群は、特化表に載らない型を宣言して作る**(この処理系なら `<integer>`)。
GENERIC のままで、かつ嘘にならない。
**そして結果が GENERIC と一致することを出力に出す。**

---

## 規則 6 (R-negative): 否定の結果は**消さずに残す**

仮説が外れたら、外れたことを書く。**説明を作らない。**

PR #92 で「`*` の桁溢れ判定から 64bit 除算を消したのに速くならなかった」。
PR #93 で「`os_make_fixnum_signed` が `static inline` でないせいではないか」と
仮説を立てて検証し、**外れた**(inline 化の有無で差が出なかった)。

コードに残す場合、**理由を書き換える。**

```
悪い: /* [性能] 呼び出しオーバーヘッドが本体を上回るので inline にした */
良い: /* API の形を揃えるため。速度目的ではなく、実測でも差は出なかった(PR #93) */
```

**速度を理由に書いた瞬間、それが規則 1 の事故の種になる。**

## 規則 7 (R-lie): **「手で試したら正しかった」は何の保証にもならない**

`declare` の嘘を通常ビルドで試したときに何が返るかは、**演算ごとに違う。**

| 演算 | 嘘の宣言で返るもの | 目視で気づけるか |
|---|---|---|
| `+` `-` | ゴミの値(`1688849860263936` など) | **気づける** |
| `*` | **正しい答え** | 気づけない(が、害も無い) |
| **`/`** | **もっともらしい小さい整数**(構造的に 1〜2 付近) | **気づけない。いちばん危ない** |

### `/` が小さい整数を返すのは偶然ではない

single-float は**上位ビットに binary32 を置いている**ので、
`3.5f0` と `1.25f0` をマグニチュードとして読むとどちらも大きな整数になる。
しかし**指数部が近い値どうしはビットパターンも近い**ので、割ると 1 か 2 の
あたりに落ちる。

**そして実際のコードで割り算に渡る 2 つの値は、たいてい桁が近い。**

```
通常ビルド  (div-fixnum 3.5f0 1.25f0)  ->  1      (正しくは 2.8)
```

`1` が返ってきたら誰も疑わない。

`*` が「正しい答え」を返すのは、マグニチュードとして読んだ積が必ず桁溢れして
GENERIC へ落ち、そこで型が正しく判定されるからである。**洗われ方が演算ごとに
違うだけで、どれも目視では検出できない。**

**`ISIKIOS_DECLARE_AUDIT` が唯一の確実な検査である。**
そして**実際に嘘を通して panic を見るまで、検出器が働くかは分からない**
(PR #90 で検出器自体が壊れていた実例がある)。

この構造は将来 ratio を入れるときにも効く。タグ 0xD を使い始めると、
`/` の嘘が返す値の分布がまた変わる。
## 規則 8 (R-positive): **陽性対照を置く — 計器が対象を見られることを先に示す**

「変えたのに変わらなかった」と書く前に、**同じものを大げさに変えたら変わるか**を
確かめる。変わらなければ、それは現象ではなく計器の限界である。

### 実例

PR #89 は「`primitive_add2_fixnum` からタグ検査 1 組を省いたのに速くならない」を
謎として 4 つの PR にまたいで持ち越した。

PR #93 で**検査を 16 組に増やす版**を作って測ったところ、**そちらも動かなかった。**

```
版A 検査なし   + decl = 1484
版B 検査 1 組  + decl = 1500
版C 検査16組   + decl = 1484     ← 32 本の分岐を足しても動かない
```

**陽性対照が反応しないので、この計器は分岐を見られない。**
謎は消えた。`documents/declare-typed-arith.md` §11。

### 置き方

「消す」を測りたいなら、**逆向きに大げさに足す**版を作る。
`__asm__ volatile("" : "+r"(x))` を挟まないと gcc が畳むことがある。

## 規則 9 (R-instrument): **時間より、確保量と命令数を測る**

この環境(TCG、KVM 無し)で実測した計器の性格。

| 計器 | ぶれ | 分岐 32 本 | cons 2 個 |
|---|---|---|---|
| tick カウンタ(同一ベンチ・同一ビルド) | ±20 tick | **見えない** | — |
| tick カウンタ(ベンチの形を変える) | **±150 tick 超** | — | — |
| 命令数(`make test-qemu-instcount`、ブート全体) | **±4.3%** | 見える(+2.3%) | — |
| **確保量(`%%HEAP-USED-BYTES`)** | **ぶれ無し** | — | **見える(完全一致で 32 byte)** |

**tick カウンタは、ベンチファイルに定義した関数の個数が変わるだけで
同じ関数のコストが 150 tick 以上動く。ベンチをまたいだ比較は成立しない。**

```
11 個定義したベンチ   + fixnum 宣言なし = 床+24
 4 個定義したベンチ   + fixnum 宣言なし = 床+184
```

PR #84〜#93 の一連の作業で**唯一きれいな答えを出したのは確保量**である
(`/` の 80 → 48 byte/call、`quotient` が 1 byte も動かないこと)。

**そして `documents/performance-measurement.md` は、手法1(TCG プラグインに
よる命令数カウント)を「以後はこれを既定の手法とする」と定めている。
PR #84〜#93 はどれもそれを使わず、同じ表で「大まかな体感速度の比較」用途と
されている tick カウンタで測っていた。** 規則 1 と同じ事故である
——**定めた手法が文書にあるのに、読まれずに別の手法が使われた。**

命令数カウンタもブート全体では ±4.3% ぶれるので、
**細かい差を測るならプラグインの `start=/end=` でアドレス範囲を絞り、
ブートの基底(約 11 億命令)を測定から外すこと。**

## 規則 10 (R-resolution): **「差が無い」と書く前に、計器の分解能を示す**

示せないなら「**この計器では見えなかった**」「**再現しなかった**」と書く。
**「差が無い」と「見えなかった」は違う。**

**訂正にも同じ基準を課すこと。** 訂正は通常の報告より疑われにくい
——「前の数字は間違っていました」と書かれたものを、読む側はもう一度
検算しない。**訂正として書いた誤りは、初出の誤りより長く生き残る。**

### 実例: 同じ差を 3 回書き間違えた

`-` の fixnum 特化にコストがあるかどうかを、3 回書いて 3 回とも外した。

| いつ | 書いたこと | 実際 |
|---|---|---|
| PR #91 | 「+28 tick = **23% 遅い**」 | 大きさが違う |
| PR #93 §10-3 | 「**±0。再現しない。取り下げる**」 | 差は実在した |
| PR #94(命令数ゲート) | 「**+53.0 命令/回 = 約 6%**」 | これが確定値 |

**2 回目の訂正がいちばん危なかった。** 「再現しなかった」(事実)から
「差が無い」(主張)へ勝手に進んでおり、**しかも訂正として書いたので
権威が付いていた。** 正しくは「tick カウンタでは再現しなかった。
この計器の分解能(±20 tick)を下回る差かどうかは分からない」である。

### 書き方

```
悪い: 宣言あり/なしで差は無かった(±0)
良い: tick カウンタでは差が出なかった。この計器は分岐 32 本を
      見られないので(陽性対照)、この水準の差は測れていない
良い: 命令数ゲートで +53.0 命令/回(ぶれの幅 0 命令)
```

**分解能は陽性対照で示す**(規則 8)。示していない「±0」は、
規則 6(否定の結果を残す)を満たしたことにならない。

## 規則 11 (R-predeclare): **例外の宣言は、観測より前に置いたときだけ有効**

規則 2(完全一致は疑え)に「今回は完全一致が正常である」という例外を主張したく
なることがある。**主張が成立するのは、観測の前に書いてある場合だけ。**

測ってから同じ文章を書けば、**まったく同じ内容が言い訳になる。**
規則 10(訂正にも同じ基準)と同じ構造で、**形式が検査を弱める**。

### やること

- **実装より前に、期待値と「どう転んだら何を意味するか」を書く**
- 完全一致を予測するなら、**一致したことを別の計器で裏づける**
  (code-len、呼び先の名前、`%%INLINE-HERE` のビットなど)
- **予測が確定しているなら、それは検出器にできる。**
  観測して満足するより、**一致をテストで固定する**。そうすれば将来
  どちらかだけが変わった日に自動的に落ちる。
  予測が当たったことを確認するだけでは、**次に外れたとき誰も見ていない**

### 実例

`+` の fixnum を `inline` 宣言で展開したとき、展開される命令列は
「型宣言なし」の経路と**同一になるはず**だった(違うのは通らない
フォールバックの呼び先だけ)。これを実装前に PR へ書き、
**バイト列の一致をテストで固定した**(`documents/inline-arith.md` §9)。
