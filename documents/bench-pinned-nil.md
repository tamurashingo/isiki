# 実験: nil のレジスタ常駐(r12)— 速度の比較

> 実験日: 2026-09-16 / ブランチ: `feature/bench-pinned-nil`(分岐元 `feature/compiler-optimization` `566076b`)
> 関連: `documents/jit-pinned-register.md`(PR #65。不揮発レジスタの使用率、`-ffixed-r12` の実測)
>
> **これは実験であり実装ではない。** 全経路の r12 保存対応(`spawn` の `regs[3]` 仕込み、
> 診断プローブの移設)は行っていない。

## 結論: **差は出たが、一貫していない。r12 常駐は見送りで確定する。**

**nil 参照が支配的なベンチでは −10 〜 −19%、呼び出しを含むベンチでは +11% と、
符号が割れる。** 平均で見れば有利不利が打ち消し合う。

即値に占める nil の割合が 9〜11% しかない(`documents/jit-pinned-register.md`)という
既知の事実と整合しており、**「nil の参照に時間を要する」という当初の見立ては、
nil 参照が密な特定の形でしか成り立たない。**

コードサイズの削減は **1 関数あたり 3〜10 byte**(0.2〜1.1%)にとどまった。

---

## 実験の構成

**3 ビルドを比較した。** 指示書は 2 ビルドだったが、それでは
**「JIT が r12 を使う効果」と「C 全体がレジスタを 1 本失う効果」が混ざる**ため、
対照を 1 つ足した。

| | ビルド | JIT の nil | C のコード |
|---|---|---|---|
| **A** | 通常 | 即値(`mov r32, imm32`) | 通常 |
| **C** | `-ffixed-r12` | 即値(**A と完全に同一**) | **r12 を使わない** |
| **B** | `-ffixed-r12 -DISIKIOS_PINNED_NIL` | **r12 から読む** | r12 を使わない |

- **A → C** が「C がレジスタを 1 本失う効果」だけを表す(JIT コードは同一)
- **C → B** が「nil 常駐の効果」だけを表す(C コードは同一)

A と C の JIT コードサイズが**全ベンチで完全に一致**したことで、この分離が
正しく効いていることを確認した。

### 実装した仕掛け(実験用)

`src/c/za.c` に `ISIKIOS_PINNED_NIL` の `#ifdef` を 3 箇所:

1. `jit_load_imm_reg`: 値が `nil` なら `mov reg, r12`(3 byte)を出す。
   **これ 1 箇所で nil の materialize を全部拾える**
2. `za_emit_cmp_rax_nil`: nil との比較を `cmp rax, r12`(1 命令 3 byte)にする。
   通常は `mov r11, nil` + `cmp rax, r11` の 2 命令 8 byte。
   **命令数が 2 → 1 に減るのはここだけで、速度差が出るとすればこの形である**
3. `za_emit_pin_nil`: プロローグで `mov r12d, imm32(nil)` を出す(5 byte)

`-ffixed-r12` で gcc が r12 を使わないので、**JIT が r12 を壊しても C に影響しない。
したがって保存・復元は不要**(実験の範囲では)。

## 4-2: r12 が nil を保持していることの確認(測定前に実施)

```
#V immobilized 0xCC46000..0xDC46000
#V JIT内の r12        = 0xDC46031     ← immobilized 終端 + 0x31 = nil
#V C呼び出し後の r12  = 0xDC46031
#V ループ1000回後      = 0xDC46031
#V インタプリタから    = 0xDC46031
```

命令列も意図どおりだった。

```
0003  41 bc 31 60 c4 0d    mov r12d, 0xdc46031   ← プロローグ(両エントリ)
01a7  4c 39 e0             cmp rax, r12          ← 1命令
01b4  4c 89 e0             mov rax, r12          ← 3 byte
```

## 測定結果

2,000,000 回(リスト走査系は 20,000 回 × 100 要素)、**6 往復**。tick = 10ms。

| ベンチ | A 平均(最小〜最大) | C 平均(最小〜最大) | B 平均(最小〜最大) |
|---|---|---|---|
| `(null nil)` | 349.3(340〜372) | 312.0(304〜332) | 335.3(328〜360) |
| `(null *foo*)` | 662.0(652〜676) | 618.0(608〜636) | **554.7(536〜576)** |
| `(eq nil *foo*)` | 607.3(592〜636) | 603.3(588〜628) | 610.7(596〜636) |
| `null-check`(100要素走査) | 396.0(388〜416) | 396.0(388〜420) | **321.3(316〜340)** |
| `length`(末尾再帰) | 568.0(560〜592) | 583.3(572〜604) | **645.3(636〜664)** |
| `and-chain` | 653.3(640〜672) | 658.7(648〜696) | **732.7(712〜760)** |

### C → B(nil 常駐だけの効果)

| ベンチ | 差 | レンジ |
|---|---|---|
| `(null nil)` | +7.5% | **重なる(差なし)** |
| `(null *foo*)` | **−10.2%** | 重ならない |
| `(eq nil *foo*)` | +1.2% | **重なる(差なし)** |
| `null-check` | **−18.9%** | 重ならない |
| `length` | **+10.6%** | 重ならない |
| `and-chain` | **+11.2%** | 重ならない |

**速くなるものと遅くなるものが両方ある。**

### A → C(`-ffixed-r12` だけの効果。JIT コードは同一)

| ベンチ | 差 | レンジ |
|---|---|---|
| `(null nil)` | −10.7% | 重ならない |
| `(null *foo*)` | −6.6% | 重ならない |
| `(eq nil *foo*)` | −0.7% | **重なる(差なし)** |
| `null-check` | +0.0% | **重なる(差なし)** |
| `length` | +2.7% | **重なる(差なし)** |
| `and-chain` | +0.8% | **重なる(差なし)** |

**レジスタを 1 本落としても C 側は遅くならない**(むしろ 2 件で速くなった)。
`documents/jit-pinned-register.md` で `.text` が +32 byte しか増えなかったことと整合する。
**対照を取らずに A と B だけを比べていたら、この分を nil 常駐の効果と取り違えていた。**

## 6-2: nil 参照の回数と差の相関

各ベンチの生成コード中の即値の個数(`%%DIAG-ZA-SCAN`、PR #64 で記録ベースになり正確)。
**B では nil が即値でなくなるので、その差が nil 参照の回数にあたる。**

| ベンチ | A の即値 | B の即値 | **nil 参照** | len 差 | C→B の速度 |
|---|---|---|---|---|---|
| `(null nil)` | 66 | 60 | **6** | −5 | +7.5%(差なし) |
| `(null *foo*)` | 68 | 63 | **5** | −3 | **−10.2%** |
| `(eq nil *foo*)` | 74 | 68 | **6** | −5 | +1.2%(差なし) |
| `null-check` | 65 | 60 | **5** | −3 | **−18.9%** |
| `length` | 63 | 58 | **5** | −6 | **+10.6%** |
| `and-chain` | 31 | 26 | **5** | −10 | **+11.2%** |

**nil 参照の回数は 5〜6 でほぼ同じなのに、速度差は −18.9% から +11.2% まで割れる。
相関していない。**

**したがって測っているものは nil 参照のコストではない。**
命令列が変わったことでコードのレイアウト(TCG のトランスレーションブロックの切れ目、
分岐の並び)が変わった影響のほうが大きい、というのが妥当な解釈である**(推測)**。

速くなった 2 件(`null-var` / `null-check`)は、いずれも**ループ本体が
nil 比較で占められている**形である。遅くなった 2 件(`length` / `and-chain`)は
**関数呼び出しを含む**。この違いが原因かもしれないが、**裏は取れていない。**

## 測定条件

- **KVM 無しの QEMU(TCG)である。** TCG のコストは命令数に比例し、命令長には
  あまり効かない。分岐やブロック境界の影響を受けやすい
- **3 ビルドの比較なので実行間ドリフトの影響を受ける。** PR #64 で
  「同じコードでも実行間で 20% 以上ドリフトする」ことが判明している。
  本実験では**レンジ(最小〜最大)を併記し、重なるものは「差なし」と判定した**
- 各ベンチは同一実行内で 6 往復。リスト走査系は入力リストの長さを 100 に揃えた

### ベンチの形について報告すべきこと

- **指示書 5-2 の `tagbody` / `go` 版は JIT が断念する**(`%%za-compiled-p` が nil、
  断念行は `za.c:5996` = tagbody 本体の `za_compile_expr` 失敗)。
  インタプリタに落ちると JIT の nil 処理を測れないので、**`while` 版に書き直した**
- **指示書 5-3 の末尾再帰版はそのまま動いた**(100 要素でスタックは溢れない)。
  `bench-length-iter` は JIT コンパイルされている
- 指示書 5-1 の `(null nil)`(リテラル引数)は参考値。**判断には使っていない**

## 6-4: 結論

**差は出たが一貫していない。r12 常駐は見送りで確定する。**

- nil 参照が密な形では **−10 〜 −19%** 速くなる
- 呼び出しを含む形では **+11%** 遅くなる
- nil 参照の回数(5〜6 で横並び)と速度差が**相関していない**ため、
  測っているものが nil 参照のコストだとは言えない
- コードサイズの削減は 3〜10 byte / 関数(0.2〜1.1%)

**当初の動機だった「nil の参照に時間を要する」という見立ては、
nil 参照が密な特定の形でしか成り立たない。**
即値に占める nil の割合が 9〜11% しかないので、これは当然の帰結でもある。

**副産物として、`-ffixed-r12` は C 側の速度をむしろ改善しうる**ことが分かった
(2 件で −6.6% / −10.7%、4 件で差なし)。レジスタを 1 本落とす代償は、
サイズ(+32 byte)でも速度でも観測できない。

## Phase 4 への引き継ぎ

**判断は変わらず「Phase 4 で再測定」。** ただし本実験で分かったことを足しておく。

- **2 ビルド比較では足りない。** `-ffixed-r12` のみの対照(ビルド C)を必ず取ること。
  取らないと C 側の変化を nil 常駐の効果と取り違える
- **nil 参照の回数と速度差が相関するかを必ず見ること。** 相関しないなら
  測っているものが違う
- 本実験の仕掛け(`ISIKIOS_PINNED_NIL`)は 3 箇所の `#ifdef` だけなので、
  Phase 4 でそのまま再利用できる
- **`tagbody` / `go` を含む関数は JIT されない**(`za.c:5996`)。
  ベンチを書くときは `%%za-compiled-p` で必ず確認すること
