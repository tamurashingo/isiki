# 確保の理由別の数え上げ(M8-T1 / T2)

> 状態: 計器は実装し、試験が通っている(2026-11-01)。内訳の実測はこの文書の §3。

## 1. なぜ要るか

既にある計器は 2 つとも**「何のために確保したか」では分けられない**。

| 計器 | 何が出るか | 何が出ないか |
|---|---|---|
| `%%HEAP-USED-BYTES` | From 空間が進んだ量 | **合計しかない** |
| `ALIGN_SITE_*`(`ALIGN_AUDIT=1`) | 確保の**入口**ごとの件数 | Lisp の物体はほぼ全部が `os_alloc_bytes` という 1 つの入口を通るので、**1 本の棒にしかならない** |

そのため `documents/for-expansion.md` のインタプリタ `for` の
**「毎反復 96 byte」の内訳が「〜など」のまま**止まっていた。
単位(タグ付きの物体 32 / 対 16)は分かっていても、
個数の組み合わせが `32×1+16×4` / `32×2+16×2` / `32×3` のどれか決められない。

## 2. 作った計器

`ALLOC_AUDIT=1`(= `EXTRA_CFLAGS=-DISIKIOS_ALLOC_AUDIT`)のビルドでだけ有効になる。

```
make test-qemu-alloc-audit
```

### 合計が合うことを、検査ではなく構造で保証する

「理由ごとに数える」実装でありがちな失敗は**数え漏れと二重計上**である。
どちらも起こりえない形にした:

1. 理由は確保の**直前**に `ALLOC_AUDIT_REASON()` で置く(「次の確保の理由」)
2. 数えるのは **`os_alloc_bytes` の中の 1 箇所だけ**。整列後の量を、
   置かれていた理由の桶へ入れ、理由を未分類へ戻す

**1 回の確保はちょうど 1 つの桶に入る**ので、合計は常に水位と一致する。

### 数え漏れは「黙って」起きない

理由を置かずに確保すると `ALLOC_REASON_UNATTRIBUTED` に入る。
**これ自身が検出器である**: 新しい確保を足した人が理由を置き忘れると、
未分類の桶が 0 でなくなって `make test-qemu-alloc-audit` が落ちる。

検査スクリプトで「呼び出し口を数える」形にしなかったのは、
**その検査自身が腐る**(原則 12)のに対し、未分類の桶は実行時の事実だからである。

### 既定ビルドは 1 命令も増えない — 測って確かめた

マクロが `((void)0)` に畳まれ、組み込み関数も監査ビルドでしか登録しない。
**実測(2026-11-01)**:

| | 大きさ | 食い違ったバイト |
|---|---:|---|
| 変更前 | 2,879,868 | — |
| 変更後 | 2,879,868 | **10 箇所(すべて揮発領域の中)** |
| 同じソースをもう 1 回ビルド(**陰性対照**) | 2,879,868 | **11 箇所(同じ位置)** |

揮発領域はビルド時刻(`2026-11-01T13:29:37Z`)と git のハッシュが埋め込まれる場所で、
**同じソースでも毎回変わる**。変更前後で動いたバイトは**すべてその中**に入っていた。

> **陰性対照を先に取らなければ「ハッシュが違う = 変わった」と誤判定していた。**
> カーネルの実行ファイルは**バイト単位で再現しない**(時刻が埋まる)。
> ハッシュの一致を既定ビルド不変の判定に使ってはいけない。

組み込みを既定ビルドで増やさないのは、`test/c/runtime_test.c` の
`SMALL_HEAP_SIZE`(余裕 5KB 未満。症状は NG ではなく**ハング**)の
再調整を避けるためでもある。

### 測る量がぶれないこと

命令数と違い**確保量はぶれない**(規則 11 で「断言してよい計器」とされている)。
したがって監査ビルドで測った内訳は、既定ビルドの内訳としてそのまま使える。
**計器を入れたビルドで測っても結論が歪まない、数少ない量である。**

### Lisp から 2 つの計器を読んで引き算してはいけない

最初はこう書いて落ちた:

```lisp
(assert-equal (- (%%heap-used-bytes) h0) (全部の桶を足した値))
```

**インタプリタでは「測る行為そのものが確保する」**(関数を呼ぶたびに引数リストを
対で作る)。左辺を読んだ後・右辺を数える間にも確保が起きるので**必ずずれる**。
実測では桶の合計 4304 / 水位の差 3584 で、**差 720** は
`reset` と「水位を読む」の間に挟まった評価の確保だった。

だから差は **C の中で、間に何も挟まらない形で**取る(`%%ALLOC-REASON-DIFF`)。
こうすると**いつ呼んでも 0** になる(呼ぶまでの確保は合計と水位の両方に等しく入る)。
同じ理由で「reset 直後に合計が 0」も Lisp からは観測できないので、
**その読み取りが触らない理由の桶**が 0 に戻っていることで確かめている。

## 3. インタプリタ `for` の 96 byte/反復の内訳

### 測る前の宣言(規則 11)

`init.lisp` の `for` の展開形は、1 反復ごとにこれを評価する:

```lisp
(if (>= i n)
    (return-from nil ...)
    (progn (setq %for-tmp-1 (+ i 1))
           (setq i %for-tmp-1)
           (go %for-loop)))
```

**導けること**(★ ではない。インタプリタの評価の形から出る):

| 反復ごとの確保 | 単位 | 個数 | 量 |
|---|---:|---:|---:|
| `(>= i n)` の引数リスト | 対 16 | 2 | 32 |
| `(+ i 1)` の引数リスト | 対 16 | 2 | 32 |
| `(go %for-loop)` の脱出の印(`MAGIC_GO_EXIT`) | 物体 32 | 1 | 32 |
| `(setq i %for-tmp-1)` | — | 0 | 0 |
| **合計** | | | **96** |

**宣言: 内訳は `ALLOC_REASON_CONS` 64(対 4 個)+ `ALLOC_REASON_INST_GO` 32(物体 1 個)。**
計画が挙げていた 3 通りのうち **`32×1 + 16×4`** である。
`32×2+16×2` と `32×3` は**外れると宣言する**(脱出の印は 1 反復に 1 つしか作らない)。

R-set: 上の 2 つの桶だけが動く。**それ以外の桶は 1 byte も動かない**と宣言する。

### 測り方

絶対値は事前に導けない(測る行為自身が確保する)ので、
**反復数を変えた 2 点の差(傾き)**で出す。測定のたびの一定の雑音は差で消える。

```
make test-qemu-alloc-breakdown
```

### 実測(2026-11-01)— **宣言どおり**

```
#alloc-slope reason=1  delta=6400 per-iter=64     ← ALLOC_REASON_CONS
#alloc-slope reason=17 delta=3200 per-iter=32     ← ALLOC_REASON_INST_GO
#alloc-for-interp cons=64 go=32 total=96
```

| | 宣言 | 実測 | 判定 |
|---|---:|---:|---|
| `ALLOC_REASON_CONS` | 64(対 4 個) | **64** | **当たり** |
| `ALLOC_REASON_INST_GO` | 32(物体 1 個) | **32** | **当たり** |
| 合計 | 96 | **96** | **当たり** |
| 動く桶は上の 2 つだけ | — | **2 つだけ** | **当たり**(R-set も当たり) |

**`documents/for-expansion.md` の「〜など」で止まっていた内訳が確定した。**
96 = **`32×1 + 16×4`**(計画が挙げた 3 通りの 1 つ目)。
`32×2+16×2` と `32×3` は外れると宣言しており、そのとおり外れた。

> 内訳が導けたのは、**インタプリタの評価の形から個数が決まる**からである
> (呼び出し 2 つ × 引数 2 個 + `go` 1 つ)。
> 絶対値を測れる計器が無かっただけで、**予測できない量ではなかった。**

## 4. 対処するか見送るか(G6 の価値判断)

**結論: 両方とも見送る。** 脱出の印の方は別 Issue に切り出す。

### 対 64 byte(引数リスト)— 見送る

`(>= i n)` と `(+ i 1)` の引数リストで、**インタプリタの呼び出し規約そのもの**である。
消すには評価器の引数の渡し方を作り変えることになり、**あらゆる呼び出しに触る**。

見送る理由: **インタプリタは性能の経路ではない。**
速さが要る所は AOT と JIT が受け持っており、両経路ともこの確保をしない
(AOT の `for` は 0 byte、JIT の `for` も 0 byte)。
払っている費用の割に、直す範囲が釣り合わない。

### 脱出の印 32 byte(`go`)— 見送るが、別 Issue に切り出す

`(go %for-loop)` は**跳ぶことを知らせるためだけに、毎反復 32 byte の物体を作る**。
運ぶのは magic と行き先の名前の 2 つで、**名前は固定のプール**
(`%for-tmp-*` と同じ考えで `%for-loop` は固定)なので、
**名前ごとに 1 つ作って使い回せる可能性がある**(記号の intern と同じ形)。
効けば**解釈実行のあらゆるループの確保が 1/3 減る**。

それでも今は見送る理由が 3 つある:

1. **使い回す物体は共有された可変状態になる。** 誰かが書き換えたり、
   入れ子の `tagbody` で同じ名前を使ったときに、**非決定的に壊れる形**になる。
   この種のバグは本リポジトリで既に何度も踏んでいる(生のビットパターンを
   `GC_PROTECT` した件など)
2. **M8 の後半(T5)でヒープ枯渇を知らせる仕組みを入れる。**
   確保量を今変えると、**枯渇がいつ起きるかが動く**。
   同じミルストンで両方やると、どちらの影響か分からなくなる
3. インタプリタは性能の経路ではない(上と同じ)

**→ #153 に切り出した。** 内訳と測り方がこの文書にあるので、
次に着手する人は `make test-qemu-alloc-breakdown` で前後を比べられる。


## 5. 件数の導出(規則 13)

新しい試験を 2 つ増やした。報告される件数は**数えて導ける**:

| ミルストン | ファイル内の `assert-equal` | `isiki-file-end-check` | 報告 |

**既定の `make test` と `make test-qemu` の件数は変わらない。**

(`make test` の前提に入れると、既定ビルドで `%%ALLOC-REASON-BYTES` が
未定義なので落ちる。それがゲートである)。
