# `declare` の型を使った `+` の特化

対象: PR(`feature/declare-typed-add`、base は `feature/compiler-optimization`)

関連: `documents/type-specialized-dispatch.md`(4 象限の枠組み)、
`documents/declare-types.md`(型情報の記録)、`documents/float-contagion.md`

---

## 1. 何をしたか

**コンパイル時に型が分かっているとき、`+` を型別の呼び先へ振り分ける。**

PR #84 で `declare (type ...)` の型情報はコンパイラに届いていたが、
**コード生成では一切参照されていなかった**(`g_za_param_decl_types` の参照は
定義・代入・診断の 3 箇所のみ)。**本作業で初めて使う。**

**`+` だけ、引数 2 つだけ。** 他の演算子は同じ形で順に足す。

| 型の組 | 行き先 |
|---|---|
| fixnum × fixnum | `primitive_add2_fixnum` |
| single × single | `primitive_add2_single` |
| **それ以外すべて** | **GENERIC(`primitive_add2`)** |

---

## 2. 結果

### 2-1 振り分け(§5-2)

`disassemble` の code-len で確認した。

| 宣言 | code-len | 判定 |
|---|---:|---|
| なし | 735 | GENERIC |
| **fixnum** | **690** | 特化 |
| **single-float** | **690** | 特化 |
| double-float | 735 | GENERIC ✓ |
| bignum | 735 | GENERIC ✓ |
| 混在(fixnum × single) | 735 | GENERIC ✓ |
| 引数 3 つ | 1011 | GENERIC ✓ |

**735 → 690 の 45 byte 減**は、`za_emit_arith_call_or_inline` が持つ fixnum の
インライン高速路(タグ検査 + `add` + `js`)が消えて call だけになったぶんである。

### 2-2 速度(§5-5。n=200,000、3 回の最小値、同一ブート内)

| 型 | 宣言なし | 宣言あり | 差 |
|---|---:|---:|---:|
| **fixnum** | 236 | 244 | **+8(約 3% 遅い)** |
| **single-float** | 264 | 236 | **-28(約 11% 速い)** |
| double-float(対照) | 148 | 152 | +4 |
| bignum(対照) | 44 | 48 | +4 |

**fixnum が遅くなったのは意図した帰結である**(§3-2)。
single が速くなったのは、汎用関数の入口で `fixnum_add_signed` を試して外し、
`float_kind_max` で型を判定する処理が丸ごと消えたためである。

**対照群の double / bignum は +4 に留まり**、fixnum の +8・single の -28 とは
別の水準である。GENERIC に留まっていることの裏づけになる。

## 3. 設計

### 3-1 宣言は無検査で信じる

**タグ検査を一切出さない。** 宣言された型の専用経路へ直接渡す。

宣言は利用者の約束であり、**守られなかったときの動作は未定義**とする。
CommonLisp の `(safety 0)` と同じ立場である。

#### 嘘をついたら型によらず壊れる

| | 嘘の宣言(通常ビルド) | 結果 | GENERIC なら |
|---|---|---|---|
| `add-fixnum` に double | `(+ 1.5d0 2)` | **1921102** | 3.5 |
| `add-single` に整数 | `(+ 1 2)` | **0.0** | 3 |

`1921102` は double のビットをマグニチュードとして読んだゴミである。

> **【経緯】当初は fixnum だけ偶然に正しく動いていた。**
> `primitive_add2_fixnum` が `fixnum_add_signed` を使っており、**それが入口で
> タグを見て GENERIC へ落としていた**ためである(当時の実測で `3.5` が返った)。
>
> **これは「試したら平気だった」という誤った安心を与える。** レビューで
> 指摘を受け、コアを分離して(§3-1a)タグ検査だけを省く形に変えた。
> **いまは型によらず一様に壊れる。**

### 3-1a コアを共有してタグ検査だけを省く

**別実装を書くと GENERIC と乖離する。** 桁溢れの境界や符号の扱いがずれれば、
§3-5 の「結果が GENERIC と一致する」が崩れる。

かといって `fixnum_add_signed` をそのまま使うと、**宣言で保証されている
タグ検査を毎回やる**ことになる。

**分解すれば両立する。**

```
fixnum_add_signed_unchecked(a, b, &sum)   コアだけ(マグニチュード抽出・符号・桁溢れ)
fixnum_add_signed(a, b, &sum)             タグ検査してから上を呼ぶ
```

GENERIC は `fixnum_add_signed` を、特化版は `_unchecked` を呼ぶ。
**コアが 1 つなので乖離しない。**

#### 0 を返す条件が両者で違う

**ここを読み違えないこと。**

| 関数 | 0 を返す条件 |
|---|---|
| `fixnum_add_signed_unchecked` | **桁溢れのときだけ**(タグ検査をしないため、それ以外に失敗する理由が無い) |
| `fixnum_add_signed` | 「どちらかが fixnum でない」**か**「桁溢れ」 |

当初「あれが 0 を返すのは桁溢れのときだけ」とコメントに書いたが、
**タグ検査つきの関数についてはそれが誤り**だった。分解後はそれぞれに
正しい条件が書いてある。

#### 速度は戻らなかった

省けるのはタグ検査の分岐 1 本である。**fixnum の +8 tick は変わらなかった。**

見当としては、省いた分岐が `primitive_add2_fixnum` の**内部**(C 関数として
既にコンパイル済みで、しかも予測が当たる)であるのに対し、+8 の主因は
**call そのもの**(JIT コードからカーネルへの間接呼び出し)だからである。
TCG で重いのは JIT が出す分岐であって、C 側の分岐ではない。

**ただしこれは推測である。確実に言えるのは +8 が変わらなかったことだけ。**

分解の価値は速度ではなく、**乖離のリスクを負わずに検査を外せること**と、
**壊れ方が型によらず一様になること**にある。

### 3-2 型を宣言すると遅くなる場合がある(利用者向け)

**現時点では、fixnum に型を宣言すると遅くなる。**(§2-2 で +8)

| | 生成されるもの |
|---|---|
| 宣言なし | タグ検査 → インライン `add` → 桁溢れ検査(**call なし**) |
| 宣言あり | `primitive_add2_fixnum` を **call** |

`call` がインラインの `add` に勝つことはない。

**速くなるのは single-float の組である。**

インラインが実装された段階(`type-specialized-dispatch.md` §5-4)で fixnum も
速くなる見込みである。**そのときこの節を更新すること。**

### 3-3 混在(fixnum × single)は扱わない

指示書は「fixnum を single へ変換してから single 専用経路へ渡す」としていたが、
**本作業では GENERIC へ落とす判断をした。**

#### 理由

**fixnum は符号マグニチュード表現である。**

```
bit63    = 符号
bit4-62  = マグニチュード
bit0-3   = タグ
```

`cvtsi2ss` に生のタグ付き値を渡せない。2 の補数の int64 を作る処理
(マグニチュードの取り出しと符号の適用)が**変換の前に数命令かかる**。

そのうえ **2^24 を超える fixnum は single へ直接変換すると桁が落ちる**ので、
絶対値の判定も要る。判定 + 変換で、GENERIC の呼び出し 1 回とどちらが速いか
自明でない。

**指示書自身が「割に合わないと分かったら GENERIC へ送る形に変えてよい」と
していた**ので、実装前にその判断をした。**測っていないので「遅い」とは
言えない。「割に合うか不明なので、複雑さを持ち込まなかった」が正確である。**

混在を扱うなら、判定方法(絶対値が 2^24 未満か / 変換して戻して比較)と
あわせて**独立した作業として測るべき**である。

### 3-4 型の出所は `declare` だけ

リテラルからの推論はしない。

```lisp
(+ x 1)    ; 1 が fixnum と分かっていても GENERIC へ落ちる
```

**これは実際に踏んだ。** 最初のベンチを `(+ acc 1)` と書いたため特化が一度も
発動せず、宣言あり/なしで code-len が完全に一致した(§5 の測定の作法)。

`(+ x (f y))` のように片方が式の場合も不明として GENERIC へ落ちる。

### 3-5 結果は GENERIC と一致する

型特化は最適化であり、意味論を変えない。

`primitive_add2_fixnum` は桁溢れを GENERIC と同じ経路で bignum へ昇格させる。
`primitive_add2_single` は **GENERIC と同じく double を経由する**
(single どうしの和は正確な結果が double で表現できるため一致する。
除算だけは二重丸めになるので別扱い。`single-float-arith.md` §5)。

## 4. 監査ビルド

**通常ビルドは無検査のまま、`ISIKIOS_DECLARE_AUDIT` を付けたときだけ検査する。**

```bash
make test-qemu-milestone MILESTONE=... EXTRA_CFLAGS=-DISIKIOS_DECLARE_AUDIT
```

検査に外れると `os_panic` で止まり、**シリアルへ関数名・宣言された型・実際の型**を出す。

```
PANIC: declare が嘘をついている
  関数: primitive_add2_single
  宣言された型: <single-float>
  実際のタグ: 0x0 (0=fixnum 4=single-float 7=instance)
```

**通常ビルドの実行時コストはゼロである**(マクロが `((void)0)` に展開される)。

### 検出器が働くことを確認済み(§5-4)

**試していない検出器は働かない。** 実際に確かめた。

1. 監査ビルドで `(add-single 1 2)` を呼ぶ → **panic して止まる**(上のメッセージ)
2. 正しい呼び出し `(add-single 1.5f0 2.5f0)` → 通る(4.0f0)
3. 通常ビルドで同じ嘘 → **止まらず 0.0 を返す**(壊れた値)

## 5. 測定の作法(踏んだ罠)

### ベンチが一度も特化を発動していなかった

最初のベンチをこう書いた。

```lisp
(defun d-fix (n acc) (declare (type <fixnum> acc)) ... (+ acc 1))
```

**`1` はリテラルなので型不明**(§3-4)。片方が不明なら GENERIC へ落ちるため、
特化が一度も発動しなかった。

**気づけたのは code-len が宣言あり/なしで完全一致していたから**である
(2009/2009、2014/2014)。`documents/declare-types.md` §6-2 の
「同じ数字が出たら疑う」が、**測定手順ではなくベンチの書き方の誤りを捕まえた**。

**両引数に宣言が要る。** 直したら 735/690 と差が出た。

### ループのコストが支配的にならない形にする

最初のベンチは再帰ループの中に `+` を埋めていたため、ループ自体のコストが
支配的だった。2 引数関数を `funcall` で回す形に変えた。

## 6. 分かったこと: disassembler は call 先の名前を出せない

`type-specialized-dispatch.md` §5-4 の「call 形を残す理由 2(可読性)」は
**現時点では成立していない**。

```
41 bb 71 57 79 02    mov r11d, 0x2795771    ; <kernel>
41 ff d3             call r11
```

`disasm_lisp.c` が付ける注釈は `os_addr_region_name(os_classify_addr(...))` に
よる**領域分類のみ**で、関数名は出ない。

**本作業の §5-2 でもこれに当たった。** 呼び先が変わったことを確認するのに
関数名が使えず、**code-len の差(735 対 690)で判定した**。

名前解決は別作業として必要である。Phase 1 の調査で方針は出ている
(ビルド時にカーネルのシンボルを抽出し、アドレス昇順の静的テーブルを作って
二分探索で引く)。

## 7. 次の段階

**同じ形で `-` `*` `/` と比較を足す。** ただし演算ごとに判断が違う
(`type-specialized-dispatch.md` §6)。**`+` での判断をそのまま適用しないこと。**

混在(§3-3)を扱うかは、独立して測ってから決める。
