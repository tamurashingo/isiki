# safety 3 で宣言した型を検証する(#148)

> 状態: 実装して試験が通った(2026-11-07)。

## 1. 何を解いたか

`#112` が提案した 3 段のうち **safety 3 だけが未実装**だった。

| safety | 汎用経路の型検査 | `declare` した型の検証 | |
|---|---|---|---|
| 0 | しない | しない | M6(PR #149) |
| 1〜2(既定) | する | しない(宣言を信じる) | 既定 |
| **3** | する | **する** | **本作業** |

### なぜ価値があるか(Issue の文面)

- 監査(`ISIKIOS_DECLARE_AUDIT`)は**別ビルド**なので、
  「**本番と同じ生成コードで嘘の宣言を捕まえる**」ことができない。
  実際 M6 では **D6**(監査ビルドでは展開を抑止する)という妥協を入れた
  —— 展開すると監査が何も見なくなるためである
- 監査の失敗は **`os_panic`** で、freestanding にハンドラが無い。
  **外から見ると QEMU の無反応と区別が付かない**
  (#110 で族として扱った「結果が無い」と同じ形。
  実際 #162 の監査の陽性対照で、**シリアルを捕まえないと対照が成立しない**ことを踏んだ)

## 2. 前提が崩れていた — **関数単位の `optimize` が効いていなかった**

着手時、`za.c` のコメント

> `g_za_declaim` は environment 単位の declaim(**+ defun 本体の declare を畳み込んだもの**)

を読んで「関数単位の仕組みはすでにある」と判断した。**読み違いだった。**
`eval.c` を見ると:

```c
UINT64 optimize = os_env_optimize(owner);              /* declaim のみ */
optimize = DECLAIM_WITH_INLINE_BITS(
    optimize, os_scan_declaration_inline(body, ...));  /* inline だけ畳む */
```

**畳み込まれていたのは inline ビットだけで、`optimize` は environment の
`declaim` からしか読まれていなかった。** つまり
**`(declare (optimize (safety 3)))` は何の効果も無かった。**

> **試験を書いて走らせたから分かった。** 検査を入れたのに発火せず、
> 嘘がゴミ値(1641798 など)を返した。
> **「特化版は選ばれているのに検査が出ていない」**という形だったので、
> safety の読み取りを疑えた。
>
> コメントを根拠に「仕組みはある」と判断したのが誤りで、
> **原則 12(コメントは腐る)をコメントの読み方の側で踏んだ。**

### 直し方 — 解析を 1 つにまとめた

`(optimize ...)` の解析は `eval_declaim` の中に**直書き**されていて、
関数単位の `declare` からは使えなかった。`os_apply_optimize_spec` として切り出し、
**`declaim` と defun 本体の `declare` の両方が同じものを使う**ようにした
(2 箇所に書くと片方だけ直される)。

`os_scan_declaration_optimize` は `os_scan_declaration_inline` と同じ形
(先頭に連続する `declare` だけを見る)。

## 3. 検査をどこに置いたか — **1 箇所で全部覆える**

`za_emit_arith_call_or_inline` の入口に置いた。この 1 箇所で足りる理由:

- **宣言された型は `wrapper_fn` から分かる**(`_fixnum` か `_single` か)
- **#165 で `za_compile_binary` もこの関数へ寄せた**ので、
  型特化した呼び先は**算術も比較もすべてここを通る**

出る命令(safety 3 のときだけ):

```
mov  r10, rcx ; and r10, 0xF ; cmp r10, <期待タグ> ; jne -> B
mov  r10, rdx ; and r10, 0xF ; cmp r10, <期待タグ> ; jne -> B
movabs r11, <特化版> ; call r11 ; jmp DONE
B:
movabs r8, <期待した型> ; movabs r11, os_za_signal_declare_mismatch ; call r11
DONE:
```

合流の作り方は `za_emit_inline_car_cdr` と同じで、
**悪い側も「正しい値を返す何か」を呼んで合流する**。
signal の戻り値は制御転送で、**算術の冷たい経路が domain error を signal するのと
同じ形**なので、JIT 側に新しい伝播の仕組みは要らない。

### D6 の妥協は要らない

**検査は呼び出し地点にあるので、展開を残しても値が見える。**
D6 の「展開すると監査が何も見なくなる」はここでは起きない
(監査は特化関数の**中**にあったので展開に飛ばされた)。

本作業では **safety 3 のとき展開しない**形にした —— 検査 + 呼び出しだけの
自己完結にして、合流点を増やさないためである。
**展開を残すのは別の仕事として開けてある。**

## 4. 実測

| | コード長 |
|---|---:|
| safety 0 | 871 |
| 既定(1/2) | 871 |
| **safety 3** | **933**(**+62**) |

**既定では 1 命令も増えない**(検査は safety 3 のときだけ出る)。

試験 **25 件 / 0 failed**:

- safety 3 + 正しい宣言 → ふつうに動く
- safety 3 + 嘘(float / 文字列)→ **`<domain-error>`**
- **捕まえたあとも生きている**(panic との違い。この行が実行されること自体が試験)
- 比較でも効く(#165 で呼び出しを 1 箇所に寄せたため)
- single の宣言でも効く
- **対照群: 既定では検査が出ない**(嘘をついても signal されない)
  —— **それが #112 の一方向の定義である**

## 5. 一方向の定義との関係

#112 の結論は「**safety は検査を外してよいという許可であって、
外れることの保証ではない**」。safety 3 はその許可を**与えない**うえに、
**食い違いを報告する**段である。

> 「許可を与えない」だけなら特化をやめれば済む(汎用が型を見て signal する)。
> **報告する**のは一歩踏み込んだ意味づけで、
> **嘘の宣言そのものを見つけたい**ときに要る。
> 害が無い嘘(fixnum と宣言して float を渡し、汎用が正しく計算してしまう形)も
> ここでは捕まる。
