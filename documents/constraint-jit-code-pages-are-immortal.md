# 制約: JIT コードページは解放・移動・上書きできない

> 記録日: 2026-09-15 / 確認ブランチ: `feature/compiler-optimization`(`6da82cb`)
>
> **これは「今は困っていないが、触った瞬間に壊れる」種類の制約である。**
> コードページに手を入れる最適化を検討するときは、必ずここへ戻ること。

## 制約

**一度確保した JIT コードページは、解放も、移動も、内容の上書きもできない。**

理由は「実行中でないことを判定する手段が現在の機構に無い」から。
到達不能性(誰からも参照されていないこと)が判定できても、それだけでは足りない。

## 根拠: GC は precise で、C スタック上の戻り番地を見ない

GC のスタック走査は **shadow stack のみ**を辿る(`src/c/runtime.c:2190-2197`):

```c
// 全プロセスのshadow stack(GC_PROTECTされたCローカル変数)をスキャンする。
for (UINT32 i = 0; i < PROCESS_COUNT; i++) {
    for (gc_rootnode *node = get_process(i)->gc_roots; node != 0; node = node->next) {
        *node->var_ptr = gc_copy_value(*node->var_ptr);
    }
}
```

`gc_rootnode`(`src/c/types.h:23-26`)が持つのは `lisp_val_t *var_ptr` と `next` だけで、
**`GC_PROTECT` で明示的に登録された Lisp 値のアドレスしか見ていない。**

一方、JIT 生成コードの**戻り番地は生の C スタック上にあり、コードページを指す。**
GC はそれを走査対象にしていないので、
**どのコードページが今まさに実行中かを知らない。**

これは precise GC として正しい設計である(conservative 走査に伴う偽の pin を避けられる)。
問題は、その帰結が**コードページの寿命管理にも及んでいる**ことにある。

## 到達不能性だけでは不十分であることの実例

次の3つはいずれも**実機で到達可能**であることを確認済み
(`documents/investigation-code-page-reclaim.md` 項目 D)。
回収機構が存在しないため現状は無害だが、**回収を入れた瞬間に危険になる。**

```lisp
;; 1. 自分自身を実行中に再定義する
(defun dsel () (progn (defun dsel () 1) 2))
(dsel)   ; → 2。この時点で旧 dsel のコードページは cells から外れるが、
         ;   旧コードの戻り番地はまだ C スタック上にある

;; 2. ループ本体が動いている最中に、その中で定義した関数を再定義する
(defun dloop (n) (let ((i 0)) (while (< i n) (progn (defun dtgt () i) (setq i (+ i 1))))))

;; 3. 呼び出しの途中で、スタックに積まれている側の関数を再定義する
(defun dinner () (progn (defun douter () 9) 3))
(defun douter () (dinner))
(douter) ; → 3。douter のフレームが積まれたまま douter が差し替わる
```

実測結果:

```
#D 1回目 dsel=2 compiled=T
#D 2回目 dsel=1 compiled=T
#D ループ内再定義 dtgt=5 compiled=T
#D 呼び出し中に下位を再定義 douter=3
#D その後 douter=9
```

いずれのケースでも、旧コードページを回収して別の用途へ再利用すれば、
**戻り先が別の関数の機械語の途中になる。** 症状はクラッシュとは限らず、
「別の関数が実行される」「スタックが壊れる」など、原因を追いにくい形になる。

## 現在この制約に暗黙に依存しているもの

- **`za_fn_meta_t` の `code_base` / `code_len`**(`src/c/runtime.h`)。
  逆アセンブラ(PR #57)がこれを読む。ページが再利用されれば別の関数の機械語を表示する
- **`os_imm_pages_alloc_contiguous`**(`src/c/runtime.c:1403-1411`)が
  **フリーリストを一切見ない**こと。結果としてコードページは決して再利用されない。
  これは意図した設計というより、この制約と偶然噛み合っている状態である
- **`os_environment_reclaim_pages`**(`src/c/runtime.c:3705-3717`)は
  `%%DESTROY-ENVIRONMENT-RECLAIM` からしか呼ばれず、
  トップレベル `defun` の owner である `global_environment` は破棄されない
  (`src/c/eval.c:399-402`)。**実質、返る経路が無い**

## 影響を受ける最適化

コードページを触るものはすべてこの制約の下にある。

| 最適化 | どう引っかかるか |
|---|---|
| **コードページの回収** | 実行中でないことを保証できない |
| **コンパクション**(断片化したコードを詰め直す) | 移動すると戻り番地が無効になる |
| **ティアリング**(後から JIT する / 捨てる) | 捨てる側が同じ問題を踏む |
| **ホットパッチ**(実行中のコードを書き換える) | 同上。加えて他コアからの実行も考慮が要る |
| **サブページのパッキング** | **確保だけなら影響を受けない。** 解放を伴う設計にすると引っかかる |

**パッキングは、解放を伴わない限りこの制約の外にある。**
現在 Immobilized Space が枯渇する主因は「異なる名前の定義の蓄積」であり
(`documents/investigation-defun-page-cost.md`、
`documents/investigation-code-page-reclaim.md`)、
**解放を伴わないパッキングだけで有効である**ことが、この制約と両立する理由になっている。

## パッキング導入後(2026-09-15)に強まった点

`os_imm_code_alloc`(`src/c/runtime.c`)の導入により、状況が2つ変わった。

**1. 1ページに複数の関数が同居するようになった。**
以前は 1 関数 = 1 ページ以上だったので、「この関数のページ」を指す操作に曖昧さが
無かった。いまは 1 ページに平均 3 個前後が載る。**個別の関数だけを回収・移動する
という発想は、もう成立しない。** ページに同居している全員が対象になる。

**2. ただし同居するのは同一環境の関数に限られる。**
ページは必ず 1 つの環境に属し、別の環境の `defun` が来たら新しいページを取る。
連続している場合にページ境界をまたぐことはあるが、またいだ 2 ページも同じ環境のもので、
両方が `pages` スロットへ登録される。**したがって `destroy-environment` による
ページ単位の回収は引き続き正しく働く**(`os_environment_reclaim_pages`)。
これはこの制約の例外ではなく、「環境ごと捨てる」という粒度でしか回収しないことで
制約を踏まずに済ませている、という関係である。

**将来コンパクションや個別回収を検討する場合、同居関係を考慮する必要がある。**
あるページを動かす/捨てるには、そこに載っている**すべての**関数について
「誰からも参照されておらず、かつ実行中でもない」ことを示す必要がある。
実行中でないことを示す手段が無い、という本文の制約はそのまま残っているので、
同居はその困難をさらに増やす方向にしか働かない。

## 制約を外すとしたら何が要るか(所見・未検証)

**(所見)** C スタックを保守的に走査し、戻り番地がコードページ範囲に入るものを
pin する仕組みが要る。これは GC を precise から一部 conservative へ変える話になり、
影響範囲は GC 全体に及ぶ。

**(所見)** あるいは「safepoint を設けて、そこでのみ回収する」形。
ただし safepoint では「どのコードページが実行中か」を別途記録する必要があり、
結局コールスタックの情報が要る。

**(所見)** どちらも小さな変更ではない。
**「コードページは不死である」という前提を保ったまま設計するほうが安い**と考える。
