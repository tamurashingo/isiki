## 2. 未解決の本丸: `cc_car`/`cc_cdr` インライン化ハング

### 症状

`cc_car`/`cc_cdr`(生成コード中2,784箇所)を `static inline` にすると、
`init.lisp` の `(defun make-environment (name &rest parent-env) ...)` を
JITコンパイルする途中で**無限ループに入る**。

```
za_try_compile_defun の呼び出し回数   55のまま不変
JITバッファ使用量                     233のまま不変
GC回数                                単調増加
za_macroexpand の呼び出し(site 0)    132,028 -> 191,571,768
```

**1回のコンパイル呼び出しの中で、コードを1バイトも出さずに確保だけを続けている。**

### 再現

```
tools/repro/cc_car_hang.sh
```

**重要: za.c の上限コードとFloyd検出器を外さないと再現しない。**
スクリプトがやってくれるが、手で再現するときは注意。

### 棄却済みの仮説

| 仮説 | 検証 | 結果 |
|---|---|---|
| GC圧不足 | `QEMU_MEM=80M`(GC26倍) | 棄却。同じくハング |
| 最適化可視性 | `asm volatile("":::"memory")` のみ | 棄却。効かない |
| `.bss` レイアウト | グローバルを宣言のみ(未使用) | 棄却。効かない |
| 上限の値 | 10^12(実質無効) | 棄却。通る |
| 未初期化ローカル読み出し | `-ftrivial-auto-var-init=pattern` | 棄却。何も変わらない |
| 解析の計算量が指数 | ネスト深さ vs mx呼び出し回数 | 棄却。**d²(二次)** |
| `za_macroexpand` の暴走 | 上限1000 | 棄却。一度も到達しない |
| bodyの循環リスト | Floyd検出器 | 現時点では検出0件 |

### 摂動実験の表(これが現状の全て)

| インライン | 追加コード | 上限値 | 結果 |
|---|---|---|---|
| なし | — | — | 通過(基準) |
| あり | なし | — | **ハング** |
| あり | カウンタ+上限 | 10000等 | 通過(発火0) |
| あり | カウンタ+上限 | 10^12 | 通過 |
| あり | メモリバリアのみ | — | **ハング** |
| あり | グローバル宣言のみ | — | **ハング** |
| あり | Floyd検出器のみ | — | 通過 |

**効いているのは「関数の中で実際に実行されるコード」だけ。**
スタックフレームのレイアウトと制御フローに敏感。

### 残っている線

1. **配列の範囲外スタック読み出し。** `-ftrivial-auto-var-init` は自動変数しか
   覆わないので棄却されていない。`za.c` の固定長配列
   (`usages[]`/`items[]`/`end_patches[]`/`init_forms[]` 等)の境界を
   検査するのが次の一手。
2. **`za_compile_let` の `r8` と同根の可能性。** 2026-09-12 に
   ループ上限 `r8 = 0x449AA7E0` がゴミになる件を追い、機序を特定できないまま
   `init_forms`/`operand_forms`/`arg_forms` の保護追加で消えた。
   **どちらも za.c のループまわりで、値がゴミになり、無関係な変更で消え、
   機序が未特定。3件目が出たら3つ並べて見ること。**

### 方針

**インライン化はマージしない。** マージすると再現手順がベースラインになり、
次に同じ根が別の形で出たときの比較対象を失う。

## 3. 監査の構造的な限界(原則10)

**塗り潰しもアンマップも「読んだとき」しか捕まえない。**

| 機構 | 捕まえるもの |
|---|---|
| 塗り潰し | 1世代前の stale を**読んだ**とき |
| アンマップ | 世代を問わず stale を**読んだ**とき |
| **どちらも捕まえない** | **stale を比較に使ったとき** |

`tags[].tag == elem` はポインタ比較でデリファレンスではないので、
被覆100%の監査をすり抜けた。理由は世代限界ではなくこれである。

**「監査で0件」は「その監査が見られる範囲での0件」でしかない。**

### ポインタ等価の静的列挙(この盲点は列挙で埋められる)

`src/c/*.c` に `lisp_val_t` の `==`/`!=` は820箇所。片辺がGCの更新対象外
(Cスタック上の構造体フィールド・配列要素)のものに絞ると46件で、全件確認済み。

| 対象 | 件数 | 状態 |
|---|---|---|
| MAGIC定数/生UINT64/`lisp_val_t*` の比較 | 11 | 安全 |
| `usages[i].sym` | 3 | 修正済 `c35758d` |
| `bindings[].orig_name` / `vars[].sym` | 2 | 修正済 `fdd6df2` |
| `tags[].tag` | 3 | 修正済 `0defcb1` |
| `out_syms[i]` | 1 | 安全(関数内に確保が無い) |
| `syms->xxx` (`za_syms_t`) | 26 | 修正済 `d698a7b` |

### 被覆100%の意味

`aot_leaf_gc_test` を除外しない母数で 1620/1620。ただしこれは
**実行されたアサーションの被覆**であって、コードベースの被覆ではない。
その実例として `fat16n_resolve_device`(監査対象22ファイルの外)に
同じクラスのバグが実在した。FS層・デバイスドライバ・テストのない領域は手つかず。

## 4. 使える道具

### `QEMU_MEM`: 生成コードを変えずにGC圧を上げる

```
make test-qemu QEMU_MEM=80M
```

Lispヒープは起動時にUEFIの最大 `EfiConventionalMemory` 領域から取るので、
ゲストメモリ量でGC頻度が決まる。**`%%DIAG-GC-STRESS` は GC_DEBUG 専用で、
GC_DEBUG は `cc_car` 内に呼び出しを入れてインライン化自体を消す**ため、
「インライン化した状態でGC圧を上げる」にはこれしかない。

| -m | 全件のGC回数 |
|---|---|
| 256M(既定) | 2 |
| 128M | 12 |
| 96M | 19 |
| 80M | 52 |
| 72M以下 | 起動しない |

### タイマーサンプラ(通常ビルドで使える)

```lisp
(%%diag-tick-sample-pub 50)   ; 50tickごとに割り込み時ripをシリアルへ
(%%diag-tick-sample-pub 0)    ; 停止
```

出力に `anchor`(= `c_timer_switch` の実行時アドレス)が付くので逆引きできる。

```
python3 tools/bench/locate_rip.py tmp/bootx64.dis \
  --anchor-symbol c_timer_switch --handler <anchor> <rip>...
```

**逆アセンブルはビルドのたびに再生成すること。** 使い回すと
もっともらしい別の関数名が返る(同じ一連で2回踏んだ)。

### 診断プリミティブ

```
%%DIAG-ZA-MX-CALLS n      za_macroexpandの呼び出し回数(呼び出し元site別)
%%DIAG-ZA-BAIL-LINE       JITが断念した行(最初)
%%DIAG-ZA-BAIL-COUNT / -AT  断念の全記録
%%DIAG-LIMB-PEAK          limb作業領域の最高水位
%%DIAG-GC-TO-REVISITS     To空間を指す値でgc_copy_valueが呼ばれた回数
%%DIAG-IMAGE-ANCHOR-PUB   逆引きの基準点
```

サンプラ出力には `gc` / `zacalls`(コンパイル呼び出し回数)/ `jit`(バッファ使用量)/
`mx` も付く。**「1回のコンパイルの中で回っている」か「何度も呼ばれている」かは
これが無いと区別できない。**

## 5. 測定の落とし穴(実際に踏んだもの)

1. **`make build` はブートイメージを更新しない**(修正済)。QEMUが起動するのは
   `images/boot_fat32.img` の中のEFI。手でqemuを起動する測定は古いカーネルを測る。
   EFIとイメージのmtimeが同じ秒に収まるとmakeは作り直さない。
   なお `build: $(BOOT_FAT32_IMG)` は**変数定義より後**に書く必要がある
   (prerequisiteはルール読み込み時に展開されるので、前置き部に足すと空になり黙って効かない)。
2. **`make test-qemu` はシリアルをファイルに落とさない。** 診断が出たかを
   makeの標準出力で確認しても意味がない(一度誤った)。
   `make test-qemu-audit-run ... QEMU_EXTRA_FLAGS="-serial file:..."` を使う。
3. **逆アセンブルの使い回し**(上記)。
4. **QEMUは直列に。** 並行させると `Failed to get "write" lock` で後発が
   rc=1・0秒で落ち、「試験が壊れた」と誤読しかける。
5. **検出器は「0を返すこと」より先に「誤って発火しないこと」を確かめる。**
   Floyd検出器の初版は亀の前進条件に `body_walk > 0` を欠いており、
   1反復目で亀と兎が同じ位置になって偽陽性を16件出した。
6. ウォームアップを捨てる/ビルド構成を跨いで比較しない(既出、`documents/` 参照)。

## 6. 残件

### 優先度高

- **インライン化ハングの根本原因**(上記の残り2線)
- **配列の範囲外スタック読み出しの検査**(`za.c` の固定長配列の境界)

### 優先度中

- `tags[].tag` / `syms->*` の**誤一致側の人工再現**。どちらも「一致しなければbail(安全側)、
  誤って一致すれば誤ったコード」という二面性を持つ。bail側は塞いだが誤答側は未再現。
  `for` の間欠バグ(以後永久に結果が壊れる)の候補として記録してある。
- `za_analyze_var_usage` が解析とマクロ展開を同じパスで走らせる構造(二次のコスト)。
  メモ化か解析前の一度きりの展開。

### 優先度低

- アンマップ方式の投資判断。**ポインタ等価の盲点には効かない**ことが確定しているので、
  それを根拠にはできない。残る利点は `cc_car`/`cc_cdr` の判定を外せることと、
  例外ハンドラでのトラップ識別が不要になること。
- 監査の届いていない領域(FS層・デバイスドライバ)。`fat16n_resolve_device` が1件目。
