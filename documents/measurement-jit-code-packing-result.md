# 測定: JIT コードのパッキング — 前後比較

> 測定日: 2026-09-15 / ブランチ: `feature/jit-code-packing`
> 前提となる分布の測定は `documents/measurement-jit-code-length-distribution.md`。

## 何を変えたか

`za_try_compile_defun` はコード長を 4,096 byte へ切り上げて**丸ごとページを専有**していた。
200 byte の関数でも 1 ページ、1,284 byte(中央値)でも 1 ページ。

`os_imm_code_alloc`(`src/c/runtime.c`)を追加し、**環境ごとの bump カーソル**から
必要な byte 数だけ 16 byte アラインで切り出す。

**1ページは必ず1つの環境に属する。** `destroy-environment` がページ単位で回収し
(`os_environment_reclaim_pages` → `os_imm_page_free`)、`os_imm_page_free` は解放した
ページの先頭 8 byte をフリーリストの next ポインタで上書きするため、環境をまたいで
同居させると生きているコードが壊れる。

走行(その環境が所有する連続したページの並び)の終端が `g_imm_bump` と一致している
ときに限り、次のページを取って**走行を延長しページ境界をまたぐ**。またいだ 2 ページは
どちらも同じ owner のもので両方とも `pages` へ登録されるので、回収の単位は壊れない。

## 前後比較

| | 前 | 後 | 倍率 |
|---|---|---|---|
| フルテスト完走後の使用量 | 4,856,352 byte(**28.9%**) | 2,189,104 byte(**13.0%**) | **2.22 倍** |
| 充填率 | **37.9%** | **84.9%** | 2.24 倍 |
| コード用に取ったページ | 1,158 | **518** | 2.24 倍 |
| 分断(ページ末尾の破棄) | — | 54 回 / 57,568 byte | |
| 走行の延長(またぎ) | — | **270 回** | |
| 環境の作成・破棄 10 サイクル(30 defun)の増分 | 124,800 byte 相当 | **1,936 byte**(コードページは 0) | **64 倍** |

`defun` 1回あたりの実効コストは、フルテストの実績から
`518 ページ × 4,096 / 1,125 回 + 48(meta)+ 16(cell)≒ 1,950 byte`(パッキング前は 4,160)。
16MB を使い切るまでの回数は **約 4,032 → 約 8,600** になる。

### 段階ごとの寄与

| 段階 | 充填率 | 使用率 |
|---|---|---|
| パッキング前 | 37.9% | 28.9% |
| カーソルのみ(またぎ無し) | 76.5% | 15.0% |
| **+ 走行の延長(またぎ)** | **84.9%** | **13.0%** |

またぎ無しの段階では分断が 388 回 / 306,912 byte あり、これが最大の損失だった。
延長を入れて 54 回 / 57,568 byte まで落ちた。

## 残る未使用の内訳(総 518 ページ = 2,121,728 byte、未使用 319,200 byte)

| 内訳 | byte | 総ページに対する割合 |
|---|---|---|
| 実コード | 1,802,528 | **84.9%** |
| **複数ページ確保の端数** | **190,352** | **9.0%** |
| 生きているカーソルの末尾 | 71,280 | 3.4% |
| 分断(ページ末尾の破棄) | 57,568 | 2.7% |

**残る損失は複数ページ確保の端数が支配的**になった。1 ページを超える関数(72 回)は
`os_imm_pages_alloc_contiguous` で連続確保し、カーソルには影響させていないため、
最後のページの末尾が丸ごと余る(平均 2,644 byte)。

**(所見)** ここを詰めるには「複数ページ確保の直後に、その最後のページの末尾を
カーソルの走行として引き継ぐ」形にすればよい。確保したページはすべて同じ owner へ
登録されるので、**1ページ=1環境の不変条件は保たれる**。効果は充填率で +9 ポイント
(84.9% → 約 94%)と見積もる。実装指示書が「E のカーソルには影響させない」と
明記していたため、今回は入れていない。

## 測定方法

`%%DIAG-CODE-PACKING` が
`(カーソルから ページ新規 複数ページ 分断回数 分断byte 総ページ数 総確保byte 延長回数 複数ページ端数byte)`
を返す。充填率 = 総確保byte / (総ページ数 × 4096)。

```bash
# qemu_boot_test.lisp と同内容 + レポート行のブートファイルを作って実行する
make test-qemu-milestone MILESTONE=<boot-entry> QEMU_EXTRA_FLAGS='-serial stdio'
```

実測値(フルテスト完走後):

```
#PACK (694 77 72 54 57568 518 1802528 270 190352)
#PACK 充填率=849/1000 総byte=1802528 総ページ=518(=2121728byte)
#PACK 未使用の内訳: 分断=57568 複数ページ端数=190352 生きているカーソル末尾=71280
#PACK used=2189104 使用率=130/1000
```

## 環境の分離が保たれていることの実測

```
#S2 同一環境3関数: used増=4288byte ページ番号 f1=52414 f2=52414 f3=52414
#S2 破棄後 512回(2ページ要求)の bump 消費=4096byte (返ったページ数=1枚相当)
#S2 REPL環境の連続defun ページ番号 q1=52415 q2=52415 (同居=T)
```

- 同一環境の 3 関数は**同じページ**(52414)に載る。旧実装なら 3 ページ = 12,288 byte
- 環境を破棄すると**そのページが 1 枚返り**、続く 2 ページ要求のうち 1 ページ分が
  フリーリストから賄われる(bump 消費が 8,192 ではなく 4,096)
- 環境が違えば別ページになることは `test/lisp/jit_code_packing_test.lisp` の項目 2 が
  ページ番号の不一致で検証している

## 既存テストの期待値を変えた箇所

| ファイル | 変更 | 理由 |
|---|---|---|
| `test/lisp/frame_definition_test.lisp` | 「破棄後は 0 byte」→「回収前より消費が減る」 | 4 関数が 1 ページに同居し、返るページが 4 枚→1 枚に減ったため 0 にはならない。フリーリスト経由の再利用という**検証したい性質**はページ数に依存しない形で張れる |
| `test/lisp/environment_pages_test.lisp` | 項目 4 のコメント | 「それぞれ別のページへ再配置され」が同一環境では不正確になった。アサーションは変更なし |

いずれもテスト内に理由をコメントとして残してある。

## 回帰テスト

`test/lisp/jit_code_packing_test.lisp`:

1. 同一環境の 4 関数が 1 ページに同居し、実行結果も正しい
2. **環境が違えば必ず別ページ**(設計の中核。破れると `os_imm_page_free` が
   生きているコードの先頭 8 byte を上書きする)
3. 破棄した環境のページがフリーリスト経由で再利用される
4. **環境の作成 → defun → 破棄を 10 サイクル繰り返してもコードページを 1 枚も消費しない**
   (想定する開発フローそのもの。今回の設計変更の主目的)
5. 1 ページを超える関数が従来どおり連続確保される
