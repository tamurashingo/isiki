# `init.lisp` の `for` を新展開形にする — 準備と、止まっているところ

> **状態: 移植した(2026-10-04)。**
> GC バグの主張は再現せず、issue #119 へ切り離した(案 C)。
> 移植は性能と展開形の一致のために行った。
>
> 結果: **`jit/for` が 643.41 → 199.08 命令/単位(−444.33)。**
> `for` は JIT が AOT より 2.38 倍遅い状態から **25% 速い**状態になった。
> 確保量は JIT 32→**0**、インタプリタ 928→**96**(`while` と同値)。

## 0. やろうとしていること

`init.lisp` の `for` を、`transpile.lisp` の `expand-for` と同じ**新展開形**にする。

| | 展開形 | 1 反復あたりの確保 |
|---|---|---:|
| `init.lisp`(インタプリタ / JIT) | 毎反復 `(let ((%for-next-values (list step1 step2))) (setq i (car ...)) ...)` | **32.00 byte(cons 2 個)** |
| `transpile.lisp`(AOT) | 一時変数へ全部評価してから書き戻す | **0** |

得られるもの:

1. `ide.lisp:40-45` の既知の GC バグが閉じる(**仮説。§1 で確かめようとして再現しなかった**)
2. インタプリタと JIT の `for` から毎反復の cons 2 個が消える
3. `for` の基準値が有効に戻る(いま `bench_baseline.tsv` で帯が `-`)
4. `transpile.lisp:721` のコメントが再び正しくなる

## 1. `ide.lisp` の GC バグは再現しなかった(2026-10-04)

### 1-1 直す前に再現させようとした理由

「原因が同じ」は**仮説**である。直してから「消えました」と言っても、
**消したのが移植なのか、別の何かが隠したのかが分からない。**

### 1-2 まず、記録が無い

`src/lisp/ide.lisp:40-45` は根拠として `documents/partition.md` PART-M4 調査を挙げている。

> **`documents/partition.md` は、どのブランチにも 1 度も存在しない。**
> `git log --all --diff-filter=A -- "documents/partition*.md"` が空である。

バグの記述は `ide.lisp` / `fat16.lisp` / `fat32.lisp` / `transpile.lisp` の

(「確認済み」と書くなら何をどう確認したかを同じ行に書く)。

分かっているのはコメントが書いていることだけ:

- `for` マクロ(ループ本体に毎回新規生成される `let`)は **GC が特定のタイミングで

- **300,000 回の `(setq junk (cons i junk))` 連続実行では再現しない**ことは確認済み
- `fat32.lisp:146` はこう一般化している: **`for` に限らず、`tagbody`/`go` の
  ループ本体内で毎回新規に評価・確保される `let` 束縛は同種のリスクを持つ**

### 1-4 踏んだ罠 — `GC_DEBUG=1` は test 側にも渡さないと効かない

最初の試行は `gc=0` のまま結果が正しく、「GC_STRESS が効いていない」と分かるまで

`test-qemu-milestone` は `build` に依存するので、フラグを渡さないと
**その場で通常ビルドへ戻される。** Makefile のビルドスタンプのコメントが


### 1-5 計器の限界が、そのままバグの不可能性になる

**`%%DIAG-GC-STRESS` は `os_alloc_bytes` の中でしか GC を起こさない。**
`%for-next-values` を作ってから `(car ...)` で読むまでの区間には確保が無いので、
**その区間に GC を置くことはこの計器ではできない。**

**これを裏から読む。**

> **GC が確保の中でしか走らないなら、確保を含まない区間では GC が走らない。
> つまり、その区間で stale を読むことは原理的に起きない。**

**窓に GC を置けないのは計器の都合ではなく、本番でもそこに GC が来ないからである。**
確かめるべきことは「GC の起動点が確保以外にあるか」だけになる。

#### GC の起動点を数えた — **4 つしかない**

| 場所 | いつ | ループ本体の内側に来るか |
|---|---|---|
| `runtime.c:232` | `os_alloc_bytes` 内の GC_DEBUG 強制 GC | **確保の中だけ** |
| `runtime.c:239` | `os_alloc_bytes` 内で From 空間が枯渇したとき | **確保の中だけ** |
| `repl.c:78` | **REPL のセーフポイント。**`os_eval_top_level_ex` の呼び出しの間、次の `os_read` より前 | **来ない**(トップレベルフォームの評価が終わったあと) |
| `bench_subprimitive.c:267` | `%%DIAG-STALE-POSITIVE` / `%%DIAG-STALE-NEGATIVE`(GC 監査の対照用の診断組み込み) | **来ない**(明示的に呼んだときだけ) |

- **ヒープ確保の入口は 1 つに集約されている。**`g_from_ptr` を進めるのは
  `runtime.c:246` だけである(= すべての確保が `os_alloc_bytes` を通る)
- **Lisp から呼べる GC は無い。**`%%...GC...` の組み込みはすべて読み出し専用の診断で、
  `os_gc_collect` を呼ぶものは 1 つも無い
- **割り込み経路から GC は呼ばれない。**`interrupt.c` / `clock.c` は
  `os_gc_collect_count()` を読んで出力するだけである(単一スレッドで safepoint も無い)

#### したがって、構造の主張として書ける

> `for` の旧展開形が作る中間リストは、**構築中は GC_PROTECT され**
> (`%%DIAG-GC-STRESS 1` で毎反復突いて trap 0 件)、
> **読み出し区間には確保が無い。GC は確保の中でしか走らないため、
> この区間で GC は発生しない。**
> したがって `ide.lisp:40-45` が述べる症状は、**現在の GC 起動モデルでは発生しない。**

「9,000 回試したが出なかった」より強い。**探索の記録ではなく構造の主張である。**

**ただし GC の起動点が将来増えたら、この主張は崩れる。**
safepoint を増やす / 割り込みから GC を走らせる / ユーザから呼べる `gc` を足す、の
いずれかをしたら**ここを読み直すこと。** issue #119 にも同じことを書いた。

### 1-6 §2-4 の仮説は成立しない — 展開形は保持されていない

作業指示書は「**展開済みの S 式がどこかに保持されていて、その中のヒープ参照が
GC で移動し、保持側が更新されない**」という形を疑っていた。調べた結果:

| 問い | 答え |
|---|---|
| マクロ展開の結果はどこかに保持されるか(memo / Function Cell / frame) | **されない。** 展開のキャッシュは実装に存在しない(`primitive_macroexpand_1` が呼ばれるたびに作る) |

**したがって「保持された展開形が GC ルートでない」という問題は見つからなかった。**
issue として切り出す対象は無い。

## 3. 意味論を 3 経路で固定した(§4)

**移植はコピーではない。** `test/lisp/for_semantics_test.lisp`(27 件)に
**移植前の**意味論を固定した。`make test-qemu-all` で常時回る。
**移植したあとに 1 件も落ちないことを確認する。**

### 3-1 並列代入 — 3 経路で一致した(いちばん危ないところ)

旧展開形が毎反復 `(list step1 step2)` を作っていたのは、**まさに並列代入のため**
かもしれない(全部評価してから、まとめて代入する形)。
新展開形が `list` を使わずに並列性を保っているかを、交換で判定した。

```lisp
(for ((i 0 j) (j 1 i) (k 0 (+ k 1))) ((>= k n) (+ (* i 10) j)))
```

並列なら 1 反復ごとに入れ替わる。逐次(`i` を先に書き換えて `j` がその新値を読む)なら
両方 1 になる。

| n | インタプリタ | JIT | AOT | 生成した JIT | 並列の期待 | 逐次なら |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 1 | 1 | 1 | 1 | 1 = `(0 1)` | 1 |
| 1 | **10** | **10** | **10** | **10** | 10 = `(1 0)` | 11 |
| 2 | 1 | 1 | 1 | 1 | 1 = `(0 1)` | 11 |
| 3 | **10** | **10** | **10** | **10** | 10 = `(1 0)` | 11 |

> **3 経路すべて並列である。AOT は間違っていない。**
> PR #116 の「AOT 側の展開形のほうが新しい」という結論はそのまま成立する。

probe は `src/lisp/bench_aot.lisp` の `%%bench-aot-for-swap` に置いた
(生成される `bench_jit.lisp` 側が JIT 版になるので、**1 箇所の追加で AOT と JIT の
両方が手に入る**)。

既存のベンチでも間接的に確認できる。`%%bench-aot-for` は
`(acc 0 (+ acc i))` で `acc` の step が `i` を読むので、
**並列なら旧 `i` を足して n(n−1)/2、逐次なら新 `i` を足して n(n+1)/2** になる。
n=300 の実測は **44850 = 300×299/2** で、並列である。

### 3-2 step の評価回数 / end-test の評価順 / 戻り値

n=5 のときの実測:

| | 回数 |
|---|---:|
| step 式の評価 | **5**(1 反復 1 回) |
| end-test の評価 | **6**(5 反復 + 最後の判定 = **本体の前**) |
| 本体の評価 | **5** |
| 戻り値 | `(5 5)` |

### 3-3 境界と変数の見え方

| | 実測 |
|---|---|
| step 式の省略 `(fixed 7)` | `(3 7)`(変わらない) |
| 変数 1 個 | `3` |
| 変数 0 個 `(for () (t 'done))` | `DONE` |
| **本体から変数が見えるか** | 見える。`(setq acc (cons i acc))` が効いて `(2 1 0)` |
| **本体の `setq` が外へ残るか** | 残る。`for-sem-seen` = 2 |

**「ループ本体の `let` 廃止」は変数の見え方を変えていない**(AOT 側で既に廃止済みで、
AOT も同じ答えを返している)。

## 4. 移植の手順(実施済み)

1. 予測を先に書いた(§5-1)
2. `init.lisp` の `for` を一時変数方式へ移植した

   確保量の行は `32` → `0` に直し、**経緯をコメントに残した**
5. `transpile.lisp:721` のコメントを現状へ直した
   (`while` は同じ、`for` は一時変数方式では同じで置き場所だけ違う、と書いた)

7. `ide.lisp` / `fat16.lisp` / `fat32.lisp` のコメントを issue #119 へのポインタにした

| | 予測 | 実測 | 判定 |

### 5-4 1 つ見つかった制限 — 単一 `let` の束縛は 4 個まで

**最初は `transpile.lisp` と同じ「1 つの `let` に append」で書いた。
そうしたら束縛 3 個の `for` が JIT に乗らなくなった。**

| | `%%za-compiled-p` |
|---|---|
| `for` 1 変数(2 束縛) | T |
| `for` 2 変数(4 束縛) | T |
| **`for` 3 変数(6 束縛)** | **NIL** |
| `for` 4 変数(8 束縛) | NIL |
| **素の `let` 6 束縛**(`for` と無関係) | **NIL** |
| 素の `let` 8 束縛 | NIL |

**`for` の退行ではなく、`let` の既存の制限だった。**
`ZA_MAX_LOCALS_PER_LET = 4`(`src/c/za.c:963`)。
1 つの `let` の束縛は 4 個までで、5 個以上は JIT が断念する。

> **PR #115 で「原因は未調査」としていた `%%bench-aot-let5par` が JIT に
> 乗らない理由も、これである。** 5 束縛だから超えていた。
> `let*` 版(`let10` など)が T なのは、`let*` が 1 束縛ずつ `let` へ
> 入れ子展開されるため(`ZA_MAX_LET_DEPTH` は 16)。

したがって **`init.lisp` 側は一時変数を入れ子の `let` に置いた。**
外側 N 個・内側 N 個となり、どちらも 4 以下に収まるので
**移植前と同じ「4 変数まで JIT」を保てる**(1 つの `let` にすると 2 変数までになる)。

```lisp
(let (<for の変数。並列>)
  (let (<一時変数。すべて nil>)
    (block nil (tagbody %for-loop ...))))
```

**AOT 側にこの上限は無いので `transpile.lisp` は変えていない**(作業指示書 §6)。
残る差は一時変数を置く場所だけで、意味は同じである。
`tools/macro_parity_expected.tsv` では `FOR` を **`cosmetic`** として記録した
(`DIVERGENT` ではなくなった。**`same` にはできない**)。

> **お伺いしたいこと**: `transpile.lisp` の `expand-for` も入れ子にすれば
> 両者は完全に一致して `same` にできます。AOT 側は上限が無いので入れ子でも
> 損はありません。**作業指示書 §6 が `expand-for` の変更を除外しているので
> やっていません。** やってよければ次の作業で揃えます。

### 5-5 一時変数の名前に `gensym` を使っていない

`init.lisp` には `intern` が無いので名前を作れない。**固定名のプールから取る。**

```lisp
(defun %for-temp-name-pool ()
  '(%for-tmp-1 ... %for-tmp-16))
```

**`gensym` を使ってはいけない。** マクロは評価されるたびに展開され直すので、
多重ループでシンボルテーブルが枯渇する。`init.lisp` の `for` のコメントに
旧実装がそれで壊れた記録が残っている。名前は `transpile.lisp` 側の
`%%for-temp-names` と同じ `%FOR-TMP-n` に揃えた。

プールを超えたら**黙って壊れた展開形を作らずエラーにする**
(`(car nil)` が `nil` を返すので、黙ると `(setq nil ...)` という形になって
原因が分からなくなる)。上限は 16 束縛。

### 5-6 族は閉じたのか — **JIT/AOT では閉じ、インタプリタでは閉じない**

| | 移植前 | 移植後 |
|---|---:|---:|
| JIT `for` | 16(1 変数)/ 32(2 変数) | **0** |
| JIT `while` | 0 | 0 |
| AOT `for` / `while` | 0 | 0 |
| **インタプリタ `for`** | **928** | **96** |
| **インタプリタ `while`** | **96** | **96** |

- **JIT と AOT では `for` も `while` も 0 になった。族が閉じた**
- **インタプリタでは `for` が `while` と同じ 96 になった。**
  つまり **`for` 固有の上積みは 0 になり、残っている 96 は
  「インタプリタでループを回すこと自体の費用」**である
  (`go` が作る `MAGIC_GO_EXIT` の instance など)。
  **族の最後の 1 つとして残る。** GC バグの主張(issue #119)が再燃したときに
  見る先はここになる
