## 0. 前提条件は満たした

作業指示書の「前提条件(満たすまで着手しない)」である命令数ゲートを先に実装し、
**陰性対照・陽性対照とも合格**した(`documents/performance-measurement.md`

- 陰性対照: 同じバイナリを 3 ブートして**補正後が 1 命令も違わない**

ゲートのマーカーは C 側の `noinline` 関数なので、Lisp 側で `declaim inline` を
どれだけかけても展開されない(指示書の要求)。

## 1. Phase 1: 現状の調査

### 1-1 **`inline` 宣言の仕組みは既にある。ただし `declaim` だけ**

Phase 3(`documents/inline-builtin.md`)で `car` / `cdr` / `null` / `eq` の
インライン展開が入っており、**`declaim (inline ...)` / `(notinline ...)` は
完全に動いている。**

```
既定の %%current-inline            = NIL
(declaim (inline car))             = (CAR)
(declaim (notinline car))          = NIL
```

| 部品 | 場所 |
|---|---|
| 宣言のパース | `eval_declaim`(`src/c/eval.c`) |
| 名前 → ビット | `os_inline_bit_of`(`src/c/runtime.c`) |
| 保持 | environment の declaim スロット。`optimize` と同じ fixnum の bit8〜 |
| 生成側の参照 | `za_inline_enabled`(`src/c/za.c`) |
| 診断 | `%%CURRENT-INLINE` / `%%INLINE-OF` |

**算術を足す作業は、この表に 4 つビットを増やすことである。**
`os_inline_bit_of` は未知の名前に 0 を返して黙って無視するので、
いまは `(declaim (inline +))` を書いても何も起きない(実測で確認)。

```
(declaim (inline + - * /)) 後の %%current-inline = (CAR)   ← + - * / は無視された
```

### 1-2 **`declare (inline ...)` は読み捨てられている**

`decl_apply_spec`(`src/c/runtime.c`)は **`(type <class> v...)` の形しか見ない。**
それ以外の宣言指定子は黙って読み飛ばす。

```lisp
(defun f (x) (declare (inline car)) (car x))
;; %%inline-of f = NIL、code-len = 487(展開されていない)

(declaim (inline car))
(defun g (x) (car x))
;; %%inline-of g = (CAR)、code-len = 532(展開されている。+45 byte)
```

**指示書は `declare` と `declaim` の両方を要求しているので、
`declare` 側は新規に作る必要がある。**

### 1-3 **`+` と `-` は、宣言と無関係に常に展開されている**

指示書 §目的 が確認を求めていた点。**そのとおりだった。**

`za_emit_arith_call_or_inline`(`src/c/za.c`)は、呼び先が `primitive_add2` か
`primitive_subtract2` のとき、**`za_inline_enabled` を一切見ずに**
fixnum のインライン高速路を出す。

実機で生成コードを数えて裏づけた(`%%current-inline` = NIL のとき)。

| 関数 | code-len | 全項目 | `js` | `jb` | `call` |
|---|---:|---:|---:|---:|---:|
| `(+ x y)` | **735** | 147 | **1** | 0 | 17 |
| `(- x y)` | **738** | 148 | 0 | **1** | 17 |
| `(* x y)` | 690 | 137 | 0 | 0 | 17 |
| `(/ x y)` | 690 | 137 | 0 | 0 | 17 |

`js` / `jb` は fixnum 高速路の桁溢れ判定の分岐である。**`+` `-` にだけあり、
`*` `/` には無い。** 690 が「call だけ」の長さ。

#### これは意図された組み込みの最適化である(副作用ではない)

`za_emit_arith_call_or_inline` は**型特化(PR #89〜#93)より前からある**。
改善 A の時期に、JIT が `+` `-` の fixnum 高速路を直接出すために入れたもので、
**`declaim inline` の仕組み(Phase 3)とは別系統**である。
型特化を足したときの副作用ではない。

#### 方針との食い違いをどうするか

指示書の方針は「**`inline` 宣言がない場合は展開しない**」である。
**合わせると `+` `-` は宣言なしで遅くなる。** Phase 0 の実測では
宣言なしの `+` が 21.9 命令/回、call 版が 62.9 命令/回なので、
**41 命令/回(1 回あたり約 887 命令の 4.6%)の悪化**になる。

**判断: 合わせる。ただし独立した PR にする。**

理由:

- 二本立ての規則(「`+` `-` だけは宣言が無くても展開される」)は、
  次に触る人が必ず踏む。**`*` `/` を展開できるようにした直後に
  「なぜ `*` は宣言が要るのか」と聞かれる形**になる
- `inline` 宣言で展開できるようになれば、**同じ速度は宣言 1 行で取り戻せる**
- 指示書が「性能が落ちる変更なので他の変更と混ぜない」としている

**この PR では変えない。** 展開の仕組みを算術へ広げたあと、
最後に独立した PR として出す。

### 1-4 `declaim` の意味論は CommonLisp と違う

`documents/declaim-design.md` のとおり **environment 単位**で、親からは
引き継がない。指示書が「未確定」としていた点を実測した。

| 問い | 実測 |
|---|---|
| ファイルの終わりで切れるか | **切れない。** `load` した別ファイルにも効き、戻ってからも残る |
| `let` の中の `declaim` は | **environment へ届く**(frame は `os_definition_env` が読み飛ばす) |
| 関数ごとに記録されるか | される。`%%inline-of` がコンパイル時の値を返す |

```
(declaim (inline car cdr))
(load "sub.lisp")
  [sub.lisp の中] %%current-inline = (CAR CDR)      ← 効いている
  load から戻った後             = (CAR CDR)      ← 残っている
```

**つまり「ファイル単位」ではなく「そのあと全部」である。**
`declare` 側を作るときは、**`declare` が `declaim` を打ち消せること**が
実用上重要になる(いまは `declare` が何もしないので打ち消せない)。

### 1-5 型宣言の伝達経路に `inline` も乗るか

型は `os_scan_declarations` → `os_decl_types_t` → `g_za_param_decl_types` と
**変数ごとの配列**で渡っている。`inline` は**変数ではなく演算子**に付くので、
この配列には乗らない。

**`declaim` 側と同じ「ビットの集合」を、フォームのスコープで持ち回る形になる。**
`za_compile_*` はすでに `za_local_scope_t` を引数で持ち回っているので、
そこへ inline ビットを足すのが素直である(Phase 2 で設計する)。

### 1-6 特化版の呼び出しはどこで生成されているか

**JIT(`src/c/za.c`)だけ。**

| 経路 | 型特化 |
|---|---|
| インタプリタ(`eval.c`) | しない。`primitive_add` 等の n 項版を呼ぶ |
| AOT トランスパイラ | していない(`lisp_compiled.c` は `primitive_add2` 等を直接呼ぶ) |
| **JIT** | **`za_specialized_wrapper` が呼び先を差し替える** |

差し替えの場所は 2 つある。**`/` だけ経路が違う**ので注意
(PR #93 でこれに引っかかった)。

- `za_compile_fold` … `+` `-` `*`(n 項の畳み込み)
- `za_compile_binary` … `/`(PR #88 で二項専用の直接呼び出しにした)

### 1-7 型宣言と実際の値が食い違ったとき(現状)

**壊れる。それが仕様である**(`documents/declare-typed-add.md` §3-1)。

```
(defun f (x y) (declare (type <fixnum> x)) (declare (type <fixnum> y)) (+ x y))
(f 1.5f0 2.5f0)  =>  575897802350002176
```

`ISIKIOS_DECLARE_AUDIT` を付けたビルドでだけ panic する。
**`inline` 宣言の有無でこの振る舞いを変えないこと**が指示書の要求である。

## 2. `inline` 宣言の仕様(確定分)

| 項目 | 決定 |
|---|---|
| `declaim (inline op)` | **既存の仕組みをそのまま使う。** environment 単位、`load` をまたいで残る |
| `declaim (notinline op)` | 同上。ビットを落とす |
| `declare (inline op)` | **新規に作る。** そのフォームの内側だけ |
| 内側と外側 | **内側が優先**(`declare` が `declaim` を打ち消せる) |
| `let` の初期化式 | **効かない**(本体だけ)。CL と同じ |
| 対象の指定 | `(inline +)` のように演算子を列挙 |
| 型宣言との組み合わせ | 同じ `declare` でも別々の `declare` でも同じ意味 |
| 未知の名前 | **黙って無視**(既存の `os_inline_bit_of` の方針を踏襲) |
| インタプリタ | **無視する。** 展開しなくても結果は同じなので仕様上の問題は無い |
| AOT トランスパイラ | **本フェーズでは扱わない**(型特化もしていないため) |

### 未確定のまま残すもの

- **`declare` のスコープをどう実装するか。** `za_local_scope_t` に乗せるのが
  素直だが、`declaim` が environment 側にあるので**2 系統を合成する**必要がある。
  Phase 2 で設計する

## 3. Phase 0: 変更前の基準値

`make test-qemu-instcount-gate MILESTONE=test/lisp/qemu_boot_inline_phase0.lisp`

n=200,000、**命令数(割り込み補正後)**。`ISR_INSNS_PER_TICK` = 914。

### 3-1 ぶれの幅

**0 命令。** 26 区間すべてが 2 ブートで 1 命令も違わなかった。

> **【罠】区間の中で GC が走ると端数が出る。**
> 最初の測定で `gc=1` だった 3 区間だけ、他と違う端数を持っていた
> (`/fix-decl` +528,013、`+dbl-nodecl` +156,098、`*dbl-decl` +2,128,866)。
> **gc=0 の区間と gc=1 の区間が完全に一致していた**ので原因が特定できた。
> ゲートに入る前に GC を起こして半空間を空にしたら消えた。
> 区間ごとに `gc=` を出しておくこと。

### 3-2 床

| | 命令数 | 1 回あたり |
|---|---:|---:|
| 空のゲート | 11,772 | — |
| `f-id`(primitive を呼ばない) | 172,813,921 | **864.1** |

**864 命令が `funcall` + ループ + JIT フレームの床**である。
以下の数字はすべてここからの差。

### 3-3 基準値(**1 回あたりの命令数、床を引いた値**)

| 演算 | 型 | 宣言なし | 宣言あり | 差 |
|---|---|---:|---:|---:|
| `+` | fixnum | **21.9** | **62.9** | **+41.0** |
| `+` | single | 156.9 | **24.9** | **−132.0** |
| `+` | double | 385.9 | 385.9 | **±0.0** |
| `-` | fixnum | **22.9** | **75.9** | **+53.0** |

#### 読み取り

- **double は宣言あり/なしが完全に一致している。** 特化表に載っていないので
  当然であり、**対照群が正しく機能していることの確認**になる
- **single は 4 演算とも宣言ありが 24.9 でぴたり揃う。** 特化版は
  「call + 即値の演算」で、演算の種類によらず同じコストである。
  宣言なしは 143.9〜156.9 で、**特化が 119〜132 命令/回を削っている**
- **fixnum の `+` `-` は宣言すると遅くなる。** JIT のインライン高速路
  (21.9 / 22.9)を失って call(62.9 / 75.9)になるため。§1-3 のとおり
- **fixnum の `*` `/` は宣言すると −8.0 命令/回速くなる。**
  タグ検査 2 回ぶん(陽性対照で測った 1 組 = 10 命令)とほぼ一致する
- `*` の宣言なし 62.9 と `+` の宣言あり 62.9 が一致する。
  **どちらも「primitive を 1 回 call して fixnum の演算をする」**ので、
  同じ値になるのは辻褄が合っている

### 3-4 確保量(byte/call、n=10,000、GC なし)

| | byte/call |
|---|---:|
| `f-id`(底) | 48 |
| `+` fixnum 宣言なし / あり | 48 / 48 |

| `+` single 宣言あり | 48 |
| `/` single 宣言あり | 48 |

48 はループ自体(`funcall` / `while` / `setq`)の確保。
**double だけが 32 byte 多い**(結果の instance)。
**インライン化で確保量が増えてはならない。**

### 3-5 code-len(展開の静的な指標)

| | 宣言なし | fixnum 宣言 |
|---|---:|---:|
| `+` | **735** | 690 |

690 が「call だけ」。`+` `-` の宣言なしだけが長いのは §1-3 のインライン高速路。

- PR #91 の **+28 tick = 23%** … 大きさが違う。実際は 1 回 887 命令中の
  53 命令 = **約 6%**

tick ベースの床を分母にしたもので、命令数の実態とは合わない。

## 6. Phase 0 の追測(レビュー指摘 1〜3)

`make test-qemu-instcount-gate MILESTONE=test/lisp/qemu_boot_inline_phase0b.lisp`

### 6-1 指摘 1: single の 24.9 は本物だった(計算は消えていない)

**疑う理由は妥当だった**(床のすぐ上、fixnum より小さい、4 演算で完全一致)。
**3 通りで確かめた。**

#### (a) 結果を累積して値を出す

```
single + の累積 = 750000.0f0    (1 回 3.75 × 200,000)  ✓
single * の累積 = 600000.0f0    (1 回 3.0)             ✓
single / の累積 = 300000.0f0    (1 回 1.5)             ✓
fixnum + の累積 = 1400000       (1 回 7)               ✓
double + の累積 = 750000.0      (1 回 3.75)            ✓
```

**全 200,000 回が実行されている。** 定数畳み込みも脱落も起きていない。

#### (b) 累積版の命令数が、足し算で説明できる

累積版は `(+ s (funcall f a b))` を毎回やるので、**累積用の `+` が乗る。**
その `+` は宣言の無い GENERIC で、s の型で値が変わる。

```
累積版の床(acc-f-id、s は fixnum)        184,214,033
acc-+fix − 床 = 62.9/回     捨てる版の +fix-decl と同じ 62.9    ✓
acc-+sgl − 床 = 159.9/回
```

**159.9 = (156.9 − 21.9) + 24.9 である。**
累積用の `+` が fixnum(21.9)から single の GENERIC(156.9)へ変わったぶんと、
測っている `+sgl-decl`(24.9)の和にぴたり一致する。

**Phase 0 の 3 つの独立した数字(156.9 / 21.9 / 24.9)が、
別の測り方で辻褄が合った。**

#### (c) なぜ single のほうが安いのか — **葉関数だから**

C 側の生成コードを数えた。

| 関数 | 命令数 | 内部の call |
|---|---:|---:|
| `primitive_add2_single` | **9** | **0** |
| `primitive_subtract2_single` | **9** | **0** |
| `primitive_multiply2_single` | **9** | **0** |
| `primitive_divide2_single` | **9** | **0** |
| `primitive_add2_fixnum` | 54 | 4 |
| `primitive_multiply2_fixnum` | 54 | 4 |
| `primitive_divide2_fixnum` | 54 | 4 |
| `primitive_add2`(GENERIC) | 81 | 9 |

**single 特化版は 4 つとも 9 命令・call 無しの葉関数**である。
フレームも呼び出し規約の保存も要らない。
**4 演算で完全に一致するのは、4 つとも同じ形・同じ長さだから**である。

fixnum 特化版が 54 命令あるのは、**桁溢れ(`/` はゼロ除算)のとき
GENERIC へ落ちる経路を持つ**ためで、そこで `os_make_cons` と
n 項版を呼ぶので葉になれない。single は昇格も例外も無いので落ち先が要らない。

**「float のほうが速い」のではなく「落ち先を持たない関数のほうが安い」**である。

### 6-2 指摘 2: double は**特化版がそもそも存在しない**

**完全一致は正しかったが、理由は「対照群として機能している」である。**

```
pb-agen (宣言なし)          len=735  primitive_add2 を呼ぶ
pb-adbl (double 宣言)       len=735  primitive_add2 を呼ぶ   ← 同じ
%%declared-types-of pb-adbl = (<DOUBLE-FLOAT> <DOUBLE-FLOAT>)   ← 宣言は届いている
```

**宣言は記録されているが、`za_specialized_wrapper` が
fixnum / single-float 以外を受け付けない**ので GENERIC のままになる。
`primitive_add2_double` のような関数は**1 つも無い。**

#### **Phase 3 の前提が変わる**

指示書は Phase 3 を「single / double」としているが、

- **single**: 特化版があり、`inline` を足せば展開できる
- **double**: **特化版が無い。** 「double を展開する」には先に決めることがある

| 案 | 内容 |
|---|---|
| A | `primitive_*2_double` を作ってから展開する(型特化の作業が先に要る) |
| B | GENERIC を展開する(型宣言なしの汎用版と同じ扱い。Phase 3 後半と統合) |
| C | double は対象から外す(対照群として残す) |

**C を推す。理由は 1 つだけである。**

> **`double` を「展開する」は、実質「特化版を新規に作る」である。**
> `primitive_*2_double` が存在しないので、インラインの前に型特化の作業が
> 丸ごと 1 つ要る。**それはインラインのフェーズでやる作業ではない。**

補強になる見立て(**未確認**):

- double は結果が instance なので**確保が必ず伴う**(80 byte/call。
  fixnum / single は 48 byte/call = ループ自体のぶんだけ)。
  **372.9 命令/回のうち確保が大半を占めていると見られるが、これは測っていない。**
  single との差を取れば裏は取れる(確保量が分かっているので)。
  **外すなら測る必要が無いので、未確認のまま残す**(規則 1)

測定上の副次的な利点(**判断の理由ではない**):

- double を対象外にしておくと、**4 演算ぶんの対照群がそのまま残る。**
  宣言あり/なしが完全一致することが、以後も「特化が効いていない側」の
  基準として使える

判断は Phase 3 の入口で改めて出す。

### 6-3 指摘 3: `* /` の「宣言ありが速い」は **call 対 call の差**

`+` `-` とは状況が違う。**並べると分かる。**

| 演算 | 宣言なし | 中身 | 宣言あり | 中身 | 差 |
|---|---:|---|---:|---|---:|
| `+` | **21.9** | **JIT が展開** | 62.9 | 特化版を call | +41.0 |
| `-` | **22.9** | **JIT が展開** | 75.9 | 特化版を call | +53.0 |
| `*` | 62.9 | GENERIC を call | 54.9 | 特化版を call | **−8.0** |
| `/` | 57.9 | GENERIC を call | 49.9 | 特化版を call | **−8.0** |

- **`+` `-` は「展開 対 call」**なので、宣言すると call のぶん(41〜53)増える
- **`*` `/` は「call 対 call」**なので、差は中身だけ。**−8.0 はタグ検査 2 回ぶん**で、
  陽性対照で測った「タグ検査 1 組 = 10 命令」とほぼ一致する

#### `* /` を展開したときの目標値

**call を消せば床に近づくはずである。** 目安は `+` `-` の展開版。

| | いま | 目標 | 根拠 |
|---|---:|---:|---|
| `*` fixnum | 54.9 | **20 前後** | `+` の展開版が 21.9、`-` が 22.9 |
| `/` fixnum | 49.9 | **20 前後** | 同上。ただし `div` は TCG で高い可能性がある |

**`/` は除算命令そのものが TCG で高いかもしれない**ので、
`*` より目標から離れても不思議ではない。**先に `*` を書いて基準を作る。**

#### **ただし `* /` の展開命令列は `+ -` より長くなり得る**

**目標に届かなくても、それは失敗ではなく演算の性質である。**

`+` `-` の展開が `js` / `jb` **1 本**で済んでいるのは、
**加減算の桁溢れがフラグ 1 本で判定できる**からである
(生のタグ付き値をそのまま足して bit63 を見る。
`documents/declare-typed-arith.md` §2-1)。

| 演算 | 桁溢れ/例外の判定 | 展開命令列の見込み |
|---|---|---|
| `+` | `add` の結果の符号ビット 1 本 | **1 分岐**(実測 21.9 命令/回) |
| `-` | `cmp` + `jb` 1 本 | **1 分岐**(実測 22.9) |
| **`*`** | **事前検査か、128bit で計算してから比較** | **`+ -` より長い** |
| **`/`** | **ゼロ除算の分岐が必ず要る**(§`/` のゼロ検査は外せない) | **`+ -` より長い** |

`*` は `imul` + `jo` が使えない(符号マグニチュード表現。
`documents/type-system-survey.md` §9-4)ので、
**マグニチュードを取り出して `mul` で 128bit の積を作り、上位を見る**形になる。
`/` は `div` の前にゼロ検査が要る(外すと #DE でマシンが止まる)。

**目標 20 前後は「`+` `-` がそこにいる」という参考値であって、
`* /` がそこへ行くべきだという根拠ではない。**

### 6-4 まとめ: Phase 2 に入る前に確定したこと

| 問い | 答え |
|---|---|
| single の 24.9 は本物か | **本物。** 葉関数(9 命令)だから安い |
| double の完全一致は異常か | **正常。** 特化版が存在しないので GENERIC のまま |
| `* /` の −8.0 は何か | **タグ検査 2 回ぶん。** call 対 call の差 |
| 展開の目標値は | `+` `-` は 21.9 / 22.9(実測済み)、`*` `/` は 20 前後 |

## 7. Phase 2: `inline` / `notinline` 宣言の解釈(**展開はまだしない**)

**このフェーズで入れたのは「宣言が読まれて生成側まで届く」ところまで。**
`za_emit_arith_call_or_inline` はまだビットを見ないので、生成コードは変わらない。
テストでも「宣言を付けても code-len が変わらないこと」を固定している。

### 7-1 合成の規則(**実装前に決めた**)

| 規則 | 決定 |
|---|---|
| 外側と内側 | **内側が優先** |
| 同じ深さ | **後から来たものが優先**(宣言指定子を現れた順に適用) |
| `declaim` と `declare` | `declaim` が下地、`declare` がその上に重なる |
| `let` の初期化式 | **効かない**(本体だけ) |
| 未知の名前 | 黙って無視(`declaim` の既存方針を踏襲) |

「立てる/落とす」の集合ではなく、**継承したビット集合を入力にして、
宣言を順に適用した結果を返す**形にした。これで 2 つの規則が同時に落ちる。

```c
UINT64 os_scan_declaration_inline(lisp_val_t body, UINT64 inherited);
```

### 7-2 どこで持ち回るか — **既存の `za_fn_scope` と同じ形**

新しい引数を `za_compile_*` 全体へスレッドするのは避けた。
`flet`/`labels` のスコープ(`g_za_fn_scope`)が既に
**「グローバルを save/restore する」**方式を採っており、その理由が
そのまま当てはまる。

> C の再帰がレキシカルネストと 1 対 1 に対応するため、
> この方式はパラメータスレッディングと意味的に等価である(za.c のコメント)

| 変数 | 意味 |
|---|---|
| `g_za_declaim` | environment 単位の `declaim` + **defun 本体の `declare` を畳み込んだもの** |
| `g_za_inline_scope` | **いまコンパイルしているレキシカルスコープの現在値** |

`za_inline_enabled` は `g_za_inline_scope` を読む。
**`car`/`cdr`/`null`/`eq` も同じ経路になったので、副産物として
`(declare (inline car))` が効くようになった**(以前は `declaim` だけ)。

#### defun 本体の `declare` は `optimize` へ畳み込んだ

`eval.c` で **宣言を剥がす前に** 読み、`DECLAIM_WITH_INLINE_BITS` で
`optimize` の bit8〜 へ重ねてから `za_try_compile_defun` へ渡す。

**`za_try_compile_defun` の署名を変えずに済み、`%%INLINE-OF` が
そのまま「この関数に効いた指定」を返すようになる。**

> **順序が要である。** `os_scan_declarations` が `declare` を剥がしてしまうので、
> inline の走査はその**前**に置く。剥がしたあとに読むと常に空になる。

#### `let` の初期化式に効かないのは、**適用位置で自然にそうなる**

`let` は `((lambda (v...) . body) init...)` へ展開されるので、
`za_compile_let` の中では **init 式のコンパイルが body より先**に来る。

```
os_scan_declaration_inline(lambda_body, g_za_inline_scope)  ← 読むだけ(まだ適用しない)
os_scan_declarations(...)                                   ← declare を剥がす
  ... init 式のコンパイル ...                                ← 外側のスコープのまま
g_za_inline_scope = body_inline_bits                        ← ここで適用
  ... body のコンパイル ...
```

**明示的に外す処理は要らなかった。** 適用を body ループの直前に置くだけで済む。
復元は `__attribute__((cleanup))` にしてあるので、body の途中で
コンパイルが失敗して `return 0` しても戻る。

### 7-3 観測する口: `%%INLINE-HERE`

`%%INLINE-OF` は**関数単位**までしか見えないので、`let` の内側の `declare` が
届いているかを読めない。**コンパイル時に畳む組み込み**を足した。

```lisp
(defun f (n)
  (declare (inline +))
  (let ((a 1))
    (declare (notinline +) (inline *))
    (%%inline-here)))        ; => * のビットだけが立った fixnum
```

- **JIT**: `za.c` が `(%%inline-here)` を見つけたら、その場所の
  `g_za_inline_scope` を **fixnum の即値**にして返す。実行時には何も起きない
- **インタプリタ**: `declare` のレキシカルスコープを持たないので、
  environment の `declaim` をそのまま返す。
  **食い違うのは「JIT 済み関数の `let` の内側」だけ**で、そこを見るのが用途である

ビット位置は C 側にしか無いので、読むための `%%INLINE-BIT-OF`(名前 → ビット)も
足した。`logand` が無いので、テストでは `(= 1 (mod (div bits b) 2))` で見ている。

### 7-4 踏んだこと

#### `inline_to_list` にビットを足し忘れた

`os_inline_bit_of` に 4 ビット足しただけでは、**`%%CURRENT-INLINE` と
`%%INLINE-OF` が黙って `nil` を返す。** 表示用の `inline_to_list` が
`car/cdr/null/eq` しか知らなかった。

**「宣言が効いていない」ように見えるが、効いている。** テストが
11 件落ちて分かった。ビットを足す場所は 3 箇所ある。

1. `INLINE_BIT_*` の定義(`runtime.h`)
2. `os_inline_bit_of`(名前 → ビット)
3. **`inline_to_list`(ビット → 名前)** ← 忘れやすい

#### そのついでに原則4の危険を持ち込んだ

`inline_to_list` に `os_make_symbol("+")` を足したが、**算術の名前は
`g_sym_*` を持たないので intern が走り、確保しうる。**
積み上げ中の `r` が GC で stale になる形だった
(`car/cdr/null/eq` だけだった頃は全部グローバルで確保が無かった)。
`GC_PROTECT(r)` を足した。**ビットを足す作業が、確保の有無を変えていた。**

#### 既存テストが「`+` は未知の名前」を固定していた

`inline_builtin_test.lisp` にこの行があった。

```lisp
(assert-equal nil (declaim (inline +)))   ; 未実装の builtin の例として + を使っていた
```

**`+` が対象になったので、この前提が崩れた。** `declaim` が実際にビットを立て、
以降のファイル全体で `+` が立ちっぱなしになり、**同じファイルの後続の
`(assert-equal nil (%%current-inline))` が 10 件連鎖で落ちた。**

`declaim` は environment 単位でファイルをまたいで残るので、
**落ちた場所(後続の assert)と原因の場所(1 行の declaim)が離れる。**
切り分けは「ファイル単位で `%%current-inline` を出して、どこで立つかを見る」で付いた。

対象外の例を `cons`(確保を伴うので対象にならない)へ差し替え、
**算術が対象になったことの確認と、その打ち消し**を同じ場所に足した。

> **旧いテストは旧い真実を固定している。** 「未知の名前は無視される」の
> 例として使われていた名前が実装されると、そのテストは**仕様の変化を
> 正しく検出している。** 落ちたら、テストを直すのか実装を直すのかを
> 先に決めること。

## 8. レビュー指摘への対応(Phase 2 の後始末)

### 8-1 `declaim` 漏れの検出器を置いた — **そして一度壊れていた**

§7-4 で直したのは**症状**だった。原因は「そのテストが古かったこと」ではなく
**`declaim` がファイルをまたいで残ること**で、それは仕様どおりであり変えない。
**次に誰かがファイルの途中に `declaim` を書いた瞬間、同じ連鎖がまた起きる。**

`isiki-test-load` の出口で、**ファイルの前後で `%%current-inline` が
一致すること**を見るようにした。落ちた場所と原因の場所が一致する。

```
[NG] (LIST PATH (%%CURRENT-INLINE))
     => ("test/lisp/inline_decl_test.lisp" (*))
     (expected ("test/lisp/inline_decl_test.lisp" NIL))
```

**除外リストは作らなかった。** 宣言を試すファイルも最後に打ち消せば通るので、
除外を用意すると**漏れを恒久化できてしまう。** 実際、既存の 3 ファイル
(`declaim_test` / `inline_builtin_test` / `inline_decl_test`)はどれも
打ち消しており、除外なしで通った。

#### **検出器は最初、一度も走っていなかった**

陽性対照(わざと `declaim` を漏らす)を当てたら、**反応しなかった。**

原因は `assert-equal` が**マクロ**で、`isiki-test-load` の `defun` より
**後ろで定義されている**こと。マクロ定義より前に書いた `(assert-equal ...)` は
展開されず、ただの関数呼び出しとして解釈される。`assert-equal` は関数としては
存在しないので **EVAL-ERROR が値として返り、検査は黙って素通りした。**

検査本体を別関数(`isiki-declaim-check`)へ出して、マクロ定義より後ろに置いた。
**関数呼び出しなら実行時解決なので、定義が後ろでも問題ない。**

| | アサーション数 |
|---|---:|
| 検出器を書いたつもり(走っていない) | 167 |
| **実際に走るようにした** | **170**(3 ファイル × 1 件) |

**件数が増えないことで気づけたはずだった。** 陽性対照を当てるまで分からなかった。
PR #90 の「検出器自体が壊れていた」と同じ形で、これで 2 例目である。

### 8-2 ビットの足し忘れは**ビルドで落ちる**ようにした

「名前 → ビット」と「ビット → 名前」が別々に並んでいたのを、
**名前表 1 つに統合**した。両方をそこから導くので、足す場所が 2 箇所から
1 箇所になる。さらに要素数を `_Static_assert` で `INLINE_BIT_COUNT` と
突き合わせた。

```c
static const struct { UINT64 bit; lisp_val_t *sym; } g_inline_names[] = { ... };
_Static_assert(sizeof(g_inline_names) / sizeof(g_inline_names[0]) == INLINE_BIT_COUNT, ...);
```

`za_syms_t` の `_Static_assert` と同じ手である。X マクロは使わなかった
(この規模なら `_Static_assert` 1 行のほうが読む側の負担が少ない)。

**わざと `INLINE_BIT_COUNT` を 9 にして、ビルドが落ちることを確認済み**(規則 8)。

#### `g_sym_plus` などを足して、確保の危険を構造ごと消した

`g_sym_*` の基準は **「JIT の外の C コードがこのシンボルと比較するか」**である
(JIT は `za_syms_t` を自前で intern して GC へ繋いでいる)。
算術は長らく JIT の中だけで使われていたので `g_sym_*` を持たなかった。
**意図的な除外ではなく、基準に合致していなかっただけ**である。

`os_inline_bit_of` が `runtime.c` から比較するようになったので基準に合致した。
事前に intern したことで:

- `find_interned_symbol` の引き直しが消えた
- **`os_make_symbol` が `cons` の前に走る形が無くなった**(原則4の危険が
  構造ごと消えた。`GC_PROTECT(r)` は要らなくなったので外した)

### 8-3 「`type` キーワードのみ」は上書きした

`documents/declare-types.md` §3-1 の決定に**取り消しを明記した。**
決定は取り消されない限り生き続ける(`quotient` の件と同じ形)。

副産物で効くようになった `(declare (inline car))` は、
**仕様として `documents/inline-builtin.md` に追記し、テストを持たせた。**
意図して作ったものではないが、いま動くものは誰かが必ず依存する。

### 8-4 「落とす方向」は実際に走っている

合成規則の半分(内側が外側を**打ち消す** / 後の宣言が前を**取り消す**)が
一度も実行されないなら、壊れていても分からない、という指摘。
**`notinline` は実装済みで、両方向とも走っている。**

| テスト | 何を走らせるか |
|---|---|
| `idt-override` | 内側の `notinline` が外側の `declaim` を打ち消す |
| `idt-last-wins` | 同じ深さで後の `notinline` が前の `inline` を取り消す |
| `idt-last-wins2` | 同じ深さで後の `inline` が前の `notinline` を取り消す |
| `idt-here-nest` | `let` の内側の `notinline` を `%%INLINE-HERE` で読む |

テストにその旨のコメントを入れ、どのケースがどの規則を走らせるかを書いた。

### 8-5 `let` の初期化式のテストは「コンパイル順序の番人」である

正しさが「init 式が body より先にコンパイルされる」という**別の場所の性質**に
依存している。明示的な処理が無いぶん、`let` の展開や評価順を触ると**静かに壊れる。**

テストにその旨と、落ちたときに最初に見る場所
(`za_compile_let` の「init のコンパイル」と「`g_za_inline_scope` の適用」の
前後関係)を書いた。

## 9. Phase 3: `+` `-` fixnum の展開

### 9-0 **数字の単位が変わった。ここが境目である**

> **PR #94 より前の数字は tick、PR #94 以降は命令数(割り込み補正後)である。**
>
> | 文書 | 単位 |
> |---|---|
> | `documents/declare-typed-add.md` / `declare-typed-arith.md` §1〜§9 | **tick** |
> | `declare-typed-arith.md` §10〜 | tick(§10-1 だけ命令数) |
> | **`documents/inline-arith.md`(この文書)** | **命令数** |
> | `documents/fixnum-signed-fastpath.md`(改善A の 15.2 倍) | **tick** |
> | `documents/performance-measurement.md`「手法1」 | 命令数 |
>
> **単位の付いていない数字は必ずいつか取り違えられる**(規則 1 と同じ構造)。
> 以降は数字に単位を付けること。

#### 命令数と時間は別の量である

**精度の高い指標が、関連性の高い指標を静かに置き換えないようにする。**

| 変更 | 命令数 | 時間 |
|---|---|---|
| `div` を 1 つ消す | −1 | **大きく減るはず** |
| 予測される分岐を 1 つ消す | −1 | ほぼ変わらない |

インラインの作業は**コードの形**の話なので命令数が正しい指標である。
**しかし「で、速くなったのか」には tick でしか答えられない。** 両方残すこと。

### 9-1 何を変えたか — **加算的な変更**

`za_emit_arith_call_or_inline` が、**型宣言つきの特化版でも `inline` 宣言が
あれば同じ高速路を出す**ようにした。

```c
if (wrapper_fn == (void *)primitive_add2_fixnum && za_inline_enabled(INLINE_BIT_ADD)) {
    is_add = 1;
}
```

- **`inline` 宣言が無ければ従来どおり call だけ**
- **宣言なしの経路(GENERIC)は一切触っていない**
- 「`inline` 宣言が無ければ展開しない」へ寄せるのは**別の PR**(§1-3)

`-` を `+` と同時にやったのは、**門番が同じ 1 つの条件**だからである。
`+` だけ通して `-` を通さない中間状態は、§1-3 で「二本立ての規則は次に触る人が
必ず踏む」と書いたものそのものになる。
(同じブートで 41 と 53 の両側から呼び出し費用を挟めるのは副次的な利得。)

`-fix-inline` は `-fix-nodecl` と 216 命令違った(`+` は完全一致)。

割り込み補正の残差である。tick はゲートの外で読んでいるので、
**区間内の実際の ISR 回数とサンプルした tick 差が 1 回未満ずれうる。**
ISR 1 回が 914 命令なので、**216 は 1 回分に満たない。**
per-call の値(22.9)は変わらない。

### 9-3 呼び出しの費用が上下から挟めた

| | 展開 | call | 差 = 呼び出しの費用 |
|---|---:|---:|---:|
| `+` fixnum | 21.9 | 62.9 | **41.0** |
| `-` fixnum | 22.9 | 75.9 | **53.0** |

`-` のほうが 12 命令高いのは、`primitive_subtract2_fixnum` が
`fixnum_negate` を挟むぶんである(`+` は素通し)。

**呼び出しそのものは 41 命令前後**で、残りが呼び先の中身になる。
`primitive_identity2_fixnum`(何もしない特化関数)を別途作る必要は無くなった。

### 9-4 まだ答えていないこと

**「で、速くなったのか」は tick で測っていない**(§9-0)。
命令数が 62.9 → 21.9 に減ったのは**コードの形**の話である。
`+` `-` のインライン路は分岐 1 本と算術 1 命令なので、
**時間でも減るはずだが、それは別に測る必要がある。**
