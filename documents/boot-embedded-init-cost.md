# 同梱した基盤ライブラリを起動ごとに読む費用(M1-T6 / issue #185)

- 対象: PR #188 / #190 で `src/lisp/init.lisp` と `src/lisp/disassemble.lisp` を
  カーネルへ同梱し、**起動ごとに読み・解析し・機械語化する**ようになった費用
- 位置づけ: **これは計測である。合格線は決めない**(`docs/plans/local-load-and-core-image.md`
  の決定 **D5 / D6**)。数字を出して記録し、コアイメージ(M4 以降)の見積りに使う
- 規則: `documents/records-and-measurement-rules.md`。とくに
  **規則 11(測る前に予測を宣言する)**・**規則 8(陽性対照)**・
  **規則 9(時間より確保量)**・**規則 10(分解能)**・**規則 13(数は導出する)**

---

## 1. 測る 4 つ

| # | 量 | 計器 | 性格 |
|---|---|---|---|
| 1 | Immobilized Space の消費 | `%%IMM-SPACE-USED-BYTES` / `%%IMM-SPACE-TOTAL-BYTES` | **高水位。解放されない**(F9) |
| 2 | ブート時のヒープ確保量 | `%%HEAP-USED-BYTES`(+ `%%GC-COLLECT-COUNT`) | From 空間の bump。**GC で巻き戻る** |
| 3 | ブートから対話を受け付けるまでの tick | `(GET-INTERNAL-REAL-TIME)` | 1 tick = 10ms(`clock.c` の `TICKS_PER_SECOND` = 100) |
| 4 | `SMALL_HEAP_SIZE` 試験が通ること | `make test`(`test/c/runtime_test.c`) | 余裕 5KB 未満・**症状はハング** |

**3 が刻みで測れる理由(設計判断 L7)**: 同梱の読み込みは
`run_boot_entry`(`src/c/kernel.c`)の中、**割り込み許可より後**に走る。
刻みは割り込み許可の時点から数え始めるので、**同梱の読み込みは刻みに入る**。
**起動前半(中核の登録・AOT 層の初期化)は刻みに含まれないので範囲外**である。

### 2-3. 予測

**単価の出どころ**: `documents/performance-measurement.md`
「Immobilized Space(`defun` ごとの消費)」が **20 defun で 71,008 byte
(1 defun あたり約 3,550 byte)**を実測で記録している。
同じ節は **`bench_jit.lisp` を load する前の総量を 484,496 byte** と記録しており、
**その測定は `init.lisp` を読んだ起動で取られている**。
つまり「`init.lisp` + `disassemble.lisp` を読み終えた状態の imm 消費」は
**2026-10-02 時点で約 484KB だった**ことになる。2 つの見積りが独立に噛み合うか見る。

| # | 予測 | 導出 |
|---|---|---|
| **P1a** | 同梱ありの imm 消費 = **420,000 〜 560,000 byte**(16,777,216 の **2.5 〜 3.3%**) | 上の 484,496 byte(別経路の実測)と、defun 単価からの積の両方がこの帯に入る |

| **P2a** | ブート中の GC 回数 = **0** | `QEMU_MEM` = 256M。From 空間は数十 MB あるので数百 KB では発火しない |
| **P2b** | 同梱ありのヒープ消費 = **200,000 〜 700,000 byte**、差も同程度 | 同梱 83KB 弱のソースの構文木(cons 16 byte)が定義として生き残る。トークン 1 万数千個の見当 |

### 2-4. どう転んだら何を意味するか

| 転び方 | 意味 |
|---|---|
| P1b が大きく外れて**上**に出る | 二重 load が残っている(R8)か、`defun` 単価が 3,550 byte より重い定義(`defclass` のアクセサ等)がある |
| P1a が **16MB の 10% を越える** | コアイメージ(M4 以降)の動機が imm space 側にも立つ。**ただし合格線ではない**(D6) |
| P2a が **0 でない** | `%%HEAP-USED-BYTES` は「累積確保量」ではなく「最後の GC 以後の量 + 生存集合」になる。その場合は**累積確保量は測れていない**と書く(規則 10) |
| P3c が **分解能(±20 tick。規則 9)以下** | 同梱の費用は tick では見えない。その場合は「この計器では見えなかった」と書く(規則 10) |
| P4 が外れる | 既知の罠(余裕 5KB 未満・症状はハング)。同梱が恒久消費を増やしたか、組み込みが増えている |

### 2-5. 陽性対照(規則 8)

**計器が対象を見られることを、同じ口で先に示す。**
`NO_EMBEDDED_INIT=1`(`-DISIKIOS_NO_EMBEDDED_INIT`。設計判断 **L5**)で同梱を外すと、
**約 83KB の Lisp を読み・解析し・機械語化する作業がまるごと消える**。
これは「同じものを大げさに変える」側の操作である。

- **発火の条件**: 3 つの数字(imm / ヒープ / tick)が**すべて下がる**こと
- **下がらなければ**、それは現象ではなく計器の限界である(規則 8)
- このつまみは `BUILD_FLAG_SIGNATURE`(`Makefile`)に入っているので、
  **付け外しで古いバイナリを測る事故が起きない**(`EXTRA_CFLAGS` の先例の教訓)

## 3. 測り方(次の人が同じ数字を出せるように)

```
make boot-cost              # 4 つのうち 1〜3。同梱あり / なしを 3 回ずつ、順に
make test                   # 4 つのうち 4(SMALL_HEAP_SIZE 試験を含む)
make check-small-heap-knob  # 4 の陽性対照。**わざと 1 分ハングさせる**
```

| 使うもの | 中身 |
|---|---|
| `test/lisp/qemu_boot_m1_cost.lisp` | 台本。**先頭 3 フォームで採取する。**`let` も条件システムも使わないので、**同梱あり / なしの両方で走る** |
| `tools/boot_cost_report.sh` | 2 構成 × 3 回を順に回し、min / median / max と差、陽性対照・陰性対照の判定を出す |
| `make boot-cost` | 上を呼ぶ口。`BOOT_COST_RUNS=5` で回数を変えられる |
| `make check-small-heap-knob` | `SMALL_HEAP_SIZE=80000` でビルドして走らせ、**打ち切られること**を確かめる |

**組み込み関数は 1 つも足していない。** 計器は 4 つとも既存である
(`%%IMM-SPACE-USED-BYTES` / `%%IMM-SPACE-TOTAL-BYTES` / `%%HEAP-USED-BYTES` /
`GET-INTERNAL-REAL-TIME`。周辺に `%%GC-COLLECT-COUNT` /
`%%DIAG-FN-CELL-COUNT` / `%%BOOT-ALLOC-USED-BYTES` / `%%HEAP-TOTAL-BYTES`)。
**組み込みを 1 つ増やすと `SMALL_HEAP_SIZE` の窓(余裕 5KB 未満)を掃引し直すことになる**
ので、これは意図して避けた。

### なぜ台本の先頭で採取するのが「対話を受け付けるまで」なのか

`src/c/kernel.c` の `run_boot_entry` は **「同梱 → 台本」の順**に実行する。
素の起動では台本が無く、ここで REPL が最初のプロンプトを出す。
したがって**台本の最初のフォームが評価される時点** = 「対話を受け付けられる時点」である。

### 既知の偏り(規則 10)

- **9P を開いて台本の 1 フォーム目を読むぶんがすべての数字に乗っている。**
  素の REPL 起動には無い費用である。**同梱あり / なしの両方に同じだけ乗る**ので
  **差には効かない**(絶対値には効く)
- **tick は割り込み許可より後だけを数える**(設計判断 L7)。
  **起動前半(中核の登録・AOT 層の初期化・UEFI)は入っていない。**
  つまり下の tick は**起動時間の全体ではない**。範囲外である
- `%%HEAP-USED-BYTES` は From 空間の bump なので GC で巻き戻る。
  **今回は GC 回数が 0 だったので、この値は「ブート以後の累積確保量」である**(下記)

## 4. 実測(2026-11-09)

- HEAD: `02053f8`(この文書の予測を固定したコミット)
- QEMU 10.2.1 / `QEMU_MEM` = 256M / **KVM は使っていない(TCG)**
- 1 構成あたり **3 回**

| 量 | 同梱あり(min/median/max) | 同梱なし(min/median/max) | 差(median) |
|---|---|---|---:|
| **tick** | 65 / **65** / 69 | 1 / **1** / 1 | **64** |
| **heap-used (byte)** | 922,256(3 回一致) | 591,936(3 回一致) | **330,320** |
| **imm-used (byte)** | 455,904(3 回一致) | 50,480(3 回一致) | **405,424** |
| gc-count | 0 | 0 | 0 |
| fn-cells | 758 | 631 | 127 |
| boot-alloc-used | 640,760 | 640,760 | **0**(陰性対照) |
| heap-total | 85,621,888 | 85,621,888 | **0**(陰性対照) |
| imm-total | 16,777,216 | 16,777,216 | **0**(陰性対照) |

### 4-1. 答えの 4 つ

| # | 問い | 答え |
|---|---|---|
| **1** | **Immobilized Space の消費** | 起動直後 **455,904 byte = 16MB の 2.717%**。うち**同梱ぶんは 405,424 byte = 2.417%**。**これは解放されない** |
| **2** | **ブート時のヒープ確保量** | **922,256 byte**。うち**同梱ぶんは 330,320 byte**。**ブート中の GC は 0 回**なので、この値は累積確保量そのもの(生存集合ではない)。From 空間 85,621,888 byte の **1.08%** しか使っておらず、**GC が 0 回だった理由もこれで説明がつく**(P2a の裏づけ) |
| **3** | **ブートから対話を受け付けるまでの tick** | **65 tick = 0.65 秒**。うち**同梱ぶんが 64 tick = 0.64 秒**。**測った区間の 98.5% が同梱の読み込みである**(64/65) |
| **4** | **`SMALL_HEAP_SIZE` 試験** | **通る。再調整は要らなかった**(`make test` 合格。`runtime_test.c:2305` の「GC が発火する」も OK) |

> **3 を「起動時間」と読まないこと。** 刻みは割り込み許可より後しか数えない(L7)。
> **0.65 秒は起動の後半だけ**で、UEFI と起動前半は入っていない。

### 4-2. imm 消費は不滅なので、何回ぶん入るかが意味を持つ(F9)

```
16,777,216 / 405,424 = 41.4
```

**同じ基盤ライブラリを読み直せるのは 41 回ぶんである。**
1 回のブートでは 1 回しか読まないので枯れないが、**二重 load は恒久的に 2 回ぶん食う**
(リスク R8 がここに効く)。

## 5. 予測の当たり外れ(規則 11)

**8 つ宣言して 5 つ当たり、3 つ外した。** 外した 3 つはどれも**同じ型の誤り**だった。

| # | 予測 | 実測 | 判定 |
|---|---|---|---|
| **P1a** | imm 消費 420,000〜560,000(2.5〜3.3%) | 455,904(2.717%) | **当たり** |
| **P1b** | imm の差 400,000〜540,000 | 405,424 | **当たり**(帯の下端ぎわ) |
| **P1c** | 同梱なしの imm < 50,000 | **50,480** | **外し**(480 byte = 1.0% 超過) |
| **P2a** | ブート中の GC 回数 = 0 | 0 | **当たり** |
| **P2b**(差) | ヒープの差 200,000〜700,000 | 330,320 | **当たり** |
| **P2b**(絶対) | ヒープ 200,000〜700,000 | **922,256** | **外し** |
| **P3a** | tick 150〜600 | **65** | **外し**(2.3 倍以上の過大) |
| **P3b** | 同梱なしの tick < 60 | 1 | **当たり** |
| **P3c** | tick の差 120〜550 | **64** | **外し**(過大) |
| **P4** | `SMALL_HEAP_SIZE` は再調整なしで通る | 通った | **当たり** |

### 5-1. P2b の絶対値を外した理由 — **床を測らずに差を絶対値として書いた(規則 3)**

ヒープの絶対値を 200,000〜700,000 と書いたとき、**頭の中で見積もっていたのは
「同梱が増やすぶん」だけ**だった。実際には**同梱を外しても 591,936 byte 使われている**
(AOT 層のトップレベルフォーム・9P のマウント・台本の 1 フォーム目)。

```
591,936(床) + 330,320(同梱ぶん) = 922,256(実測)
```

**差の予測は当たっている。外したのは床を 0 と置いたことである。**
規則 3(床を測ってから差を語る)が言っているのはまさにこれで、
**床を測る前に絶対値を宣言してはいけなかった。**

### 5-2. P1c を外した理由 — 同じ誤りの小さい版

「AOT 層が食うのは Function Cell(1 個 16 byte)だけのはず」と書いた。
631 cell × 16 = **10,096 byte** にしかならず、実測の 50,480 とは 40,384 byte 合わない。
**起動前半でも JIT のコードページが積まれている**(AOT のトップレベルフォームと
台本の 1 フォーム目の読み出し)。**ここも床のモデルが粗かった。**

### 5-3. P3a / P3c を外した理由 — **別の区間を測った数字から外挿した(規則 1)**

導出に使ったのは `documents/performance-measurement.md` の
**「ブートの基底 約 11 億命令」**だった。この数字は
**UEFI から試験本体まで含んだブート全体**の命令数であって、
**同梱の読み込み区間のものではない**。それを「ほぼ同梱の読み込みだろう」と
暗黙に置き換えたうえ、TCG の処理能力(2〜5 億命令/秒)も**未検証の★のまま**掛けた。

**★を 2 つ重ねた見積りは外れる。** 規則 1 が言う「何をどう確認したかを同じ行に書く」を
予測の側にも課すべきだった。「11 億命令は**別の区間**の値である」と書いていれば、
帯を宣言する前に気づけた。

**外れの向きも記録しておく**(規則 6): **実測は予測より速かった。**
同梱の読み込みは 0.64 秒で済んでいる。

### 5-4. 別の形の証拠 — 1 定義あたりの imm 消費が独立に噛み合った(規則 14)

imm の数字が計器の人工物でないことを、**別経路の実測**で裏づける。

| 出どころ | 値 |
|---|---|
| 今回: imm の差 ÷ `defun`+`defmacro`+`defmethod` の件数(133、導出) | **3,048 byte/定義** |
| 今回: imm の差 ÷ 増えた Function Cell(127) | **3,192 byte/cell** |
| 既存の実測(`performance-measurement.md`、2026-10-02、`bench_jit.lisp` の 20 defun) | **約 3,550 byte/defun** |

**まったく別の測定(別の日・別のファイル・別の台本)が 15% 以内で一致する。**
さらに同じ節は「`init.lisp` を読んだ起動の imm 総量 = 484,496 byte」を記録しており、
今回の **455,904** と 6% 以内で噛み合う(あちらは台本とベンチの前準備も含む起動)。

### 5-5. 確保量は本当にぶれなかった(規則 2 の例外を先に宣言していた)

`heap-used` と `imm-used` は **3 回とも 1 byte も違わなかった**(4 構成すべて)。
規則 2 は「完全一致は疑え」だが、規則 9 の表が
**「確保量はぶれ無し」**と先に書いているので、**一致はその前提の検算になる**。

**tick だけがぶれた**: 同梱あり 3 回で幅 **4**(65 / 65 / 69)、同梱なしで幅 **0**。
差 **64** は観測したぶれの **16 倍**なので、**この計器でも見えている**。
規則 9 の表の「±20」はベンチの形で測ったときの値で、
**ブート全体の tick の実測のぶれは 4 だった**(1 tick = 10ms が分解能の下限)。

## 6. 対照(規則 8 / 規則 5)

### 6-1. 陽性対照 — **合格**

`NO_EMBEDDED_INIT=1`(設計判断 L5)で約 83KB の Lisp の読み・解析・機械語化を
まるごと消すと、**3 つとも下がった**。

```
[発火] imm-used   455,904 -> 50,480
[発火] heap-used  922,256 -> 591,936
[発火] tick            65 -> 1
```

**つまり 3 つの計器はどれも対象を見られている。**
このつまみは `BUILD_FLAG_SIGNATURE` に入っているので、
**付け外しで古いバイナリを測る事故が起きない。**

### 6-2. 陰性対照 — **合格**

**同梱と無関係な量は動いてはいけない。** `boot-alloc-used` は
`run_boot_entry` より前に確定するので、同梱の有無で変わるはずがない。

```
[静止] boot-alloc-used  640,760 = 640,760
[静止] heap-total        85,621,888 = 85,621,888
[静止] imm-total         16,777,216 = 16,777,216
```

**3 つとも 1 byte も動かなかった。** 動いていたら測定が壊れている合図である。

### 6-3. `SMALL_HEAP_SIZE` のつまみの陽性対照 — **合格**

「既定の 85KB で通った」だけでは、**つまみが死んでいても同じ結果になる**。
そこで `make check-small-heap-knob` が **わざと下側へ外した値(80,000 byte)**で
ビルドして走らせる。

```
exit 124(60 秒で打ち切り)。最後に出た行は runtime_test.c:2169
```

**打ち切られた = 既知の症状(ハング)が再現した。**
つまみは生きていて、窓の下端は既定の 85KB より上にある。
**だから「85KB で通った」は意味のある合格である。**

> `timeout` は**コンテナの中**で効かせている。`timeout N docker run ...` は
> docker クライアントしか殺さず、ハングしたコンテナが生き残る(既知の罠)。

## 7. この数字が M3 / M4(コアイメージ)に対して意味すること

**判断はしない(D5 / D6 により合格線を決めない)。** 数字の含意だけを並べる。

| 量 | 含意 |
|---|---|
| **imm space 2.72%(同梱ぶん 2.42%)** | **コアイメージの動機は imm space 側には立たない。** 1 ブート 1 回なら 16MB の 2.4% で、41 回ぶん入る。ただし**解放されない**ので、二重 load(R8)と「走りながら読み直す」使い方では効いてくる |
| **ヒープ 330,320 byte/ブート** | GC で回収できるので**恒久的な費用ではない**。動機は立たない |
| **tick 64 / 65 = 98.5%** | **測った区間のほぼ全部が同梱の読み込みである。** コアイメージで消せるのはここ。ただし**絶対値は 0.64 秒**でしかない |
| **起動前半は測っていない**(L7) | **0.65 秒は起動時間の全体ではない。** 「コアイメージで起動が何割速くなるか」を言うには**起動前半を測る手立てが要る**(M3-T2 / 設計判断 L7 の「足すのは別件」) |
| **イメージの大きさの上限** | **922,256 byte(約 0.9MB)**。ブート中の GC が 0 回なので**生存集合はこれ以下**である。M5-T4(保存先を 9p かディスクか)の判断材料になる。**数 MB ではない** |

### 次に測るべきこと(M3-T1 / M3-T2 への申し送り)

1. **0.64 秒の内訳**(読み / パース / intern / JIT)。M3-T1 がそれである
2. **起動前半の長さ。** これが分からないと「起動が何割速くなるか」は言えない。
   刻みは使えない(割り込み許可より後だけ)ので、**別の時計を足す判断が必要**(L7)
3. `init.lisp` のうち **AOT へ移せるもの**(F18: AOT へ移すと imm が減る)。
   移せば imm と tick の両方が下がるはずだが、**今回は測っていない**(規則 6)
