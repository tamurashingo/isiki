# 調査: nil / 静的スロットのレジスタ常駐(r12)

> 調査日: 2026-09-16 / ブランチ: `feature/jit-pinned-register`
> 分岐元: **`feature/jit-immediate-operands`(PR #64)**。指示書は
> 「PR #64 マージ済み」を前提にしていたが調査時点で #64 は OPEN だったため、
> 基準を揃えるためそちらから分岐した
> 関連: `documents/jit-immediate-operands.md`

## 結論: **中止する。実装しない。**

理由は独立に 2 つある。どちらか一方だけでも中止に足りる。

| # | 理由 |
|---|---|
| **安全性** | **r12 をグローバルに常駐させることはできない。** カーネルの 2,648 関数のうち **667 関数が r12 を使用**しており、その中に **`os_eval`** が含まれる。`os_eval` → `os_apply_function` → JIT という経路があるため、**`os_eval` の実行中に JIT へ入ると r12 は `os_eval` の作業値になっている** |
| **効果** | 安全な代替(関数ごとにプロローグで載せる)にしても、**11 個中 8 個の関数でサイズが増える。** nil は即値全体の 9〜11% にすぎず、大半はカーネル関数のアドレスで r12 では解決できない |

指示書 8 章「**確信が持てない場合は中止するほうが正しい。得られるのは数 byte である**」
に該当する。

---

## 4-1: `r12` は空いている(確認)

`za.c` で `ZA_REG_R12` は enum の定義(`za.c:185`)にあるだけで、**一度も使われていない。**
JIT が使うのは rax / rcx / rdx / r8 / r9 / r10 / r11 / r13 / r14。
レジスタ枯渇の懸念は無く、**空いているという前提は正しい。**

## 4-2: `r12` が保たれる経路(ここで中止が決まった)

### 保たれる経路(確認)

| 経路 | 結果 |
|---|---|
| タイマ割り込み / コンテキストスイッチ | `push %r12` / `pop %r12` あり(`interrupt.c:386, 406`) |
| その他の割り込み | 同上(`interrupt.c:466, 487`) |
| CPU 例外 | `push %r12` あり(`interrupt.c:248`)。ハンドラは `hlt` で戻らないので復元は不要 |
| C 関数呼び出しからの**復帰時** | Win64 で r12 は不揮発。gcc は使うなら保存・復元する |
| 非局所脱出(`block` / `catch`) | **戻り値の伝播**で実装されている(`MAGIC_BLOCK_EXIT` を返し `os_is_control_transfer` で判定)。スタックの巻き戻しをしないので通常の呼び出し規約どおり保たれる |

### 保たれない経路(これが致命的)

**`callee-saved` は「戻る時までに復元される」であって「実行中ずっと不変」ではない。**

C 関数が r12 を自分の作業用に使う場合、その関数は入口で保存し出口で復元するが、
**その間 r12 は別の値**である。その窓の中から JIT コードを呼べば、
JIT は nil ではない値を見る。

実測(`x86_64-w64-mingw32-objdump -d esp_dir/EFI/BOOT/BOOTX64.EFI`):

```
逆アセンブルできた関数数: 2648
r12 を使っている関数数:   667   (25%)

os_eval            使用 23 箇所   ← JIT を呼ぶ経路の途中
os_apply_function  使っていない
os_apply_via_cell  使っていない
za_compile_expr_inner 使用 74 箇所
```

**`os_eval` が r12 を使っている。** `os_eval` は呼び出し式を評価するとき
`os_apply_function` を経由して JIT コードへ入るので、
**JIT コードは `os_eval` の作業値を r12 に見ることになる。**

SBCL がこの方式を採れるのは、**実行時のコードをすべて自分でコンパイルしていて
レジスタを大域的に予約できる**からである。isiki-os は gcc でビルドした C を
常時経由し、JIT コードは **C から呼ばれる**ので、同じ前提が成り立たない。

**指示書 1 章の「JIT 側で一度入れれば C 呼び出しをまたいで生き残る」は誤りである。**
「C 呼び出しから戻った後は生き残る」までは正しいが、
「C の中から呼ばれた JIT で生き残る」は成り立たない。

### 安全な代替: 関数活性ごとにプロローグで載せる

JIT 関数のプロローグで毎回 r12 へ nil を載せ、エピローグで復元する形なら安全である。

- 関数の中では C を呼んでも戻ってくれば r12 は復元されている(不揮発)
- JIT が JIT を呼ぶ場合、呼ばれた側も自分のプロローグで同じ値を載せる
- **JIT は C から呼ばれるので、r12 を書き換えるなら保存・復元が必須**
  (`documents/pitfalls.md` 原則11。過去に r14 の復元漏れで実際に壊れた事例がある)

コスト: `push r12`(2)+ `mov r12d, imm32`(5)+ `pop r12`(2)= **9 byte / 関数**
利得: nil 1 回につき `mov r11d, imm32` + `cmp`(8 byte)が `cmp rax, r12`(3 byte)= **−5 byte**

→ **損益分岐は「1 関数あたり nil 2 回」。**

## 4-4: 頻度の実測(これで効果が否定された)

生成コード中の即値を数えた(PR #64 で監査を記録ベースにしたので、
`%%DIAG-ZA-SCAN` は誤検出なしで正確に数えられる)。

| 関数 | len | 即値 | うち nil | nil 割合 | 関数活性方式の正味 |
|---|---|---|---|---|---|
| `(defun f (x) x)` | 412 | 10 | 0 | 0.0% | **+9 byte** |
| `(car x)` | 489 | 13 | 0 | 0.0% | **+9 byte** |
| `(null x)` | 481 | 13 | 0 | 0.0% | **+9 byte** |
| `(eq x y)` | 694 | 19 | 0 | 0.0% | **+9 byte** |
| `(+ a b)` | 739 | 20 | 0 | 0.0% | **+9 byte** |
| `(if (null x) 1 2)` | 560 | 18 | 1 | 5.6% | **+4 byte** |
| `let` + `car` + `cdr` | 761 | 22 | 0 | 0.0% | **+9 byte** |
| `while` + `cons` ループ | 1954 | 67 | 6 | 9.0% | −21 byte(−1.1%) |
| 一般呼び出し 2 個 | 1818 | 55 | 6 | 10.9% | −21 byte(−1.2%) |
| `inline (car x)` | 534 | 14 | 1 | 7.1% | **+4 byte** |
| `inline (null x)` | 489 | 15 | 2 | 13.3% | −1 byte(−0.2%) |

**11 個中 8 個でサイズが増える。** 縮む 3 個も最大 1.2% である。

理由は明快で、**即値の大半はカーネル関数のアドレス**だからである。
1 コールサイトには `os_is_control_transfer` / `za_gc_link` / `za_gc_unlink` /
`os_make_symbol` / `os_get_function_cell` / `os_make_cons` / `os_apply_via_cell` 等の
アドレスが並ぶ(`documents/measurement-callsite-breakdown.md`)。
**これらは r12 では解決できない。**

`(car x)` / `(null x)` / `(eq x y)` の notinline 版で nil が 0 個なのは、
nil との比較が呼び出し先の C(`os_car_checked` / `primitive_null1` / `primitive_eq2`)の
中で行われ、生成コードには出ないためである。
**つまり Phase 3 で「nil の materialize が効いている」と見ていたのは
インライン展開版に限った話だった。**

## 3 章の P1 / P2 の判断

**どちらも採らない。**

- **P1(nil を直接)**: 上記のとおり安全性・効果の両方で不成立
- **P2(スロット配列のベース)**: 安全性の問題は P1 と同一。
  加えて nil が 3 byte → 4 byte になるため効果はさらに小さい

P2 の唯一の利点だった「`t` の移設が不要になる」は、**そもそも移設が不要**である。
PR #64 で確認したとおり、現在の `movabs &g_sym_t` + `mov rax, [rax]`(8 byte)で
既に安全かつ十分に短い。

## 検討した他の案

| 案 | 判定 |
|---|---|
| `r15` など他の不揮発レジスタ | **同じ問題。** 不揮発レジスタはどれも C 側が作業用に使う |
| nil をフレームスロットに置く | `mov rax, [rsp+disp32]` は 8 byte で、`mov eax, imm32`(5 byte)より長い。**逆効果** |
| `cmp rax, imm32`(7 byte) | 符号拡張のため 2^31 未満が必要。**RAM 4GB 以上で成立しない**(PR #64 で実測・却下済み) |

## Phase 4 への引き継ぎ

- **型オブジェクト・クラスオブジェクトもレジスタ常駐にはできない。** 同じ理由である
- 規則は PR #64 で明文化した「**GC ヒープ上のオブジェクトのアドレスを焼いてはならない。
  スロットのアドレスを焼いて実行時に deref する**」に従えばよい。
  スロット経由は 8 byte で、レジスタ常駐(3〜4 byte)との差は 4〜5 byte にすぎない
- **PR #64 で見送った B2(`t` を Immobilized へ移す)は、引き続き不要である。**
  P2 を採らないので前提が変わらない

## 補足: この調査で分かった副次的な事実

- **`za_compile_expr_inner` は r12 を 74 箇所で使っている**(カーネル関数中 2 位)。
  JIT コンパイラ自身がレジスタを使い切っているという意味ではなく、
  gcc が割り当てた結果である
- nil のアドレスは `Immobilized の終端 + 0x31`(`g_nil_cell` が `.bss` で
  `g_imm_space` の直後に置かれるため)。**リンク順に依存するので当てにしないこと。**
  この調査では `inline (null x)` の即値が正確に 2 個、`inline (car x)` が 1 個と
  一致したことで推定値の妥当性を確認した
