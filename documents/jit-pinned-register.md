# 調査: nil / 静的スロットのレジスタ常駐(r12)

> 調査日: 2026-09-16 / ブランチ: `feature/jit-pinned-register`
> 分岐元: `feature/jit-immediate-operands`(PR #64)。調査時点で #64 は OPEN だったため
> そちらから分岐し、**#64 のマージ後に PR の base を `feature/compiler-optimization` へ
> 切り替えた**(#65 は #64 に依存しているため、この順序が正しい)
> 関連: `documents/jit-immediate-operands.md`

## 結論: **Phase 4 まで保留。今は実装しない。**

**理由は「効果が 0〜2% にとどまる」の 1 点だけである。**

当初は「安全性」も理由に挙げていたが、**`-ffixed-r12` が機能することを実測で確認したため
撤回した**(下記「結論の訂正」)。**レジスタ 1 本を予約する代償は `.text` で +32 byte
(+0.0015%)しかない。** したがって Phase 4 で効果が見込めた時点で踏み切れる。

| # | 当初の理由 | 現在 |
|---|---|---|
| 安全性 | r12 をグローバルに常駐させることはできない | **撤回。`-ffixed-r12` で解消できる** |
| 効果 | nil は即値全体の 9〜11% にすぎない | **有効。削減は 0〜2%** |

「静かに壊れる」種類の変更に対して 0〜2% は釣り合わない
(指示書 8 章「確信が持てない場合は中止するほうが正しい」)。
ただし **Phase 4 で型判定が入ると生成コードの即値構成が変わる**ため、
そこで測り直して判断する。

---

## 4-1: `r12` は JIT 側では空いている(確認)

`za.c` で `ZA_REG_R12` は enum の定義(`za.c:185`)にあるだけで、**一度も使われていない。**
JIT が使うのは rax / rcx / rdx / r8 / r9 / r10 / r11 / r13 / r14。
レジスタ枯渇の懸念は無く、**JIT 側で空いているという前提は正しい。**

### C 側は 8 本すべてを使っている

「もっと空いているレジスタを選べばよいのでは」という疑問に答えるため、
Win64 の不揮発レジスタ 8 本すべての使用状況を測った
(`objdump -d esp_dir/EFI/BOOT/BOOTX64.EFI`、関数 2,645 個)。

| reg | 使用関数数 | 割合 |
|---|---|---|
| rbx | 2,272 | 85.9% |
| rsi | 2,157 | 81.6% |
| rdi | 1,069 | 40.4% |
| rbp | 920 | 34.8% |
| **r12** | 667 | 25.2% |
| r13 | 512 | 19.4% |
| r14 | 274 | 10.4% |
| **r15** | **182** | **6.9%** |

r15 が最も空いているが、**使用率は判断材料にならない。** 決定的なのは次の事実である。

```
os_eval が使う不揮発レジスタ: r12 r13 r14 r15 rbp rbx rdi rsi   ← 8本すべて
os_apply_function             (不揮発レジスタを使っていない)
os_apply_via_cell             (不揮発レジスタを使っていない)
```

**`os_eval` は 8 本すべてを使う。** `os_eval` は JIT を呼ぶ経路の途中にあるので、
**どのレジスタを選んでも同じ問題が起きる。**

## 4-2: `r12` が保たれる経路(ここで中止が決まった)

### 保たれる経路(確認)

| 経路 | 結果 |
|---|---|
| タイマ割り込み / コンテキストスイッチ | `push %r12` / `pop %r12` あり(`interrupt.c:386, 406`) |
| その他の割り込み | 同上(`interrupt.c:466, 487`) |
| CPU 例外 | `push %r12` あり(`interrupt.c:248`)。ハンドラは `hlt` で戻らないので復元は不要 |
| C 関数呼び出しからの**復帰時** | Win64 で r12 は不揮発。gcc は使うなら保存・復元する |
| 非局所脱出(`block` / `catch`) | **戻り値の伝播**で実装されている(`MAGIC_BLOCK_EXIT` を返し `os_is_control_transfer` で判定)。スタックの巻き戻しをしないので通常の呼び出し規約どおり保たれる |

### 保たれない経路(これが致命的)

**`callee-saved` は「戻る時までに復元される」であって「実行中ずっと不変」ではない。**

C 関数が r12 を自分の作業用に使う場合、その関数は入口で保存し出口で復元するが、
**その間 r12 は別の値**である。その窓の中から JIT コードを呼べば、
JIT は nil ではない値を見る。

実測(`x86_64-w64-mingw32-objdump -d esp_dir/EFI/BOOT/BOOTX64.EFI`):

```
逆アセンブルできた関数数: 2648
r12 を使っている関数数:   667   (25%)

os_eval            使用 23 箇所   ← JIT を呼ぶ経路の途中
os_apply_function  使っていない
os_apply_via_cell  使っていない
za_compile_expr_inner 使用 74 箇所
```

**`os_eval` が r12 を使っている。** `os_eval` は呼び出し式を評価するとき
`os_apply_function` を経由して JIT コードへ入るので、
**JIT コードは `os_eval` の作業値を r12 に見ることになる。**

SBCL がこの方式を採れるのは、**実行時のコードをすべて自分でコンパイルしていて
レジスタを大域的に予約できる**からである。isiki-os は gcc でビルドした C を
常時経由し、JIT コードは **C から呼ばれる**ので、同じ前提が成り立たない。

**指示書 1 章の「JIT 側で一度入れれば C 呼び出しをまたいで生き残る」は誤りである。**
「C 呼び出しから戻った後は生き残る」までは正しいが、
「C の中から呼ばれた JIT で生き残る」は成り立たない。

### 結論の訂正: `-ffixed-r12` で安全性の問題は解消する

**当初「どのレジスタも C が使うので常駐は不可能」と結論したが、これは撤回する。**
「空いているレジスタを選ぶ」のではなく **gcc に使わせない**という道があった。

`Makefile` が `EXTRA_CFLAGS` を受けるので、カーネル全体をビルドして実測した。

```bash
make build EXTRA_CFLAGS=-ffixed-r12
```

| 項目 | 通常 | `-ffixed-r12` |
|---|---|---|
| r12 を使う関数 | 667 / 2,645 | **4 / 2,645** |
| `os_eval` が r12 を使うか | **はい** | **いいえ** |
| `.text` サイズ | 2,145,552 byte | **2,145,584 byte(+32、+0.0015%)** |
| `make test-qemu` | 3,454 passed / 0 failed | **3,454 passed / 0 failed** |

**レジスタ 1 本を予約する代償が `.text` で +32 byte しかない。**
`-O1` でビルドしているため元々レジスタに余裕がある、というのが理由だと**推測する**
(裏は取っていない)。

**この数字が本調査で最も価値のある発見である。** 代償がほぼゼロだと分かっているので、
**Phase 4 で効果が見込めた瞬間に踏み切れる。**

#### 残った 4 関数の内訳

| 関数 | 内容 | r12 常駐時の扱い |
|---|---|---|
| `asm_timer_handler` | 手書き asm の `push`/`pop` | **そのままでよい**(保存・復元なので必要) |
| `asm_keyboard_handler` | 同上 | 同上 |
| `cpu_exception_common` | 同上 | 同上 |
| `primitive_za_diag_clobber_probe` | **r12 を故意に壊す診断プローブ** | **要移設**(下記) |

#### `primitive_za_diag_clobber_probe` の経緯と、常駐時に変わること

このプローブは **`documents/pitfalls.md` 原則11 の検出手段が機能することの確認**として
置かれている(`za.c` の `[陽性確認]` コメント)。

原則11 は **JIT 生成コードが callee-saved レジスタを壊した事故**である。
`cc_car` のインライン化を入れたところ `make-environment` のコンパイル中に無限ループした。
真因は、

1. gcc が `za_compile_expr` のループで **`&nil` を r14 に載せて使い回していた**
2. ループ本体からマクロ展開経由で JIT 済み関数が**実行**された
3. その生成コードが `movabs $slot,%r14` で **r14 を書き、復元しなかった**
   (プロローグは rbx と r13 しか退避していなかった)
4. 戻ると r14 がキャッシュスロットのアドレスになっており、
   `nil` との一致判定が二度と成立せず無音のハングになった

プローブは `kind=1` で r12 を退避せず書き換える断片、`kind=0` で `push`/`pop` する断片を
Immobilized Space 上に生成し、C 側が inline asm で r12 に既知の値を置いて呼び、
戻った後の r12 を読む。**「壊れたことを C 側から検出できる」ことの陽性確認である。**

**原則11 と r12 常駐は、同じ構造の問題の表と裏である。**

| | 誰が値を持つか | 誰が壊すか |
|---|---|---|
| 原則11 | **C** が callee-saved に値をキャッシュ | **C の中から呼ばれた JIT** |
| r12 常駐 | **JIT** が callee-saved に nil を置く | **JIT を呼ぶ側の C**(自分の作業用に使う) |

**どちらも「C と JIT が callee-saved レジスタを共有し、JIT が C の実行中に
呼ばれる」ことに起因する。** `-ffixed-r12` は gcc の割り当てから r12 を外すので、
**両方向を同時に解決する**(C が r12 に何かをキャッシュすることも無くなる)。

**常駐を入れるならプローブの意味が変わる。**

- 現在: 「JIT が C のレジスタを壊していないか」を見る陽性確認。
  対象を **r12 以外(r13 / r14 など、C がまだ使うレジスタ)へ移す必要がある**
- 追加で必要になる不変条件: 「**JIT も r12 を壊してはならない**(nil が入っているため)」。
  これは原則11 とは別の性質で、**新しい検査が要る**。
  `%%PINNED-REGISTER` のような内省で、各経路の後に r12 が nil のままかを
  確認する形が考えられる**(未検証の案)**

**移設だけでは足りない。** Phase 4 で判断する際はここを見落とさないこと。

### 安全な代替: 関数活性ごとにプロローグで載せる

JIT 関数のプロローグで毎回 r12 へ nil を載せ、エピローグで復元する形なら安全である。

- 関数の中では C を呼んでも戻ってくれば r12 は復元されている(不揮発)
- JIT が JIT を呼ぶ場合、呼ばれた側も自分のプロローグで同じ値を載せる
- **JIT は C から呼ばれるので、r12 を書き換えるなら保存・復元が必須**
  (`documents/pitfalls.md` 原則11。過去に r14 の復元漏れで実際に壊れた事例がある)

コスト: `push r12`(2)+ `mov r12d, imm32`(5)+ `pop r12`(2)= **9 byte / 関数**
利得: nil 1 回につき `mov r11d, imm32` + `cmp`(8 byte)が `cmp rax, r12`(3 byte)= **−5 byte**

→ **損益分岐は「1 関数あたり nil 2 回」。**

**なお `-ffixed-r12` でグローバルに予約するなら、この 9 byte のコストは発生しない。**
プロセス生成時に一度 r12 へ nil を入れるだけで、以後はコンテキストスイッチが
保存・復元する(4-2 で確認済み)。**下の 4-4 の表で「関数活性方式」が
8 個の関数でサイズを増やしていたのは、この 9 byte が原因である。
グローバル予約ならその列はすべて 0 以下になる。**

## 4-4: 頻度の実測(これで効果が否定された)

生成コード中の即値を数えた(PR #64 で監査を記録ベースにしたので、
`%%DIAG-ZA-SCAN` は誤検出なしで正確に数えられる)。

| 関数 | len | 即値 | うち nil | nil 割合 | 関数活性方式 | **グローバル予約** |
|---|---|---|---|---|---|---|
| `(defun f (x) x)` | 412 | 10 | 0 | 0.0% | +9 byte | **0** |
| `(car x)` | 489 | 13 | 0 | 0.0% | +9 byte | **0** |
| `(null x)` | 481 | 13 | 0 | 0.0% | +9 byte | **0** |
| `(eq x y)` | 694 | 19 | 0 | 0.0% | +9 byte | **0** |
| `(+ a b)` | 739 | 20 | 0 | 0.0% | +9 byte | **0** |
| `(if (null x) 1 2)` | 560 | 18 | 1 | 5.6% | +4 byte | **−5 byte(−0.9%)** |
| `let` + `car` + `cdr` | 761 | 22 | 0 | 0.0% | +9 byte | **0** |
| `while` + `cons` ループ | 1954 | 67 | 6 | 9.0% | −21 byte | **−30 byte(−1.5%)** |
| 一般呼び出し 2 個 | 1818 | 55 | 6 | 10.9% | −21 byte | **−30 byte(−1.7%)** |
| `inline (car x)` | 534 | 14 | 1 | 7.1% | +4 byte | **−5 byte(−0.9%)** |
| `inline (null x)` | 489 | 15 | 2 | 13.3% | −1 byte | **−10 byte(−2.0%)** |

関数活性方式(プロローグで載せる)は **11 個中 8 個でサイズが増える。**
**グローバル予約(`-ffixed-r12`)ならその問題は消えるが、削減は 0〜2% にとどまる。**

理由は明快で、**即値の大半はカーネル関数のアドレス**だからである。
1 コールサイトには `os_is_control_transfer` / `za_gc_link` / `za_gc_unlink` /
`os_make_symbol` / `os_get_function_cell` / `os_make_cons` / `os_apply_via_cell` 等の
アドレスが並ぶ(`documents/measurement-callsite-breakdown.md`)。
**これらは r12 では解決できない。**

`(car x)` / `(null x)` / `(eq x y)` の notinline 版で nil が 0 個なのは、
nil との比較が呼び出し先の C(`os_car_checked` / `primitive_null1` / `primitive_eq2`)の
中で行われ、生成コードには出ないためである。
**つまり Phase 3 で「nil の materialize が効いている」と見ていたのは
インライン展開版に限った話だった。**

### Phase 4 でこの数字がどう動くかは読めない

型判定を入れると、

- **型オブジェクト・クラスオブジェクトへの参照が増える。** ただしそれらは GC ヒープ上に
  あるので**スロット経由になり、レジスタ常駐にはできない**(本調査の結論どおり)
- 一方で **`+` のインライン展開が入れば nil 比較も増える可能性がある**

**どちらに転ぶかは今の数字では読めない。** Phase 4 の生成コードを見てから決めるのが
正しい順序である。

## 3 章の P1 / P2 の判断

**どちらも採らない。**

- **P1(nil を直接)**: 上記のとおり安全性・効果の両方で不成立
- **P2(スロット配列のベース)**: 安全性の問題は P1 と同一。
  加えて nil が 3 byte → 4 byte になるため効果はさらに小さい

P2 の唯一の利点だった「`t` の移設が不要になる」は、**そもそも移設が不要**である。
PR #64 で確認したとおり、現在の `movabs &g_sym_t` + `mov rax, [rax]`(8 byte)で
既に安全かつ十分に短い。

## 検討した他の案

| 案 | 判定 |
|---|---|
| `r15` など他の不揮発レジスタ | **同じ問題。** 不揮発レジスタはどれも C 側が作業用に使う |
| nil をフレームスロットに置く | `mov rax, [rsp+disp32]` は 8 byte で、`mov eax, imm32`(5 byte)より長い。**逆効果** |
| `cmp rax, imm32`(7 byte) | 符号拡張のため 2^31 未満が必要。**RAM 4GB 以上で成立しない**(PR #64 で実測・却下済み) |

## Phase 4 への引き継ぎ

**実装は Phase 4 まで保留。そのとき再検討するための前提を以下にまとめる。**

### 決まっていること

- **`-ffixed-r12` は機能する。** r12 使用が 667 → 4 関数、`os_eval` からも消える。
  `.text` は +32 byte(+0.0015%)、`make test-qemu` は 3,454 passed / 0 failed。
  **代償がほぼゼロなので、効果さえ見込めれば踏み切れる**
- **「空いているレジスタを選ぶ」方式は不可能。** `os_eval` が不揮発レジスタ 8 本
  すべてを使う。`-ffixed-*` 以外の道は無い
- **型オブジェクト・クラスオブジェクトはレジスタ常駐にできない。** GC ヒープ上にあり
  移動するため、`documents/jit-immediate-operands.md` の規則どおりスロット経由になる。
  スロット経由は 8 byte、レジスタ常駐は 3〜4 byte で、差は 4〜5 byte にすぎない

### 再検討時に測ること

1. **Phase 4 の生成コードで即値に占める nil の割合**(今回は 9〜11%)。
   `%%DIAG-ZA-SCAN` で数えられる(PR #64 で記録ベースになり誤検出なし)
2. 1 が大きく上がるなら、**P1(nil を直接)か P2(スロット配列のベース)か**を決める。
   P2 なら nil が 3 → 4 byte になる代わりに型オブジェクトも同じレジスタで賄える

### 忘れてはならない副作用

- **`primitive_za_diag_clobber_probe` の移設だけでは足りない。**
  プローブの対象を C がまだ使うレジスタへ移したうえで、
  **「JIT も r12 を壊してはならない」という新しい不変条件の検査が別途要る**
  (上記「プローブの経緯」参照)
- **プロセス生成時の仕込みが要る。** 偽 IRETQ フレームは 15 レジスタを 0 で初期化しており
  (`process.c`)、r12 は `regs[3]`
- **全ビルド経路へフラグを徹底すること。** AOT が生成する `lisp_compiled.c` も含む。
  ネイティブの `make test`(SysV ABI)は JIT を動かさない
  (`ISIKIOS_UNIT_TEST` で `za_try_compile_defun` が常に nil を返す)ので影響は小さいが、
  揃えておくほうが安全
- **今後のインライン asm が r12 を壊さない規律が要る**

## 補足: この調査で分かった副次的な事実

- **`za_compile_expr_inner` は r12 を 74 箇所で使っている**(カーネル関数中 2 位)。
  JIT コンパイラ自身がレジスタを使い切っているという意味ではなく、
  gcc が割り当てた結果である。`-ffixed-r12` を付ければ当然消える
- **`-ffixed-r12` でも `.text` がほぼ増えないのは意外だった**(+32 byte)。
  `-O1` でビルドしているため元々レジスタに余裕がある、というのが説明だと**推測する**。
  `-O2` 以上にした場合に同じとは限らない
- nil のアドレスは `Immobilized の終端 + 0x31`(`g_nil_cell` が `.bss` で
  `g_imm_space` の直後に置かれるため)。**リンク順に依存するので当てにしないこと。**
  この調査では `inline (null x)` の即値が正確に 2 個、`inline (car x)` が 1 個と
  一致したことで推定値の妥当性を確認した
