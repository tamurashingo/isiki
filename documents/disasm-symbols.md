# 逆アセンブルのシンボル解決

対象: PR(`feature/disasm-symbols`、base は `feature/compiler-optimization`)

関連: `documents/type-specialized-dispatch.md` §5-4、Phase 1 の領域分類

---

## 1. 何をしたか

逆アセンブル出力の呼び先を、**アドレスではなく名前**で表示する。

```
変更前:  mov r11d, 0x275fa11    ; <kernel>
変更後:  mov r11d, 0x275fa11    ; za_gc_current_head
```

PR #89 の検証は `disassemble` の **code-len でしか確認できず**、
`primitive_add2_fixnum` と `primitive_add2_single` を取り違えても気づけなかった。
いまは名前で直接確認できる。

```
add-fixnum   → primitive_add2_fixnum
add-single   → primitive_add2_single
add-generic  → primitive_add2
```

---

## 2. 2 つの出所

| 領域 | 解決方法 |
|---|---|
| カーネル `.text` | **ビルド時に `nm` で抽出した静的テーブル** + 二分探索 |
| Immobilized Space | **実行時にグローバル環境を走査**して範囲マッチ |

`os_classify_addr`(Phase 1)で領域を判定してからどちらを引くか決める。
**小さい即値や disp32 のほとんどはここで落ちる**ので、テーブルを無駄に走査しない。

---

## 3. 鶏と卵

```
1. リンクする  2. シンボルを抽出  3. テーブルを生成  4. 再リンク
   → テーブルが増えたぶんアドレスがずれ、2 の値が古くなる
```

### 3-1 実測: `.text` は動かない

`.rdata` に 80KB の const を足して再リンクし、`nm` で比較した。

```
.rdata:  00007d80 → 0001bda0   (80KB 増)
.text:   002134c0 → 002134c0   (不変)
シンボル 2691 件すべて完全一致
```

**`.text` が最初のセクションで、テーブルは `.rdata` へ載る**ため、
テーブルのサイズが変わっても関数のアドレスは動かない。

> **【この検証に 3 回失敗した】**
>
> | 回 | 失敗 | 気づいた指標 |
> |---|---|---|
> | 1 | Makefile の置換が不成立 | 完全一致 |
> | 2 | `SRC` には入ったがビルドがスキップ | **`.rdata` のサイズが不変** |
> | 3 | 成功 | `.rdata` +80KB、ダミーが `nm` に出現 |
>
> 1 と 2 はどちらも「**.text は動かない**」という**正しい結論**を偶然出していた。
>
> **2 回目は完全一致だけでは足りなかった。** 「変化を意図した側(`.rdata`)が
> 本当に変化したか」を見て初めて気づいた。**完全一致を疑うのと、
> 変化側を確認するのはセットである。**

### 3-2 それでも検証を入れる

実測で動かないと分かっていても、**将来リンカの挙動が変われば黙って壊れる**。
名前が 1 つずつずれても、それらしい名前が出るので気づきにくい。

Makefile が **2 パス**で作り、**再抽出して照合**する。

```
1. 空のテーブルでリンク      → アドレスが確定
2. nm で抽出してテーブル生成
3. テーブルを含めて再リンク
4. 再抽出して 1 と照合       → ずれていたらビルドを止める
```

### 3-3 検出器が働かなかった(修正済み)

**§6-6 の「試していない検出器は働かない」がそのとおりだった。**

最初の `check_disasm_symtab.sh` は `diff -q - /dev/stdin` をヒアドキュメントと
併用していて、**常に真を返して `exit 0`** していた。アドレスを 1 件書き換えても
素通りする。

`cmp -s` で素直に比べる形へ直し、**わざと 1 件ずらして止まることを確認した。**

**この検出器は普段一度も発火しない**(`.text` が動かないため)。
試さなければ壊れたまま何年も残ったはずである。

## 4. 調査結果

### 4-1 抽出手段

`x86_64-w64-mingw32-nm`(binutils 2.40)。

- 関数シンボル(`T`/`t`)は **2723 件**
- **`static` 関数の多くが名前 `.text` で出る**ため捨てる。残り **2691 件**
- `.refptr.*` のような補助シンボルは `T`/`t` でないので自然に落ちる
- **AOT の `lisp_ll_*` も 1450 件含まれる**(カーネルへ静的リンクされるため)

### 4-2 ロードアドレスの補正

**UEFI はリンク時とは別の場所へロードする。**

| QEMU_MEM | JIT コードのアドレス |
|---|---|
| 96M | 46,681,152 |
| 256M | 214,453,312 |
| 1024M | 1,019,759,680 |

`__ImageBase` が実行時の実アドレスを指すので、リンク時 ImageBase との差で補正する。

#### 符号なし引き算で破綻した(修正済み)

最初の実装は `bias = 実行時 - リンク時` を `UINT64` で計算していた。
**実行時アドレス(0x275fa11)がリンク時(0x2446c0000)より小さい**ため負になり、
巨大な値へ化けて**全件弾かれた**(名前が 1 つも出なかった)。

**UEFI のロード先はリンク時より前にも後にもなりうる。** ImageBase からの
**オフセット**で考えれば符号に依存しない。

```c
UINT64 link_addr = g_disasm_link_image_base + (runtime_addr - rt_base);
```

今回は「全く出ない」症状だったので気づけたが、**ずれが小さければ
「それらしい名前」が出て通していた。**

### 4-3 テーブルのサイズ

| | |
|---|---|
| シンボル数 | 2692 |
| 生成ソース | 197,858 byte |
| **カーネルイメージ** | 2,662,641 → 2,770,991 = **+108,350 byte (+4.1%)** |

**絞らず全件入れた。** 絞ると絞った先が解決できなくなる。
panic のバックトレースなど他の用途にも使える。

### 4-5 JIT 関数の逆引き

- **グローバル環境を起点**にする。呼び出し文脈から辿ると、同じコードを
  逆アセンブルしても場所で結果が変わる
- **`functions` スロットはシンボル名で引く。** 位置(3 番目)に依存すると
  並びが変わったとき静かに壊れる
- **範囲マッチ**で `NAME+0x1c` の形まで出す
- `code_len == 0`(組み込み primitive / AOT)は機械語ブロックを持たないので飛ばす

## 5. 分かったこと: JIT-to-JIT の呼び先はアドレスを焼かない

指示書 §6-3 は `(defun caller (x) (callee x))` で **`CALLEE` が出る**ことを
期待していたが、**出ない。**

```
caller の注釈: CALLER+0x21f
               os_get_function_cell
```

**JIT は呼び先を直接アドレスで焼かず、Function Cell 経由で間接的に呼ぶ**
(再定義に追随するため)。生成コードに現れるのは Cell のアドレスであって、
`CALLEE` のコード先頭ではない。

JIT 関数のアドレスが焼かれるのは主に**自己参照(末尾呼び出しのトランポリン)**で、
そこでは `CALLER+0x21f` と正しく範囲マッチできている。

### §6-4 の検証は成立していない

「再定義後、古いコードを指す呼び先で名前が出ないこと」を確認しようとしたが、
**そもそも古いコードのアドレスが焼かれていない**ため、検証として意味を持たない。
名前は出なかったが、それは理由が違う。

## 6. 検証

| 項目 | 結果 |
|---|---|
| `make test` | 8498 OK / 0 NG |
| `make test-qemu` 256M | **4289 passed / 0 failed** |
| `QEMU_MEM=96M` | **4289 passed / 0 failed** |

(テスト数が 4286 → 4289 に増えているのは、下の「CI で落とした」で
アサーションを 3 件足したため)

### ずれていないことの確認(§6-2)

**ロードアドレスを 1GB 動かしても同じ名前に解決される。**

```
QEMU_MEM=96M    mov r11d, 0x275c5fd    ; primitive_add2_fixnum
QEMU_MEM=1024M  mov r11d, 0x3c75c5fd   ; primitive_add2_fixnum
```

解決された名前は両方で同じ 9 種、**`<kernel>` のまま残った行は 0 件**。
名前が 1 つずつずれていれば、1GB 動かした側で違う名前が出るはずである。

### 性能(§6-5)

735 byte / 147 項目で **1 回あたり 4ms**。Phase 1 の実測(815 byte / 145 項目で
8.2ms)より速く、**シンボル解決を足しても遅くなっていない**。
二分探索と、大半の即値が `os_classify_addr` の前フィルタで落ちることによる。

### 既存テストの更新

`disassemble_test.lisp` が `<kernel>` という注釈を 1 件以上期待していたが、
**シンボル名に置き換わって 0 件になった**。狙いどおりの変化なので更新した。

**「`<kernel>` が出ないこと」と「実際の関数名が出ること」の両方**を見る形にした。
片方だけだと、解決が全滅しても気づけない。

### CI で落とした(修正済み)

`<kernel>` の側は直したが、**`<immobilized>` に同じ形のアサーションが
もう 1 つあるのを見落とし、GitHub Actions で落ちた。**

```
[NG] (> (DISASM-COUNT-COMMENT (QUOTE DIS-CALLER) "<immobilized>") 0) => NIL (expected T)
```

**原因は、JIT 逆引き(§4-5)を入れたあとにフル回帰を回さず PR を作ったこと。**
最後に通した `make test-qemu` は逆引きを入れる前のものだった。

さらに、それを直すときに書いたアサーションもそのままでは通らなかった。

```lisp
(assert-equal t (> (disasm-count-comment 'dis-caller "DIS-CALLER") 0))
```

`disasm-count-comment` は `string=` の**完全一致**なので、**範囲マッチで付く
`DIS-CALLER+0x27c` という注釈にはヒットしない。** 前方一致版
`disasm-count-comment-prefix` を足して `"DIS-CALLER+0x"` で見る形にした。
オフセット値を直書きしないのは、JIT のコード生成が少し変われば動く数字だから。

実機での注釈の実測(`dis-caller` / `dis-rec`):

| 注釈 | dis-caller | dis-rec |
|---|---|---|
| `za_gc_link` | 9 | 8 |
| `za_gc_unlink` | 6 | 6 |
| `os_is_control_transfer` | 2 | 6 |
| `za_gc_current_head` | 3 | 3 |
| `os_make_cons` | 2 | 1 |
| `cc_car` / `cc_cdr` / `os_make_symbol` / `os_get_function_cell` | 各 1 | 各 1 |
| **自己参照** | `DIS-CALLER+0x27c` (1) | `DIS-REC+0x3ad` (1) |
| `<kernel>` / `<immobilized>` / `<gc-heap>` | **0** | **0** |

`dis-rec` は自分を名前で呼ぶ再帰関数だが、**再帰呼び出しも Function Cell 経由**
なので、`DIS-REC` の名前が出るのは末尾呼び出しトランポリンの自己参照 1 件だけ
である(§5 と同じ話)。
