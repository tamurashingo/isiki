# #142 の切り分け — **直っていない。上限のすぐ外側に居る**

> 状態: 診断・二分探索・窓を開けた実測まで進めた(2026-11-07)。
> **結論: 形の崩れは消えていない。`ZA_MAX_COMPILE_NEST` が隠しているだけで、余裕は 1 段しかない。**
> 原因は GC でもマクロ展開の失敗でもなく、**コンパイル経路のスタックの枯渇**である。

> 2026-11-07 の最初の計測では「窓の全域で再現しない」と書いた(§3)。
> **それは窓が狭かったためで、窓を開けたら 30 段から全段で再現した(§5)。**
> 「再現しない」を「直った」と書かなかったことだけが救いである。

## 1. 何が分かっていなかったか

26 段以降の入れ子で `za_local_validate_lambda_vars` の
**「仮引数が平坦なリストではない」**が当たって断念していた。
断念は安全側(インタプリタへ落ちる)で誤った結果は観測されていないが、
**コンパイル中に形が崩れているなら、崩れ方が別の経路で害になりうる。**

仮説は 2 つあり、**どちらとも決められなかった**:

1. **コンパイル中の GC で保護漏れの form が壊れている**
   (`za_macroexpand` は `os_make_cons` を呼ぶ = コンパイル中に確保がある)
2. マクロ展開が途中で失敗し、展開しきれていない形か `EVAL-ERROR`(タグ 3)が渡っている

## 2. 足した診断

既存の `%%DIAG-ZA-BAIL-AT` は**行番号しか返さない**ので、
「cons ではない何か」の**中身**が分からず仮説を分けられなかった。

断念地点で **`lambda_vars`(全体)と `cur`(壊れた位置)の両方**について
値とタグをシリアルへ出すようにした。**両方出すのが要点**である:

- `lambda_vars == cur` … **先頭から別物**
- 違う … **途中で切れている**

参照のために `nil` / `EVAL-ERROR` / `macroexpand-runaway` の値も並べて出す。
**タグ 3 かつ `EVAL-ERROR` なら仮説 (2)、ゴミや fixnum なら (1)** と分かれる。

**組み込み関数は増やしていない**(1 つ足すと `SMALL_HEAP_SIZE` の再調整が要る。
余裕 5KB 未満で症状はハング)。シリアルなので `-serial file:` で捕まえられる。

## 3. 実測(第 1 段) — **窓の内側(24〜29 段)では発火しない**

| 段数 | 起点の行 | 意味 | 形の検査 |
|---|---|---|---|
| 24 / 26 / 27 / 28 / 29 | **4272** | `ZA_MAX_LOCALS_PER_LET`(5 束縛 > 上限 4。**文書どおり**) | **0 回** |
| 31 / 35 / 41 | **4672** | `ZA_MAX_COMPILE_NEST`(60)。**`let` に到達する前に止まる** | **0 回** |

**既定の上限では観測できる窓は 24〜29 段である**(30 段以降は 1 段 2 単位で
`ZA_MAX_COMPILE_NEST` に先に当たり、`let` まで到達しない)。**その全域で形の検査は当たらない。**

> **この窓の狭さが結論を誤らせる。** 上限を外して 30 段以降を測ったら
> **全段で再現した(§5)。** ここで止めてはいけなかった。

### 決定的な実験 — **確保ごとに GC を強制しても同じ**

`GC_DEBUG=1` + `(%%diag-gc-stress 1)`(**確保 1 回ごとに GC**)で測り直した。

**起点も件数も、GC 無しの run と完全に同一。形の検査は 0 回。**

> **仮説 (1) が正しければ、確保ごとに GC を走らせれば「より出やすくなる」はずで、
> 消えることはない。** コンパイルが **GC のタイミングに対して鈍感**だと分かったので、
> **仮説 (1) は大きく弱まった。**

仮説 (2) も、形の検査自体が当たらない(= 壊れた形が検証器に届いていない)ので
この窓では起きていない。

## 4. 二分探索 — 症状を消したのは `f6722af`(ただし**直したのではない**)

`8ff6ab5`(症状あり)から `origin/main`(症状なし)までの 86 コミットを二分探索した。
**判定は機械にやらせた**(`git bisect run`)。要点は 2 つ:

- **行番号を固定しない。** 断念地点の行番号はコミットごとに違う(`8ff6ab5` では形の検査が
  3787、いまは 4256)。各コミットの `za.c` から**注記の文言で grep して引く**
- **`ZA_MAX_COMPILE_NEST` に当たった回は `skip` にする。** 窓が動いて `let` に到達しない回を
  「症状なし」と読むと二分探索が嘘をつく(結果として skip は 1 件も出なかった)

| コミット | 起点 | 判定 |
|---|---|---|
| `8ff6ab5` | 3787 = 形の検査 | 症状あり |
| `36cba68` | 3880 = 形の検査 | 症状あり |
| `0562369` (Merge PR #145) | 3880 = 形の検査 | 症状あり |
| **`f6722af`** | **3956 = LOCALS** | **症状なし** |
| `a65ee86` / `709f08f` / `4366374` | 3956 = LOCALS | 症状なし |

**`f6722af` = 「perf(jit): フレームの寸法を関数ごとの実寸にする(案 d 第 3 段。M4-T1〜T3)」**
(PR #146 の中の 1 コミット)。親の `0562369` では症状が出る。

このコミット自身の計測に **「実測の再帰深さ 26 -> 49」「1 段 7480 -> 4152 byte」**とある。
#142 の反転点は **26 段**だった。**同じ数が出ている**ので、資源は
「解析の歩数」ではなく**スタックの深さ**だろうと見当がついた。

### つまずき: good/bad の極性を取り違えた

`git bisect` は**祖先側が good** でなければならない。最初は判定を
「症状あり = exit 1 = git の bad」にしたので、git は**転換点の反対側**
(`4366374..origin/main`)を探していた。1 歩ぶん無駄にしてから気づいた。
直したあとは「症状あり = exit 0 = good」で、**"first bad commit" = 症状が消えた最初のコミット**
という読みになる。

## 5. 窓を開けて測る — **30 段から 36 段まで全段で再現する**

`f6722af` が「直した」のかどうかは、**窓を開けないと分からない**。
`ZA_MAX_COMPILE_NEST` を一時的に 60 -> 400 にして(測ったあと必ず戻した)段数を振った。

| 段数 | 結果 | 起点 |
|---|---|---|
| **29**(= 上限 60 が許す実質の上限。**陽性対照**) | 正常 | 4272 = `ZA_MAX_LOCALS_PER_LET` |
| **30 / 31 / 32 / 33 / 34 / 35 / 36** | **形の崩れ(#142 の症状)** | **4256 = 形の検査** |
| **37 / 38 / 40** | **CPU 例外** | — |

**陽性対照が要点である**(規則 8)。上限を 400 に上げても **29 段の結果は変わらない**
(起点 4272、形の検査 0 回)。だから 30 段以降の変化は**上限をいじったせいではない**。

37 段以上で出る例外は次のとおりで、**コンパイル経路が無保護**だと分かる:

```
!! CPU EXCEPTION vector=0x0E rip=0x0C7FE4F9 rsp=0x0CA50450 cr2=0x0CA50448
   ** STACK OVERFLOW (下端側): 再帰が深すぎる **
   jit-stack-guard-hits=0  (0 = 守られていない経路)
```

`jit-stack-guard-hits=0` は **JIT 生成コードのスタック残量検査を一度も通っていない**
ことを意味する。生成コードを動かしているのではなく、**コンパイル中の C 再帰**が溢れている。

> **「形の崩れ」は溢れの手前の症状である。** 同じ資源(スタック)の枯渇が、
> 段数によって **30〜36 段では静かな破壊、37 段以上では例外**として現れる。

## 6. 診断が仮説を分けた — 犯人は `TAG_INSTANCE`、`EVAL-ERROR` ではない

35 段・36 段で形の検査が当たったときのシリアル出力:

```
[za][#142] 仮引数が平坦なリストではない:
  lambda_vars=0x00000000018fefa7 tag=0x7 / cur=0x00000000018fefa7 tag=0x7 [先頭から別物]
  nil=0x000000000dc76031  EVAL-ERROR=0x000000000181d543  macroexpand-runaway=0x0
```

- **タグ 7 = `TAG_INSTANCE`。** `EVAL-ERROR`(タグ 3)でも `nil` でもない
  -> **仮説 (2)(展開しきれていない形や `EVAL-ERROR` が渡っている)は否定された**
- `lambda_vars == cur` -> **先頭から別物**(途中で切れたのではない)。
  仮引数リストそのものが**別の値に置き換わっている**
- `macroexpand-runaway = 0` -> マクロ展開は断念していない

仮説 (1)(GC の保護漏れ)も、§3 の「確保ごとに GC を強制しても結果がビット単位で同一」
という実測で大きく弱まっている。**残るのは「スタックの枯渇による破壊」である。**

> **置き換わった先が `TAG_INSTANCE` である理由は、まだ突き止めていない。**
> この族(float / vector / bignum limb)は MAGIC つきのインスタンスで表される。

## 7. 本当の問題 — **上限と実際の限界の余裕が 1 段しかない**

| | 破壊が始まる段数 | 上限 60 が許す段数 | 余裕 |
|---|---|---|---|
| `f6722af` の前 | **26** | 29 | **-3(内側。だから症状が出た)** |
| いま | **30** | 29 | **+1** |

**`ZA_MAX_COMPILE_NEST = 60` は、実際のスタックの余裕から導かれていない。**
`f6722af` が余裕を稼いだのは**副作用**であって、この上限を直したからではない。
したがって:

- **いま症状が出ないのは偶然に近い。** コンパイル経路の 1 段あたりのスタック消費が
  わずかに増えれば、破壊は再び上限の内側に入る(そして**静かに**壊れる)
- **断念は「安全側」ではない。** 形の検査は**すでに起きた破壊を見つけている**のであって、
  上限として品よく止まっているのではない(issue 本文の「断念自体は安全側」は、
  この点で読み替えが必要)

### 直すなら

1. **コンパイル経路にスタック残量の検査を入れる**(いまは `jit-stack-guard-hits=0` =
   通っていない)。溢れる前に断念できれば、破壊ではなく正規の断念になる
2. **`ZA_MAX_COMPILE_NEST` を実測から導く**(規則 13)。固定値のままにするなら、
   「破壊が始まる段数」を測る試験を置いて**余裕を監視できる**ようにする
3. ★ 未検証: `f6722af` が余裕を稼いだ機構は特定していない。
   `jit_emit_rsp_disp32` に最高水位の更新が入って `-O1` の展開が変わり、
   再帰関数のフレームが縮んだ可能性がある(この種の `-O1` の罠は
   `documents/heap-exhaustion.md` §11 にも記録がある)。**逆アセンブルで確かめていない**

## 8. 予測の当たり外れ(規則 11)

測る前に宣言した予測と結果:

| 宣言 | 結果 |
|---|---|
| 資源は「コンパイル時の C 再帰によるスタックの枯渇」で、GC ではない | **当たり**(37 段以上で `STACK OVERFLOW`、`guard-hits=0`) |
| 窓を開ければ**40〜55 段**付近で形の検査が再び当たる | **外し。実際は 30 段から。** 帯の外 |
| 現れ方は「形の検査が当たる」 | **半分外し。** 30〜36 段は形の検査だが、37 段以上は**CPU 例外** |

**帯を外した理由**: 反転点が「1 段あたりのフレーム寸法 7480 -> 4152」に比例して
26 x 1.80 ≒ 47 段へ動く、と見積もった。これは**生成コードのフレームが
コンパイル時のスタックを食う**という前提で、誤りだった。
コンパイル時に積まれるのは **C のフレーム**であって、生成コードのフレームではない。
実際の移動は 26 -> 30 段で、**比例ではなかった**。

## 9. 途中で間違えたこと

### 窓の内側だけ見て「再現しない」で止めかけた

`ZA_MAX_COMPILE_NEST` が先に当たる段数を「観測できない」と書いて済ませた(§3)。
**上限は外せる**(測るあいだだけ上げて戻す)。外したら 30 段から全段で再現した。
**「観測できない」と「起きていない」は別である。**

### 二分探索の good/bad の極性を取り違えた

詳細は §4。`git bisect` は祖先側を good と要求するので、
「症状あり = bad」にすると**転換点の反対側**を探しに行く。1 歩ぶん無駄にした。


### プローブの段数が 1 つずれていた

段数を生成する関数が **n+1 段**を作っていた(最内の `(tagbody (let ...))` が
1 段ぶん増える)。「25/27/29 段」と書いた run は実際には 26/28/30 段だった。
**手書きの題材(`jlm-trunc` から写したもの)と `(tagbody` の数を比べて気づいた**
(27 対 26)。

### 深い関数を 3 つ 1 ブートで回すと完走しない

生成したプローブ 3 つを 1 ブートで回すと **2 回とも結果が出なかった**。
**1 つに絞ると完走する**(27 段単体 → 起点 4272)。
元のバグではなく**プローブ側の資源の問題**だった。

> **「結果が無い」は PR #151 で族として扱った形である。** 再試行の仕組みが
> 2 回試して落としてくれたので、**本物の失敗と混ざらなかった。**
