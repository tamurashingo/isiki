# 型特化ディスパッチ

四則演算と比較を、**引数の個数**と**型が分かっているか**で振り分ける枠組み。

関連: `documents/declare-types.md`(型情報の記録)、
`documents/divide-direct-call.md`(二項版の直接 call)

---

## 1. 4 象限

|  | 引数 3 以上 | 引数 2 つ |
|---|---|---|
| **型不明** | GENERIC | GENERIC-2 |
| **型判明** | 型特化 | 特化-2 |

### 現状(2026-09-21 時点)

**型不明の 2 象限だけが実装されている。**

| | 引数 3 以上 | 引数 2 つ |
|---|---|---|
| 型不明 | ✅ `primitive_add` / `subtract` / `multiply` / `divide` | ✅ `primitive_add2` / `subtract2` / `multiply2` / `divide2` |
| 型判明 | ❌ 未実装 | ❌ 未実装 |

型判定はすべて**汎用関数の内部**で行われる。`primitive_add2` は入口で
`fixnum_add_signed` を試し、外れたら `float_kind_max` を見て、それでも外れたら
cons を作って n 項版へ委譲する。SBCL の `generic-+` と同じ構造である。

JIT が指定する呼び先も 4 種のみで、**型による出し分けは無い**。

---

## 2. なぜ象限を分けるか

**引数の個数で分ける理由。** n 項版は引数の cons リストを前提にするため、
呼び出し側が cons を構築する。二項版は `rcx` / `rdx` のレジスタ渡しで呼べるので
確保が消える(`documents/divide-direct-call.md` の実測で 32 byte/回)。

**型で分ける理由。** 汎用関数は入口で型を判定する。コンパイル時に型が分かって
いれば、その判定を丸ごと省ける。

**両方が揃って初めて「引数 2 つ・型判明」の最短経路になる。**

## 3. 命名規則

### 3-5 関数名

```
primitive_<op>2_<type>      引数 2 つ・型判明
primitive_<op>_<type>       引数 3 以上・型判明(将来)
primitive_<op>2             引数 2 つ・型不明(既存)
primitive_<op>              引数 3 以上・型不明(既存)
```

| 部分 | 値 |
|---|---|
| `<op>` | `add` / `sub` / `mul` / `div` / 比較は `lt` `gt` `le` `ge` `eq` `ne` |
| `<type>` | `fixnum` / `single` / `double` / `bignum` |

**同型の組にだけ専用関数を作る。** 混在(`fixnum × single` など)のために
専用関数を作らない。呼び出し側で一方を変換して同型へ寄せるか、GENERIC へ落とす。

**理由:** 型の組み合わせは型数の 2 乗で増える。4 型なら 16 通りになり、
演算子ごとにそれを用意すると管理できない。同型だけなら 4 つで済む。

---

## 4. 型の組の扱い

| 組 | 行き先 |
|---|---|
| 同型 | **専用関数** |
| 混在で、変換しても情報が落ちない | 変換して同型の専用関数へ |
| 混在で、変換すると情報が落ちる | **GENERIC** |
| 一方でも型が分からない | **GENERIC** |
| 引数 3 つ以上 | **型が分かっていても GENERIC**(当面) |

### 情報が落ちる例

single の仮数は 24 bit、fixnum のマグニチュードは 59 bit である。
**2^24 を超える fixnum を single へ直接変換すると桁が落ちる。**

GENERIC は double(仮数 53 bit)を経由するので、より正確な答えを返す。
**宣言の有無で答えが変わってはならない**ので、落ちる場合は GENERIC へ送る。

## 5. インラインとの関係

### 5-4 インラインへの移行手順

**既定は call のままにする。** インラインは宣言による opt-in とする。

1. 型特化のセルを埋める(本枠組み)。**既定は call**
2. 宣言で inline を指示できるようにする
3. 指示されたセルだけ「call」から「インライン展開」へ差し替える

セルの中身を差し替えるだけなので、**移行は局所的な変更で済む**。

### call 形を残す理由

**理由 1: 足場の一様性**

すべての型が同じ形を通るので、セルの追加が機械的になる。インラインが効かない
演算(整数除算など)では、専用 call がそのまま最終形になる。

**理由 2: 逆アセンブルの可読性**

```
call primitive_add2_fixnum      ← 何が起きているか一目で分かる
```

全部をインラインにすると、命令の羅列から意図を復元することになる。

> **【更新 / disasm-symbols】理由 2 は成立するようになった。**
>
> シンボル名解決を実装したので、いまは呼び先が名前で出る。
>
> ```
> mov r11d, 0x275c5fd    ; primitive_add2_fixnum
> call r11
> ```
>
> **PR #89 の検証は code-len でしか確認できず**、`primitive_add2_fixnum` と
> `primitive_add2_single` を取り違えても気づけなかった。いまは名前で直接
> 確認できる。詳細は `documents/disasm-symbols.md`。
>
> 以下は実装前の記録である。
>
> **【当時】理由 2 は現時点では成立していない。**
>
> disassembler はまだ **call 先の関数名を出せない**。`disasm_lisp.c` が付ける
> 注釈は `os_addr_region_name(os_classify_addr(...))` による**領域分類のみ**で、
> 実際の出力はこうなる。
>
> ```
> 41 bb 71 57 79 02    mov r11d, 0x2795771    ; <kernel>
> 41 ff d3             call r11
> ```
>
> **`; <kernel>` までで、関数名は出ない。**
> 理由 2 は「シンボル名解決が実装された後に成立する前提」である。
>
> 名前解決の方針は Phase 1 の調査で出ている(ビルド時にカーネルのシンボルを
> 抽出し、アドレス昇順の静的テーブルを作って二分探索で引く)。**別作業。**
>
> **この注記を消さないこと。** 実態と食い違ったまま「可読性のため」と
> 書き続けると、根拠が無いまま設計判断だけが残る。

## 6. 演算ごとに判断が違う

**`+` での判断をそのまま他へ適用しないこと。** 演算ごとに測る。

| 演算 | 注意 |
|---|---|
| `+` `-` | ほぼ同じ形になる |
| `*` | fixnum のオーバーフロー判定が `+` より難しい。符号マグニチュード表現では `imul` + `jo` が使えない(`type-system-survey.md` §9-4) |
| `/` | 切り捨て方向がある(ゼロ方向。`divide-direct-call.md` で確認済み) |
| 比較 | 結果が t / nil なので確保が無い。NaN の非順序を正しく扱うこと(`nan-comparison.md`) |

## 7. 型を宣言すると遅くなる段階がある

**利用者向けの注意。**

型特化のセルが「call」である間は、**fixnum に型を宣言すると遅くなる**。

| | 生成されるもの |
|---|---|
| 宣言なし | タグ検査 → インライン `add` → 桁溢れ検査(**call なし**) |
| 宣言あり | `primitive_add2_fixnum` を **call** |

`za_emit_arith_call_or_inline` は既に `+` と `-` に対して fixnum のインライン
高速路を持っているため、**call がインラインに勝つことはない**。

速くなるのは、汎用関数の入口の型判定が重い型(single-float など)である。

**インラインが実装された段階(§5-4)で fixnum も速くなる見込みである。
そのときこの節を更新すること。**
