# 調査報告: JIT コード長の分布

> 調査日: 2026-09-15 / ブランチ: `feature/compiler-optimization`(`6da82cb`)
> **調査のみ。コードは変更していない。ブランチも切っていない。一時パッチも不要だった。**

## 測定方法(変更なしで足りた)

`%%DIAG-ZA-CODE-LEN` は引数を無視して「直近1件」を返すだけ(`za.c` の
`cc_diag_za_code_len`)なので使えない。代わりに **`%%DISASM-CODE-LEN`** を使った。
こちらは `d_fn_meta`(`src/c/disasm_lisp.c`)経由で
**関数オブジェクトを直接受け取れる**:

```c
static za_fn_meta_t *d_fn_meta(lisp_val_t val, lisp_val_t env) {
    if ((val & TAG_MASK) == TAG_SYMBOL) { val = os_get_function(val, env); }
    if ((val & TAG_MASK) != TAG_INSTANCE) { return 0; }
    UINT64 *obj = (UINT64 *)(val & ~TAG_MASK);
    if (obj[0] != MAGIC_FUNCTION_NATIVE) { return 0; }
    return (za_fn_meta_t *)obj[1];
}
```

`global_environment` の functions スロットの alist を走査し、
各 cdr(関数オブジェクト)を `%%disasm-code-len` に渡した。
nil が返るもの(組み込み primitive、AOT、インタプリタ実行)は除外している。

再現手順:

```bash
# 測定用 lisp(genv-functions で alist を取り、%%disasm-code-len で長さを集計)を
# test/lisp/tmp_dist.lisp へ置き、ブート用エントリから load する
make test-qemu-milestone MILESTONE=<boot-entry> QEMU_EXTRA_FLAGS='-serial stdio'
```

**ブート直後の測定では、alist が先頭に push される性質を使って
「測定用ヘルパーを定義する前の alist の尾」を `defglobal` で捕まえた**ので、
ヘルパー自身は集計に入っていない(`genv-functions` の1件のみ含む)。

**この測定が数えるのは「今生きている関数」であって、
コンパイルされた延べ回数ではない。** 再定義で置き換えられた旧関数は alist に無い。
前回調査で再定義による JIT コード破棄は 33 件と分かっているので、差は小さい。

充填率はフルテストで 37.9%、ブートで 65.3%。

## 調査項目 B: 1ページを超える関数

### 確認したこと

**B-1. 分布**

| ページ数 | ブート | フルテスト |
|---|---|---|
| 1 ページ | 65 | **965(93.4%)** |
| 2 ページ | 13 | 57 |
| 3 ページ | 6 | 7 |
| 4 ページ | 1 | 1 |
| 5 ページ以上 | 1(`%CONVERT` 10 ページ) | 3 |
| **合計** | 86 | 1,033 |

前回カウンタで測った「1ページ要求 93.4%」と一致する
(`documents/investigation-code-page-reclaim.md` 項目 B)。

**B-2. 大きい関数の正体(フルテスト、byte 降順)**

| byte | ページ | 関数 |
|---|---|---|
| 41,244 | 11 | `JND-59` |
| 38,313 | 10 | `%CONVERT` |
| 34,423 | 9 | `REPORT-DIST` |
| 12,666 | 4 | `EXPT` |
| 11,617 | 3 | `DISASSEMBLE-TO-LIST` |
| 11,291 | 3 | `DISASSEMBLE-TO-STREAM` |
| 9,918 | 3 | `%QUOTIENT2` |
| 9,783 | 3 | `DISASSEMBLE-TO-STRING` |
| 9,615 | 3 | `ISIKI-AUDIT-TRAP-REPORT` |
| 9,400 | 3 | `ISIKI-AUDIT-RECORD` |
| 9,249 | 3 | `IZ14-TRIPLE-NESTED-FOR` |

特徴がはっきりしている:

- **`JND-59` は `if` を 59 段ネストした回帰テスト**
  (`test/lisp/jit_nest_depth_test.lisp`)。691 byte/段 × 59 = 40,769 でほぼ説明がつく。
  **測定のための人工的な関数で、実コードの代表ではない**
- **`REPORT-DIST` は今回の測定用ヘルパーそのもの。** 同じく実コードではない
- **`%CONVERT`(38,313 byte)が実コードの最大。** `init.lisp` の型変換で、
  `cond` の枝が多い
- 残りは `cond` / `case` の枝が多い関数と、コールサイトが多い関数
  (`DISASSEMBLE-TO-*` 系はフォーマット呼び出しが並ぶ)

**つまり大きい関数は「コールサイトが多い」か「分岐が多い」かのどちらか**で、
1 コールサイト 762 byte・ネスト 1 段 691 byte という単価から素直に出ている
(`documents/measurement-callsite-breakdown.md`)。

### 推測・未確認

- **(推測)** パッキングを入れても、1 ページを超える関数は従来どおり
  連続ページで確保することになる。依頼書の指摘どおり
  **bump カーソルとページ確保が混在する。**
  素直な整理は「`code_len` が閾値(例えば 1 ページ)未満なら bump、
  以上なら従来の `os_imm_pages_alloc_contiguous`」という
  **サイズによる二本立て**だと考える。これは一般的なアロケータの
  small/large 分離と同じ形で、境界が 1 ページなので判定も単純
- **(未確認)** 閾値をページ丁度にするか、半ページなどにするかは測っていない。
  Q3 が 1,730 byte(フルテスト)なので、
  **1 ページ閾値なら 93.4% が bump 側に入る**

## 調査項目 C: パッキングの設計制約

### 確認したこと

**C-1. アライン要求は 16 byte で足りる**

- x86-64 の命令フェッチにアライン要求は無い
- `jit_serialize_icache()`(`src/c/za.c:462-466`)は `cpuid` 1 発で、
  **粒度を持たない**(特定アドレス範囲ではなく命令ストリーム全体を直列化する)。
  コピー直後に 1 回呼ぶ(`za.c:6168`)形はパッキングでも変わらない
- `za_fn_meta_t` からの逆引きは絶対アドレス(`cons_entry` / `fixed_entry` /
  `code_base`)なので境界に依存しない

**C-2. `code_base` にページ先頭の前提は無い**

`os_fn_set_code_range`(`src/c/runtime.c:3261-3275`)は
受け取った値を meta へ代入するだけ。
逆アセンブラ側(`primitive_disasm_code_base` / `primitive_disasm_code_len`、
`src/c/disasm_lisp.c`)も `meta->code_base` / `code_len` をそのまま返すだけで、
**ページ境界の仮定は無い。**

`primitive_disasm_entry_offset` は
`entry < meta->code_base || entry >= meta->code_base + meta->code_len` を
範囲検査に使っている(`disasm_lisp.c`)。これも相対位置の話で、ページとは無関係。

**C-3. 関数オブジェクトのコードポインタもページ先頭を仮定していない**

`za.c:6230-6242`:

```c
lisp_addr_t cons_entry_addr = (lisp_addr_t)(void *)(dest_bytes + (cons_entry_offset - entry));
...
lisp_val_t fn = os_make_jit_function_dual(cons_entry_addr, fixed_entry_addr, fixed_count, capture_env);
os_fn_set_code_range(fn, (UINT64)(lisp_addr_t)dest_bytes, code_len);
```

**すでに `dest_bytes` からのオフセットとして計算している。**
`cons_entry_addr` は `dest_bytes` と一致するとは限らない
(dual-entry では `fixed_entry` が先頭で `cons_entry` は 0x8E など)。
**ページ先頭 = エントリという前提はどこにも無い。**

**C-4. `destroy-environment` を使うテストは 3 ファイル 12 箇所**

`test/lisp/frame_definition_test.lisp`、
`test/lisp/environment_literal_slots_test.lisp`、
`test/lisp/environment_utilities_test.lisp`。

**(推測)** パッキング後、これらのテストは
「ページが返らなくても失敗しない」形であれば壊れない。
`environment_literal_slots_test.lisp` が**リテラルスロットの返却**を
検証している可能性があり、そちらはページとは別経路
(`os_environment_reclaim_literal_slots`)なので影響しないと考えるが、
**中身は読んでいない。**

**C-5. ページをまたぐコードは物理的に問題ない(確認)**

`g_imm_space` は `static UINT8 g_imm_space[IMM_SPACE_SIZE]`
(`src/c/runtime.c:1098`)で、**16MB の連続した静的配列**。
`g_imm_bump` はその中を進むだけなので、隣接ページは必ず物理的に連続している。
ページテーブルも UEFI の恒等マップのままで、カーネルが触るのは
スタックガードの `unmap_range` だけ(`src/c/process.c:120, 142`)。

## 所見

**(所見)効果は 2.6 倍で、桁は変わらない。** 依頼書の「5〜10 倍」には届かない。
理由は中央値が 1,284 byte あることで、これは
**1 コールサイト 762 byte という単価が効いている**
(`documents/measurement-callsite-breakdown.md`)。
数個の呼び出しを含む普通の関数がすぐ 1KB を超える。

**(所見)それでも入れる価値はあると考える。** `defun` 可能回数が
4,032 → 約 12,300 になり、CI の消費は 29% → 11% 相当に落ちる。
**当面の枯渇は回避でき、しかも解放を伴わないので
`documents/constraint-jit-code-pages-are-immortal.md` の制約に抵触しない。**

**(所見)効果を 2.6 倍より上げたいなら、コールサイトの 762 byte を削るほうが本筋。**
コード長そのものが縮めば、パッキングの効果とは乗算で効く。
前回の内訳では GC link/unlink が 233 byte(30.6%)、関数解決が 185 byte(24.3%)だった。

**(所見)ブートとテストで充填率が倍違う(65.3% vs 37.9%)のは、
パッキングの効果がワークロード依存であることを意味する。**
「起動だけなら 1.5 倍、使い込むほど 2.6 倍に近づく」と読むのが妥当。
**枯渇が問題になるのは使い込んだ後なので、実用上は 2.6 倍側の数字で見てよい。**

**(所見)アロケータは small/large の二本立てが素直。** 1 ページ未満は bump、
以上は従来の連続ページ確保。境界がページ丁度なので判定が単純で、
93.4% が bump 側に入る。

## 未調査・積み残し

- **再定義で置き換えられた旧関数のコード長は測っていない。** この測定は
  「今生きている関数」のみ。前回調査で旧関数は 33 件と分かっているので影響は小さいが、
  厳密には延べコンパイル 1,062 回に対し 1,033 件しか見ていない
- **`global_environment` 以外の環境で定義された関数を数えていない。**
  テストが `create-environment` で作った環境の関数は alist に無い
- **`environment_literal_slots_test.lisp` の中身を読んでいない**(C-4)。
  パッキングでページが返らなくなったときに壊れるかは未確認
- **パッキング時の端数の扱いは見積もっていない。** 「ページ末尾に入りきらない関数を
  次ページへ送る」場合の無駄(平均で関数サイズの半分程度?)は計算に入れていない。
  上の 2.62 倍はこの無駄をゼロと仮定した上限
- **`JND-59`(41KB)と `REPORT-DIST`(34KB)は測定由来の人工的な関数**で、
  実コードの分布を歪めている。除外した場合の数字は出していない
