# letのJITコンパイル対応 検討メモ

`let`/`let*`(および内部でこれらを使う`or`/`case`/`case-using`/`for`/
`with-open-*`系)が、defun本体に含まれるとza.c(JITコンパイラ)が
コンパイルを断念し、そのdefun全体がインタプリタ実行にfallbackしてしまう
問題についての検討結果。

## 実装状況(追記)

以下の「案B」がza.cに実装済み。クロージャキャプチャ対策は本メモ135節の
(a)(`za_compile_lambda`側でlet-localもコピー対象に加える)を採用しており、
(b)(body内にlambdaが出現したらインライン化自体を諦める)は採用していない。
`za_local_scope_t`によるスコープチェーンの導入、`ZA_OFF_LOCAL_BASE`等の
スロット領域追加、`za_classify_operand`の探索順序拡張(内側スコープ→外側→
既存の固定引数/quote/fixnum)は、いずれも本メモの設計どおり。

加えて、`let*`の展開の末端が必ず`(progn ,@body)`を経由するため、`let*`が
案Bの恩恵を受けるには`progn`自体もインライン展開できる必要があることが
実装中に判明し、`za_compile_progn`を新設して対応した(これにより`cond`
(`if`/`progn`の入れ子に展開される)も副次的にJIT対象になる)。

案B/progn対応により従来インタプリタへfallbackしていた関数が大量にJIT対象へ
変わった結果、プロセス全体で累積するJITコード量(`g_jit_code`、旧64KB)が
テストスイート全体を通すと不足するようになったため、`JIT_CODE_SIZE`を
256KBへ拡張した。

さらに拡張9として、下記「スコープ外にすべきもの: `setq`」節で述べていた制約の
一部を解消した。**let-localへの`setq`のみ**対応済み(`za_compile_setq`、
新設)。外側defunの固定引数・グローバル変数・dynamic変数への`setq`は書き込み
可能なスロットが無いため引き続きfallbackする。クロージャキャプチャとの食い違い
(下記参照)は、同一defun内に`setq`とエスケープする(値の位置に現れる裸の)
`lambda`の両方が存在する場合に関数全体を無条件にfallbackさせる粗い安全網
(`g_za_saw_setq_local`/`g_za_saw_escaping_lambda`、`za_try_compile_defun`末尾で
判定)で対処している。

また、`for`/`while`マクロがどちらも`(block nil (tagbody ...))`に展開されることに
関連し、`(block nil ...)`/`(return-from nil ...)`がJITコンパイルできない
(`nil`が内部的に`TAG_CONS`であり、既存の`TAG_SYMBOL`限定のブロック名チェックに
常に落ちる)という、setqとは独立した既存バグも同時に修正した。これにより
`setq`対応と合わせて`for`/`while`ループ自体もJIT対象になった。

本メモは、`let`/`let*`が現在の実装どおり**init.lispのdefmacroのまま**
であることを前提にした解決案(案A・案B)をまとめる。C側にletを直接実装する
場合の検討は別メモ(let-native.md相当、本ドキュメント末尾の「今後の検討」
参照)で扱う。

## 問題の構造

`let`は`src/lisp/init.lisp`で次のようにマクロ展開される。

```lisp
(let ((v1 i1) (v2 i2) ...) body...)
  => ((lambda (v1 v2 ...) body...) i1 i2 ...)
```

za_compile_exprは対象フォームに対して必ず`za_macroexpand`を最初に通すため、
za.cが実際に目にするのは展開後の`((lambda ...) ...)`という形である。この
フォームのhead(呼び出し先)が`TAG_SYMBOL`ではなく`TAG_CONS`(lambda式そのもの)
であるため、一般呼び出しの判定ゲート(`za_compile_call`の手前、
`if ((head & TAG_MASK) != TAG_SYMBOL) return 0;`)に落ち、コンパイル不可となる。

これは`let`という特殊形式そのものの制約ではなく、
「呼び出し先が式(lambda式)であるcallをza.cがサポートしていない」という、
より一般的な制約である。したがって`let*`(letのネスト展開)、および内部で
`let`を使う`or`/`case`/`case-using`/`for`/`with-open-*`系マクロも、
展開後は同じ形に帰着するため、すべて同じ理由でコンパイル不可になる。

## 案A: `funcall`経由への書き換え(letのマクロ定義のみを変更)

### 発見の経緯

- `FUNCALL`はza.c側で特別扱いされていない、ふつうの登録済みnative関数
  (`global_environment`に`os_set_function`で登録されているだけ)である。
  `za_is_excluded_special_form`にも入っておらず、headがプレーンシンボル
  なので一般呼び出しのゲートを問題なく通過する。
- 一方、`za_compile_lambda`という既存機構が、`lambda`式が**値の位置
  (呼び出しの引数位置など)に現れた場合**にそれを新しいクロージャとして
  コンパイルする処理を既に持っている(za.c:926-1024)。呼び出しの引数として
  bareな`(lambda ...)`を渡すこと自体は既に問題なくコンパイルできる。
- 検証: `(funcall (lambda (y) y) x)`という形(`#'`/`function`は**付けない**)
  は、追加のC側変更なしに、現在のza.cで実際にJITコンパイル対象になることを
  QEMU上で確認済み。
  - `(function (lambda ...))` (`#'`付き)は逆に非対応化する
    (`function`特殊形式にはza.c側の対応が一切無いため、どの位置でも
    コンパイル不可になる)。**`#'`は付けてはいけない。**

### 対応内容

`init.lisp`の`let`マクロの展開先を

```lisp
((lambda (v1 v2 ...) body...) i1 i2 ...)
```

から

```lisp
(funcall (lambda (v1 v2 ...) body...) i1 i2 ...)
```

に変更するだけ。**za.c/C側の変更は一切不要。**

`let*`はletのネスト展開なので自動的に追随する。`or`/`case`/
`case-using`/`for`/`with-open-*`系も、内部で使っている`let`の定義が
変わるだけで自動的に恩恵を受ける。

### 効果と限界

- 効果: `let`を含む**外側のdefun自体**がJITコンパイル対象になる
  (`%%za-compiled-p`がtrueになる)。
- 限界: `let`の**body自体は今までと同様にインタプリタで実行される**。
  `funcall`は実行時にクロージャを構築し`apply_function`経由でインタプリタに
  ディスパッチするだけであり、body内の式が機械語になるわけではない。
  つまり「外側の関数呼び出しコストはJIT化されるが、let本体の実行コストは
  変わらない」という部分的な改善になる。
- 既存の関連する制約(未解決のまま残るもの):
  - `za_compile_lambda`は外側defunの**固定引数のみ**を新しいクロージャ環境へ
    コピーする(za.c:974-994)。`&rest`引数は対象外。したがって
    `let`のbodyが外側defunの`&rest`引数を参照するケースは、この案では
    正しく動かない可能性がある(既存の別課題であり、案Aで新たに生じる
    問題ではない)。
  - `za_compile_call`の引数評価ループは`allow_call=0`で再帰するため、
    一般呼び出しの引数位置に**別の**一般呼び出しをネストさせることは
    できない(`apply`/`error`がインタプリタに落ちる理由と同じ、これも既存の
    別課題)。

### 推奨

実装コストがinit.lispの1行変更のみで、リスクも極めて小さい。まずこちらを
先に導入するのが妥当。

## 案B: let本体の直接インライン化(true inlining)

### 目的

案Aの限界(let本体自体はインタプリタ実行のまま)を解消し、let本体を含めて
完全にネイティブコードにする。

### 前提の言い換え

za.cはマクロ展開後の形しか見ないため、案Bは「letを特別扱いする」のではなく、
**「呼び出し先が`(lambda 仮引数 . body)`という形のcons(即時呼び出し、IIFE)
であるcall全般を、実際の関数呼び出し手続きを経ずにbodyをその場に展開
(インライン化)する」**という、より一般的な最適化になる。この一般性のおかげで、
let/let\*/or/case/case-using/forの外側letすべてに自動的に効く。

### 必要な変更

1. **スコープチェーンの追加**: 既存の`params`/`fixed_count`(外側defunの
   引数)はそのままに、並行して`let`ローカル変数のスコープ情報
   (シンボル名の配列・親スコープへのポインタ)を新しい引数として全関数へ
   スレッドする(拡張5で`nlx_depth`/`tb_ctx`を追加した前例と同じやり方)。
2. **新しいスロット領域**: `ZA_OFF_NLX_BASE`/`ZA_MAX_NLX_DEPTH`と同型の
   `ZA_OFF_LOCAL_BASE`/`ZA_MAX_LET_DEPTH`/`ZA_MAX_LOCALS_PER_LET`を追加する。
   ネスト深さ×1letあたりの変数数で固定サイズのスロット領域を確保し、
   兄弟let同士(ネストしていない)はスロットを再利用する。上限を超えたletは
   インライン化を諦めてfallbackする。
3. **新しいコンパイル関数**(`za_compile_iife`相当): 各init式を外側スコープで
   評価してスロットに格納・GCリンクし、新しいローカルスコープを積んでbodyを
   コンパイルする。既存の「SAVED_HEAD保存→実行→`za_gc_unlink`で一括
   アンリンク」パターン(za_compile_call/za_compile_lambdaが既に使っている)
   を再利用することで、通常のフォールスルーだけでなくreturn-from/throw/go
   による早期脱出時のGC安全性もほぼそのまま既存機構に乗せられる。
4. **変数解決の拡張**(`za_classify_operand`): シンボル参照の探索順序を
   「ローカルスコープ(内側→外側)→既存の固定引数/`&rest`→quote/fixnum
   リテラル」に変更する。内側から順に一致を探すことで、シャドーイング
   (letが外側paramや外側letと同名)も自然に正しく解決される。

### 最大のリスク: ネストしたlambdaによるクロージャキャプチャ

`za_compile_lambda`は新しいクロージャ環境を作る際、**外側defunの固定引数
だけ**をコピーする。let-localは(実インタプリタ環境ではなく)生のJITスタック
スロットになるため、このコピー処理はlet-localの存在を一切知らない。

```lisp
(let ((x 1)) (lambda () x))
```

のように、**let-localを実lambdaが閉じ込める**パターンをそのまま
インライン化すると、生成されるクロージャがxを正しく見られず、
エラーにならずに不定値を返す静かなバグになる。

対策は二択:

- (a) `za_compile_lambda`側も、そのlambdaの外側で生きているlet-localを
  すべて新環境へコピーするよう拡張する(正しく解決するが実装コスト増)。
- (b) インライン化を判定する際にbody内を静的に走査し、`(lambda ...)`が
  出現する場合はインライン化自体を諦め、案A(funcall+クロージャ)の経路、
  あるいは全体を非コンパイルにfallbackさせる。

安全側に倒すなら(b)を初版の必須ガードとするのが妥当。

### スコープ外にすべきもの: `setq`(拡張9で一部解消済み)

`setq`(`g_sym_setq`)は本メモ執筆時点では`za_is_excluded_special_form`に
入っており、**letとは無関係に、setqを使う関数は現在すでに全部インタプリタ
fallback**していた。これは案Bが新たに背負う制約ではなく既存の制約だが、実利上
の影響があった: `for`マクロの展開はletで束縛したループ変数へ`setq`するため、
案Bを実装しても`for`はインライン化の対象にならない(letの束縛自体はできる
ようになっても、その後のsetqが別の理由でfallbackさせる)、という状態だった。

拡張9(冒頭「実装状況(追記)」節参照)で、**let-localへの`setq`のみ**対応した。
`for`/`while`のループ変数はいずれもlet-localなので、この対応と、独立に発見・
修正した`block nil`/`return-from nil`バグの修正が揃ったことで、`for`/`while`
自体もJIT対象になった。外側defunの固定引数・グローバル変数・dynamic変数への
`setq`は引き続き非対応でfallbackする(将来の別拡張の対象)。

### 推奨v1スコープ

- 固定引数のみのIIFE(`&rest`なし)
- body内に`lambda`が出現しない(クロージャキャプチャ問題を静的ガードで回避)
- setqは対象外
- ネスト深さ・変数数はNLX同等の小さい固定上限

### コスト/リスクの総括

- 変更範囲: za.cの主要関数10箇所以上にスコープ引き回しを追加する必要があり、
  案A(init.lispの1行変更)と比べて桁違いに大きい。
- 正当性リスク: クロージャキャプチャの見落としが最大の懸念。
- 効果: let系body自体もネイティブコードになるので、案Aより実行時性能は
  上がるが、対象範囲(setq/lambda capture不可)は案Aより狭い。

## 結論・推奨する進め方

1. まず案Aを導入する(init.lispの1行変更のみ、za.c変更なし、リスク極小)。
   これだけで`let`/`let*`/`or`/`case`/`case-using`/`for`/`with-open-*`を
   含む外側defunがJITコンパイル対象になる。
2. 案Aだけでは不十分なホットパス(let本体自体の実行コストが問題になる箇所)
   が具体的に見えてきた段階で、案Bへの着手を検討する。

## 今後の検討

`let`/`let*`をinit.lispのdefmacroのままにするのではなく、C側
(eval.c/za.c)に直接組み込む特殊形式として実装する場合の設計は、
本メモの対象外(別途検討)。
