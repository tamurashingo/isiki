# ヒープ枯渇をハングではなくエラーにする(issue #110、M8-T4〜T6)

> 状態: **D9 を決めた(2026-11-01)。実装はこの決定に従って行う。**
> スタック側は `documents/stack-guard.md`(PR #121 で完了)。
> **#110 はスタックとヒープの両方を含む**(2026-10-29 のユーザー判断)。

## 0. スタックの解法がそのまま使えない理由

スタック枯渇の解法が成り立ったのは、**検査の場所が「値を返せる場所」だった**からである
(JIT のプロローグ。`sub rsp` より前)。ヒープは違う:

| | スタック | ヒープ |
|---|---|---|
| 枯渇が起きる場所 | 関数の入口(**値を返せる**) | **確保の内部**(`os_alloc_bytes`。番地を返す) |
| 割り込み | 生きている | **止めている**(`cli`〜`sti`) |
| signal に必要なもの | スタックの余裕 | **確保**(条件の実体・引数の対・呼び戻し) |

**回収器の最中には signal できない**(signal 自身が確保する)。
`os_alloc_bytes` の中で「確保できません」と言う手段は無い。番地を返す関数だからである。

**再利用できるのは構造だけ**: 本当の限界より上に閾値 / 床 / 知らせている間だけ予備を開ける /
重ねない / 最後はエラー値へ落ちる。

## 1. D9 の決定 — **安全な地点は「確保を要求する primitive」**

**決定: 検査は確保器(`os_alloc_bytes`)ではなく、確保を要求する primitive に置く。**

### なぜそこなのか — スタック側にできなかったことができる

スタックガードの弱点は、**3 経路のうち JIT だけを守れた**ことだった
(`documents/stack-guard.md` §4。「0 = 守られていない経路」という診断を出すほど、
この片手落ちは意識されている)。スタックの深さは**呼び出す側のフレーム**で増えるので、
経路ごとに別の場所へ検査を置くしかなかった。

**ヒープは違う。確保の要求は 3 経路が共有する C の primitive を通る。**

| 経路 | `(create-array '(1000000000) 0)` が通る道 |
|---|---|
| インタプリタ | `os_eval` → `primitive_make_array` |
| AOT | 生成された C → `primitive_make_array` |
| JIT | 生成された機械語 → `primitive_make_array` |

**同じ 1 つの関数である。** だから **1 箇所に置けば 3 経路が覆える。**
しかも primitive は既に signal している
(`signal_domain_error_for_class` など)ので、**signal してよい場所**であることが
既存の作りから分かる。

### 2 種類の要求を分ける

| | 例 | 失敗を返せるか | 扱い |
|---|---|---|---|
| **大口** | `create-array` / `create-vector` / `create-string` | **返せる**(引数から大きさが決まり、呼び出し元は値を受け取る) | **その場で `<storage-exhausted>` を signal する** |
| **小口** | `os_make_cons`(16)/ `os_make_instance`(32) | **返せない**(「対を作れませんでした」を返す先が無い。あらゆる呼び出し元が対を前提にしている) | **閾値と予備**。印を立て、次の安全な地点で signal する |

**大口だけで「配列 1 つで機械を殺せる」経路は閉じる**(= ゲストの再現手段)。
小口は構造(閾値・予備・床)で受ける。

## 2. 掛け算より前に判定する — **今は検査が無い**

`alloc_vector_block` の現状:

```c
static lisp_addr_t alloc_vector_block(UINT64 rank, const UINT64 *dims) {
    UINT64 total = 1;
    for (UINT64 i = 0; i < rank; i++) {
        total *= dims[i];          /* ← 桁あふれの検査が無い */
    }
    lisp_addr_t addr = os_alloc_bytes(8 * (1 + rank + total));   /* ← ここも溢れる */
```

**桁あふれの検査も負値の検査も無い。**
`total` が巻き上がると**小さい値になって検査を通り抜け**、小さい塊を確保したあとに
要素を書き込んで**ヒープを踏み越える**。枯渇の判定を掛け算の**後**に置くと、
まさにこの場合だけ検査が効かない。

**したがって判定は掛け算より前に置く。** 具体的には、掛けながら
「この 1 回の掛け算で溢れるか」を見る(`__builtin_mul_overflow`。
A の `fixnum_fast_mul` と同じ道具)。溢れたら**その時点で**
`<storage-exhausted>` を signal する(確保を試みない)。

> **桁あふれと枯渇は同じ答えでよい。** 要求が表せる大きさを超えているなら、
> それは「入らない」のであって、`<storage-exhausted>` が正しい。
> 別の条件を作ると、呼び出し側が 2 つを区別して扱う理由が無いのに
> 区別させることになる。

負値は `create-array` の入口で見る(次元は非負の整数でなければならない)。

## 3. 小口 — 閾値と予備、そして**常道の命令数を 1 つも増やさない**

いまの常道:

```c
UINT8 *p = g_from_ptr;
if (p + aligned > g_from_end) { ...GC して、それでも足りなければ panic... }
g_from_ptr = p + aligned;
```

**比較の相手を「柔らかい端」に変えるだけにする。**

```c
if (p + aligned > g_from_soft_end) { ...遅い側... }
```

`g_from_soft_end = g_from_end - HEAP_SIGNAL_RESERVE` を確保器の初期化時に 1 回計算する。
**比較は 1 つのままなので、常道の命令数は 1 つも増えない**(定数が変わるだけ)。
これは G1(回帰ゼロ)のために重要である。

遅い側の筋:

1. GC を 1 回走らせる(現状と同じ)
2. それでも柔らかい端を超える → **印を立て、予備から確保を続ける**
   (signal 自身が確保するので、予備が無いと知らせることすらできない)
3. **本当の端まで使い切った** → `panic`(最後の砦。現状と同じ)

**重ねない**: 知らせている間に再び枯渇したら、閾値を床まで下げる
(スタック側の `ZA_STACK_HARD_FLOOR` と同じ考え方)。
床でも足りなければ `panic` へ落ちる。

### 印を見る場所 — **解釈実行の評価の入口**

印を立てても、誰かが見なければ signal は起きない。見る場所の候補:

| 見る場所 | 覆う経路 | 費用が見えるか |
|---|---|---|
| 大口の primitive | 3 経路 | **見える**(`vector` の行。ただし 1 回だけなので 1 単位あたりほぼ 0) |
| **`os_eval` の評価の入口** | **インタプリタ** | **見える(M8-T3 で解釈実行の行を作ったから)** |
| JIT のプロローグ | JIT | 見える(`jit/*` の行) |
| AOT の関数入口 | AOT | 見える(`aot/*` の行) |

**今回は大口 + `os_eval` の入口までとする。** JIT と AOT の小口は
**守らないことを記録する**(スタック側が「JIT だけ守った」ことを記録したのと同じ作法)。

> **M8-T3(解釈実行の計器)を先に作った理由がここにある。**
> `os_eval` の入口に検査を置く費用は、**それまでどの基準値にも現れなかった**。
> 計器が無いまま置けば「費用はゼロだと思っていた」と書くしかなかった。

## 4. 枯渇を起こす 2 通りの手段(T6)

| | 手段 | いまどうなるか |
|---|---|---|
| **ネイティブ** | 試験のヒープを 80KB 以下にする(`SMALL_HEAP_SIZE`) | **ハング**(`os_panic` の `for(;;)` は `ISIKIOS_UNIT_TEST` では `hlt` が無く、CPU を回し続ける) |
| **ゲスト** | 上限検査の無い巨大な配列を 1 つ作る | **機械停止**。`g_panic_hook` が電源を切る |

### ゲストの停止が「外から見えない」ことの正体

最初は「`os_panic` の診断がフレームバッファにしか出ないからだ」と考えたが、
**読んでみたら違った**: `panic_write_string` はフレームバッファと
**シリアルの両方**へ出している(カーネルビルドでは)。
診断自体はシリアルログに出る。

**本当の問題は試験の側である。** panic すると電源が切れるので
**`test-results.txt` が書かれない**。これは E(PR #151)で族として扱った
「結果が無い」flake と**外から見て区別がつかない**。
しかも再試行の仕組みが入ったので、**本物の枯渇を 2 回試してから落ちる**。

**→ 枯渇の試験は「panic するか」ではなく「`<storage-exhausted>` が signal されて
試験が続行できるか」で見る。** signal になれば結果ファイルは書かれる。
これが T6 の「停止表示が外部へ出ない経路の扱い」の答えである。

### `SMALL_HEAP_SIZE` のつまみとの衝突(T6 の確認事項)

ネイティブの再現は `test/c/runtime_test.c` の `SMALL_HEAP_SIZE` を使う。
**これは `os_bootstrap` の恒久ヒープ消費ぎりぎりに調整されており、余裕は 5KB 未満**
(85KB は通る / 80KB は 60 秒で打ち切り)。組み込みを 1 つ足すだけでハングする。

**だから枯渇の試験は既存の掃引と同じつまみを共有してはいけない。**
枯渇専用の値を別に持ち、`SMALL_HEAP_SIZE` の既定値は動かさない。

## 5. 予測の宣言(規則 11・14・16)

**R-set の宣言し直し**(計画の時点では「空。置く場所を決めたら宣言し直す」だった):

| 行 | 動くか | 理由 |
|---|---|---|
| `c/*` の 10 行 | **動かない**(断言) | C の素の実装は Lisp のヒープを触らない |
| `aot/*` の 10 行 | **動かない**(断言) | 大口の検査は `vector` の 1 回だけ。1 単位あたり 1/1,000,000 は分解能の下 |
| `jit/*` の 6 行 | **動かない**(断言) | 同上。JIT の小口は今回守らない |
| **`interp/*` の 3 行** | **動く**(★ 幅は未定) | `os_eval` の入口に検査が 1 つ増える |
| 確保量 | **動かない**(断言) | 検査は分岐だけで、確保を増やさない |

**`os_alloc_bytes` の常道の命令数は 1 つも増えない**と断言する
(比較の相手を柔らかい端に変えるだけ)。これは**逆アセンブルで確かめられる**。

### 増分を導く — **置く費用は、見るはずの計器の分解能より小さい**

M8-T3 の実測が出たので、★ を導ける値に直す。

`interp/loop` の実測:

| 量 | 値 |
|---|---:|
| 命令/単位(総命令数) | **31,261.48** |
| `os_eval` 区間の傾き | **+1,135.0** |
| `os_eval` が総命令数に占める割合 | **0.04** |

`os_eval` が 1 回の呼び出しで自分の範囲で使う命令を 100〜200 とすると、
1 反復あたりの `os_eval` の呼び出しは **6〜11 回**である。
評価の入口に置く検査は **1 比較 + 1 分岐 = 約 2 命令**なので、増分は

    2 命令 × 6〜11 回 = **12〜22 命令/単位**

**ところが N=100,000 の分解能は 55〜155 命令/単位である。**

> **置く費用(12〜22)は、そのために作った計器の分解能(55〜155)より小さい。**
> つまり `interp/*` の 3 行では**見えない**。
> 「計器を先に作れば費用が見える」という M8 の前提は、**半分しか成り立たない。**

**隠さずに書く。** そのうえで、見える計器はある:

| 計器 | 分解能 | この費用が見えるか |
|---|---|---|
| `interp/*` の行(命令/単位) | 55〜155 | **見えない**(12〜22) |
| **`os_eval` 区間の傾き**(+1,135.0) | 同じブートの 2 カウンタの比なので雑音が小さい | **1〜2% の変化として見える見込み** |
| **命令数ゲート**(`make test-qemu-instcount-gate`) | **1 命令**(A では「動かない区間」が ±0.00 で出た) | **見える。ここで測るのが正しい** |
| 確保量 | 0 byte(検査は分岐だけ) | 動かないことの確認に使える |

**→ D9 の「置いた費用の測り方」は、ベンチの行ではなく命令数ゲートである。**
`interp/*` の 3 行は「**動かないこと**」の対照群として使う
(動いたら 12〜22 命令より大きい何かを入れたということ)。

**宣言(規則 11)**:

- `interp/*` の 3 行: **分解能の下なので動かない**(帯の中に収まる)
- `os_eval` 区間の傾き: **+12〜+22**(1〜2% 増)
- 命令数ゲート: **解釈実行の区間に +2 前後**。他の区間は **±0.00**
- 確保量: **1 byte も動かない**(断言)
- `os_alloc_bytes` の常道: **命令数が 1 つも増えない**(断言。逆アセンブルで確かめる)

> 状態: **実装した。** 設計(D9)から変えた点は §9 に全部書く。

## 6. 置いた場所(grep で辿れる形)

| 場所 | 何をするか |
|---|---|
| `src/c/runtime.c` 予備領域の導出式 | `HEAP_SIGNAL_RESERVE_MIN` = 条件の実体 + signal の引数 + 解釈実行のフレーム + ハンドラの保証分 + 床 |
| `src/c/runtime.c` `heap_update_soft_end` | 柔らかい端と床を計算。**`os_heap_init` と GC のフリップの直後に必ず呼ぶ** |
| `src/c/runtime.c` `os_alloc_bytes` | 比較の相手を `g_from_soft_end` へ。遅い側で `heap_open_reserve()`、床を割ったら `os_panic` |
| `src/c/runtime.c` `os_heap_signal_exhausted` | `<storage-exhausted>` を signal。**`za.c` の `os_za_signal_stack_exhausted` を写した形** |
| `src/c/runtime.c` `vector_block_bytes` | **掛けながら桁あふれを見る**(`__builtin_mul_overflow`) |
| `src/c/runtime.c` `array_size_arg` | **負の fixnum / 非 fixnum を弾く**(`<domain-error>`) |
| `src/c/runtime.c` `heap_request_fits` | 要求が**柔らかい端より下に入るか**。差で見る(ポインタ演算は回り込む) |
| `src/c/runtime.c` `primitive_create_vector` / `primitive_make_array` / `primitive_create_string` | 大口の入口。**確保より前**に判定し、印も見る |
| `src/c/eval.c` `os_eval` の先頭 | **印を見る唯一の「評価の入口」**。1 比較 + 1 分岐 |

守らない経路(**記録する**。スタック側が「JIT だけ守った」ことを記録したのと同じ作法):

- **JIT と AOT の生成コードが小口(cons / instance)の確保だけを続ける区間。**
  印は立つが見る人がいないので、床まで達すると `panic` する。
  守るには JIT のプロローグと AOT の関数入口に検査が要る(= 常道に命令が増える)。
- **半空間が予備領域の 8 倍に届かない構成**(ネイティブのユニットテストの小さいヒープ)。
  予備 0 / 床 0 で検査は無効になり、従来どおりその場で `panic` する。理由は §7-2。

## 7. 設計から変えた / 決め直した点

### 7-1. 予備領域の大きさは**まだ実測ではない**(★)

導出式の 5 項のうち 2 つが未実測である:

| 項 | 値 | 状態 |
|---|---:|---|
| 条件の実体(`HEAP_CONDITION_INSTANCE_MAX`) | 112 | 導出(INSTANCE 32 + 8*(1+1+8)) |
| signal が組む対(`HEAP_SIGNAL_ARGS_MAX`) | 48 | 導出(対 3 つ) |
| 解釈実行のフレーム(`HEAP_SIGNAL_LISP_FRAMES`) | 32,768 | **★ 未実測** |
| ハンドラの保証分(`HEAP_HANDLER_ALLOWANCE`) | 32,768 | **★ 未実測** |
| 床(`HEAP_HARD_FLOOR_WANT`) | 4,096 | `za.c` と同じ値・同じ役割 |
| **合計(`HEAP_SIGNAL_RESERVE`)** | **69,792** | |

**測る手段を同梱した。** `os_heap_signal_path_bytes()` が
「signal 経路が 1 回で確保した最大バイト数」を返す(GC を挟んだ回は数えない。
水位が戻って差が意味を失うため。`os_alloc_audit_diff` と同じ註)。
ネイティブの試験はこの値が予備領域に収まっていることを見る。
**ゲストで本物のハンドラ(`%report-condition-string` → `create-string-output-stream`)を
通した値は、まだ誰も見ていない。** 親が `make test-qemu-heap-exhaustion` を流したあと、
この値を実測へ直すこと(規則 9)。

### 7-2. **「予備を切り詰める」案を実測で捨てた**(規則 6)

最初は「予備領域が半空間より大きい構成では、半空間の 1/8 まで切り詰める」ことにした。
**動かしたら SMALL_HEAP_SIZE の試験が落ちた。**

半空間 42.5KB(= `SMALL_HEAP_SIZE` 85KB)で予備 5.3KB を取ると、使える領域がその分
減って GC の発火位置が前へずれる。その結果
`test_gc_fires_during_gcd_and_isqrt_and_results_are_correct` の
「isqrt の途中で GC が発火する」判定が落ちた。

| ビルド | 件数 |
|---|---|
| 基準(この作業の前) | **5,446 OK / 0 NG** |
| 予備を 1/8 まで切り詰める版 | 5,478 OK / **1 NG**(isqrt の GC 発火) |
| 予備が入らなければ 0(採用) | **5,478 OK / 0 NG**(その後 判定を 2 件足して 5,480) |

> **つまみを共有しないという T6 の方針は、「値を別に持つ」だけでは足りない。**
> **実効容量を削った時点で衝突する。**

採用した形: **予備が丸ごと入らない構成では検査を無効にする**(予備 0 / 床 0)。
閾値は「予備が半空間の 1/8 以下」= 使える領域を 12.5% 以上削らないこと。
ゲスト(`QEMU_MEM 256M`)の半空間は MB 単位なので、**実機では常に有効である。**

### 7-3. 床を割った時点で `panic` する(真の端は使い切らない)

設計は「本当の端まで使い切ったら panic」と書いたが、実装は**床**
(`g_from_end - 4096`)を割った時点で panic する。床は「使わずに残す領域」であり、
`za.c` の `ZA_STACK_HARD_FLOOR` と同じ役割(予備の中でさらに潜ったときに捕まえる)。
**真の端との差は 4KB で、挙動の違いは「panic が 4KB 早い」だけである。**

予備を `-D` で 0 にすると床が柔らかい端より上に来て逆効果になるので、
`za.c` と同じ**コンパイル時の切り詰め**(`HEAP_HARD_FLOOR = HEAP_SIGNAL_RESERVE / 2`)を入れた。
**これは陽性対照 D を取ったときに実際に踏んだ**(予備 0 / 床 4096 の構成で小さいヒープの
試験がハングした。exit=124)。

### 7-4. 配列の桁あふれ検査・負値検査は**この計画で直した**(別 Issue にしない)

完了条件の「直すか別 Issue に切り出すかを決めて記録」への答え: **ここで直した。**
理由は、**これが枯渇ではなくヒープの踏み越えだから**である。

`(create-array '(4294967296 4294967296))` は `2^32 × 2^32 = 2^64` で巻き上がって
`total = 0` になり、`8*(1+2+0) = 24` byte の塊を確保したうえで、ヘッダには
「各次元 2^32」と書いていた。`aref` / `set-aref` の範囲検査はそのヘッダを見るので、
`(set-aref 1 a 0 0)` は**範囲内と判定されたうえで塊の外へ書く。**
枯渇を直すついでに閉じられる穴を、別 Issue にして開けたまま残す理由が無い。

**負値のクラスだけは判断が残る。** `<domain-error>`(期待クラス `<integer>`)にした。
仕様に `<non-negative-integer>` のようなクラスは無いので、
`index_signal_test.lisp` が `<basic-vector>` を入れているのと同じ扱いで、
**受け付けるクラスの側**を入れている。**ここは仕様との差として PR に記録する。**

### 7-5. 残る穴(**記録する**)

- **`os_alloc_bytes` の常道は、要求が巻き上がると比較が逆になる。**
  `p + aligned` のポインタ演算は 2^64 を回り込むので、`aligned` が 1e18 規模だと
  「空きがある」と判定されうる。**これは入れる前と同じ性質で、悪くはしていない。**
  到達経路(大口の 3 つの primitive)は塞いだ。塞いでいないのは
  「C の内部から絶対値の大きい `n` で `os_alloc_bytes` を呼ぶ」経路だけである。
  常道で差を取る形(`soft_end - p` と比較)にすれば閉じるが、**命令が 1 つ増える**ので
  G1(回帰ゼロ)と引き換えになる。やるなら別の判断として。
- 大口の判定は**柔らかい端**で見るので、予備領域(~68KB)に収まる大きさの確保が
  予備の中からは取れない。枯渇寸前に `(create-vector 1000)` が
  `<storage-exhausted>` になることがある。**予備は知らせるための領域なので、
  これは意図どおりである。**

### 8-1b. 回収器の最中に signal しないこと

### 8-3. 陽性対照(規則 8。**ホストの gcc で実行して確かめた。2026-11-01**)

**検出器を 1 つずつ壊して、落ちることを実際に見た。**
基準は **5,478 OK / 0 NG**(対照を取ったあとに判定を 2 件足したので、現在の基準は 5,480。
**NG の件数と落ちた判定は変わらない**)。

| 壊したもの | 落ちた判定 | 件数 |
|---|---|---|
| A: `os_eval` の入口から印の検査を外す | 「印が立っているとos_evalは知らせる」他 | **4 NG** |
| B: 掛け算の桁あふれ検査を外す(素の `total *= dims[i]`) | 「2^32×2^32 は枯渇として知らされる」「1byteも進めない」他 | **3 NG** |
| C: 重ねない(再入フラグ)を外す | 「signalを重ねずEVAL-ERRORを返す」「発火回数」 | **2 NG** |
| D: `-DHEAP_SIGNAL_RESERVE=0` で予備を無くす | 「このヒープの大きさでは枯渇の検査が有効である」「signal経路が予備に収まっている」 | **2 NG** |

#### D を取るときに 2 回踏んだこと(**記録する**。規則 6)

1. **床が柔らかい端より上に来る構成を作ってしまった。** 予備 0 / 床 4096 だと
   「柔らかい端(= 真の端)を超えたら、さらに低い床と比べて必ず panic」になり、
   小さいヒープの試験がハングした(exit=124)。
   → `za.c` と同じコンパイル時の切り詰め(`HEAP_HARD_FLOOR = HEAP_SIGNAL_RESERVE / 2`)を入れた。
2. **検査が無効な構成では、枯渇の試験自身が panic してハングした。**
   印が立たないので「埋める」ループが止まらず、床まで埋め切る。
   `os_panic` はユニットテストでは `hlt` が無いので**無限ループ**になり、
   **出力はバッファに残ったまま失われる**(NG が 1 行も読めない)。
   **600 秒走らせても終わらなかった**(`exit=124`、出力は 5,429 件で途切れ、NG は 0 件。
   番犬を置いた版は同じ構成で **110 秒以内に 2 NG を出して終わる**)。
   **ハングと「NG が 0 件」が同時に出るのがいちばん悪い。** 件数だけ見ると通ったように読める。
   → 試験の先頭に**番犬**を置いた(`guard_active`。無効な構成なら NG を出して引き返す)。
   **これは `HEAP_EXHAUSTION_SIZE` を小さく掃引したときにも踏む罠である**
   (半空間の 1/8 が予備領域に届かなくなった瞬間に検査が無効になる)。

ゲスト側の陽性対照は**親が取る**。手順:

```
# 大口の検査が効いていないことの対照 = 検査を外したら「結果が無い」に戻る
#   src/c/runtime.c の primitive_create_vector から
#   heap_signal_if_pending / vector_block_signal_if_too_large の 3 行を外して
#   make test-qemu-heap-exhaustion を流す
#   -> 期待: 電源が切れて test-results.txt が書かれない(= PR #151 の flake と
#      外から区別が付かない状態に戻る)。**これが T6 の「signal になれば
#      結果ファイルは書かれる」の対照である**
```

### 8-4. **カーネルにヒープ量の定数は無い**(記録)

`kernel_main` は UEFI から渡された「いちばん大きい空き領域」をそのまま
`os_boot_alloc_init` → `os_boot_alloc_finalize` → `os_heap_init` へ流す
(`src/c/main.c` が `max_free_size` を渡す)。**ソースにヒープ量の定数は無い。**
ゲスト側で枯渇の条件を変えられるのは **`QEMU_MEM`(既定 256M)だけ**である。

**だから予備領域の有効・無効が仮想機械のメモリ量で決まる。**
`QEMU_MEM` を極端に小さくすると半空間が予備領域の 8 倍に届かず、
**検査ごと無効になる**(§7-2)。小さいメモリ量で測るときは、
`os_heap_soft_limit_normal_bytes() < os_heap_floor_limit_bytes()` が
成り立っているかを先に見ること。
