# 調査報告: defun 4,144 byte の削減方針

> 調査日: 2026-09-15 / ブランチ: `feature/compiler-optimization`(`6da82cb`)
> **調査のみ。コードは変更していない。ブランチも切っていない。**

## S の結果(未説明 16 byte)

**仮説どおり Function Cell だった。確認(実測)。**

| 測定(各100回) | 消費/回 | cell 増 |
|---|---|---|
| **同名で再定義** | **4,144 byte** | +1 |
| **毎回別名で定義** | **4,160 byte** | +100 |
| JIT を断念する定義(固定引数への `setq`)を別名で | 16 byte | +100 |

差はちょうど 16 byte。3行目が「JIT しなければ cell の 16 byte だけ」になることも裏付けている。

内訳が確定した:

| 要素 | byte | 根拠 |
|---|---|---|
| JIT コードページ | 4,096 | `os_imm_pages_alloc_contiguous(page_count)`、`za.c:6124` |
| `za_fn_meta_t` | 48 | 下記 D-3。5 フィールド 40 byte → 16 byte アラインで 48 |
| Function Cell | 16 | 新しい名前のときだけ。`runtime.c:3609` |
| **合計(新規名)** | **4,160** | |
| **合計(同名再定義)** | **4,144** | |

`flet` cell リークの案A(cell の遅延生成)を入れると新規名も 4,144 になる。**0.4% で、
枯渇回数はほぼ変わらない。**

## サマリ

**パッキングを推す。** ただし単独では効果が半減する(後述 B-4)。

枯渇までの現実的なシナリオ:
**`make test-qemu` を1回通すだけで 16MB の 29% を使う**(実測 4,856,288 byte)。
残りは 2,865 回。**REPL で関数を 2,865 回書き直せば停止する。**
1関数のファイルを直して再ロードするたびに 4,144 byte、`disassemble.lisp`(24 関数)
なら 1 回の再ロードで 99,024 byte。**165 回の再ロードで枯渇する。**

## 調査項目 A: 枯渇に至る現実的な経路

### 確認したこと

**結論: 支配的なのは「1. 同じ定義の再実行」。** 「2. 異なる定義の蓄積」は
起動分だけなら 3.4% にすぎない。

#### A-1. 起動直後の状態(実測)

```
#A boot used=565408 cells=736 関数総数=736 JIT済み=89
```

- 16,777,216 byte 中 **565,408 byte(3.4%)**
- グローバル関数 **736 個のうち JIT されているのは 89 個だけ**
  (残りは組み込み native と AOT。どちらも JIT コードページを取らない)
- **cells 736 = 関数 736 で厳密に 1:1**(前回調査の 713:713 と同じ性質)
- JIT 分の内訳: 89 × 4,144 = 368,816 byte。**起動時消費の 65%**

#### A-2. 起動時に同名で複数回コンパイルされるものは無い(確認)

| ファイル | `defun` 数 | 重複名 |
|---|---|---|
| `src/lisp/init.lisp` | 68 | **0** |
| `src/lisp/init_aot.lisp` | 95 | **0** |
| `src/lisp/utility.lisp` | 6 | **0** |

`init.lisp` が `load` するのは `src/lisp/disassemble.lisp` の1本のみ
(`src/lisp/init.lisp:1112`)。**起動経路に再定義は無い。**

#### A-3. 再ロードは丸ごと積み増す(実測)

```
#A disassemble.lisp 2回目ロード: +99024byte, cell増=0
#A disassemble.lisp 3回目ロード: +99024byte
#A 再ロード後 関数総数=736 JIT済み=89 used=763456
```

- **毎回ちょうど +99,024 byte**(= 4,144 × 23.9、`disassemble.lisp` の関数数に一致)
- **cell 増は 0**(名前は既存なので cells は再利用される)
- **関数総数も JIT 済み数も変わらない**(736 / 89 のまま)。
  つまり**同じ関数が作り直され、古いコードは誰からも参照されないまま残っている**
- 回収はゼロ。3回目も2回目と完全に同じ量

#### A-4. ループ内の `defun` も同じ(実測)

```
#C3 ループ内defun 100回: +414432byte = 4144byte/回
#C3 loop-defun compiled=NIL / lp-f compiled=T
```

`(while ... (defun lp-f (x) (+ x 1)) ...)` を 100 回回すと 4,144 byte × 100。
外側の `loop-defun` は `defun` を含むため JIT されない
(`za_is_excluded_special_form`、`src/c/za.c:1705-1713`)が、
**内側の `lp-f` は毎回 JIT され直す。**

#### A-5. フルテスト完走後(実測)

```
#FULL 全テスト完走後 used=4856288 / total=16777216, cells=2812
#FULL 残り defun 可能回数=2865
==== isiki tests: 3325 passed, 0 failed ====
```

**`make test-qemu` 相当を1回通すだけで 29%(4.86MB)を消費する。**
起動分 565KB を引くと 4.29MB = 約 1,035 回分の JIT コンパイル。

### 枯渇までの現実的なシナリオ(実測値から)

1. **REPL で関数を直しながら開発する。** 1回の `defun` で 4,144 byte。
   **2,865 回**(フルテスト後の状態から)、**3,849 回**(起動直後から)で停止
2. **ファイルを直して再ロードする。** `disassemble.lisp`(24 関数)なら 1 回 99,024 byte。
   起動直後から **約 163 回**の再ロードで枯渇
3. **テストを増やす。** 現状で既に 29%。同規模のテストをあと 2.4 倍足すと枯渇する

### 推測・未確認

- **(推測)**「異なる定義の蓄積」だけで枯渇に至るのは、現状のコード規模では考えにくい。
  起動 89 関数、フルテストで約 1,124 関数分。**1桁足りない**
- **(推測)** 危険なのは REPL とループ。どちらも「同じ名前を何度も定義する」形

## 調査項目 B: サブページのパッキングは可能か

### 確認したこと

**B-1. なぜページ単位か**

`za.c:6123-6124`:

```c
UINT64 page_count = (code_len + IMM_PAGE_SIZE - 1) / IMM_PAGE_SIZE;
void *dest = os_imm_pages_alloc_contiguous(page_count);
```

`os_imm_pages_alloc_contiguous`(`runtime.c:1403-1411`)は純粋なバンプで、
`count * IMM_PAGE_SIZE` を切り出すだけ。**アラインや実行権限の都合ではなく、
「環境の `pages` スロットにページ単位で登録して破棄時に返す」という回収設計に
合わせた粒度**である(`runtime.c:2998-3001`)。

**B-2. 命令アラインの障害は無い(推測を含む)**

- x86-64 の命令フェッチにアライン要求は無い。**(確認)** 生成コードが
  `dest_bytes` 先頭からの相対で自己参照 movabs をパッチしている
  (`za.c:6135-6148`)ので、開始アドレスが 16 byte 境界にさえ乗っていればよい
- `za_fn_meta_t` の `cons_entry` / `fixed_entry` は絶対アドレスを持つ
  (`runtime.h` の定義)。ページ先頭に依存していない
- `os_fn_set_code_range` が記録するのは `(dest_bytes, code_len)` の組
  (`za.c:6237-6242`)で、これもページ境界に依存しない
- **(推測)** したがって「コード用の bump カーソルを持ち 16 byte 境界に詰める」ことに
  技術的障害は無い

**B-3. `destroy-environment` との衝突は実在する**

回収は `primitive_destroy_environment_reclaim`(`za.c:6256-6261`)→
`os_environment_reclaim_pages`(`runtime.c:3705-3717`)で、
**`pages` スロットに登録したページを1枚ずつ `os_imm_page_free` へ返す。**

1ページに複数環境の関数が同居すると回収できない。
**「同じ owner_env の関数だけを同じページに詰める」制約で回避できる(推測)。**
`za.c:6218` が `os_environment_register_pages(owner_env, ...)` を呼んでいるので、
owner_env ごとに bump カーソルを持てばよい。ただし環境ごとにカーソルを持つと
**環境が多いと端数ページが増える**。

**B-4. コードページはフリーリストから再利用されない(確認。現在も正しい)**

| 関数 | フリーリストを見るか |
|---|---|
| `os_imm_page_alloc`(`runtime.c:1172-1184`) | **見る**(`g_imm_free_list`) |
| `os_imm_pages_alloc_contiguous`(`runtime.c:1403-1411`) | **見ない** |

`os_imm_page_free`(`runtime.c:1398-1401`)が返したページは、
**slot 確保系(Function Cell / `za_fn_meta_t`)からしか再利用されない。**
新しい JIT コードには戻らない。

**さらに重要: そもそも `global_environment` は破棄されない。**
回収経路は `%%DESTROY-ENVIRONMENT-RECLAIM` だけで、トップレベルの `defun` は
`os_definition_env(env)` = `global_environment` を owner にする
(`src/c/eval.c:399-402`)。**トップレベル `defun` のページは永久に返らない。**

### 推測・未確認

- **(推測)** パッキング単独の効果は「新規に積む量」にしか効かない。
  A-3 で見たとおり再ロードは丸ごと積み増すので、
  `(defun t1 () 1)` が 4,096 → 数百 byte になれば **枯渇回数は1桁伸びる**
- **(未確認)** 実際の関数のコード長分布は測っていない。
  起動時 89 関数の平均コード長が分かれば、パッキングの効果を正確に見積もれる

## 調査項目 C: 重複排除は可能か、どれだけ効くか

### 確認したこと

**C-1/C-2. コンパイルごとに新規確保されるスロットは3種類あり、共有すると混線する**

- 呼び出し先キャッシュ `g_za_fn_cell_cache_slots`(`za.c:1078`)
- quote / number / lambda のリテラルスロット(`za.c:252-266`、
  `za_track_literal_slot_alloc` が追跡)
- これらは `os_environment_register_literal_slot(owner_env, ...)`(`za.c:6219`)で
  **owner_env の所有物として登録される**

呼び出し先キャッシュは `os_get_function_cell(sym, env)` の結果を持つので、
**env が違えば違う cell を指す。** 依頼書のとおり
**キーは `(body S式, 登録先環境)` の組でなければならない。確認。**

**C-3. ループ内の `defun` は毎回同じ cons 木(実測)**

```
#C3 本体のquoteリテラルは呼び出し間で eq か: T
```

関数本体に書かれたリテラルは呼び出しをまたいで `eq`。
したがって**ループ内の `defun` フォームも毎回同じ cons 木**であり、
`eq` をキーにした重複排除が効く。

**C-4. ただし再ロードには効かない**

A-3 で `disassemble.lisp` の再ロードが毎回 +99,024 byte だったのは、
**リーダーがロードのたびに新しい cons 木を作るから**である。
`eq` をキーにする限り**再ロードは1件も当たらない。**
当てるには構造比較(`equal`)が要る。

したがって効く範囲は:

| シナリオ | `eq` 重複排除 |
|---|---|
| ループ内の `defun` | **効く** |
| REPL で同じ定義をもう一度貼る | **効かない**(読み直すたびに新しい cons) |
| ファイルの再ロード | **効かない** |
| REPL で中身を変えて直す | **効かない**(そもそも別の body) |

### 推測・未確認

- **(推測)** A の結果と照らすと、**重複排除が効くのはループ内 `defun` だけ**で、
  これは3つのシナリオのうち最も起きにくい。**費用対効果は低い**
- **(未確認)** `eval` で毎回新しいリストを組んで `defun` する経路を測ろうとしたが、
  **測定に失敗した**(`ev-f` が定義されず `EVAL-ERROR`、消費 0 byte)。
  `eval` の使い方を誤った可能性がある。この行は根拠として使っていない

## 調査項目 D: 他に削れるものはないか

### 確認したこと

**D-1. すべての `defun` が無条件に JIT される**

`src/c/eval.c:402`:

```c
lisp_val_t fn = za_try_compile_defun(params, body, env, owner);
if (fn == nil) {
    fn = make_interpreted_function(params, body, env);
}
```

**呼び出し回数を一切見ていない。** 一度も呼ばれない関数もコンパイルされ、
4,144 byte を消費する。起動時 JIT 89 個のうち何個が実際に呼ばれるかは**未確認**。

**(推測)** ティアリング(N 回呼ばれてから JIT)には余地がある。
特に `disassemble.lisp` のような「使うときだけ使う」機能群は、
ロードしただけで全関数分のページを取っている。

**D-2. 再定義しても古いコードページは回収されない(実測)**

S の測定で同名再定義が 4,144 byte/回 だったことがそのまま証拠になる。
回収されていれば 0 に近づくはずである。理由は B-4 のとおり、
回収経路が `destroy-environment` にしか無く、`global_environment` は破棄されないため。

**D-3. `za_fn_meta_t` は 5 フィールド 40 byte → 48(確認)**

`src/c/runtime.h` の定義:

| offset | フィールド |
|---|---|
| 0 | `cons_entry` |
| 8 | `fixed_entry` |
| 16 | `arity` |
| 24 | `code_base` |
| 32 | `code_len` |

以前の「3 フィールド 24 byte → 32」という観察は**逆アセンブラ(PR #57)が
`code_base` / `code_len` を足す前のもの**。
コメントにも「disassembler(`src/c/disasm.c`)用のコード範囲」とある。
**逆アセンブラ機能が 1 関数あたり 16 byte を足している。**
ただし 4,144 のうちの 16 byte なので、削っても意味は無い。

## 所見

**(所見)まず `os_imm_pages_alloc_contiguous` がフリーリストを見ないことを直すべきだと考える。**
これは1箇所の変更で、パッキングにもページ回収にも前提として効く。
現状は「返したページがコードには二度と使われない」ので、
**どの案を入れても効果が半減する。** B-4 がこの調査で一番効く発見だと思う。

**(所見)次にパッキング。** A の3つのシナリオすべてに効く唯一の案である。
`destroy-environment` との衝突は「owner_env ごとに bump カーソルを持つ」で
回避できそうに見えるが、**環境が多いと端数ページが増える**ので、
まず「`global_environment` 専用のカーソルを1本足す」だけでも大半が取れるはず
(トップレベル `defun` がそもそも支配的なので)。

**(所見)重複排除は推さない。** `eq` キーでは再ロードにも REPL の貼り直しにも
当たらず、当たるのはループ内 `defun` だけ。A の実測では、そのループ内 `defun` が
現実的な枯渇経路の中で最も起きにくい形だった。

**(所見)ティアリングは効くが、性格が違う。** 消費を減らすというより
「払うタイミングを遅らせる」策で、結局呼ばれれば 4,144 byte 払う。
ただし `disassemble.lisp` のようなロードするだけの機能群には素直に効く。

**(所見)数字として一番驚いたのは、フルテスト1回で 29% を使うこと。**
これは仮説ではなく現在の実測値で、**テストを 2.4 倍に増やせば CI が枯渇で落ちる。**
「対話的に使えば踏む」よりも先に、そちらが顕在化する可能性がある。

## 未調査・積み残し

- **関数ごとのコード長の分布を測っていない。** 起動時 89 関数の平均コード長が
  分かればパッキングの効果を正確に見積もれる。`%%DIAG-ZA-CODE-LEN` は
  「直近の1件」しか返さないので、全件を取るには定義のたびに読む必要がある
- **起動時 JIT 89 個のうち、実際に呼ばれるのが何個か**は未確認。
  ティアリングの効果見積もりに要る
- **`eval` で毎回新しいリストを組んで `defun` する測定は失敗した**
  (`ev-f` が `EVAL-ERROR`)。再ロードの証拠は A-3 で足りているので追わなかった
- **`global_environment` 以外の環境で `defun` したときのページ所有**は
  コードを読んだだけで、実測していない
- **フリーリストをコード確保からも見るようにした場合の断片化**は未検討。
  連続ページを要求する経路(`page_count > 1`)があるため、
  単純な単一ページフリーリストでは足りない場合がある
